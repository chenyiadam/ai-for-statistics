# 第8章 AI编程与科研自动化

> **本章定位**：回答"统计研究者如何把对话式问答升级为能读数据、写脚本、跑命令、看报错、自动修正并输出可复现报告的科研流水线"。
> **关键词**：AI 编程智能体、Claude Code、Aider、生成—执行—验证闭环、可复现工作流、ellmer、实验设计自动化

## 本章导读

前七章讨论的是模型与智能体的原理：注意力、训练与对齐、提示词、工具调用与 Skill 封装。这些东西落在研究者的日常里，最终要通过一个具体界面发生作用，一个能打开 `data/`，读 `experiment.csv`，写出 `analysis.R`，运行它，看见 `object of type 'closure' is not subsettable`，然后自己回去改代码的**编程智能体**（coding agent）。与对话框里的问答相比，差别不在模型能力，而在三件事：它能访问文件系统，它能执行代码并拿到真实的返回值，它能把执行结果作为下一轮输入。这三点合起来，把语言模型从"文本生成器"变成了"带反馈的执行器"。

本章沿"工具—机制—工作流—复现"的顺序展开。8.1 给出全景分类；8.2 至 8.7 逐个拆解六款主流编程智能体（Claude Code、GitHub Copilot、Cursor、Windsurf、Gemini CLI、Aider），统一按定位与开发商、核心机制、上下文管理、权限模型、扩展能力、定价、适用与不适用场景七个维度描述；8.8 汇总为可查的对比表，并补充完全免费的开源替代方案。8.9 至 8.14 是统计学者最关心的部分：代码生成与执行闭环、数据分析自动化、文献管理与知识库、科研绘图与报告、实验设计与自动化、可复现工作流。8.15 专门讨论 R 语言生态与大模型的工作流集成，8.16 列出核心软件工具链。

本章与第 7 章是继承关系：第 7 章给出 Agent 的形式化与 Skill 的封装格式，本章讨论这些机制在编程与科研场景中的具体载体。8.9 提出的"代码作为可验证的中间表示"与第 13 章的"评估器即验证器"是同一条原则的两种表述；8.14 的可复现基础设施在第 17 章展开为完整的工程方案；8.13 的实验设计与第 9 章线上 A/B 测试使用同一套统计工具。

一个需要预先澄清的立场：本章讨论的所有工具都不能替代统计判断。智能体能写出 `stats.ttest_ind` 的调用，但不能替使用者决定这个检验的识别假设是否成立；它能生成森林图，但不能替使用者判断亚组分析是否应当做多重比较校正。本章反复强调的工作方式是把智能体的输出当作**待验证的候选方案**，而不是结论。

## 8.1 AI编程智能体总览

### 8.1.1 三类形态

按交互界面的不同，AI 编程工具可以分为三类，三类的能力边界差异主要来自"能观察到什么"与"能操作什么"。

| 形态 | 观察对象 | 可执行的动作 | 代表工具 | 主要短板 |
|------|----------|--------------|----------|----------|
| 终端智能体（CLI Agent） | 工作目录下的文件、命令的标准输出与错误 | 读写文件、执行任意 shell 命令、调用 MCP 服务器 | Claude Code、Aider、Gemini CLI、OpenCode、Goose | 无图形界面，结果需通过文件或终端文本查看 |
| IDE 智能体 | 编辑器中的打开缓冲区、选中区域、语言服务器诊断 | 行内补全、多文件编辑、运行内置终端与调试器 | GitHub Copilot、Cursor、Windsurf、Cline | 长程无人值守任务的轨迹记录不如 CLI 直观 |
| 桌面/GUI 智能体（Computer Use） | 屏幕截图、可访问性树 | 模拟鼠标键盘操作任意软件 | Claude Computer Use、OpenAI Operator、UI-TARS Desktop | 可靠性低，据原稿引用的报告，Operator 类工具在真实任务上失败率约 62%，单次失败成本约 3.86 美元 |

第三类的存在价值在于处理没有 API 的传统软件：老版本 SPSS、实验室自建的桌面录入程序、需要人工点击才能导出的数据库前端。对于以代码为主的统计工作，前两类的可靠性明显更高，因为代码执行给出的是确定性的、可重放的反馈，而截图理解给出的是一个概率性的视觉判断。

### 8.1.3 统计研究者应当优先考察的四项能力

面对上表的诸多选项，统计研究者的筛选标准与通用软件工程略有不同，有四项的优先级最高。

**第一，能否执行脚本并把 stderr 完整读回。** 统计分析的失败方式大多是运行时错误：`KeyError`、`singular matrix`、`NA/NaN/Inf in foreign function call`。只能生成代码而不能运行的工具，会把这些错误留给使用者手动搬运，反馈回路因此断裂。

**第二，能否在会话中保持长上下文而不丢失关键决策。** 一次完整分析往往包含"缺失值如何处理""用哪种检验""是否校正多重比较"等十余个决策点。上下文窗口小或压缩策略激进的智能体，会在会话后期遗忘早期约定，表现为反复推翻已确认的方案。

**第三，改动是否可审计、可回滚。** 这一项直接关系学术诚信。以 Git 提交为粒度记录每次改动的智能体（Aider 的自动提交是这一设计的代表），允许使用者事后逐条复核"模型到底改了什么"，而不是面对一堆无历史的文件。

**第四，是否支持外部工具扩展（MCP）与流程封装（Skill）。** 前者决定智能体能否连到实验室的文献库、数据库与内部 API，后者决定使用者的标准分析流程能否被固化复用。这两项机制的原理在第 7 章已有完整讨论。

### 8.1.4 与传统统计软件脚本的类比

对习惯了 Stata do-file、SAS 程序或 R 脚本的研究者，编程智能体可以类比为"会自动写 do-file 并自动跑一遍的助手"，但有两点本质区别。传统脚本是**一次性写定、重复执行**的，脚本内容在研究者的完全控制之下；智能体生成的脚本是**条件于上下文随机采样**的结果，同一需求两次生成可能不同，因此必须纳入版本管理与结果比对。另一点是传统脚本的错误是确定性的（同一份数据和代码永远给出同一结果），而智能体的错误带有随机性，这种随机性无法靠"再跑一次确认"消除，只能靠固定的验证脚本与固定的随机种子来控制。

## 8.2 Claude Code

### 8.2.1 定位与开发商

Claude Code 由 Anthropic 开发，以 npm 包 `@anthropic-ai/claude-code` 分发，安装后在终端中以 `claude` 命令启动。它是典型的**终端优先**（terminal-first）智能体：交互界面是命令行，工作对象是当前目录下的文件树，能力边界是使用者愿意授予的 shell 权限。除本地 CLI 形态外，还有云端版（code.claude.com），可直接在浏览器或移动端连接 GitHub 仓库工作。官方仓库为 github.com/anthropics/claude-code，文档入口为 platform.claude.com。

### 8.2.2 核心机制

一次典型交互的轨迹可以写成：读取文件 → 生成或修改代码 → 执行命令 → 读取标准输出与错误 → 修正 → 重跑。工具集包括文件读取与写入、编辑、glob 与 grep 检索、Bash 执行、网络抓取与搜索，以及用于派生子任务的子智能体（subagent）。这个循环与第 7 章给出的 ReAct 骨架一致，区别在于观测 $o_t$ 是真实文件系统的状态，而不是模型记忆中的描述。

对统计工作最有价值的一点是：**它会真的执行**。下面是一段最小的交互记录：

```bash
# 进入项目目录
cd my-statistics-project
# 启动
claude
# 只说一句自然语言
> 帮我分析 data.csv，做一个线性回归，把结果画成图保存到 output.png
# 智能体自动完成：Read(data.csv) 看结构 -> Write(analysis.py) 生成脚本
# -> Bash(python analysis.py) 执行 -> 看到 ModuleNotFoundError
# -> 自动 pip install 缺失的包 -> 重跑直到成功 -> 展示结果待确认
```

上下文管理采用三级项目规则文件：`~/.claude/CLAUDE.md` 为用户级规则，项目根目录的 `CLAUDE.md` 为项目级规则（通常纳入版本控制，团队共享），子目录下的 `CLAUDE.md` 只在该子树工作时加载。规则文件中可用 `@文件名` 引用其他文档。会话接近窗口上限时可手动压缩历史。规则文件的内容应当写成**可执行的约定**，而不是模糊的期望，例如"所有随机过程必须显式设置种子并在代码注释中记录""缺失值处理策略必须在动手前询问使用者""报告 p 值必须同时报告效应量与置信区间"。

### 8.2.3 权限模型与扩展能力

权限采用默认审批加白名单的机制：涉及写文件与执行命令的动作会请求确认，使用者可将其加入允许清单以避免重复打扰；`/plan` 类只读模式用于先出方案再动手的场景。这套机制的意义在于把"智能体能做什么"变成一个显式可配置的集合，而不是隐含的默认行为。

扩展能力方面，Claude Code 支持 MCP（Model Context Protocol，模型上下文协议，见 modelcontextprotocol.io），可通过命令行添加 MCP 服务器，从而连接文献库、数据库、内部 API；也支持第 7 章讨论的 Skill 封装（SKILL.md 目录）与生命周期钩子（Hooks，在工具调用前后插入脚本），后者常被用来强制执行格式化或运行测试。

### 8.2.4 安装、定价与账户

安装的前置条件是 Node.js 18 及以上版本：

```bash
node --version                                  # 检查 Node.js 版本
npm install -g @anthropic-ai/claude-code        # 安装
claude --version                                # 验证
# 也可使用安装脚本
curl -fsSL https://claude.ai/install.sh | bash
```

定价方面，客户端本身免费，费用来自 Claude 订阅。下表为原稿统计时点数据（2026 年），实际价格以官网为准。

### 8.2.5 国内可用的替代接入方式

原稿汇总的国内替代方案中，门槛最低的是火山引擎 Ark Coding Plan：支持支付宝与微信支付，有每日免费额度，通过设置环境变量即可复用 Claude Code 客户端。

```bash
export ANTHROPIC_API_KEY="your-ark-api-key"
export ANTHROPIC_BASE_URL="https://ark.cn-beijing.volces.com/api/v3/"
npm install -g @anthropic-ai/claude-code

```

可用模型包括 doubao-seed-code、DeepSeek-V3.2、GLM-4.7、Kimi-K2.5 等。代价是模型能力与官方 Claude 存在差异，且第三方中转的安全与合规责任需自行评估，涉及未发表数据的研究项目，应先确认数据出境与留存策略是否符合所在单位的规定。AWS 的 Kiro 与各类第三方 API 中转平台是另外两类选项，成本与稳定性差异较大。

### 8.2.6 适用与不适用场景

**适用**：长时间、多步骤、需要反复试错的脚本开发（数据清洗、模型诊断、图表迭代）；需要跨文件理解的项目（把一份 Stata do-file 翻译成 R 脚本）；需要在真实数据上验证结果的分析任务；需要接入自有工具链（MCP）的流程。

**不适用**：需要 GUI 交互的软件操作；纯快速补全（终端交互的往返成本高于 IDE 内补全过程）；严格离线环境（依赖网络与订阅）；需要逐行人工审阅的高风险代码（应改用 IDE 形态，在编辑器内逐处确认差异）。

## 8.3 GitHub Copilot

### 8.3.1 定位与开发商

GitHub Copilot 由 GitHub 与 Microsoft 提供，形态是 IDE 插件（VS Code、JetBrains 系列、Visual Studio），并延伸到命令行、网页与移动端。它是三类形态中覆盖面最广的一个：不追求自主完成整个任务，而是嵌入使用者已有的编辑流程，在光标处提供建议。原稿记录的定价为 $10/月起，学生、教师与开源项目维护者可免费使用。

### 8.3.2 核心机制

Copilot 的能力分三层。**补全层**是当前行内的灰字建议，依据光标上下文与打开的标签页预测后续 token；**对话层**（Copilot Chat）是侧边栏问答，可通过 `@workspace`、`@terminal` 等显式注入上下文；**智能体层**（Agent 模式）可自主规划多步修改并在 IDE 内执行，云端形态还能在 GitHub Actions 环境中异步完成一个 issue 并直接开 PR。原稿提到的 Partner Agent 属于与外部智能体/服务集成的扩展形态，不同时期的具体支持范围变化较快，以官方文档为准。

上下文管理依赖 IDE 状态：打开的文件、光标位置、语言服务器给出的诊断信息，都可以作为上下文来源。这一设计的好处是上下文天然相关（使用者正在看的代码大概率就是需要改的代码），代价是跨文件的全局理解弱于显式构建仓库地图的方案（8.7 的 Aider 采用后者）。

权限方面，IDE 内的修改以差异视图（diff）呈现，由使用者逐处接受或拒绝；云端智能体在隔离的 Actions 环境中运行，不接触本地文件系统，这一隔离对需要保护未发表数据的研究者是明确的优点。

### 8.3.3 扩展能力与科研场景

Copilot 所在的 VS Code 生态支持 MCP 服务器接入，因此在智能体模式下也能连接外部工具。对统计研究者的典型用途是：补全重复的样板代码（读取多个 `.dta` 文件、批量拟合模型的循环）、为函数生成文档与单元测试、解释报错信息、把注释翻译成代码。它的强项是**降低打字成本**，弱项是**不承担端到端责任**：一次补全建议的正确性由使用者当场判断，而智能体模式下的长程任务可靠性低于专门的 CLI 工具。

需要注意的一类失效是建议中引用不存在的函数或参数（例如虚构 `pandas` 的方法名、虚构 R 包的参数）。这类幻觉在补全场景尤其危险，因为它混入大量正确代码，逐行审阅容易漏过。唯一的可靠防御是执行，凡接受的建议都要跑一遍，这正与 8.9 的"生成—执行—验证"闭环一致。

### 8.3.4 适用与不适用场景

**适用**：已深度使用 VS Code/JetBrains 的团队；以编写为主、执行为辅的工作；需要跨设备一致体验（网页、移动端）；符合免费资格的学生与教师。

**不适用**：需要智能体自主运行数十步的长任务；需要完整记录执行轨迹以备审计；需要离线运行（依赖云端服务）。

## 8.4 Cursor

### 8.4.1 定位与开发商

Cursor 由 Anysphere 开发，是一个以 VS Code 为基础分支的 AI 优先编辑器，从 cursor.com 下载安装。它保留了 VS Code 的键位、插件生态与设置格式，因此迁移成本很低。原稿记录的定价为免费版加 Pro（$20/月），另提供可在终端与 CI 中使用的 CLI 形态。文档入口为 docs.cursor.com。

### 8.4.2 核心机制

Cursor 提供四种交互层次，覆盖从补全到自主执行的完整频谱。

| 层次 | 触发方式 | 作用范围 | 典型用途 |
|------|----------|----------|----------|
| Tab 补全 | 直接按 Tab | 当前光标处的多行预测 | 续写循环、补全参数列表 |
| 内联编辑 | Cmd/Ctrl+K | 选中的一段代码 | 局部重构、加注释、改变量名 |
| Composer | 独立面板 | 跨文件的多处修改 | 新增一个分析模块并同步改测试 |
| Agent 模式 | 独立面板 | 自主运行命令与工具，直到任务完成 | 端到端实现一个分析脚本 |

上下文通过 `@` 显式注入：`@文件`、`@代码符号`、`@文档`（可索引第三方库文档）、`@web`（联网检索）、`@git`（提交历史与差异）。这一机制把"上下文是什么"的決定权交还给使用者，避免了隐式全量扫描带来的噪声与成本。项目规则早期写在根目录的 `.cursorrules` 文件中，后续版本支持 `.cursor/rules/` 目录下的多规则文件并可按路径匹配自动加载。

### 8.4.3 模型选择与扩展能力

Cursor 允许自定义模型，可接入 OpenAI、Anthropic 等商用 API，也可指向自建服务。这一点的实用意义在于可以按任务切换模型：日常补全用小模型省钱，复杂重构用强模型。IDE 形态下同样支持 MCP 服务器，从而把实验室内部工具接入编辑器。

### 8.4.4 适用与不适用场景

**适用**：需要可视化比对改动的研究者；R 与 Python 混用、需要频繁在编辑器与图表预览之间切换的探索性分析；需要保留 VS Code 插件生态（如 R 语言服务器、Quarto 预览）的场景。

**不适用**：需要数小时无人值守的长任务；需要完整的、可归档的执行日志（CLI 形态的日志更便于纳入可复现记录）；对成本敏感且已有多余订阅（Cursor 的订阅与 Claude、Copilot 并不互通）。

## 8.5 Windsurf

### 8.5.1 定位与开发商

Windsurf 由 Codeium（Exafunction）团队推出，自称 AI 原生 IDE（agentic IDE），从 windsurf.com 下载，文档入口为 docs.windsurf.com。原稿记录的定价为免费档加付费档（约 $15/月）。与 Cursor 的差别不在功能清单，而在两处设计取向：一是更强调智能体自主完成整段流程（Cascade 引擎），二是提供跨会话保留的持久化记忆。

### 8.5.2 核心机制

Cascade 是 Windsurf 的智能体执行引擎，其设计目标是让智能体"深度感知"使用者的编辑状态，包括刚刚手动改过什么、正在看哪个文件，从而在无需显式 @ 提及的情况下推断上下文。这对探索性工作友好，代价是上下文来源不如显式注入那样可预测，出现偏差时排查难度更高。

持久化记忆是该工具的显著特征：跨会话保留项目约定与使用者偏好，不必每次重新说明"本项目用 `targets` 管理管道""图表统一用 `theme_bw()`"。从认知科学的角度看，这对应长期记忆中的语义成分；从工程角度看，它等价于把 8.2 中 `CLAUDE.md` 的内容改为由工具自动维护。自动维护的便利性与可控性之间存在取舍：规则由人写下来时，团队可以评审；由工具自动积累时，错误偏好也会被固化。涉及多人协作的研究项目，仍建议把关键约定写成显式的、纳入版本控制的规则文件。

其他机制包括 MCP 支持、Write/Talk 双模式（前者允许写文件，后者只讨论不动手），以及桌面 IDE 与插件形态的多种部署方式。

### 8.5.3 适用与不适用场景

**适用**：周期长、约定多的研究项目（记忆机制的价值随项目时长上升）；偏好由智能体主动推进而非逐条指令的使用者；需要免费档起步、暂不订阅的团队。

**不适用**：需要完全离线或私有化部署；需要严格审计"上下文到底包含什么"（隐式上下文推断使这一点难以复现）；已经深度投入其他 IDE 生态且迁移收益有限的场景。

## 8.6 Gemini CLI

### 8.6.1 定位与开发商

Gemini CLI 是 Google 开源的终端智能体，仓库为 github.com/google-gemini/gemini-cli（原稿记录约 94,775 星至 106k 星，为统计时点数据），安装命令为 `npm install -g @google/gemini-cli`，启动命令为 `gemini`。它的最大吸引力在于：**用 Google 账号登录即可获得免费额度**，同时拥有原稿记录的 1M token 上下文窗口。对预算为零的学生，这是门槛最低的 CLI 智能体选项。

### 8.6.2 核心机制

作为终端形态，它的工具集与同类产品结构相似：文件读写、shell 执行、检索、联网。两项特性值得单独说明。

**内置 Google Search 工具**（grounding）：智能体可把检索结果作为事实来源，并在回答中给出来源标注。对需要核对文献、核对 API 用法、核对统计量定义的场景，这比模型凭记忆作答可靠。代价是检索质量决定了回答质量，且检索结果本身可能是低质量的二手来源。

**Extensions 机制**：通过扩展包挂载额外的工具与提示，作用上接近 Skill 与 MCP 的中间形态。此外，Gemini CLI 支持 MCP 服务器，可以接入自有工具。

权限与沙箱方面，它提供命令执行的确认与沙箱选项，但审批粒度与审计能力弱于以权限白名单为核心设计的 Claude Code。对需要在无监督环境下运行长任务的场景，这一点需要额外评估。

### 8.6.3 适用与不适用场景

**适用**：零成本起步；需要一次性读进整个代码仓库或数十篇论文文本的任务（长上下文的价值在此）；需要联网核对事实的任务；教学与培训场景（免费额度便于批量分发）。

**不适用**：数据敏感、不能出网的研究项目；需要精细权限控制与完整审计轨迹；需要离线运行。

## 8.7 Aider

### 8.7.1 定位与开发商

Aider 是一个开源（Apache 2.0）的终端结对编程工具，官网 aider.chat，仓库 github.com/Aider-AI/aider，文档 aider.chat/docs/。安装命令为 `pip install aider-chat`，启动为 `aider`。它是本章讨论的六款工具中唯一完全免费开源、且可以完全在本地离线运行的 CLI 智能体，因此对预算有限、数据敏感、或希望完全掌控工具链的研究者具有特别价值。

### 8.7.2 核心机制

**Repo Map（仓库地图）**。Aider 使用 tree-sitter 解析源码，抽取函数、类与调用关系，生成一份紧凑的仓库结构摘要随请求发送。这一设计解决的是上下文预算问题：全量塞入代码既昂贵又稀释注意力，只塞结构摘要则让模型知道"有哪些东西在哪儿"，需要细节时再读取具体文件。这与第 7 章讨论的动态工具检索是同一思路在代码场景的实现。

**Git 自动提交**。每次改动后 Aider 自动生成一条语义化的 commit。这不是便利功能，而是安全机制：它把智能体的每一次修改变成可回滚、可 `git diff` 审查的离散单元。配合 `/undo` 与分支策略，研究者可以放心让智能体大改代码而不担心丢失原稿。对学术写作而言，它还提供了一个隐含的审计记录，"这段分析是谁、在什么时候、因为什么改的"。

**模型后端**。Aider 通过 LiteLLM 支持多种后端，因此可接 DeepSeek、Ollama 本地模型、OpenAI、Anthropic 等。低成本路线是接 DeepSeek API（原稿估计约 $0.001/次请求），零成本路线是接本地 Ollama 模型。

```bash
# 安装
pip install aider-chat
# 接 DeepSeek（低成本）
export DEEPSEEK_API_KEY="你的key"
aider --model deepseek/deepseek-chat
# 接本地 Ollama（完全离线）
aider --model ollama/qwen2.5-coder
```

配置文件支持 `.aider.conf.yml`（项目级）与环境变量（如 `AIDER_MODEL`），便于把模型选择、Git 行为、lint 与测试命令固化下来。

### 8.7.3 适用与不适用场景

**适用**：终端重度使用者；需要可审计 Git 历史的协作项目；预算为零或需要接国内模型；需要离线运行（配本地模型）；偏好开源可控工具链的研究者。

**不适用**：需要 IDE 图形界面与可视化差异比对；需要操作非代码软件；对项目结构不清晰、符号抽取困难的仓库（Repo Map 的效果依赖代码可解析性），例如由大量无结构 `.csv` 与临时脚本组成的工作目录。

## 8.9 代码生成与执行

### 8.9.1 代码作为可验证的中间表示

语言模型直接回答"这两组的均值差是多少"时，输出的是一个从参数中采样出来的字符串；它既可能正确，也可能因为记忆偏差、算术能力不足或幻觉而错误，且**没有任何外部机制能在输出那一刻区分二者**。若改为让模型输出一段读取真实数据、计算差值并打印结果的脚本，则输出变成了一个可以被独立执行、重复执行、逐行审查的对象。

形式化地，设问题为 $q$。直接回答建模的是 $P_\theta(y \mid q)$，其中 $y$ 是答案文本，误差完全由模型的参数决定。程序生成路径建模的是 $P_\theta(c \mid q)$，其中 $c$ 是程序，答案由确定性执行器给出：

$$y = \mathcal{E}(c), \qquad \text{判据 } V(y) \in \{0, 1\}$$

这里 $\mathcal{E}$ 是解释器（Python、R、Shell），$V$ 是验证器，可以是一句断言、一次独立的数值复算、或一个统计检验。关键的收益是：误差来源从"模型对数值的记忆"转移到了"模型对程序的构造"。前者难以检验，后者可以被机器检验。

这一思路与第 13 章讨论的"评估器即验证器"是同一条原则的两种表述。第 13 章关心的是如何为自动发现的程序构造评估函数，本节关心的是如何为模型生成的分析脚本构造验证函数；二者的共同前提是**评估标准必须是可计算的**。统计学在此处有特殊优势：大量统计对象是算法性的，估计量有闭式或迭代解法，不等式可在网格上数值验证，渐近性质可用蒙特卡洛检验，因此为统计任务构造 $V$ 通常不需要形式化证明工具，一段二十行的脚本即可。

代码作为中间表示还带来三项附带收益。一是**可重复执行**：同一段脚本换一组数据、换一个带宽、换一个协变量集合即可重跑，敏感性分析几乎是免费的。二是**可审计**：合作者与审稿人可以逐行检查，而不是面对一段无法拆开的自然语言推理。三是**可定位**：出错时能定位到具体行，而不是在一段文字里猜测哪里算错了。

### 8.9.2 工具集成推理范式

工具集成推理（Tool-Integrated Reasoning, TIR）是上述思想的工程化形态：模型在推理过程中交替生成自然语言推理与可执行代码片段，把解释器的输出回灌到上下文中，再继续推理。相关的代表性工作包括程序辅助语言模型（Program-Aided Language models, PAL，把定量推理外包给 Python 解释器）、面向数学解题的工具集成推理智能体（ToRA），以及让模型自监督地学习"何时调用外部 API"的 Toolformer。NuminaMath 等数学解题数据集进一步把这类轨迹作为训练数据，使模型在训练阶段就学会"需要算的时候写码"。

从统计学角度可以给出一个简单的误差分解。设真值为 $y^\ast$，直接回答的误差为

$$y - y^\ast = \underbrace{(y - \hat y)}_{\text{模型输出偏差}} + \underbrace{(\hat y - y^\ast)}_{\text{数值/知识误差}}$$

其中 $\hat y$ 是模型"想表达"的值。在程序生成路径下，第二项被替换为执行器的浮点误差，量级在 $10^{-15}$ 相对精度，可以视为零；第一项转化为"程序是否正确表达了模型意图"，其检验成本远低于检验数值记忆。这正是为什么在算术、符号运算、数据汇总这类任务上，程序生成路径的准确率显著高于直接回答。

需要区分的是，这一收益只在**答案可由确定性程序计算**的任务上成立。对"这段结果该怎么解释""这个识别假设是否可信"这类没有唯一计算答案的问题，代码不能充当验证器。

### 8.9.3 生成—执行—验证闭环的实现

一个可用的闭环包含四个要素：隔离的执行环境、超时与资源限制、返回码与契约检查、独立复算。下表列出三类失败及其捕获手段。

| 失败类型 | 表现 | 捕获手段 | 捕获难度 |
|----------|------|----------|----------|
| 语法错误 | 解释器报错，返回码非 0 | 返回码检查、traceback 回灌 | 低 |
| 运行时错误 | 键不存在、除零、内存溢出、奇异矩阵 | 返回码检查、超时限制、traceback 回灌 | 低 |
| 静默的数值错误 | 执行成功但算错（错列、错单位、错公式） | 断言、独立复算、与已知结果比对 | 中 |
| 语义错误 | 执行成功但答非所问（检验选错、变量定义错） | 人工审查、规范化的任务契约 | 高 |
| 环境不确定性 | 同一脚本两次运行结果不同 | 固定种子、锁定环境、记录硬件与版本 | 中 |

整个闭环可以概括为五道验证闸门，按验证成本从低到高排列：静态检查毫秒级完成，测试以秒计，独立复算与人工抽检最贵，因此放在后面、只对通过前面各关的候选脚本执行。

```text
需求 ──▶ 1 生成 ──▶ 2 静态检查 ──▶ 3 测试 ──▶ 4 数值复算 ──▶ 5 人工抽检 ──▶ 结果入库
        写出脚本    ruff/AST 规则   属性测试    第二实现复算   统计语义判断    Git 提交
           ▲            ▲              ▲            ▲             ▲
           └────────────┴──────┬───────┴────────────┴─────────────┘
                               │
          闸门 1 至 4 不通过时：把诊断信息回灌给模型，回到闸门 1 重新生成
          闸门 5 不通过时：修改需求或分析方案，而不是让模型反复重试
```

闸门 1 至 4 的判断全部是机械的，可以交给脚本与解释器；闸门 5 不可机械化，它检查的是 8.9.5 所说的统计语义，识别假设、估计目标、方法与数据结构的匹配。前两类由解释器免费提供，后三类需要主动设计。以下是一个最小可用的执行—校验脚本，它运行模型生成的脚本，检查返回码与超时，并要求脚本以约定的 JSON 契约输出关键结果：

```python
# run_check.py ， 生成—执行—验证闭环的最小实现
import json, subprocess, sys, tempfile, os

def run_and_check(script_path: str, contract_schema: dict, timeout: int = 120):
    """执行脚本，要求其向 stdout 打印一行 JSON 结果，并校验关键字段。"""
    proc = subprocess.run(
        [sys.executable, script_path],
        capture_output=True, text=True, timeout=timeout,
        cwd=os.path.dirname(script_path) or ".",
    )
    if proc.returncode != 0:
        # 语法/运行时错误：把 traceback 完整回灌给模型，让它自己修
        return {"ok": False, "stage": "exec", "stderr": proc.stderr[-4000:]}

    try:
        result = json.loads(proc.stdout.strip().splitlines()[-1])
    except (json.JSONDecodeError, IndexError):
        return {"ok": False, "stage": "contract", "stderr": proc.stdout[-2000:]}

    problems = []
    for key, rule in contract_schema.items():
        if key not in result:
            problems.append(f"missing:{key}")
            continue
        lo, hi = rule.get("range", (float("-inf"), float("inf")))
        if not (lo <= result[key] <= hi):
            problems.append(f"out_of_range:{key}={result[key]}")
    if problems:
        return {"ok": False, "stage": "assert", "problems": problems}
    return {"ok": True, "result": result}

# 例：要求脚本报告样本量、估计值、标准误、95% 置信区间
schema = {
    "n":        {"range": (1, 10**7)},
    "estimate": {"range": (-1e6, 1e6)},
    "se":       {"range": (0, 1e6)},
    "ci_low":   {"range": (-1e6, 1e6)},
    "ci_high":  {"range": (-1e6, 1e6)},
}
print(run_and_check("analysis.py", schema))
```

对应的 shell 封装适合直接接进智能体的命令循环：

```bash
#!/usr/bin/env bash
# run_check.sh <script.py> ， 非 0 退出码即视为失败，便于智能体自动重试
set -uo pipefail
script="$1"
timeout 120 python "$script" 2>err.log
rc=$?
if [ $rc -ne 0 ]; then
  echo "FAILED rc=$rc"
  tail -n 30 err.log          # 把错误回灌给智能体
  exit $rc
fi
echo "OK"
```

**独立复算**是捕获静默数值错误的核心手段，做法是要求模型用第二种实现重算同一个量，再比对。两条实现路径应当在算法层面真正不同，而不是同一函数的两次调用：

```python
# 复算示例：回归系数用两条路径核对
import numpy as np, statsmodels.api as sm
y = df["sbp_followup"].to_numpy(); X = df[["age", "bmi"]].to_numpy()
beta_ols = np.linalg.lstsq(np.c_[np.ones(len(X)), X], y, rcond=None)[0]   # 路径一：正规方程
beta_sm  = sm.OLS(y, sm.add_constant(X)).fit().params                     # 路径二：statsmodels
assert np.allclose(beta_ols, beta_sm, rtol=1e-8, atol=1e-10), "两条路径不一致"
```

### 8.9.4 提示词层面的约束

让模型输出可执行脚本而非数字，需要在任务描述中显式约定。以下模板可直接复用：

```text
任务：分析 data/patient_data.csv，估计治疗组与对照组随访收缩压的均值差。

约束：
1. 只使用文件中真实存在的列；禁止用示例数据或假设值替代真实数据。
2. 读取后先报告：行数、列类型、每列缺失数。缺失值处理策略须经我确认后再执行。
3. 所有涉及随机性的步骤（抽样、插补、交叉验证、初始化）必须显式设置种子并在注释中记录。
4. 把关键结果以一行 JSON 打印到 stdout，字段为 n / estimate / se / ci_low / ci_high / method。
5. 不要输出任何未经脚本计算的数值；需要引用的文献或常数须注明来源。
6. 脚本必须能在当前目录下以 `python analysis.py` 独立运行，不得依赖交互式状态。
7. 若某一步的前提假设（正态性、独立性、缺失机制）无法从数据验证，显式写出该假设。
```

第 4 条的 JSON 契约尤其重要：它把"结果"从散文变成结构化对象，从而可以被 8.9.3 的校验脚本消费，也可以被 Quarto 报告（8.12）与实验记录（8.13）直接读取。

### 8.9.5 局限与风险

代码能运行不等于分析正确。执行器只能检查程序的**语法与运行时语义**，无法检查**统计语义**：独立性假设是否成立、缺失是否为随机缺失（MAR）、区组结构是否被忽略、多重比较是否需要校正，这些判断不在解释器的职责范围内，必须由研究者承担。智能体倾向于选择"能跑通"的方案，而"能跑通"与"合适"之间存在系统性差距，例如对聚类数据默认使用忽略聚类的普通标准误。

第二类风险来自执行不受信代码本身。智能体生成的脚本具有与使用者相同的文件系统权限，一次 `rm -rf` 或一次把数据上传到外部 API 的调用都会造成实质损害。建议始终在容器或受限用户下执行，并限制网络出口。第三类风险是非确定性：网络请求、时间戳、并行调度、浮点加法的非结合性、GPU 归约的非确定性，都会导致同一脚本两次运行给出不同结果。处理方式是把环境与种子视为一等公民，详见 8.14。

### 8.9.6 AI 生成代码的验收测试：一个属性测试的最小示例

8.9.3 的独立复算回答的是"这个函数算得对不对"，但研究者面对的更常见情形是：智能体交来一个从没见过的实现，需要在合并进分析脚本之前判断它是否可信。这类验收可以借鉴软件工程中的**属性测试**（property-based testing）思路：不逐个构造输入输出用例，而是陈述函数应当满足的若干数学性质，再在大量随机生成的输入上检查这些性质是否成立。这与 7.10.1 的蒙特卡洛验证 Skill 是同一思想，那里检验的是第一类错误率与功效是否接近名义水平，这里检验的是实现是否符合统计定义。

以自助法置信区间为例。设智能体交来一个 `bootstrap_ci` 函数，验收方掌握一个可信的参照实现（或直接由研究者写出），然后陈述三条性质：一是**平移等变性**，对数据加常数 $c$，区间两端应同样平移 $c$，这来自均值估计的仿射性质；二是**非退化性**，对有方差的样本，区间宽度必须为正且量级合理；三是**覆盖率**，在真值已知的模拟数据上，覆盖率应接近名义水平。下面的脚本同时实现了正确的自助法区间与一个含典型 bug 的"AI 生成"版本（重抽时不慎写成了无放回抽样），然后用同一组性质检查二者：

```python
# verify_bootstrap.py ， 用属性测试对照检查 AI 生成的自助法置信区间函数
# 实测环境：Python 3.10.20，numpy 1.26.4
import numpy as np

def bootstrap_ci_reference(x, B=2000, alpha=0.05, seed=0):
    """正确实现：有放回重抽，取均值抽样分布的百分位数。"""
    rng = np.random.default_rng(seed)
    n = len(x)
    idx = rng.integers(0, n, size=(B, n))
    stat = x[idx].mean(axis=1)
    lo, hi = np.percentile(stat, [100 * alpha / 2, 100 * (1 - alpha / 2)])
    return lo, hi

def bootstrap_ci_ai(x, B=2000, alpha=0.05, seed=0):
    """AI 生成版本：结构与正确实现相同，但重抽时不慎写成了无放回。"""
    rng = np.random.default_rng(seed)
    n = len(x)
    idx = np.array([rng.choice(n, size=n, replace=False) for _ in range(B)])  # bug
    stat = x[idx].mean(axis=1)
    lo, hi = np.percentile(stat, [100 * alpha / 2, 100 * (1 - alpha / 2)])
    return lo, hi

master = np.random.default_rng(20260101)   # 测试自身的种子也要固定

def prop_shift(fn):
    """平移等变性：数据加常数 c，区间两端应同样平移 c。"""
    x = master.normal(0, 1, 60)
    lo1, hi1 = fn(x, seed=1)
    lo2, hi2 = fn(x + 100.0, seed=1)
    return bool(np.allclose([lo1 + 100, hi1 + 100], [lo2, hi2], atol=1e-8))

def prop_nondegenerate(fn, reps=20):
    """非退化性：对有方差的样本，区间宽度必须为正且量级合理。"""
    for _ in range(reps):
        x = master.normal(0, 1, 40)
        lo, hi = fn(x, seed=2)
        if not (hi - lo) > 0.1:   # n=40 的正态均值 95% 区间宽度约 0.6
            return False
    return True

def prop_coverage(fn, reps=400, n=50, alpha=0.05, mu=0.5):
    """覆盖率：在真值已知的模拟数据上，覆盖率应接近名义水平 95%。"""
    cover = 0
    for r in range(reps):
        x = master.normal(mu, 1.0, n)
        lo, hi = fn(x, seed=1000 + r)
        cover += (lo <= mu <= hi)
    return cover / reps

for name, fn in [("reference", bootstrap_ci_reference), ("ai_version", bootstrap_ci_ai)]:
    print(f"{name:10s} shift={prop_shift(fn)}  "
          f"nondegenerate={prop_nondegenerate(fn)}  "
          f"coverage={prop_coverage(fn):.3f}")
```

输出（脚本约 13 秒跑完，主要开销在 AI 版本的逐行循环）：

```text
reference  shift=True  nondegenerate=True  coverage=0.938
ai_version shift=True  nondegenerate=False  coverage=0.000
```

结果值得逐行读。bug 版本通过了平移等变性检验，因为排列抽样的均值确实满足仿射性质，所以**单一性质的通过不能作为正确的证据**，验收需要一组性质。真正暴露问题的是非退化性：`replace=False` 时每次"重抽"其实是原样本的一个排列，样本均值恒等于 $\bar x$，自助分布退化为一点，区间宽度为零，一个对有方差数据宽度不为零的断言即可拦下。覆盖率检查则给出了统计意义上的完整诊断：bug 版本的覆盖率为 0.000，参照实现为 0.938，略低于名义的 0.95，这与百分位自助法在 $n = 50$ 的正态数据上覆盖不足的已知表现一致，属于方法本身的性质而非实现的错误。

两点操作建议。一是测试自身的随机性必须固定种子（脚本中的 `master`），否则验收结论本身不可复现；二是性质的构造优先从统计定义出发（估计量的不变性、区间的非退化性、名义水平的覆盖率），它们比"与参照实现逐位一致"更稳健，因为参照实现同样可能有错。若需要更大规模的用例生成与最小反例收缩，hypothesis 库（延伸资源）提供了现成的属性测试框架，pytest 的参数化机制也可以组织这类检查。

### 8.9.7 代码评审清单的可执行化：AST 静态检查

8.9.4 的提示词约束与 8.10.5 的审核要点都以清单形式出现，但清单里有一部分条目不需要人眼：例如"不得在模块顶层执行分析""随机性必须设种子"，它们是关于代码**结构**的规则，而结构可以由抽象语法树（abstract syntax tree, AST）机械检查。把这部分条目下沉为脚本，接进 8.9.3 闸门图的第 2 关，人工评审就能把注意力留给语义问题。下面是一个最小实现，检查两类问题：模块级的可变全局状态与顶层执行副作用，以及存在随机性调用但未见种子设置：

```python
# ast_review.py ， 把评审清单中两条机械可查的规则写成 AST 检查
# 规则 A：模块级可变全局状态与顶层执行副作用
# 规则 B：存在随机性调用但未见种子设置
import ast

RANDOM_FUNCS = {"random", "choice", "integers", "normal", "uniform", "permutation",
                "shuffle", "sample", "rand", "randn", "randint", "beta", "binomial", "poisson"}
SEED_FUNCS = {"seed", "default_rng", "Generator", "set_state"}

def call_name(node):
    f = node.func
    if isinstance(f, ast.Attribute):
        return f.attr
    if isinstance(f, ast.Name):
        return f.id
    return ""

def check_source(src):
    tree = ast.parse(src)
    problems = []
    # 规则 A：模块顶层除 import、def、class、常量赋值、__main__ 守卫外都标记
    for node in tree.body:
        if isinstance(node, (ast.FunctionDef, ast.AsyncFunctionDef, ast.ClassDef,
                             ast.Import, ast.ImportFrom)):
            continue
        if isinstance(node, ast.Assign) and isinstance(node.value, ast.Constant):
            continue
        if isinstance(node, ast.If) and "main" in ast.dump(node.test):
            continue
        kind = "顶层可变赋值" if isinstance(node, ast.Assign) else "顶层执行语句"
        problems.append(f"global_state: 第 {node.lineno} 行附近存在{kind}（{type(node).__name__}）")
    # 规则 B：随机性调用与种子设置
    calls = [n for n in ast.walk(tree) if isinstance(n, ast.Call)]
    has_seed = any(call_name(c) in SEED_FUNCS for c in calls)
    uses_random = any(call_name(c) in RANDOM_FUNCS for c in calls)
    if uses_random and not has_seed:
        problems.append("no_seed: 检测到随机性调用，但未见 seed / default_rng")
    return problems

BAD = '''
import numpy as np
import pandas as pd

df = pd.read_csv("data.csv")
df["z"] = np.random.normal(0, 1, len(df))
result = df.groupby("group")["z"].mean()
print(result)
'''

GOOD = '''
import numpy as np
import pandas as pd

SEED = 20260101

def add_noise(df, seed=SEED):
    rng = np.random.default_rng(seed)
    out = df.copy()
    out["z"] = rng.normal(0, 1, len(out))
    return out

def main():
    df = pd.read_csv("data.csv")
    print(add_noise(df).groupby("group")["z"].mean())

if __name__ == "__main__":
    main()
'''

for label, src in [("BAD（AI 生成，含两类问题）", BAD), ("GOOD（修正后）", GOOD)]:
    print(label)
    if check_source(src):
        for p in check_source(src):
            print("  -", p)
    else:
        print("  - 通过")
```

实测输出：

```text
BAD（AI 生成，含两类问题）
  - global_state: 第 5 行附近存在顶层可变赋值（Assign）
  - global_state: 第 6 行附近存在顶层可变赋值（Assign）
  - global_state: 第 7 行附近存在顶层可变赋值（Assign）
  - global_state: 第 8 行附近存在顶层执行语句（Expr）
  - no_seed: 检测到随机性调用，但未见 seed / default_rng
GOOD（修正后）
  - 通过
```

需要说明这类检查的边界。AST 检查的是结构而不是语义：规则 A 会把一切顺序式脚本（包括交互式探索阶段完全合理的写法）整体标记，其中不乏误报，使用者需要决定是重构为函数还是暂时豁免；规则 B 只能确认"存在种子调用"，不能确认种子的取值被记录在案、也不能确认 `Generator` 对象被传递给了每一个随机步骤（8.14 的运行清单负责前者）。更完整的静态检查应交给 ruff 一类成熟工具（延伸资源），其 S311 规则会对 `random` 模块的非密码学使用给出提示。本例的意义不在于替代专业工具，而在于展示一个做法：**评审清单中凡是判断标准可以写成代码的条目，都应该写成代码**，否则清单会随着项目增长而逐渐退化为形式。接入方式上，Claude Code 的 Hooks（8.2.3）与 Git 的 pre-commit 钩子都可以在每次生成或提交代码后自动运行这类脚本。

### 8.9.8 AI 生成代码的典型失败模式与检查方法

8.9.3 的失败类型表按错误发生的位置（语法、运行时、语义）分类；本节换一个角度，按 AI 生成代码反复出现的具体错误模式分类，并给出对应的检测手段。

| 失败模式 | 典型表现 | 检测手段 |
|----------|----------|----------|
| 变量名幻觉 | 引用数据中不存在的列名、包中不存在的函数或参数，代码看起来完全合理 | 执行前机械核对：对脚本引用的列名做集合差断言；用 `hasattr(模块, 名称)` 核对函数存在性；运行时一旦出现 `AttributeError`、`KeyError` 即把 traceback 回灌 |
| API 版本不匹配 | 使用已被移除或改名的接口（如 pandas 2.0 移除了 `DataFrame.append`，需改用 `pd.concat`），旧环境能跑、新环境报错 | 锁定依赖版本（8.14.2）；以 `python -W error::DeprecationWarning analysis.py` 运行，把弃用警告升级为错误，提前暴露而非等待失效 |
| 统计方法误用 | 把异方差稳健标准误当聚类稳健标准误；忽略配对结构做独立样本检验；把 Mann-Whitney U 的结论表述为均值差异 | JSON 契约要求脚本显式报告 `method` 字段并说明方差估计口径；先诊断数据结构（是否存在聚类、配对、区组）再核对方法是否匹配，示例见 8.15.8；对照已知结果复算 |
| 随机种子缺失 | 同一脚本两次运行给出不同的估计值或不同的图 | AST 静态扫描随机性调用（8.9.7）；让脚本连跑两遍，对比 JSON 契约输出是否逐字段一致 |
| 静默数值错误 | 列错位、单位混淆、公式抄错，执行成功但结果错误 | JSON 契约加取值范围检查（8.9.3）；第二条实现路径独立复算；与理论值或文献值比对 |

前两类失败在闸门 2 与 3 就能拦截，成本最低。统计方法误用最难机械化，因为它涉及"方法与数据结构是否匹配"的判断，但其中可以前置的部分仍然不少：聚类结构、配对结构、区组结构都可以从数据本身诊断出来（组内相关、差分的自相关、区组标识的存在），不需要等待研究者逐行读代码。变量名幻觉还有一层容易被忽视的危害：它常混在大量正确的代码中间（8.3.3 已在补全场景下指出），逐行审阅的漏检率高，因此对这类错误的防御优先级应放在机械核对而非人工细读上。

## 8.10 数据分析自动化

### 8.10.1 六个阶段与人工介入点

一次完整的统计分析可以拆为六个阶段。下表给出每阶段的任务、智能体可承担的部分，以及必须由研究者确认的部分。

| 阶段 | 主要任务 | 智能体可承担 | 必须人工确认 |
|------|----------|--------------|--------------|
| 读取 | 导入数据、核对字典、检查编码 | 写导入代码、识别分隔符与编码、生成数据字典摘要 | 变量定义与单位、隐私字段的脱敏策略 |
| 清洗 | 缺失值、异常值、去重、类型转换、合并 | 生成诊断报告（缺失模式、离群点）、执行已确认的策略 | 缺失机制假设、删除与插补的选择、离群点是否为真实值 |
| 探索 | 单变量分布、相关结构、分组描述 | 批量出图与描述统计表、标记可疑分布 | 变量的科学含义、是否需要变换 |
| 建模 | 选择模型形式、拟合、推断 | 生成候选模型代码、跑通并汇总结果 | 识别策略、混杂调整集合、模型形式的统计依据 |
| 诊断 | 残差、影响点、共线性、收敛、校准 | 生成诊断图与数值检查、自动标注异常 | 诊断结果对应的处理动作（是否剔除、是否换模型） |
| 报告 | 表格、图形、文字解读、可复现产物 | 生成三线表、森林图、Quarto 文档初稿 | 结论表述的分寸、局限性的陈述 |

阶段划分的意义在于把"自动化"限定在明确的子任务上，而不是整体托管。经验规则是：**凡是可以用断言检验的，交给智能体；凡是需要学科判断的，保留在人手中。**

### 8.10.2 Python 骨架

下面是一份可直接作为模板的 Python 骨架，覆盖六阶段且每阶段都有显式的检查点。

```python
# analysis.py ， 六阶段骨架（阶段之间设置显式检查点）
import numpy as np, pandas as pd, json
SEED = 20260101
np.random.seed(SEED)

# ---- 阶段 1：读取 ----
df = pd.read_csv("data/patient_data.csv")
assert df.shape[0] > 0, "空数据"
print(df.dtypes.to_string())
print("缺失数：\n" + df.isna().sum().to_string())

# ---- 阶段 2：清洗（策略须经确认后写入） ----
num_cols = df.select_dtypes("number").columns
miss = df[num_cols].isna().mean()
print("缺失比例：\n" + miss[miss > 0].to_string())
# 例：中位数插补（记录被插补的列与中位数）
fill_values = df[num_cols].median()
df[num_cols] = df[num_cols].fillna(fill_values)

# ---- 阶段 3：探索 ----
desc = df.groupby("treatment_group")[num_cols].agg(["mean", "std", "median"])
print(desc.round(3).to_string())

# ---- 阶段 4：建模 ----
import statsmodels.formula.api as smf
fit = smf.ols("sbp_followup ~ treatment_group + age + bmi + sbp_baseline", data=df).fit()
print(fit.summary().tables[1])

# ---- 阶段 5：诊断 ----
infl = fit.get_influence()
cooks = infl.cooks_distance[0]
print("Cook 距离超过 4/n 的观测数：", int((cooks > 4 / len(df)).sum()))
vif = pd.Series(
    [1 / (1 - smf.ols(f"{c} ~ " + " + ".join([x for x in ["age", "bmi", "sbp_baseline"] if x != c]),
                      data=df).fit().rsquared)
     for c in ["age", "bmi", "sbp_baseline"]],
    index=["age", "bmi", "sbp_baseline"], name="VIF")
print(vif.round(2).to_string())

# ---- 阶段 6：输出结构化结果 ----
key = "treatment_group[T.drug]"
res = {
    "n": int(fit.nobs), "estimate": float(fit.params[key]), "se": float(fit.bse[key]),
    "ci_low": float(fit.conf_int().loc[key, 0]), "ci_high": float(fit.conf_int().loc[key, 1]),
    "method": "OLS with age/bmi/baseline adjustment", "seed": SEED,
}
print(json.dumps(res))   # 供 run_check.py 消费
```

### 8.10.3 R 骨架

同一流程的 R 版本，使用 tidyverse 与 broom 产出 tidy 结果：

```r
# analysis.R ， 六阶段骨架（R 版本）
set.seed(20260101)
library(dplyr); library(tidyr); library(broom); library(ggplot2)

## 阶段 1-2：读取与清洗
df <- readr::read_csv("data/patient_data.csv")
skimr::skim(df)                                   # 缺失与分布概览
df <- df |> mutate(across(where(is.numeric), ~ ifelse(is.na(.x), median(.x, na.rm = TRUE), .x)))

## 阶段 3：探索
df |> group_by(treatment_group) |>
  summarise(across(c(age, bmi, sbp_baseline, sbp_followup),
                   list(mean = ~mean(.x, na.rm = TRUE), sd = ~sd(.x, na.rm = TRUE))),
            .groups = "drop")

## 阶段 4：建模
fit <- lm(sbp_followup ~ treatment_group + age + bmi + sbp_baseline, data = df)
tidy(fit, conf.int = TRUE)                        # tidy 系数表，可直接进报告

## 阶段 5：诊断
par(mfrow = c(2, 2)); plot(fit)                   # 残差、QQ、尺度-位置、杠杆
car::vif(fit)

## 阶段 6：结构化输出
coef_tbl <- tidy(fit, conf.int = TRUE) |>
  filter(term == "treatment_groupdrug") |>
  transmute(n = nobs(fit), estimate = estimate, se = std.error,
            ci_low = conf.low, ci_high = conf.high, method = "OLS")
jsonlite::toJSON(coef_tbl, auto_unbox = TRUE)
```

两套骨架刻意保持结构一致，目的是让跨语言核对（8.15）变得机械：同一估计量在两个生态中分别算出，`allclose` 级别的差异说明实现无误，数量级的差异说明某处变量定义或编码不一致，后者是最常见也最危险的 bug 来源。

### 8.10.4 案例：用终端智能体完成一次完整统计分析

下面这个案例演示智能体在真实统计任务中的行为方式，以及哪些环节仍需要研究者把关。

**案例背景。** 数据文件 `patient_data.csv` 含 500 名患者，任务要求完成描述统计、组间差异检验、效应量计算与森林图绘制。数据字典为：`age`（年龄）、`bmi`（BMI）、`sbp_baseline`（基线收缩压）、`sbp_followup`（随访收缩压）、`treatment_group`（用药组别，drug/placebo）、`response`（疗效指标，二分类）。

**第一步，进入工作目录并启动智能体。**

```bash
cd ~/research/hypertension_study
claude        # 或 aider / interpreter
```

**第二步，用自然语言下达任务。** 需求描述应当包含数据字典与明确的步骤，而不是一句"帮我分析一下"：

```text
我有一个 CSV 文件 patient_data.csv，包含 500 名患者数据。请帮我完成以下分析：
1. 读取数据，检查缺失值和数据类型
2. 按 treatment_group 分组，做描述性统计（均值、标准差、中位数）
3. 检验实验组 vs 对照组的收缩压差异（先做 Shapiro-Wilk 正态性检验，再选择 t 检验或 Mann-Whitney U 检验）
4. 计算 Cohen's d 效应量及其 95% 置信区间
5. 画一个森林图展示各亚组的效应量
6. 所有结果保存为 analysis_results.xlsx
7. 代码保存为 analysis.py，用 R 语言重做一遍保存为 analysis.R
数据字典：age / bmi / sbp_baseline / sbp_followup / treatment_group / response
```

**第三步，智能体自动执行。** 执行过程通常分为五个阶段。

*阶段一，数据探索。* 智能体生成并执行读取与诊断代码，发现 `bmi` 列有 12 个缺失值，随后停下来询问处理策略，这一步的停顿是必要的，因为缺失机制无法从数据本身判定。

```python
import pandas as pd
df = pd.read_csv('patient_data.csv')
print(df.info()); print(df.isnull().sum()); print(df.describe())
```

*阶段二，统计检验。* 智能体按"先检验正态性，再选择检验方法"的流程生成代码：

```python
from scipy import stats
stat_sw, p_sw = stats.shapiro(df['sbp_followup'])
if p_sw > 0.05:
    t_stat, p_val = stats.ttest_ind(
        df[df['treatment_group']=='drug']['sbp_followup'],
        df[df['treatment_group']=='placebo']['sbp_followup'])
else:
    u_stat, p_val = stats.mannwhitneyu(
        df[df['treatment_group']=='drug']['sbp_followup'],
        df[df['treatment_group']=='placebo']['sbp_followup'])
```

*阶段三，效应量计算。* Cohen's d 用合并标准差构造，置信区间用大样本近似标准误：

```python
import numpy as np
grp1 = df[df['treatment_group']=='drug']['sbp_followup']
grp2 = df[df['treatment_group']=='placebo']['sbp_followup']
n1, n2 = len(grp1), len(grp2)
sd1, sd2 = grp1.std(ddof=1), grp2.std(ddof=1)
pooled_sd = np.sqrt(((n1 - 1) * sd1**2 + (n2 - 1) * sd2**2) / (n1 + n2 - 2))
cohens_d = (grp1.mean() - grp2.mean()) / pooled_sd
se_d = np.sqrt((n1 + n2) / (n1 * n2) + cohens_d**2 / (2 * (n1 + n2)))
ci_lower, ci_upper = cohens_d - 1.96 * se_d, cohens_d + 1.96 * se_d
```

*阶段四，森林图绘制。* 按年龄亚组分别计算效应量后绘图，同时导出为矢量格式。

*阶段五，结果导出。* 结果写入 `analysis_results.xlsx`，并生成等价的 `analysis.R`。

**第四步，验证。** 智能体执行完毕后会展示关键统计量、打开生成的图形，并提示检查两个脚本文件。研究者这一侧的核对清单是：两个脚本读的是不是同一份数据、缺失值处理是否一致、Python 与 R 算出的效应量是否在同一容差内、森林图的亚组划分依据是否事先确定。

**这个案例说明了什么。** 使用者全程只说了一段话，智能体完成了读数据、处理缺失、选择检验、计算效应量、画图、导出、生成 R 版本的七步流程。效率提升是实在的。但这个案例也暴露了自动化分析的一类系统性风险，值得单独指出：阶段二的"先做正态性检验，再决定用 t 检验还是 Mann-Whitney U 检验"是一条流传很广但统计性质存疑的规则。它是一个**条件于数据的检验选择**，最终检验的分布依赖于前一步的检验结果，因此名义水平 $\alpha$ 并不等于实际的 I 类错误率。同时，Shapiro-Wilk 在大样本下对轻微偏离极为敏感，在 $n = 500$ 时几乎必然拒绝正态性，从而把流程推向 Mann-Whitney U；而 Mann-Whitney U 检验的是随机占优（$P(X > Y) = 1/2$），与"均值差是否为零"并非同一估计目标。换言之，智能体忠实执行的这条流程，在小样本下功效不足，在大样本下估计目标漂移。研究者在采用这类自动化流程时，应当把"检验的选择"作为分析方案的一部分**事先固定**（见 8.13 的实验设计原则与第 17 章的预注册讨论），而不是交给一个数据依赖的分支。

### 8.10.6 自动化分析工具生态的定位

除通用编程智能体外，还有一批面向自动化的专用工具，它们与智能体的关系是互补而非替代。

| 工具 | 定位 | 在统计工作流中的位置 | 局限 |
|------|------|----------------------|------|
| FLAML | 轻量 AutoML，强调低算力下的高效搜索 | 预测任务中的模型与超参选择 | 侧重预测精度，推断与不确定性量化支持有限 |
| TPOT | 基于遗传编程的机器学习管道搜索 | 端到端管道原型 | 搜索成本高，可解释性差 |
| auto-sklearn | 基于贝叶斯优化与元学习的 AutoML | 表格数据建模基线 | 输出管道复杂，难以写进论文的统计方法部分 |
| LIDA | 自然语言驱动的数据可视化与探索 | 探索性分析与图表初稿 | 图形规范需人工调整才能满足期刊要求 |
| Optuna / Ax | 超参与实验优化框架（TPE、贝叶斯优化） | 8.13 的实验设计与调参 | 目标函数需自行定义，不解决因果问题 |

这类工具解决的是"在给定的目标函数下搜索"，而统计研究中的核心困难常常是"目标函数与识别策略本身如何设定"，后者不在自动化范围内。一个实用的判断标准是：如果任务能被写成"最小化某个可计算的损失"，工具可用；如果需要回答"这个估计量识别的是什么"，工具不可用。

## 8.11 文献管理与知识库

### 8.11.1 从关键词检索到语义检索

统计研究者的文献工作有三类：找相关文献、读并提取信息、在写作时正确引用。传统工具解决第一类（关键词检索、引文索引），智能体介入后真正改变的是第二类与第三类，把"读"变成可批量的操作，把"引用"变成可追溯的链接。

检索增强生成（Retrieval-Augmented Generation, RAG，Lewis 等 2020，arXiv:2005.11401）是当前的主流结构：把语料切分为块（chunk），用嵌入模型映射为向量，检索时按向量相似度取回若干块，拼进上下文后由语言模型作答。形式化地，给定查询 $q$，检索器返回 $R(q) = \text{top-}k(\{d_i\})$，生成模型给出

$$P(y \mid q) = \sum_{d \in R(q)} P(y \mid q, d)\, P(d \mid q)$$

其中 $P(d \mid q)$ 由相似度归一化给出。这一框架的价值在于把答案的**事实来源**从参数记忆换成了外部文档，从而使答案可以被溯源；代价是检索质量成为新的瓶颈，检索不到的文献，模型无从知晓，且模型往往不会承认这一点。

### 8.11.2 文献库的技术结构

构建一个可用的文献知识库需要四个组件。

| 组件 | 可选方案 | 选择要点 |
|------|----------|----------|
| 文献来源与元数据 | Zotero（zotero.org）、PAPER 目录、机构库导出 | 元数据质量决定引用准确性，优先用带 DOI 的条目 |
| 文本抽取与分块 | PDF 解析（MinerU、marker、pypdf）、按页或按段落分块加重叠 | 公式与表格是主要难点，需保留页面号以支持页码级溯源 |
| 向量库 | FAISS、Chroma、Qdrant、pgvector | 万级文献以下，单机内存索引已足够，不必引入分布式方案 |
| 生成与工具层 | ellmer（8.15）、paper-qa、LangChain 系框架 | 关键看是否强制输出引用标识符 |

分块（chunking）策略对效果影响很大。按固定 token 数切分实现简单，但会把一个论证切断；按章节或段落切分语义完整，但长度不均；实践中常用的折中是按段落切分并保留 100 至 200 token 的重叠，同时在元数据中保留文档标识与页码。**页码必须保留**，否则溯源只能到"某篇论文"，无法到"第几页"，而后者才是审稿人需要的精度。

### 8.11.3 Zotero 与 MCP 的结合

Zotero 是统计学界使用最广的开源文献管理器，支持条目同步、PDF 附件管理与 BibTeX 导出。把它接入智能体的标准做法是 MCP：MCP 服务器把 Zotero 的本地 SQLite 数据库（或官方 Web API）暴露为一组工具（检索条目、读取笔记、读取 PDF 文本、按集合筛选），智能体按需要调用。MCP 的协议规范见 modelcontextprotocol.io，具体服务器实现由社区维护，选择时应考察三项：是否只读（避免智能体误删条目）、是否支持本地数据库直连（避免依赖网络）、是否返回页码与附件路径。

一个典型的调用链条是：研究者问"我收藏的文献里，有哪些讨论过多重检验下的 FDR 控制"→ 智能体调用全文检索 → 拿到候选条目 → 读取摘要与相关段落 → 给出带条目标识与页码的回答 → 研究者点击标识跳回 Zotero 核对原文。链条的最后一环不可省略：**任何由模型给出的引用都必须回到原文确认**。

### 8.11.4 引用溯源与幻觉引用

幻觉引用是文献场景中后果最严重的失效模式：模型生成一个格式正确、作者与期刊看似合理、但实际不存在的条目。这类条目的危险之处在于它通常能通过格式检查，只有在真正去检索时才会暴露。

防御手段有三层。第一层是**结构上禁止**：提示词要求所有引用必须来自检索结果，并输出条目标识与页码，禁止凭记忆生成参考文献；生成后做机械校验，每个条目的 DOI 是否可解析、标题是否与检索库中的记录完全匹配。第二层是**抽样人工核验**：从一次回答的 $n$ 条引用中随机抽取若干条核对，用 Wilson 区间估计真实错误率的下界。若抽取 30 条发现 0 条错误，Wilson 95% 区间上界约为 11.4%，即只能断定错误率不超过约 11%，不能断定为零，这一结论本身应当写进使用规范。第三层是**库外引用单独标记**：模型若引用了库中不存在的文献，应显式标注"未在库中，需核实"，而不是混在已核实条目中。

### 8.11.6 最小实现

一个不依赖重型框架的本地检索脚本，适合先把流程跑通：

```python
# mini_rag.py ， 最小文献检索：分块、嵌入、检索、带出处输出
import numpy as np, json, re
from pathlib import Path

def chunk(text, size=800, overlap=150):
    """按字符数切分并保留重叠，返回 (块, 起始位置)。"""
    step = size - overlap
    return [(text[i:i + size], i) for i in range(0, len(text), step)]

def embed(chunks, model):
    # model 为任一嵌入模型封装，返回 shape=(n, d) 的二维数组
    return np.asarray(model.encode(chunks), dtype="float32")

def retrieve(query_vec, doc_vecs, k=5):
    # 余弦相似度；向量已归一化时点积即余弦
    sims = doc_vecs @ query_vec / (np.linalg.norm(doc_vecs, axis=1) * np.linalg.norm(query_vec) + 1e-12)
    return np.argsort(-sims)[:k], np.sort(sims)[::-1][:k]

# 检索结果必须携带 (doc_id, page, char_start)，否则无法溯源
```

检索到的块连同出处一起拼进上下文，并要求模型按 `[doc_id:page]` 格式标注每一句的事实来源。

### 8.12.4 配色的统计考量

配色不只是审美问题。三类配色方案对应三类数据：定性（categorical）数据用离散色相，如 Okabe-Ito 或 ColorBrewer 的 Set2；有序（sequential）数据用单色渐变，如 viridis 系列，它在亮度上单调、对色觉障碍友好、且在灰度打印后仍保留顺序信息；发散（diverging）数据用双色渐变，中点应有实质含义（如零效应、均值、临床界值），用 RdBu 一类方案并避免红绿组合。

需要避免的做法包括：用彩虹色（jet）编码连续量（亮度非单调，会制造虚假的边界感）；仅靠颜色区分组别而不加形状或线型（灰度打印后失效）；在同一图中混用多套调色板。

### 8.12.5 图形中的统计约定

图形是统计结论的载体，几处约定直接影响读者对结果的解读。

**误差棒的标注必须明示含义。** 标准差（SD）描述数据的离散程度，标准误（SE）描述估计量的精度，置信区间（CI）给出估计的不确定性范围。三者数值关系为 $\mathrm{SE} = \mathrm{SD}/\sqrt{n}$，$\mathrm{CI} = \hat\theta \pm z_{1-\alpha/2}\,\mathrm{SE}$。报告组间比较时应使用 CI，因为推断的对象是估计量而非样本；用 SD 做误差棒会让读者低估估计精度（$\sqrt{n}$ 倍的差距）。图注中必须写明"误差棒为 95% 置信区间"这类说明。

**直方图的分箱宽度应当显式选择。** 默认分箱常掩盖或伪造分布特征。两个常用规则是 Sturges 规则 $k = \lceil \log_2 n \rceil + 1$（适合近正态数据）与 Freedman-Diaconis 规则 $h = 2\,\mathrm{IQR}\,n^{-1/3}$（对重尾与多峰更稳健）。同一图内更换分箱后结论应稳定，否则结论是分箱的产物。

**纵轴截断需谨慎。** 非零起点的柱状图会放大视觉差异，若使用必须在图上明确标注断点。双纵轴图形在多数情况下应当避免，因为两个纵轴的相对缩放由绘图者任意决定，读者会从视觉重合中读出并不存在的关联。

**小样本应当展示原始数据。** 在 $n$ 较小的分组比较中，用抖动散点叠加箱线图（或雨云图）比单独的箱线图更能反映真实分布，也更容易发现离群点。

## 8.13 实验设计与自动化

### 8.13.1 为什么 AI 工作流需要实验设计

引入 AI 之后，统计研究的可调参数数量显著增加：模型选择、温度与 top-p、提示词模板、少样本示例数量、检索的 $k$ 值与分块大小、工具集构成、是否启用思维链、输出格式约束。这些参数共同构成一个**配置空间**，而每一次配置的实际代价是真实的时间与金钱。

常见的做法是单因子轮换（one-factor-at-a-time, OFAT）：固定其他参数，逐个调整。OFAT 有两个统计缺陷。一是无法估计交互效应，而 AI 系统中的交互普遍存在（温度的影响依赖于是否使用思维链，检索 $k$ 的影响依赖于分块大小）。二是在相同预算下效率更低：若总预算为 $N$ 次运行，$k$ 个因子各取两个水平，全因子设计可以在 $N$ 次运行内同时估计全部主效应与低阶交互，而 OFAT 只能沿一条路径前进。

把经典实验设计（design of experiments, DOE）的术语映射到 AI 配置搜索，对应关系如下。

| DOE 术语 | AI 工作流中的对应 | 说明 |
|----------|-------------------|------|
| 因子（factor） | 可调参数（模型、温度、$k$、模板版本） | 只把真正会变的参数设为因子 |
| 水平（level） | 参数的离散取值 | 连续参数先离散化为若干水平 |
| 处理（treatment） | 一个完整的配置组合 | 运行单位 |
| 响应（response） | 评价指标（准确率、成本、延迟、一致性） | 可多响应，但需预先确定主指标 |
| 区组（block） | 运行日期、GPU 型号、模型快照、数据批次 | 区组内条件更同质 |
| 重复（replicate） | 对同一配置的独立重复运行 | 必须真正独立，见 8.13.3 |
| 随机化（randomization） | 打乱配置的执行顺序 | 抵消漂移与系统负载的干扰 |

### 8.13.2 因子设计与功效分析

两水平全因子设计 $2^k$ 包含所有 $2^k$ 个水平组合，可估计全部主效应与各阶交互。当 $k$ 较大时（例如 $k = 7$ 需要 128 次运行），常用 $2^{k-p}$ 部分因子设计，代价是效应之间发生**别名**（alias），即主效应与高阶交互不可分离。分辨度（resolution）刻画这一性质：分辨度 III 的设计中主效应与二阶交互别名，分辨度 IV 的设计中主效应彼此不别名但与三阶交互别名。AI 配置实验中常用分辨度 IV 以上的设计，因为二阶交互往往有实质意义。

样本量与功效的规划在实验开始之前完成。对两配置比较、响应近似正态、共同方差 $\sigma^2$ 的情形，每组所需运行次数为

$$n = \frac{(z_{1-\alpha/2} + z_{1-\beta})^2 \cdot 2\sigma^2}{\Delta^2}$$

其中 $\Delta$ 是希望检出的最小效应。例如基线任务完成率为 0.70，希望检出提升到 0.73 的差异，取 $\alpha = 0.05$、功效 $1-\beta = 0.8$，比例情形的公式为

$$n = \frac{(z_{1-\alpha/2} + z_{1-\beta})^2\big[p_1(1-p_1) + p_2(1-p_2)\big]}{(p_2 - p_1)^2}$$

代入 $p_1 = 0.70$、$p_2 = 0.73$ 得 $n \approx 3.55 \times 10^3$，即每组约 3550 次观测。这个量级对线上实验可行，对离线配置搜索通常不可行，这正是离线评估必须依赖效应量更大的代理指标，或使用方差缩减技术的原因（第 9 章 9.5 给出 CUPED 等缩减手段）。

```python
# power.py ， 两比例比较的样本量
import numpy as np
from scipy.stats import norm

def n_per_arm_two_prop(p1, p2, alpha=0.05, power=0.80):
    z_a = norm.ppf(1 - alpha / 2); z_b = norm.ppf(power)
    return (z_a + z_b)**2 * (p1*(1-p1) + p2*(1-p2)) / (p2 - p1)**2

print(round(n_per_arm_two_prop(0.70, 0.73)))            # 约 3550

def n_per_arm_mean(delta, sigma, alpha=0.05, power=0.80):
    z_a = norm.ppf(1 - alpha / 2); z_b = norm.ppf(power)
    return (z_a + z_b)**2 * 2 * sigma**2 / delta**2

print(round(n_per_arm_mean(delta=0.5, sigma=2.0)))      # 连续响应示例
```
输出：
```text

251
```

### 8.13.3 伪重复：AI 实验中最常见的错误

在 AI 实验中，"重复"极易被误用。对同一配置、同一条输入重复采样 20 次，得到的 20 个结果**不是** 20 个独立观测：它们共享同一提示、同一输入、同一模型快照，只是解码路径不同。这种结构在统计学中称为**伪重复**（pseudo-replication），其后果是标准误被严重低估、置信区间过窄、显著性被夸大。

处理办法有三层。第一层是区分变异来源：若关心的是"对输入总体的平均表现"，重复单位应是输入样本（不同的问题、不同的数据点），解码重复只用于估计**同一输入上的稳定性**，二者不可混为一谈。第二层是正确地建模：对同一输入多次采样的数据应使用聚类稳健方差（以输入标识为聚类变量）或含随机效应的混合模型

$$Y_{ij} = \mu + \tau_{t(i)} + u_i + \varepsilon_{ij}, \quad u_i \sim N(0, \sigma_u^2), \ \varepsilon_{ij} \sim N(0, \sigma^2)$$

其中 $u_i$ 是输入 $i$ 的随机效应，$\tau_t$ 是配置效应。忽略 $u_i$ 等价于错误地假设观测独立。第三层是报告规范：给出结果时同时说明重复次数、重复单位与方差估计方式。

区组设计在 AI 实验中同样重要。运行日期、GPU 型号、模型快照版本、数据批次都是天然的区组因子：在区组内比较配置，可以消除区组间的系统差异。实践中的一条硬规则是**同一实验的所有配置必须在同一模型快照版本下运行**，否则测得的"配置效应"混杂了模型更新效应。

### 8.13.4 贝叶斯优化与主动学习

当配置空间连续或维度较高、且每次运行代价昂贵时，贝叶斯优化（Bayesian optimization, BO）比因子设计更高效。BO 用一个代理模型（通常是高斯过程或随机森林）拟合"配置 → 响应"的曲面，再用采集函数（acquisition function）决定下一个评估点：

$$x_{n+1} = \arg\max_x \alpha(x \mid \mathcal{D}_n), \qquad \alpha \in \{\text{EI, PI, UCB}\}$$

期望改进（Expected Improvement, EI）是最常用的采集函数，它在"均值高"与"不确定性大"之间做显式权衡。常用框架包括 Ax（facebook/Ax）与 Optuna（optuna/optuna，默认使用 TPE 采样器）。

BO 与 DOE 不是竞争关系而是分工关系：**DOE 用于全局筛选**（在实验初期，用较少的运行识别哪些因子有实质影响、交互是否重要），**BO 用于局部精修**（在确定了主要因子后，在连续空间内寻找最优取值）。跳过筛选直接做 BO，容易在高维无关方向上浪费预算；只做 DOE 不做 BO，则在连续参数上损失精度。

主动学习（active learning）是同一思想在数据标注场景的版本：模型挑选"信息量最大"的样本请求标注，从而用更少的标注达到同等精度。对统计研究者而言，它与最优实验设计（optimal design，A/D/E 最优性）文献直接相通，采集函数本质上就是一个设计准则。

### 8.13.5 把实验设计接进智能体循环

以下脚本给出一个可复用的最小 DOE 流程：构造 $2^3$ 全因子设计、随机化运行顺序、加入日期区组、拟合含交互的模型并输出效应估计。

```python
# doe.py ， 配置实验的最小 DOE 流程
import itertools, numpy as np, pandas as pd
import statsmodels.formula.api as smf

rng = np.random.default_rng(20260101)

# 1. 因子与水平：模型、检索 k、是否启用思维链
factors = {"model": ["small", "large"], "top_k": [3, 10], "cot": [0, 1]}
design = pd.DataFrame(list(itertools.product(*factors.values())), columns=factors.keys())

# 2. 随机化运行顺序 + 日期区组（每天最多跑 4 个配置）
design = design.sample(frac=1, random_state=20260101).reset_index(drop=True)
design["block"] = design.index // 4

# 3. 执行每个配置并收集响应（此处用占位函数代表真实运行）
def run_config(row):
    # 真实场景中：调用模型 API，返回准确率与成本
    return {"accuracy": 0.70 + 0.05*row["cot"] + 0.02*row["top_k"]/10
                        + 0.06*(row["model"] == "large") + rng.normal(0, 0.01),
            "cost": 1.0 + 4.0*(row["model"] == "large") + 0.1*row["top_k"]}
design = pd.concat([design, design.apply(run_config, axis=1).apply(pd.Series)], axis=1)

# 4. 拟合含二阶交互的模型，区组作为固定效应吸收批次差异
mdl = smf.ols("accuracy ~ C(model)*C(top_k)*C(cot) + C(block)", data=design).fit()
print(mdl.summary().tables[1])

# 5. 主效应与交互效应的效应量（以标准差为单位）
effects = mdl.params.drop(labels=[p for p in mdl.params.index if "block" in p])
print((effects / design["accuracy"].std()).round(3).sort_values(key=abs, ascending=False))
```

### 8.13.6 常见陷阱

配置实验中有几类错误反复出现。除 8.13.3 的伪重复外，还有：

**数据泄漏。** 把测试集或验证集内容写进提示词的少样本示例，会得到虚高的指标。防御手段是维护独立的、从未出现在任何提示或训练数据中的留出集，并定期核查示例来源。

**代理指标与真实目标脱节。** 在无法直接测度真实目标时（例如论文质量、临床决策正确性），常使用代理指标（BLEU、准确率、人类偏好打分）。代理指标与真实目标的相关性必须被估计，而不是假定；一个可行做法是抽取若干样本做人工标注，估计代理指标与人工判断的相关系数及其置信区间。

**新奇效应与漂移。** 系统刚上线时使用者的行为与稳定期不同，短期实验结果可能不可外推。此外，外部数据分布随时间漂移，实验结论具有时效性，这也是第 9 章把监控与持续评估作为独立环节的原因。

**配置与数据的混淆。** 若在更换配置的同时更换了数据集，测得的效应无法归因。实验设计的基本原则在此同样适用：一次只改变受控的、被记录的因素。

## 8.14 可复现工作流

### 8.14.1 复现的三要素

一个计算结果可被第三方复现，需要同时锁定三类输入：**代码版本**、**环境指纹**与**数据版本**，并在此之上控制**随机性**。四者缺一，复现都会在某一环节断裂。

| 要素 | 锁定手段 | 产出物 | 常见失效 |
|------|----------|--------|----------|
| 代码版本 | Git 提交哈希、tag | 40 位哈希或语义化版本号 | 未提交的临时脚本、交互式执行的代码 |
| 环境指纹 | renv.lock、conda-lock、Dockerfile、镜像摘要 | 锁文件与镜像 ID | 只记录"Python 3.11"而不记录包版本 |
| 数据版本 | DVC、内容哈希（sha256）、数据快照 | `.dvc` 指针文件、哈希清单 | 数据被原地覆盖，历史版本丢失 |
| 随机性 | 全局种子、确定性算法开关 | 种子常量与配置 | GPU 归约非确定、并行顺序不定、未设置种子 |

AI 工作流在此之上还有两类额外的不确定来源：**模型版本漂移**（同一名称的模型，服务方可能在后台更新权重）与**外部工具调用的非确定性**（检索结果变化、第三方 API 返回变化）。对应的控制手段是记录模型快照标识（如具体的模型版本号或权重哈希）、固定解码参数，以及保存每次外部调用的原始响应。

### 8.14.2 环境锁

R 侧用 renv（rstudio/renv）：`renv::init()` 建立项目级库，`renv::snapshot()` 生成 `renv.lock`，`renv::restore()` 在新机器上重建完全相同的包版本。Python 侧用 conda-lock（conda/conda-lock）从 `environment.yml` 生成跨平台锁文件，或用 Docker 固化整个系统层。

```bash
# R：项目级依赖锁
renv::init()      # 在 R 控制台中执行
renv::snapshot()  # 生成 renv.lock
renv::restore()   # 在另一台机器上重建

# Python：跨平台锁文件
conda-lock lock -f environment.yml -p linux-64 -p osx-arm64
conda create -n repro --file conda-linux-64.lock

# 容器化：把整个环境固化
docker build -t statproj:2026.01 .
docker run --rm -v "$PWD":/work -w /work statproj:2026.01 Rscript analysis.R
```

容器的优势是连系统库（如 GDAL、CUDA 运行时）一起锁定；代价是镜像体积与构建时间。对多数统计项目，"锁文件加持续集成"已足够，容器用于需要长期归档或跨平台交付的场景。

### 8.14.3 数据版本与哈希

数据版本控制用 DVC（iterative/dvc）：大文件不进 Git，而是生成一个记录内容哈希的小指针文件进 Git，实际数据存在本地缓存或对象存储中。

```bash
dvc init
dvc add data/patient_data.csv          # 生成 data/patient_data.csv.dvc
git add data/patient_data.csv.dvc && git commit -m "add raw data v1"
dvc push                                # 数据推到远端存储
# 在另一台机器上
git pull && dvc pull                    # 按哈希取回完全相同的文件
```

即便不用 DVC，也可以在分析脚本开头计算并记录输入数据的哈希，用于事后核对：

```python
import hashlib, json
def sha256(path, chunk=1 << 20):
    h = hashlib.sha256()
    with open(path, "rb") as f:
        for b in iter(lambda: f.read(chunk), b""):
            h.update(b)
    return h.hexdigest()

manifest = {"data": {"patient_data.csv": sha256("data/patient_data.csv")},
            "seed": 20260101, "model": "claude-sonnet-4-5@2026-01-01"}
json.dump(manifest, open("run_manifest.json", "w"), indent=2)
```

这份清单与结果文件一起归档，可在数月后回答"这个数字是由哪一份数据产生的"。

### 8.14.4 管道与缓存

分析步骤之间的依赖关系应被显式声明，而不是靠"先跑 A 再跑 B"的人工记忆。R 侧推荐 targets（ropensci/targets），它以对象为单位缓存结果，只重算发生变化的下游；Python 侧可用 Snakemake 或简单的 Makefile。

```r
# _targets.R ， 声明式管道
library(targets)
list(
  tar_target(raw, readr::read_csv("data/patient_data.csv"), format = "file"),
  tar_target(clean, clean_fn(raw)),
  tar_target(fit, lm(sbp_followup ~ treatment_group + age + bmi, data = clean)),
  tar_target(table, broom::tidy(fit, conf.int = TRUE)),
  tar_target(report, quarto::quarto_render("report.qmd"), format = "file")
)
# 运行：targets::tar_make()   查看：targets::tar_visnetwork()
```

管道的价值在长期项目中才充分显现：一年后回到项目时，`tar_outdated()` 会告诉使用者哪些结果需要重算，而不是让使用者凭记忆猜测。

### 8.14.6 工作流模板：论文复现

复现他人论文是统计训练的重要环节，也是智能体最能发挥作用的场景之一，因为任务边界清晰（复现 Table 2 的所有统计量），且**验证标准是现成的**（论文已发表的数字）。

```text
找到目标论文（含原始数据）
  -> 启动 claude，给出指令：
     "帮我复现这篇论文 Table 2 的所有统计结果，数据在 data/ 目录，论文 PDF 在 paper.pdf"
  -> 智能体自动完成：
     读 PDF 提取论文报告的统计量
       -> 读原始数据重跑分析
       -> 逐项对比差异
       -> 生成复现报告（含差异清单与可能原因）
  -> 研究者核对差异项，判断是数据版本差异、方法描述不全，还是论文本身有误
  -> 参考教程：academy.claude.com 中关于"从原始数据验证统计结果"的方法（原稿汇总）
```

复现报告应当包含一张逐项对照表：指标、论文值、复现值、绝对差、相对差、是否在容差内。经验上，完全复现（差异在四舍五入范围内）的比例并不高，常见原因包括：论文未说明缺失值处理方式、未说明检验的具体变体（是否 Welch 校正）、使用了未公开的加权或过滤规则。复现失败本身是有价值的研究结果，应当如实记录而不是调参凑数，用调参逼近已发表数字的做法，本质上是在拟合噪声。

## 8.15 R语言大模型应用：统计学家的工作流集成

### 8.15.1 R 在大模型生态中的三层定位

一个需要先纠正的误区是："大模型用 Python 实现"并不等于"统计学家必须切换到 Python"。模型训练确实以 Python 生态为主，但统计研究者的工作重心在**调用层**与**统计分析层**，这两层 R 完全胜任，且在后者上更强。三层的定位如下。

| 层次 | 可行性 | R 工具 | 结论 |
|------|--------|--------|------|
| 用 R **训练**大模型 | 受限 | torch for R | 不推荐，生态与分布式支持弱 |
| 用 R **调用**大模型 | 成熟 | ellmer、llm.api | 本章重点 |
| 用 R 做**统计分析加 AI 辅助** | 最强 | tidyverse 加 ellmer 加 Quarto | 本章重点 |

判断标准应当是"我的产出在哪里"。如果产出是一篇包含回归表、森林图与稳健性检验的论文，那么分析、图形与报告都在 R 中完成，只有"调用模型"这一个环节需要跨语言，而跨越这一环节的成本是三行 `reticulate::import()` 或一次 `ellmer::chat_claude()`。为了一个调用环节而把整个分析栈迁移到 Python，是把工具关系弄反了。

### 8.15.2 ellmer：tidyverse 风格的大模型客户端

ellmer（github.com/tidyverse/ellmer）由 Hadley Wickham 领衔开发，2025 年发布，设计哲学与 dplyr、ggplot2 一脉相承：函数命名一致、返回对象可组合、结构化输出直接映射为 R 的数据结构。它支持 Claude、GPT、Gemini 以及 Ollama 本地模型。

```r
library(ellmer)

## 最小可用：五行起步
chat <- chat_claude(                       # 或 chat_openai() / chat_gemini() / chat_ollama(model = "qwen2.5")
  system_prompt = "你是统计分析助手。只依据我提供的数据作答，不编造数值。",
  model = "claude-sonnet-4-5"
)
resp <- chat$chat("下面这份回归结果该怎么解释？")
cat(resp)

## 结构化输出：直接返回 list / data.frame（早期版本写作 chat_json()）
type_interp <- type_object(
  conclusion       = type_string("一句话结论"),
  direction        = type_string("效应方向：positive 或 negative"),
  caveats          = type_array(type_string(), "至少两条局限性")
)
out <- chat$chat_structured("解释以下回归结果：" , type = type_interp)
str(out)
```

结构化输出是 ellmer 对统计工作流最实用的一点：模型的回答不再是文本，而是可以直接进入 `dplyr` 管道、写入表格、渲染进 Quarto 报告的对象。结合 8.9 的契约思想，还可以在类型定义中加入数值字段，让模型报告的估计值与脚本算出的值自动比对。

提示词模板化方面，社区有 tidyprompt 一类封装包，把系统提示、少样本示例与输出格式组织为可复用的对象；面向特定统计模型的领域包（如客户生命周期价值建模的 btyd）与 ellmer 组合后，可以形成"领域模型拟合、大模型解释"的闭环。这类封装的通用性不及 ellmer 本身，选用前应先确认其与当前 ellmer 版本的兼容状态。

### 8.15.3 reticulate：桥接 Python 深度学习生态

reticulate（github.com/rstudio/reticulate）在同一 R 会话中嵌入 Python 解释器，对象可双向转换，data.frame 与 pandas DataFrame、numpy 数组与 R 矩阵之间自动映射。

```r
library(reticulate)
use_condaenv("statproj", required = TRUE)      # 显式指定环境，避免用错解释器

## 直接调用 HuggingFace 生态
transformers <- import("transformers")
pipe <- transformers$pipeline("sentiment-analysis")
res <- pipe(c("the trial was stopped early", "no significant difference"))

## 嵌入模型：R 侧拿到的是矩阵，可直接进下游统计
st <- import("sentence_transformers")
model <- st$SentenceTransformer("all-MiniLM-L6-v2")
emb <- model$encode(c("FDR control", "multiple testing", "penguins"))   # 返回 numpy 数组
emb_r <- as.matrix(emb)                        # 转成 R 矩阵
```

典型分工是：**R 管数据与统计，Python 管模型训练与推理，结果自动转回 data.frame**。这一模式与 8.9 的"生成—执行—验证"闭环形成呼应，验证环节留在 R 中，因为最终的统计推断要在 R 中做。

### 8.15.4 torch for R：R 原生的深度学习绑定

torch for R（github.com/mlverse/torch）不是 Python 包装，而是直接绑定 PyTorch 的 C++ 后端（LibTorch），因此在 R 中定义的张量运算与自定义模块运行在原生实现上，不需要 Python 运行时。

适用场景包括两类统计研究：一是在 R 内实现自定义神经网络结构（例如把深度网络嵌入混合效应模型、用神经网络参数化条件密度），二是用神经网络加速计算（如用神经后验估计辅助贝叶斯推断、用神经网络做 MCMC 的预条件化）。这类方法与第 16 章"统计计算加速"直接相关，本章不作展开。

需要明确的是边界：torch for R 适合**研究与原型**，不适合大规模预训练，分布式训练、混合精度、算子覆盖度方面 Python 生态更完整。用 R 训练超大模型是把工具用在它不擅长的方向上。

### 8.15.5 五个可落地的案例

以下五个案例按上手难度递增排列，全部给出可直接运行的骨架。

#### 案例一：回归结果的 AI 自动解释

最容易上手、也是日常使用频率最高的场景。流程是：`lm()` 建模 → `broom::tidy()` 整理系数表 → ellmer 调用模型生成解读 → 自动检查数值表述的准确性。

```r
library(dplyr); library(broom); library(ellmer); library(palmerpenguins)

## 1. 建模并整理为 tidy 表
fit <- lm(body_mass_g ~ bill_length_mm + species, data = penguins)
tbl <- tidy(fit, conf.int = TRUE)

## 2. 把真实数值交给模型，要求它只依据这些数值作答
prompt <- paste0(
  "以下是回归系数表，请解释结果。只能使用表中出现的数值，不得引入其他数字。\n",
  paste(knitr::kable(tbl, format = "markdown"), collapse = "\n"),
  "\n请给出：结论、效应方向、至少两条局限性。\n"
)
chat <- chat_claude(system_prompt = "你是统计写作助手，回答简洁、不做因果断言。")
text <- chat$chat(prompt)

## 3. 自动检查：模型文本中出现的数值必须能在系数表中找到（容差 1e-3）
check_numbers <- function(text, tbl) {
  nums <- as.numeric(regmatches(text, gregexpr("-?\\d+\\.?\\d*", text))[[1]])
  ref  <- c(tbl$estimate, tbl$std.error, tbl$statistic, tbl$conf.low, tbl$conf.high)
  bad  <- nums[!sapply(nums, function(x) any(abs(x - ref) < 1e-3))]
  if (length(bad) == 0) "通过：所有数值均可溯源" else paste("可疑数值：", paste(bad, collapse = ", "))
}
check_numbers(text, tbl)
```

这个检查函数是 8.9 所述验证器的一个具体实例：它不能判断解释是否恰当，但能拦截"模型编造了一个系数值"这类硬错误。价值在于把"R 统计加 AI 解释"的最小闭环压到一小时内可复现。

### 8.15.8 R 与 Python 的结果互核：以聚类稳健标准误为例

8.10.3 曾说明 Python 与 R 两套骨架刻意保持结构一致，目的是让跨语言核对变得机械；8.9.3 的"独立复算"在本节得到它的最强形式，两条实现路径不仅算法不同，连软件栈都不同，两个实现共享同一处 bug 的概率随之大幅下降。本节给一个完整的最小示例：同一个回归的三种标准误口径，以及 R 侧的对应命令。这个例子同时演示 8.9.8 所列"统计方法误用"的一种定量诊断：把异方差稳健标准误误当聚类稳健标准误使用时，后果有多大。

数据按典型的研究场景构造：40 个聚类（如学校、村庄、临床试验中心），每个聚类 25 个观测，误差项含聚类层面的随机效应，协变量在聚类层面取值（如 cluster 级干预）：

```python
# se_compare.py ， 聚类结构被忽略时三种标准误的差异（statsmodels）
# 实测环境：Python 3.10.20，numpy 1.26.4，statsmodels 0.15.0
import numpy as np
import pandas as pd
import statsmodels.formula.api as smf

rng = np.random.default_rng(20260101)
G, m = 40, 25                       # 40 个聚类，每个聚类 25 个观测，n = 1000
cid = np.repeat(np.arange(G), m)
u = rng.normal(0, 1.0, G)[cid]      # 聚类层面随机效应：组内相关的来源
x = rng.normal(0, 1, G)[cid]        # 协变量在聚类层面取值（如 cluster 级干预）
y = 1.0 + 0.3 * x + u + rng.normal(0, 1, G * m)
dat = pd.DataFrame({"y": y, "x": x, "cid": cid})

fit0 = smf.ols("y ~ x", dat).fit()
fit1 = smf.ols("y ~ x", dat).fit(cov_type="HC1")
fitc = smf.ols("y ~ x", dat).fit(cov_type="cluster", cov_kwds={"groups": dat["cid"]})

print("coef(x)       =", round(fit0.params["x"], 4))
print("SE 经典       =", round(fit0.bse["x"], 4))
print("SE HC1        =", round(fit1.bse["x"], 4))
print("SE cluster    =", round(fitc.bse["x"], 4))
print("SE比值 cluster/经典 =", round(fitc.bse["x"] / fit0.bse["x"], 2))
print("p 经典        =", fit0.pvalues["x"])
print("p 聚类        =", fitc.pvalues["x"])

# 系数第二条路径核对：正规方程
Xm = np.c_[np.ones(len(dat)), dat["x"].to_numpy()]
beta = np.linalg.lstsq(Xm, dat["y"].to_numpy(), rcond=None)[0]
print("coef lstsq    =", round(beta[1], 4))

# 组内相关诊断：单因素随机效应模型的方差分量矩估计
gmean = dat.groupby("cid")["y"].mean()
grand = dat["y"].mean()
ssw = ((dat["y"] - dat["cid"].map(gmean)) ** 2).sum()
ssb = m * ((gmean - grand) ** 2).sum()
msw = ssw / (G * (m - 1))
msb = ssb / (G - 1)
icc = (msb - msw) / (msb + (m - 1) * msw)
print("ICC 矩估计    =", round(icc, 3))

dat.to_csv("cluster_data.csv", index=False)   # 供 R 侧互核使用
```

实测输出：

```text
coef(x)       = 0.4384
SE 经典       = 0.0516
SE HC1        = 0.0466
SE cluster    = 0.1557
SE比值 cluster/经典 = 3.02
p 经典        = 6.962460328652604e-17
p 聚类        = 0.004885074724560043
coef lstsq    = 0.4384
ICC 矩估计    = 0.57
```

这份输出里有三组信息。其一，系数的两条实现路径一致（0.4384），8.9.3 的独立复算通过。其二，HC1 口径的标准误（0.0466）比经典口径（0.0516）还小，异方差稳健修正在此例中并未放大标准误，这说明"稳健"不是"更保守"的同义词，把 `cov_type="HC1"` 当作对聚类结构的保险是一种误解；真正的聚类口径给出 0.1557，约为经典口径的 3 倍，p 值从 $10^{-17}$ 量级回到 0.005。若研究者默认接受了 AI 生成的 `HC1` 设定，结论的精度将被高估约 3 倍。量级上，残差的组内相关为 $\sigma_u^2/(\sigma_u^2+\sigma_e^2) = 0.5$（由构造已知），设计效应公式 $1 + (m-1)\rho$ 给出 $\sqrt{13} \approx 3.6$，与实测比值同一量级；精确倍数还取决于协变量变异的位置与聚类数有限带来的估计噪声，不必苛求两者相等。其三，组内相关系数（intraclass correlation coefficient, ICC）的矩估计为 0.57，完全从数据本身算出，也就是说"这份数据存在组内相关、必须考虑聚类口径"这一判断，在人工评审之前就可以机械化完成，它属于 8.9.3 闸门图中第 3 关的检查项。

R 侧的互核命令如下（笔者本机未运行 R，命令依据 sandwich 与 lmtest 的公开文档给出，包的当前用法以官方文档为准）：

```r
# R 侧互核命令：与 Python 侧共享同一份 cluster_data.csv
library(sandwich); library(lmtest)
dat <- read.csv("cluster_data.csv")
fit <- lm(y ~ x, data = dat)
coef(fit)                                                    # 系数应与 Python 侧完全一致
coeftest(fit, vcov = vcovCL(fit, cluster = ~cid, type = "HC1"))
```

互核时的容差设定需要区分两个层面。系数层面，两侧解的是同一个 OLS 问题，结果应一致到机器精度，`allclose` 级别的断言是恰当的。标准误层面则要谨慎：statsmodels 的 cluster 口径与 `sandwich::vcovCL` 都包含有限样本校正，但两侧的默认校正约定不完全相同，标准误可能在小数点后若干位出现差异；若差异更大，第一步是回到两侧文档核对校正项的构造，而不是断言哪一侧有错。这个例子也说明了互核的适用边界：它验证的是**实现**是否一致，不能裁决哪一种方差口径在统计上更合适，后者是闸门 5 的判断，取决于研究设计（本例中协变量在聚类层面取值，聚类口径是恰当的）。

## 本章小结

1. AI 编程智能体与对话框问答的本质差别不在模型能力，而在它能否访问文件系统、执行代码并把真实输出作为下一轮输入；按形态可分为终端智能体、IDE 智能体与桌面/GUI 智能体三类，前两类在代码场景中的可靠性明显高于第三类。
2. 六款主流工具的分工清晰：Claude Code 与 Aider 面向终端（前者功能完整需订阅，后者完全开源可离线），GitHub Copilot、Cursor、Windsurf 面向 IDE（补全、多文件编辑、持久化记忆各有侧重），Gemini CLI 以免费额度与长上下文取胜；统计研究者应优先考察执行反馈、长上下文、可审计性与扩展能力四项。
3. 代码是"可验证的中间表示"：把模型的输出从答案文本改为可执行脚本，误差来源即从数值记忆转移到程序构造，后者可被返回码检查、契约校验与独立复算捕获；这一原则与第 13 章的"评估器即验证器"同源。
4. 数据分析自动化应沿"读取—清洗—探索—建模—诊断—报告"六阶段划分，智能体承担可用断言检验的部分，研究者保留需要学科判断的部分；案例显示"按正态性检验结果选择后续检验"这类数据依赖的流程会破坏名义显著性水平，检验方案应当事先固定。
5. 文献知识库的关键是引用溯源而非生成流畅度：页码级出处、DOI 机械校验与抽样人工核验（用 Wilson 区间而非"零错误"表述）三层防御缺一不可。
6. AI 配置实验应当使用实验设计而非单因子轮换，并在实验前完成功效分析；对同一输入多次解码属于伪重复，需用聚类稳健方差或混合效应模型处理，标准误不可按独立样本计算。
7. 可复现需要同时锁定代码版本、环境指纹与数据版本，并额外控制模型版本漂移与外部调用的非确定性；renv/conda-lock、DVC、targets 管道与 Quarto 的 `freeze` 机制共同构成研究者层面的最小方案，第 17 章把它提升为基础设施。
8. R 在大模型生态中的优势位于调用层与统计分析层：ellmer 提供 tidyverse 风格的结构化输出，reticulate 桥接 Python 训练生态，torch for R 适合原型而非大规模训练；"大模型用 Python 实现"不构成统计学家迁移分析栈的理由。
