# 第10章 形式化验证与证明助手

> **本章定位**：本章位于全书"怎么研究 AI"主线的底层。形式化验证为 AI 生成的数学内容提供了一套机器可判定的正确性标准，是后续"AI for math"各章（自动猜想、机器证明、AI 参与的研究工作流）的共同基础。  
> **关键词**：Curry–Howard 同构、Lean 4、Mathlib4、miniF2F、LeanDojo、自动形式化、可信计算基。

## 本章导读

统计学者面对"AI 做数学"的种种报道时，最先遇到的是一个判据问题：机器给出的证明，凭什么相信？自然语言处理领域的模型会生成流畅却错误的推导，这类错误无法用常规手段逐条排查。形式化验证给出的答案与"让模型更可信"无关，而是把判断权从人转移给一段可审计的机器代码：把命题与证明翻译成一种形式语言，由证明助手的内核做类型检查，通过即接受，不通过即拒绝。

本章沿三条线索展开。第一条是原理：命题即类型（Curry–Howard 同构）、证明即程序、类型检查即验证，以及由此引出的可信计算基概念；同时我们试着讲清"通过编译即零幻觉"这句话的严格边界，内核只保证证明与陈述一致，不保证陈述忠实于研究者的意图。第二条是工具：Lean 4 的语言特性与工程结构、Coq/Rocq、Isabelle/HOL、Metamath、HOL Light 几条技术路线的对比、Mathlib4 的规模与检索方式、miniF2F 与 LeanDojo 这两个被反复使用的基础设施。第三条是从业者的实际路径：自动形式化的困难与判定方法、从零搭建环境到写出第一条证明的命令流程，以及当前真实存在的失败模式与瓶颈。

对统计学者而言，本章最想留下的是两个判断。其一，形式化证明保证的是"在给定的定义与假设下结论成立"，定义写错则结论无意义，这与统计学中模型设定错误的处境高度相似。其二，在端到端流程中，形式化环节（而非证明环节）才是当前的主要瓶颈。这两个判断在我们的实践中反复被验证，也反复被我们自己违反，本书写作过程中，我们仍然犯过"看见编译通过就以为事情做完了"的错误。

本章 10.8 节是全书中操作性最强的一节，按安装、写第一条证明、读报错、检索定理、避坑、分周路线、交付前自检的顺序排列；其后 10.8.11 给出四类任务的提示词模板与参数选择，10.8.12 是一次从陈述到公理检查的完整走查，10.8.13 是一份第一人称的练习记录。如果只打算读一节，我们倾向于读 10.8。

## 10.1 形式化验证的思想：命题即类型

### 10.1.1 从类型论到 Curry–Howard 同构

形式化验证的底层不是逻辑学教材里的公理系统，而是类型论。在类型论中，每个表达式都有类型，写作 $\Gamma \vdash e : T$，其中 $\Gamma$ 是上下文（变量的类型假设）。类型论最初的用途是给程序语言提供类型系统，但人们发现：如果把"命题"看作一种特殊的类型，把"证明"看作该类型的元素，那么逻辑推理规则与类型构造规则之间存在着严格的对应关系。这一观察被称为 Curry–Howard 同构（Curry–Howard isomorphism），也称"命题即类型"（propositions as types）、"证明即程序"（proofs as programs）。

对应关系的具体内容如下：

| 逻辑侧                               | 类型侧                                             |
| --------------------------------- | ----------------------------------------------- |
| 命题 $P$                            | 类型 $P$（在 Lean 中属于 `Prop` 宇宙）                    |
| $P$ 的证明 $p$                       | 项 $p$ 满足 $p : P$                                |
| 蕴含 $P \Rightarrow Q$              | 函数类型 $P \to Q$                                  |
| 合取 $P \land Q$                    | 积类型 $P \times Q$                                |
| 析取 $P \lor Q$                     | 和类型 $P + Q$                                     |
| 全称量化 $\forall x : \alpha,\, P(x)$ | 依赖函数类型（$\Pi$ 类型）$(x : \alpha) \to P(x)$         |
| 存在量化 $\exists x : \alpha,\, P(x)$ | 依赖对类型（$\Sigma$ 类型）$\Sigma\, x : \alpha,\, P(x)$ |
| 真 / 假                             | 单元类型 / 空类型                                      |

这张表不是类比，而是同一套数学对象的两种读法。证明 $P \Rightarrow Q$ 就是一个把 $P$ 的证明映射为 $Q$ 的证明的函数；证明 $\forall x, P(x)$ 就是一个对任意输入 $x$ 都返回 $P(x)$ 的证明的函数。构造一个证明，等价于写一个程序。

我们第一次读到这行对照表时，卡住的地方是"假对应空类型"：为什么说不出一个元素就代表命题为假？后来想通的路径是，若 $P$ 对应空类型，那么 $P \to Q$（即"假蕴含一切"）对应从空类型出发的函数，而这样的函数确实存在且唯一（没有输入需要考虑）。逻辑里的爆炸原理在这里不是一条公理，而是一个关于空类型的平凡事实。这种"逻辑规则变成了类型构造的性质"的体验，在后续阅读中会反复出现。

在依赖类型论中，类型可以依赖于项，这是表达数学命题的关键。例如"长度为 $n$ 的向量"这一概念中，类型依赖于值 $n$；"$\forall n : \mathbb{N},\, n + 0 = n$"中，$n + 0 = n$ 这个命题本身依赖于 $n$。Lean 4 的类型论（与 Coq 同属归纳构造演算 CIC 一脉）正是建立在这种依赖结构之上，并额外引入商类型（quotient）与经典选择公理，以支撑日常数学中的非构造性论证。

### 10.1.2 证明即程序：一个具体例子

下面这段 Lean 代码同时以两种风格证明同一个命题，可以直观看到"证明项"是什么。

```lean
-- 项风格（term style）：直接写出证明项，它就是某个 λ 表达式
theorem and_comm_term (P Q : Prop) : P ∧ Q → Q ∧ P :=
  fun h => ⟨h.2, h.1⟩

-- tactic 风格：用指令逐步构造同一个证明项，内核最终看到的是同样的项
theorem and_comm_tactic (P Q : Prop) : P ∧ Q → Q ∧ P := by
  intro h
  exact ⟨h.2, h.1⟩

-- 打印内核实际接受的证明项
#print and_comm_tactic
```

`fun h => ⟨h.2, h.1⟩` 是一个函数，输入一个 $P \land Q$ 的证明（即一对证明），输出一个 $Q \land P$ 的证明。tactic 模式只是生成这一项的一套交互命令，不改变证明的本质。这一区别对理解后续的自动化证明很重要：无论 tactic 多么复杂、无论 tactic 由人还是由模型生成，最终提交给内核的都是一个普通的项。

我们曾把 `#print and_comm_tactic` 的输出逐字读过一遍，想看看 tactic 究竟生成了什么。它打印出的项与项风格写法在核外表示上并不完全一致（tactic 会插入一些繁饰期产生的中间结构），但类型是同一个。这次阅读带来的收获是：不必害怕 tactic 的黑箱，因为它交出去的东西是可以打印出来检查的。

归纳类型的引入进一步把"归纳法"变成"递归定义"。自然数在 Lean 中由 `Nat.zero` 与 `Nat.succ` 两个构造子生成，证明 $\forall n,\, n + 0 = n$ 就是对 $n$ 做结构化递归，$n = 0$ 时由定义直接成立，$n+1$ 时调用归纳假设。这种结构与统计学中按样本量归纳、按树深度归纳的证明思路一致，只是每一步都必须被机器确认。

### 10.1.3 类型检查即验证：内核与可信计算基

一个证明助手的完整实现包含词法分析、语法分析、繁饰器（elaborator）、tactic 引擎、自动化模块、IDE 服务等多个部分，代码量可达数十万行。其中绝大多数部分并不参与"正确性保证"。真正承担这一职责的是一个体量小得多的组件：内核（kernel）。内核只做一件事，检查一个项是否具有所声称的类型。

从源码到内核判定，中间经过的环节可以画成下面这条链：

```text
源文件 Main.lean（文本）
        │
        ▼
┌──────────────────────┐
│ 1. 解析 (parser)      │  文本 ──► Syntax 语法树；只管结构，不管含义
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 2. 繁饰 (elaborator)  │  补隐式参数、解类型类、展开宏与记号、
│                       │  执行 tactic 脚本；产物是一个确定的项 Expr
└──────────┬───────────┘
           ▼
┌──────────────────────┐
│ 3. 内核类型检查       │  判定  Environment ⊢ Expr : 声称的类型 ？
│    (kernel)           │  只做这一件事，代码量远小于上面两层
└──────────┬───────────┘
       ┌───┴────┐
       ▼        ▼
     通过     拒绝
       │        │
       ▼        ▼
  写入环境    报错回传（unsolved goals / type mismatch / ...）
  Environment  ── tactic 与 LLM 都只读到这一层
```

这条链上每一层的职责与可信程度并不相同：

| 环节            | 主要职责             | 出错会怎样               | 是否在可信计算基内   |
| ------------- | ---------------- | ------------------- | ----------- |
| 解析器           | 文本到语法树           | 语法错误，编译中止           | 否（错误只会导致拒绝） |
| 繁饰器           | 补全隐式信息、执行 tactic | 产生错误的项 → 被内核拒绝      | 否           |
| tactic 引擎与自动化 | 搜索、简化、算术         | 生成无效 tactic → 目标未闭合 | 否           |
| 语言模型 / 检索器    | 建议 tactic 与定理名   | 建议错 → 编译失败          | 否           |
| 内核            | 检查项的类型           | 内核自身的 bug 会让错误定理通过  | 是           |
| 显式引入的公理       | 提供不可证的出发点        | 用错公理 = 证明了另一个命题     | 是           |

这一设计原则有两个历史来源。其一是 de Bruijn 准则（de Bruijn criterion）：证明系统的正确性应当可以由一个独立的、小型的检查程序复核。其二是 LCF 传统（以 Edinburgh LCF 命名，HOL Light、Isabelle/HOL 均属此系）：定理被封装为一个抽象数据类型，只有内核中的少量函数能够构造该类型的值，因此系统外的任何代码都无法伪造定理。Lean 4 采用了 de Bruijn 式的独立内核路线，内核只接受已繁饰完成的项，繁饰器本身产生的错误只会让内核拒绝，而不会让内核接受一个错误定理。

由此引出可信计算基（trusted computing base, TCB）的概念：要相信一条被机器接受的定理，必须信任的东西的集合。对 Lean 4 而言，TCB 包括：

- 内核的类型检查算法（及其所在运行时的正确性）；
- 系统中显式引入的公理。在 `import Mathlib` 之后，`#print axioms` 的典型输出为 `propext`（命题外延性）、`Classical.choice`（选择公理）、`Quot.sound`（商类型的可靠性）；
- 用户自己额外声明的 `axiom` 或用 `sorry` 占位的未完成证明（`sorry` 会引入公理 `sorryAx`）。

TCB 不包括 tactic、简化器、检索工具、LLM。这些组件可以任意出错，只要它们产出的项通不过类型检查，内核就会拒绝。这正是"自动化不会引入不可靠性"的技术根据。

需要明确的是，TCB 不是空集。内核自身的正确性无法在本系统内自证；实践中靠三条支撑：内核代码量小因而可人工审计、存在独立实现的复核器、以及元理论层面的相对一致性研究（例如对 Lean 3 类型论与 ZFC 关系的研究）。这与统计学中对估计量性质的处理有相似之处：一致性定理的成立依赖于一组无法在该定理内部验证的正则条件，人们接受它，是因为条件明确且可逐条检查。

### 10.1.4 "通过编译即零幻觉"的严格含义

"通过编译即零幻觉"是一句流传很广的概括。它的严格含义应当拆解为三条：

第一，**不存在幻觉的引用**。模型可以凭空写出一个不存在的定理名 `measure_theory.concentration_bound`，但内核会在环境中查找该常量，找不到就报错。形式化系统中的所有引用都必须是环境中真实存在的常量。这消灭了自然语言生成中最常见的一类错误。

第二，**不存在跳步**。自然语言证明中的"显然""同理可证""经过简单计算"在形式系统中没有对应物，每一个推理步骤都必须落到某条已有定理或某个计算规则上。因此形式化证明的长度通常远超自然语言证明，这不是冗余，而是被显式化的隐含内容。

第三，**不存在事后篡改**。已编译的定理以二进制形式缓存，其正确性只依赖内核，与生成它的人或模型无关。任何人重新编译同一份源码会得到同样的判定。

但这三条都不触及一个问题：**被证明的命题，是不是研究者想证的那个命题**。内核回答的是"这份证明项的类型是否为这个陈述"，它不理解陈述与外部世界中"大数定律""相合性"这些概念的对应关系。形式化系统的这一边界，与统计学中模型设定错误（misspecification）的处境几乎同构。

### 10.1.5 与统计学模型假设的类比：定义写错则结论无意义

统计学中的定理通常形如"在假设 $H_1, \dots, H_k$ 下，估计量 $\hat\theta_n$ 具有性质 $C$"。定理的价值取决于三件事：假设是否可检验、定义是否与研究对象的实际结构匹配、结论是否回答了原本的问题。形式化验证只锁死了第二件与第三件之间的推理链条，对第一件与"定义是否匹配"完全无能为力。

对统计学者来说，这一边界有若干具体表现。

其一，收敛模式的选择。$\hat\theta_n \xrightarrow{p} \theta$（依概率收敛）、$\hat\theta_n \xrightarrow{a.s.} \theta$（几乎处处收敛）、$\hat\theta_n \xrightarrow{d} \theta$（依分布收敛）三者互不蕴含（除特殊情形外）。形式化时若把"依概率收敛"写成"几乎处处收敛"，得到的是一个更强的命题；若反过来写成更弱的命题，则更容易通过编译，但结论已不再回答原问题。机器不会指出这一点。

其二，量化顺序与范围。渐近陈述中的 $\forall \varepsilon > 0,\, \exists N,\, \forall n \ge N$ 与 $\exists N,\, \forall \varepsilon > 0,\, \forall n \ge N$ 意义完全不同，但两者都是合法的类型论命题，且后者往往更容易被证明。下面是一个演示：

```lean
import Mathlib

-- 想表达的界：对任意 t ≥ 1 都有 C / t^2 ≤ C
-- 写错版本：只要求"存在某个 t"使界成立。它完全合法、可编译、可证明，
-- 但证明的是一个弱得多的命题，与原本的尾部概率界无关。
theorem tail_bound_wrong (C : ℝ) : ∃ t : ℝ, 0 < t ∧ C / t ^ 2 ≤ C := by
  refine ⟨1, by norm_num, ?_⟩
  simpa using le_rfl
```

其三，可测性、可积性与拓扑条件。条件期望、Radon–Nikodym 导数、投影算子都带有可积性前提；在 Mathlib 中，条件期望记号 $\mu[f \mid m]$ 对被积函数不可积的情形按约定取 $0$。这意味着：如果形式化时漏写了可积性条件，命题依然成立，但语义已经不是教科书里那个条件期望。类似地，"$\sup_{\theta \in \Theta}$"写成"$\exists \theta \in \Theta$"、"相互独立"写成"两两独立"，都会得到可编译但与意图不同的命题。

其四，定义选择的非唯一性。方差既可定义为 $\mathbb{E}[(X - \mathbb{E}X)^2]$，也可视为二阶中心矩；在可积性不足时两者不相等。经验过程理论中覆盖数与度量熵的定义方式、次高斯范数的等价定义，都存在多个合法版本。形式化迫使人选定一个，这个选择本身具有实质后果。

形式化对统计学者的价值，恰恰体现在对这些隐含内容的暴露上。已有的统计学习理论形式化工作报告：形式化过程暴露了标准教材中省略掉的可测性、可积性与拓扑条件；由于系统要求每一步精确，作者采用"递归投影"得到的 Dudley 积分常数比文献中"直接投影"版本的常数更紧。这类副产品比"机器替人证明"更有价值，它把审稿人口中的"此处应补充正则条件"变成了编译器的硬性要求。

因此本章的立场可以概括为一句：形式化验证外包的**验证**（证明是否有效），留在研究者这一侧的是**陈述**（命题是否忠实）。在我们看来这一步无法外包。判断权的转移不是全部转移，而是分工。

### 10.1.6 一个命题从自然语言到 `theorem ... := by` 的拆解演示

把一句自然语言命题写成 Lean 陈述，中间要经过六次明确的选择。下面用一个最普通的代数命题演示这条路径，再给出一个统计命题的骨架。

```text
自然语言命题
"对任意实数 a、b，都有 (a + b)^2 ≤ 2 (a^2 + b^2)"
        │
        ├─ (1) 论域与变量类型 ──►  a b : ℝ          （不是 ℕ，不是 ℚ）
        │
        ├─ (2) 量词 ───────────►  "对任意" = 全称，写成 theorem 的绑定参数
        │                          若原句是"存在"，则写 ∃ 并给出构造
        │
        ├─ (3) 运算与谓词 ─────►  ^ 2、+、*、≤ 全部落到库中已有定义
        │                          没有对应物时，先自己 def，再写 theorem
        │
        ├─ (4) 隐含前件 ───────►  本例无；统计命题在这一步常要补
        │                          [MeasurableSpace α]、Integrable、0 < t
        │
        ├─ (5) 命名 ──────────►  theorem sq_add_sq：名字描述结论，不写人名
        │
        └─ (6) 选定证明方式 ──►  := by nlinarith [sq_nonneg (a - b)]
                                        │
                                        ▼
                        theorem sq_add_sq (a b : ℝ) :
                            (a + b) ^ 2 ≤ 2 * (a ^ 2 + b ^ 2) := by
                          nlinarith [sq_nonneg (a - b)]
```

第 (2) 步与第 (4) 步是统计命题最容易出错的两处，也是 10.1.5 中那四类偏差的来源。下面是一个统计命题的陈述骨架，我们刻意把证明留空，用来说明"只写陈述"这一步能暴露什么：

```lean
import Mathlib
open MeasureTheory ProbabilityTheory

-- 自然语言命题（示意）：
--   设 X 是概率空间 (Ω, F, P) 上的实值随机变量，EX = m，Var X = v。
--   则对任意 t > 0，P(|X - m| ≥ t) ≤ v / t^2。

-- 陈述骨架：只写类型与前件，证明用 sorry 占位（示意骨架，未证明）
-- 这里刻意不写出具体定理名：v 到底用 variance 还是用积分定义，
-- 取决于本地 Mathlib 中可用的声明，这一步要现场 #check 确认。
theorem chebyshev_statement
    {Ω : Type*} [MeasurableSpace Ω] (P : Measure Ω) [IsProbabilityMeasure P]
    (X : Ω → ℝ) (t : ℝ) (ht : 0 < t) :
    -- 目标：P {ω | t ≤ |X ω - ∫ ω', X ω' ∂P|} ≤ v / t^2
    True := by
  trivial

-- 写这类骨架时，我们通常会先补上这几个前件并逐个 #check：
#check Integrable          -- 可积性：几乎所有积分定理的前提
#check AEStronglyMeasurable -- 可测性（Borel 值函数的常用形式）
#check IsProbabilityMeasure -- 概率测度：μ univ = 1
#check integral            -- Bochner 积分 ∫ x, f x ∂μ
```

上面这段代码刻意把目标写成 `True`，因为我们不想假装已经完成了形式化；真做的时候，`True` 会被换成真正的界，而换的过程中必然要回答"v 怎么定义""|X - m| 上的可测性从哪来""t > 0 与 t ≥ 0 用哪个"这三个问题。我们自己的经验是：这一步花的时间常常超过后面写证明的时间。

### 10.1.7 分层示意图：从内核到 AI 层

10.1.3 画的是单个源文件从文本到内核判定的流水线。把视野放大到整个生态，各组件的分层与信任关系可以画成下面这张图。图中箭头表示"被检查对象"的流向：研究者与各层工具产出的内容，最终都要被送往底部的内核接受类型检查；信任关系则与箭头方向相反，自下而上收敛，越靠近底层的部分越稳定，越靠近顶层的部分越方便、也越容易出错。

```text
┌────────────────────────────────────────────────────────────────┐
│ 研究者：写陈述（意图）与证明脚本（手段）                          │
│ 内核只检查后者是否与前者一致；前者是否忠实于原意，只有这层能判断    │
└───────────────────────────────┬────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────┐
│ AI 层（不在 TCB 内）                                             │
│ LLM、Agent、lean-lsp-mcp、Loogle、LeanSearch、Moogle             │
│ 建议陈述与 tactic；任何错误的表现形式是编译失败，而非错误结论      │
└───────────────────────────────┬────────────────────────────────┘
                                ▼  候选陈述 / 候选 tactic
┌────────────────────────────────────────────────────────────────┐
│ tactic 与自动化层（不在 TCB 内）                                 │
│ simp、linarith、nlinarith、aesop、ring、norm_num、omega 等       │
│ 生成证明项；无效 tactic 的表现形式是目标未闭合                    │
└───────────────────────────────┬────────────────────────────────┘
                                ▼  待类型检查的证明项
┌────────────────────────────────────────────────────────────────┐
│ Mathlib（约 150 万行，社区维护）                                  │
│ 测度论、概率论、分析、代数、拓扑                                  │
│ 不需要"被信任"：每条声明都曾通过内核检查，olean 缓存可随时复核     │
└───────────────────────────────┬────────────────────────────────┘
                                ▼  依赖其定义与定理
┌────────────────────────────────────────────────────────────────┐
│ 标准库与语言核心（Init、Std、lake、elan）                        │
└───────────────────────────────┬────────────────────────────────┘
                                ▼
┌────────────────────────────────────────────────────────────────┐
│ 内核 kernel ＋ 显式公理                       （TCB 主体）        │
│ 只做类型检查；公理典型为 propext、Classical.choice、Quot.sound    │
└────────────────────────────────────────────────────────────────┘
```

对这张图有三点补充。

第一，Mathlib 体量巨大，但它不在 TCB 里，也不需要"被信任"。这与"信任一个大型语言模型"有本质区别：Mathlib 的每一条声明在进入环境之前都通过了内核检查，任何人在本地重新编译都能复核同一判定。我们信任的不是 Mathlib 的作者，而是内核对每一行代码都做了检查这一机制。

第二，AI 层与 tactic 层可以任意出错，代价只是编译失败与时间。这意味着把 AI 接进证明助手，不会削弱系统的可靠性保证，这也是后续各章敢把证明工作大比例交给模型的前提。这个前提的边界同样画在图里：AI 建议的**陈述**如果不忠实，会在图的顶部绕过所有检查直接进入"已证明"状态，这正是 10.7.6 静默失败支路在分层图上的位置。

第三，图中唯一无法自动化兜底的通道是研究者的陈述输入。这与 10.1.4 的结论一致，也与本章开头那句判断呼应：形式化验证外包的是验证，陈述的忠实性留在人这一侧。

## 10.2 Lean 4

### 10.2.1 语言特性

Lean 4 是一个依赖类型的函数式编程语言兼交互式定理证明器，由 Leonardo de Moura 与 Sebastian Ullrich 主导设计，2023 年发布稳定版本，目前由 Lean FRO（Focused Research Organization）与社区共同维护。它之所以成为 AI 与数学结合的主流载体，有三个技术原因：语法现代、元编程能力强（可以方便地写 tactic 与自动化）、以及拥有规模最大的数学库 Mathlib4。

语言层面的要点包括：

- **依赖类型**。类型可以依赖项，使得"长度为 $n$ 的向量""$\mathbb{R}^n$ 上的可测函数"这类概念可以直接在类型层面表达。数学结构（群、拓扑空间、测度空间）通过类型类（type class）组织，例如 `[MeasurableSpace α]` 是一个类型类参数，支撑了 `Measure`、`Integrable` 等定义的复用。
- **宇宙层级**。`Prop : Type : Type 1 : ...`，命题与数据分属不同宇宙。`Prop` 的证明无关性（proof irrelevance）使得同一命题的两个证明在内核看来相等，含有证明成分的数据结构（如"带可积性证明的函数"）在比较时不会因为证明细节不同而产生障碍。
- **tactic 模式**。在 `by` 块中，证明被分解为一系列 tactic，每个 tactic 作用于当前目标（goal）并产生若干子目标。常用的收尾型 tactic 包括 `simp`（按简化规则重写）、`ring`/`ring_nf`（代数恒等式）、`nlinarith`/`linarith`（线性与非线性算术）、`norm_num`（数值计算）、`omega`（Presburger 算术）、`positivity`（正性）、`gcongr`（单调性放缩）、`aesop`/`tauto`/`solve_by_elim`（搜索）。结构化 tactic 包括 `intro`、`obtain`/`rcases`、`constructor`、`calc`、`congr`、`convert`、`refine`、`ext`、`set`。
- **元编程**。Lean 4 提供了完整的元编程栈：`syntax` 定义语法类别，`macro` 做语法宏，`elab` 与 `elab_rules` 做繁饰期扩展，另有 `Lean.Meta`、`Lean.Elab.Tactic` 等 API 用于编写 tactic。用户可以给 `simp` 添加规则（`@[simp]`），也可以实现领域专用的自动化。对统计学者而言，这是实现"针对某一类不等式定制的证明过程"的入口。
- **终止性与结构递归**。所有定义必须通过终止性检查，排除了不一致的循环定义。


对只写过 R 或 Python 的人来说，头几天最不适应的大概是：Lean 没有"运行一遍看看结果"的调试循环，取而代之的是编辑器里实时显示的目标（goal）。我们一开始习惯性地想加 `print`，后来才学会用 `#check`、`#eval` 与 InfoView 面板替代。

`Prop` 与 `Type` 的分离对统计学者还有一层含义，我们花了些时间才体会到。统计学中"数据"与"关于数据的断言"是两类对象：`data.frame` 是数据，`p < 0.05` 是关于数据的命题。Lean 里这两类分别落在 `Type` 与 `Prop`，而且 `Prop` 中的证明不参与计算，删掉一个证明，可计算部分的行为不变，只影响"这条命题是否被承认"。由此得到一个实际后果：可以把"带可积性证明的随机变量"当作普通数据结构传来传去，不必担心两个不同的可积性证明导致两个结构不相等。反过来，如果把本该属于数据的对象误放进 `Prop`（例如把某个依参数变化的构造定义成命题），它携带的信息就无法被计算部分读取，后面会到处碰壁，我们犯过一次这类错误，症状是到处出现"无法从证明中取出数据"的报错。

按用途粗略分一下 tactic，对我们后来的检索与排错帮助较大：

| 类别    | 代表                                                                            | 我们常用的场合           |
| ----- | ----------------------------------------------------------------------------- | ----------------- |
| 计算与化简 | `rfl`、`norm_num`、`simp`、`simp?`                                               | 目标可由定义或数值计算闭合时    |
| 代数与算术 | `ring`、`ring_nf`、`linarith`、`nlinarith`、`positivity`、`gcongr`                 | 实数与有序环上的恒等式与不等式   |
| 结构化   | `intro`、`rcases`、`obtain`、`constructor`、`refine`、`calc`、`convert`、`ext`       | 拆开量词、合取、存在量词、函数相等 |
| 搜索    | `exact?`、`apply?`、`rw?`、`aesop`、`tauto`、`solve_by_elim`、`omega`               | 不知道用哪条库定理时先问系统    |
| 诊断    | `#check`、`#print`、`#eval`、`#find`、`#synth`、`guard_target`、`set_option pp.all` | 排查类型与实例问题         |

这张表与官方 Tactic Cheatsheet（见延伸资源）是互补的：Cheatsheet 按 tactic 列出语法，这里按"什么时候想起用它"归类。我们的经验是前两类占了日常工作的多半，第三类是卡住时的拆解工具。

### 10.2.2 安装与工程结构

Lean 的工具链由三个组件构成，三者的分工值得先分清：

| 组件     | 角色                      | 常用命令                                                       | 说明                             |
| ------ | ----------------------- | ---------------------------------------------------------- | ------------------------------ |
| `elan` | 版本管理器（类比 Rust 的 rustup） | `elan --version`、`elan toolchain list`、`elan show`         | 按 `lean-toolchain` 文件自动切换编译器版本 |
| `lake` | 包管理器与构建工具               | `lake new`、`lake update`、`lake build`、`lake exe cache get` | 解析依赖、调用编译器、管 olean 缓存          |
| `lean` | 语言核心与内核                 | `lean --version`、`lake env lean Foo.lean`                  | 一般不直接调用，而是经 `lake env` 带上依赖路径  |

`lean-toolchain` 文件把项目锁定到特定编译器版本，`lakefile.lean`（或较新的 `lakefile.toml`）声明库目标与依赖。`lake-manifest.json` 记录依赖解析后的精确 commit，它是可复现性的关键，我们倾向于把它提交进仓库，而不是写进 `.gitignore`。

一个依赖 Mathlib 的最小项目结构如下：

```text
my_proofs/
├── lean-toolchain            # 形如 leanprover/lean4:v4.xx.x
├── lakefile.lean             # 库/可执行目标与依赖声明
├── lake-manifest.json        # 依赖的解析结果（含 mathlib 的 commit）
├── MyProofs/
│   └── Basic.lean            # 源码
├── lake-packages/            # 依赖（Mathlib 等）
└── .lake/                    # 构建产物与 olean 缓存
```

较新的 `lake new` 默认生成 TOML 格式的构建文件，目录形态略有不同（以 `Main.lean` 为可执行入口）：

```text
MyProject/
├── lakefile.toml        # 声明包、库目标、可执行目标与依赖
├── lean-toolchain       # 一行文本：leanprover/lean4:v4.xx.x
├── lake-manifest.json   # 依赖锁定（mathlib 的 git rev 写在这里）
├── Main.lean            # 可执行入口（[[lean_exe]] 的 root）
├── MyProject.lean       # 库聚合入口（可选）
├── MyProject/Basic.lean # 库源码（[[lean_lib]] 之下）
├── .gitignore           # 至少忽略 .lake/
└── .lake/               # 构建产物与 olean 缓存，不入库
```

对应的 `lakefile.toml` 大致是这样（字段名以本地 lake 文档为准，不同版本略有差异）：

```toml
name = "MyProject"
version = "0.1.0"

[[require]]
name = "mathlib"
scope = "leanprover-community"
# rev = "v4.16.0"        # 钉住版本：可复现，代价是不会自动跟上上游
                          # 省略 rev：跟随上游，代价是某天突然编译不过

[[lean_lib]]
name = "MyProject"

[[lean_exe]]
name = "main"
root = "Main"
```

其中 `lake exe cache get` 从社区服务器拉取 Mathlib 的预编译产物（olean 文件）。跳过这一步而直接从源码编译 Mathlib，在普通笔记本上需要数小时。我们第一次建工程时不知道这一步，直接 `lake build` 然后去吃了个饭，回来发现还在编译核心，后来才学会先跑缓存拉取。按我们的经验，这一步不该跳过。

### 10.2.3 最小可运行示例

下面的文件可以整体保存为 `MyProofs/Basic.lean`，用 `lake env lean MyProofs/Basic.lean` 编译。

```lean
import Mathlib

-- 例 1：中心化样本的代数恒等式，ring  tactic 自动完成
theorem mean_centered (x₁ x₂ μ : ℝ) :
    (x₁ + x₂) / 2 - μ = ((x₁ - μ) + (x₂ - μ)) / 2 := by
  ring

-- 例 2：方差被积量的非负性，直接调用库定理 sq_nonneg
example (x μ : ℝ) : 0 ≤ (x - μ) ^ 2 := by
  exact sq_nonneg (x - μ)

-- 例 3：一个涉及绝对值与放缩的小引理
theorem abs_dev_bound (x μ : ℝ) (h : |x - μ| ≤ 1) : (x - μ) ^ 2 ≤ 1 := by
  nlinarith [sq_nonneg (x - μ), abs_nonneg (x - μ),
             sq_le_sq.mpr h]

-- 查询环境中已有常量的类型
#check MeasureTheory.Measure
#check MeasureTheory.Integrable

-- 求值（Lean 也是一门编程语言）
#eval (1 : ℕ) + 1
```

预期输出（节选）：

```text
MeasureTheory.Measure.{u_1} (α : Type u_1) [MeasurableSpace α] : Type u_1
MeasureTheory.Integrable.{_} {α E : Type _} [MeasurableSpace α] [NormedAddCommGroup E]
  [NormedSpace ℝ E] (f : α → E) (μ : Measure α := by volume_tac) : Prop
2
```

`#check` 输出的是常量的完整类型签名，包含类型类参数，初看繁琐，但这正是定位定理所需的信息。`#eval` 的输出说明 Lean 同时是一门可执行的函数式语言。若把 `import Mathlib` 换成 `import Mathlib.Probability`，可以只导入概率论相关部分以加快编译。

用 `example` 做一些只读的类型检查实验，是我们上手阶段使用频率最高的动作：`example` 不往环境里写入任何常量，编译完就丢掉，适合随手试：

```lean
import Mathlib

-- 例 4：一批只读实验，全部只做类型检查，不产生新常量
example : 1 + 1 = 2 := by norm_num                 -- 数值
example (P : Prop) : P → P := by intro h; exact h  -- 蕴含就是函数
example : Type := ℝ                                -- ℝ 是一个类型
example : Prop := (2 : ℝ) ≤ 3                      -- 不等式是一个命题
example {α : Type*} [MeasurableSpace α] : Type := Measure α
                                                   -- 测度类型依赖可测空间实例
example (s t : Set ℝ) (h : s ⊆ t) : s ⊆ t := h     -- 集合包含是 Prop

-- 若某条 example 编译失败，把它的类型单独 #check，是定位问题的最快手段
#check (fun {α : Type*} [MeasurableSpace α] => (α → ℝ))
```

## 10.3 Coq、Isabelle、Metamath、HOL Light

### 10.3.1 五条技术路线的对比

在 Lean 之外，还有若干成熟的证明助手。它们在逻辑基础、架构与生态上差异显著，选择哪一条取决于研究对象。

| 系统           | 逻辑基础                     | 架构/内核                  | 生态与数学库                                       | 统计相关内容                                       | 学习曲线                | 代表成果                                           |
| ------------ | ------------------------ | ---------------------- | -------------------------------------------- | -------------------------------------------- | ------------------- | ---------------------------------------------- |
| Lean 4       | 归纳构造演算（CIC）+ 商类型 + 选择公理  | 独立类型检查内核（de Bruijn 式）  | Mathlib4，超 150 万行，十万余条已验证声明                  | 测度论与概率论体系较完整：条件期望、独立性、Markov 核、矩与母函数、鞅、布朗运动  | 语法现代，入门资料充足，中等      | Mathlib、AlphaProof（2024 年 IMO 达银牌水平）           |
| Coq / Rocq   | 归纳构造演算（CIC）              | 类型检查内核 + 抽取机制          | math-comp（SSReflect 风格）、corn、Coquelicot；社区成熟 | 概率论发展弱于 Lean；优势在程序语义与编译器验证                   | 语法相对繁琐，陡            | CompCert 验证编译器、四色定理（Gonthier）、Feit–Thompson 定理 |
| Isabelle/HOL | 高阶逻辑（HOL）+ 简单类型 λ 演算     | LCF 架构，抽象类型 `thm`      | Archive of Formal Proofs（AFP）期刊式收录           | `Probability` 库含测度论、条件期望、独立性、鞅、马尔可夫链等        | Isar 结构化证明语言可读性好，中等 | seL4 操作系统内核验证、AFP 数百个项目                        |
| Metamath     | 一阶逻辑 + ZFC 集合论（`set.mm`） | 极简替换式验证器               | `set.mm` 覆盖从集合论到实分析                          | 极少；无专门的概率论库                                  | 证明脚本冗长，陡            | `set.mm`、GPT-f 自动生成新定理                         |
| HOL Light    | 高阶逻辑（HOL）                | LCF 架构，内核极小（数百行 OCaml） | Harrison 的实分析、复分析与测度论形式化                     | 测度与积分基础扎实；概率论相关的历史积累主要在 HOL4 一脉（如随机化算法的概率证明） | 需写 OCaml，陡          | Flyspeck 项目（Kepler 猜想的完整形式化验证）                 |

几点说明。Coq 于 2025 年起正式更名为 Rocq，改名不影响已有生态。Isabelle 的 LCF 架构意味着所有推理最终都归约到内核中的少数原始规则，TCB 极小；其 Isar 语言写出的证明可读性在五者中最好，适合需要人类阅读证明的场合。Metamath 的验证器只做符号替换，不依赖类型论，其优势是验证器可以被第三方轻易重写，劣势是证明脚本与人类书写习惯相差很远，早期基于语言模型的证明工作（GPT-f，arXiv:2009.03393）选择它，正是因为其动作空间简单、易于生成。

HOL Light 由 John Harrison 开发，用 OCaml 实现，是 Flyspeck 项目（Hales 团队对 Kepler 猜想的形式化验证）的载体。它在分析学上的积累深厚：实数、复分析、测度论与 Lebesgue 积分都有较完整的形式化。对统计学者而言，如果研究对象需要严格的积分与测度基础而不涉及现代概率论结构，HOL Light 的分析库仍是可选路径；若需要鞅、条件期望、Markov 核这类结构，当前更现实的选择是 Lean/Mathlib 或 Isabelle/HOL。

### 10.3.2 如何为统计问题选择系统

我们做选择时主要看三条。第一，看目标定理所需的库是否已有：需要 concentration、经验过程、渐近理论时，Lean/Mathlib 的覆盖最好，且已有统计学习理论的形式化项目可供直接复用。第二，看是否需要人类可读的证明：若形式化的目的之一是说服审稿人或合作者，Isabelle 的 Isar 与 Lean 的 tactic 脚本都可接受，Metamath 不适合。第三，看团队已有的工程能力：HOL Light 与 Coq 需要更多的系统编程基础，Lean 4 的元编程对有 Python/R 背景的人相对友好。

这三条之外还有一条我们经常忽略、事后才后悔的：看合作者与评审者熟悉什么。一个形式化产物如果没人能读，它的验证价值虽然不减，但传播价值会小很多。

## 10.4 Mathlib4与形式化数学库

### 10.4.1 规模与组织方式

Mathlib4 是 Lean 4 的标准数学库，由 Lean 社区协作维护（github.com/leanprover-community/mathlib4），代码量超过 150 万行，包含十万余条已验证声明，是规模最大的形式化数学库。它采用严格的层级组织：

| 顶层目录                    | 内容                                          |
| ----------------------- | ------------------------------------------- |
| `Mathlib/Data`          | 基础数据结构：自然数、整数、实数、有限集、多重集、矩阵                 |
| `Mathlib/Algebra`       | 代数结构：群、环、域、模、代数层级与类型类                       |
| `Mathlib/Topology`      | 拓扑空间、滤子（filter）、连续性、紧性                      |
| `Mathlib/Analysis`      | 微积分、赋范空间、凸性、特殊函数                            |
| `Mathlib/MeasureTheory` | 测度论、可测函数、Lebesgue 积分、$L^p$ 空间、Radon–Nikodym |
| `Mathlib/Probability`   | 概率论：独立性、条件期望、矩、分布、鞅、极限定理                    |
| `Mathlib/LinearAlgebra` | 线性代数、矩阵分析、谱理论                               |
| `Mathlib/Combinatorics` | 组合数学、图论                                     |
| `Mathlib/NumberTheory`  | 数论                                          |

依赖关系是单向的，画出来是这样：

```text
        Mathlib/Probability            独立性、条件期望、矩、鞅、极限定理
                 ▲
                 │  依赖
        Mathlib/MeasureTheory          测度、可测函数、Bochner 积分、L^p
                 ▲
                 │  依赖
   Mathlib/Analysis  Mathlib/Topology  赋范空间、连续、滤子、紧性、凸性
                 ▲
                 │  依赖
   Mathlib/Algebra   Mathlib/LinearAlgebra   群环域模、矩阵、谱
                 ▲
                 │  依赖
        Mathlib/Data                   Nat / Int / Rat / Real / Finset / ...
                 ▲
                 │  依赖
        Std + Lean 核心                 Init、Std
```

层级关系决定了依赖方向：概率论依赖测度论，测度论依赖拓扑与滤子。统计学者若要形式化一条集中不等式，实际路径通常是从 `MeasureTheory` 一路向下追到可测性定义。这也解释了为什么概率与统计类定理的形式化成本高，每往下追一层，就要多掌握一层的记号与类型类参数。

命名约定上有两点我们花了较长时间才适应：定理名用 `snake_case`；命名通常描述结论而非人名，例如柯西中值定理在 Mathlib 中名为 `exists_ratio_deriv_eq_ratio_slope`，用英文直译搜索往往找不到（我们按"Cauchy mean value theorem"搜过，一无所获）。这使得检索成为形式化工作中耗时最多的环节之一。


### 10.4.2 如何检索定理

| 检索方式                                              | 适用场景                       | 说明                                                  |
| ------------------------------------------------- | -------------------------- | --------------------------------------------------- |
| `#check` / `#print`                               | 已知名字，查类型签名或打印定义            | 在 Lean 文件或编辑器中即时执行                                  |
| `exact?` / `apply?` / `rw?`                       | 目标已知，问系统有没有能用的定理           | 由 tactic 搜索并给出候选，返回可替换的代码                           |
| 本地 `grep` / `rg`                                  | 知道关键词片段，在克隆的 Mathlib 中全文搜索 | 配合本地 Mathlib 副本最可靠                                  |
| `#find`（如已加载相关工具）                                 | 按类型模式查找                    | 对"找一个返回 `Integrable f μ` 的定理"这类需求有效                 |
| Loogle（loogle.lean-lang.org）                      | 按类型模式与子项模式检索               | 适合按结论形式反查                                           |
| Moogle（moogle.ai）                                 | 自然语言检索定理                   | 语义检索，命中率依赖表述                                        |
| LeanSearch（leansearch.net）                        | 自然语言检索，北大团队维护              | 已在社区被广泛使用；数据集 `FrenzyMath/mathlib_informal_v4.16.0` |
| LeanSearch v2                                     | 全局前提检索                     | 面向研究级定理，直接服务于需要多个前提的场景                              |
| `lean_local_search` / `lean_loogle`（lean-lsp-mcp） | Agent 工作流内的检索              | 专门用于抑制模型引用不存在的定理                                    |

面对这么多入口，我们给自己定的检索顺序是这样一条决策链：

```text
我要找一个定理
   │
   ├─ 已知名字？ ───────── 是 ──► #check 名字          查类型签名
   │                              └► #print 名字        查定义与实现
   │                              └► #print axioms 名字 查依赖了哪些公理
   │
   ├─ 只有目标、没有名字？
   │     ├─ 工程能编译 ──► exact? / apply? / rw?（让 tactic 自己搜）
   │     └─ 工程编译不动 ► Loogle（按类型模式）
   │                       LeanSearch（自然语言）
   │                       Moogle（语义，命中率看表述）
   │
   ├─ 只记得一个词片段？ ─► rg -n "词片段" Mathlib/   （本地副本）
   │                        └► 命中后回到第一行：#check 全名
   │
   └─ 想了解某个领域有哪些文件？ ► mathlib4_docs 按目录浏览
                                 └► 仓库里读该目录的 README / 文件头注释
```

在 Lean 文件里做检索的一组常用命令：

```lean
import Mathlib

-- 1) 已知名字：查类型签名
#check Nat.add_assoc
#check MeasureTheory.Integrable

-- 2) 已知名字：查定义本体（定理只打印陈述）
#print Nat.add_assoc

-- 3) 求值：Lean 也是可执行语言，#eval 用来验证计算类定义
#eval 2 + 2
#eval List.range 5 |>.map (· * 2)

-- 4) 按类型模式搜索（#find 由 Mathlib 提供；若版本不支持，改用 Loogle）
#find _ + 0 = _
#find (0 : ℝ) ≤ _ ^ 2

-- 5) 目标已知、名字未知：让 tactic 自己找
example (a b c : ℕ) : a + b + c = a + (b + c) := by
  exact?    -- 编译后 InfoView 会给出可用定理建议，替换掉这一行即可
```

本地全文检索的典型用法：

```bash
# 在克隆的 Mathlib 中定位与条件期望相关的声明
rg -n "condExp" Mathlib/Probability | head -40

# 找所有提到 "variance" 的声明定义
rg -n "def variance|variance_" Mathlib/Probability

# 查看某个定理所在文件（配合 VS Code 跳转）
rg -n "theorem exists_ratio_deriv_eq_ratio_slope" Mathlib
```

几条我们后来才学会、用起来省不少时间的 `rg` 变体：

```bash
# 只看声明行（theorem / lemma / def 开头），避免被正文注释淹没
rg -n "^(theorem|lemma|def) .*variance" Mathlib/Probability

# 带上下文看一条声明前后的注释，注释里常有用法说明
rg -n -A 6 "^theorem measure_mono" Mathlib/MeasureTheory

# 只列出命中文件，判断该去哪个目录深挖
rg -l "condExp" Mathlib | sort

# 限定文件类型，避免扫到 olean 与构建产物
rg -n --glob '*.lean' "IndepFun" Mathlib/Probability

# 大小写不敏感 + 全词匹配，避免命中一堆无关前缀
rg -niw "markov" Mathlib/Probability
```

### 10.4.3 概率论与测度论部分

Mathlib 的概率论内容（社区官方说明见 leanprover-community.github.io/blog/posts/basic-probability-in-mathlib/）包括：

| 类别       | 记号 / 常量                                                           |      |
| -------- | ----------------------------------------------------------------- | ---- |
| 条件期望     | $\mu[f \mid m]$，记为 \`μ[f                                          | m]\` |
| 条件概率     | \`P[s                                                             | t]\` |
| 条件分布     | `condDistrib`                                                     |      |
| 独立性      | `IndepFun`、`iIndepFun`、`IndepSet`、`iIndepSet`、`Indep`             |      |
| Markov 核 | `Kernel α β`、`ProbabilityKernel`，复合 `κ ∘ₖ η`、`κ ∘ₘ μ`，积核 `κ ×ₖ η` |      |
| 矩与母函数    | 矩、方差、协方差、矩母函数 `mgf`、累积量母函数 `cgf`                                  |      |
| 常见分布     | Exponential、Gamma、Gaussian、Geometric、Pareto、Poisson、Uniform       |      |
| 随机过程     | 鞅、布朗运动、极限定理                                                       |      |

对统计学者而言，我们优先读的是下面几类文件（具体文件名以仓库当前结构为准）：`Mathlib/MeasureTheory/Integral`（Lebesgue 积分与可积性）、`Mathlib/MeasureTheory/Function`（$L^p$ 空间、几乎处处相等）、`Mathlib/Probability/Independence`（独立性及其与期望的交互）、`Mathlib/Probability` 下与条件期望、矩、分布相关的文件（条件期望的非可积约定、矩的定义与母函数）。我们的阅读顺序是自上而下：先看这些文件顶部的注释与主要定理陈述，再按需下钻。从最底层的构造（实数怎么造出来的）开始读，我们尝试过一次，两周后仍在第一层，这次尝试不太成功。

下面这段代码是一组概率与测度方向的现场实验。需要说明的是：库中的命名会随版本变动，若某条 `#check` 返回 unknown identifier，我们倾向于先用 Loogle 或 `rg` 定位，而不是硬猜名字。

```lean
import Mathlib
open MeasureTheory ProbabilityTheory

-- 1) 概率测度在 Mathlib 里是一个类型类假设，而不是一个独立类型
example {α : Type*} [MeasurableSpace α] (μ : Measure α) [IsProbabilityMeasure μ] :
    μ Set.univ = 1 := by
  simp [measure_univ]

-- 2) 积分与可积性：几乎所有积分定理都带 Integrable 前件
#check integral                  -- ∫ x, f x ∂μ
#check Integrable                -- 可积性
#check MemLp                     -- f ∈ L^p
#check AEStronglyMeasurable      -- Borel 值函数的可测性

-- 3) 条件期望的记号与塔性质所在的命名空间
#check condExp
#check MeasureTheory.condExp

-- 4) 独立性
#check IndepFun
#check iIndepFun

-- 5) 只用到代数、不依赖库命名的小引理（这部分几乎不会因版本变化而失效）
--    Cauchy–Schwarz 证明中反复出现的 2ab ≤ a^2 + b^2
theorem two_mul_le_sq_add_sq (a b : ℝ) : 2 * a * b ≤ a ^ 2 + b ^ 2 := by
  nlinarith [sq_nonneg (a - b)]

-- 6) 协方差型界的一个代数版本
theorem cov_like_bound (x y μ_x μ_y : ℝ) :
    2 * (x - μ_x) * (y - μ_y) ≤ (x - μ_x) ^ 2 + (y - μ_y) ^ 2 := by
  nlinarith [sq_nonneg ((x - μ_x) - (y - μ_y))]
```

上面第 5、6 条属于"统计味道的代数"，它们的价值在于：把一条统计不等式里的测度论部分暂时剥掉，先确认代数核心成立，再回头处理可积性与可测性。这是我们在形式化卡住时常用的降阶手段。

## 10.5 miniF2F基准

### 10.5.1 构成与设计

miniF2F 由 OpenAI 与 CMU 等机构于 2021 年发布（arXiv:2109.00110，github.com/openai/miniF2F），是形式化数学推理的标准基准。它包含 488 道手工形式化的奥林匹克级数学题，来源为 AMC、AIME、IMO 以及本科数学课程，按 244 题验证集与 244 题测试集划分，并在 Lean、Metamath、Isabelle、HOL Light 四种形式语言中给出对齐的陈述。这一多语言设计的目的，是让不同证明助手上的系统可以在同一批题目上比较。

评估指标为通过率（pass rate）：给定题面的形式化陈述，系统在采样预算内生成的候选证明中至少有一个通过内核检查，即计为通过。采样预算（pass@k 中的 $k$）我们倾向于要求一并报告，否则不同系统的数字不可比，pass@1 与 pass@8192 可以相差几十个百分点。

### 10.5.2 当前结果与瓶颈

| 系统                   | 性质           | miniF2F-test 通过率          | 备注                         |
| -------------------- | ------------ | ------------------------- | -------------------------- |
| DeepSeek-Prover-V1.5 | 开源，7B        | 63.5%                     | 前代版本                       |
| DeepSeek-Prover-V2   | 开源，7B / 671B | 88.9%（Pass@8192）          | 配套 ProverBench             |
| Goedel-Prover-V2-32B | 开源           | 90.4%（self-correction 模式） | 8B 版本即可接近 671B 模型          |
| Kimina-Prover        | 开源           | 92.2%（TTRL）               | 首个给出证明 scaling law 的形式推理模型 |
| 端到端流程                | —            | 约 36%                     | 自然语言理解 → 形式化 → 证明          |

表中最后一行是全表最关键的一行。上述 88.9%–92.2% 的数字都是在**已给出形式化陈述**的前提下取得的：系统拿到的是一个合法的 Lean 命题，只需生成证明。而真实的使用场景是：研究者给出一个自然语言命题（或一篇论文的一段 LaTeX），系统需要先把命题翻译成形式语言，再证明它。这两个环节串联后的准确率约 36%，远低于证明环节的单独通过率。

这一落差的含义需要精确理解。设形式化环节准确率为 $a$，证明环节通过率为 $b$，端到端准确率约为 $a \cdot b$（实际还包含误差相关项）。$b \approx 0.9$ 而端到端约 $0.36$，意味着 $a$ 的量级在 0.4 上下。**形式化环节，而非证明环节，是当前的主要瓶颈。**

另一处容易被忽略的是失败的性质。证明环节的失败是显式失败：内核报错，系统知道没证出来。形式化环节的失败是静默失败：一个错误的形式化命题同样可以被成功证明，系统返回"已证明"，但证明的是另一个命题。若评估只统计"是否编译通过"，这类错误会被完全掩盖，端到端数字因此容易被高估。这也是相关局限分析工作（arXiv:2511.03108）关注的核心问题。

把这两个数字放进统计学的语言里看，会有一种熟悉感。$a \cdot b$ 这种串联结构与"灵敏度 × 特异度"决定的整体判准率同类：一个环节的提升会被另一个环节的天花板压住，而两个环节的错误还有相关性（命题改弱后更容易证出，于是 $a$ 与 $b$ 不是独立的，实际端到端数字比独立假设下的 $a\cdot b$ 更乐观也更不可信）。这提示一件具体的事：报告端到端数字时，把"形式化后人工核对通过的比例"单独列出，比只给一个总数更有用。我们自己记录的那一次，人工核对后从 36% 降到不足 20%，样本很小，只作参考，但量级上的落差与公开报告的批评一致。

## 10.6 LeanDojo

### 10.6.1 定位与组成

LeanDojo（leandojo.org，arXiv:2306.15626，NeurIPS 2023，加州理工学院与 MIT）是一个开源工具链，把"AI 与 Lean 的交互"标准化为可编程接口。它解决的是工程问题：此前每个研究组都要自己写一套与 Lean 进程通信、抽取训练数据、回放证明的脚手架，彼此不可复现。

LeanDojo 由三部分构成：

1. **数据抽取**。从任意 GitHub 上的 Lean 仓库提取结构化数据：定理的完全限定名、所在文件、证明的每一步 tactic、每一步前后的证明状态（state before / state after）、以及每步使用的前提（premises，即被引用的库定理）。这些数据构成监督学习所需的训练样本。
2. **程序化交互环境**。`Dojo` 类封装一个真实的 Lean 进程，提供 `run_tac`（执行一条 tactic 并返回新状态或错误）等操作，使外部程序（包括模型训练循环）能够以"下一条 tactic"为动作单位与环境交互。支持 Lean 3 与 Lean 4。
3. **检索增强基线模型 ReProver**。由一个基于编码器检索前提的检索器（retriever）和一个生成 tactic 的生成器（generator）组成。官方给出的复现成本约为 1 GPU 周。

配套项目 LeanCopilot（github.com/lean-dojo/LeanCopilot，MIT 许可）把同一套能力搬进 Lean 开发环境：在证明中可直接调用 `suggest_tactics`（建议 tactic）、`search_proof`（搜索完整证明）、`select_premises`（选择前提），并允许加载本地模型。

### 10.6.2 最小使用代码

```python
# 安装：pip install lean-dojo
# 前置：本机已有 Lean 4 工具链（elan / lake 可用）

from lean_dojo import LeanGitRepo, Theorem, Dojo

# 1) 指定仓库与分支。我们倾向于钉住具体 commit，否则结果不可复现
repo = LeanGitRepo("https://github.com/yangky11/lean4-example", "main")

# 2) 定位一个定理：文件相对路径 + 完全限定名
theorem = Theorem(repo, "Lean4Example/Demo.lean", "hello_world")

# 3) 启动真实 Lean 进程，取得初始证明状态
dojo, state_0 = Dojo(theorem).__enter__()
print(state_0)                      # 打印当前目标

# 4) 逐条 tactic 与内核交互；返回新状态或错误信息
result = dojo.run_tac(state_0, "rw [hello]")
print(result)

# 5) 关闭进程
dojo.__exit__(None, None, None)
```

批量抽取定理：

```python
from lean_dojo import LeanGitRepo

repo = LeanGitRepo("https://github.com/leanprover-community/mathlib4", "master")
theorems = repo.get_theorems()
```

如果只需要"把一段 Lean 代码交给本机内核判一下"，而不想引入 LeanDojo 的完整依赖，我们自己用的是一个基于 `subprocess` 的最小封装。它的好处是行为完全可见，坏处是没有增量状态，每次都是全量编译：

```python
# lean_check.py：把一段 Lean 源文本交给本机 toolchain 编译
# 依赖：项目目录里已有 lean-toolchain 与 lakefile，且已执行过 lake exe cache get
import os
import subprocess
import tempfile
from pathlib import Path

PROJECT = os.environ.get("LEAN_PROJECT_PATH", "/path/to/your/lean/project")


def lean_check(src: str, timeout: int = 300):
    """返回 (returncode, stdout+stderr)。returncode == 0 表示内核全部接受。"""
    with tempfile.TemporaryDirectory(dir=PROJECT) as tmp:
        f = Path(tmp) / "Snippet.lean"
        f.write_text(src, encoding="utf-8")
        r = subprocess.run(
            ["lake", "env", "lean", str(f)],
            cwd=PROJECT, capture_output=True, text=True, timeout=timeout,
        )
    return r.returncode, (r.stdout or "") + (r.stderr or "")


if __name__ == "__main__":
    code, out = lean_check("import Mathlib\nexample : 1 + 1 = 2 := by norm_num\n")
    print("returncode =", code)
    print(out[:2000])
```

这段代码的价值在于：它把"模型说它证出来了"这句话变成了一个可以自动执行的判定。我们在自己的闭环里坚持每条候选都过这一关，不用模型自评代替内核判定，我们试过用模型自评，结果漏掉了一次静默失败（命题被改弱后编译通过，自评也通过）。

### 10.6.3 用它训练自己的证明器

一个完整的训练流程由四步组成。

**第一步，数据构造。** 从目标仓库（通常是 Mathlib 或某个专业库）抽取定理与证明，构造样本 $(\text{state}, \text{tactic}, \text{premises})$。预训练语料可直接使用 Mathlib 全量；微调语料我们倾向于限定在与目标定理同类的分支上，对统计方向而言，用 `Mathlib/Probability` 与 `Mathlib/MeasureTheory` 的数据微调，比用全量数据更有效率。

**第二步，监督微调。** 以证明状态为输入、下一条 tactic 为输出，对基座模型做监督微调。状态文本包含当前目标的完整上下文，长度可达数千 token，需要相应调整上下文窗口。

**第三步，检索增强。** 训练一个前提检索器：给定当前状态，从前提库（库中所有定理的形式化陈述）中检索若干候选，拼进生成器输入。这一步是 ReProver 的核心，也是抑制"引用不存在定理"的关键手段。

**第四步，闭环验证与迭代。** 用 `Dojo` 环境做采样—编译—反馈循环。示意如下：

```python
# 采样 → 编译 → 反馈的最小闭环（示意代码）
for thm in theorems_batch:
    dojo, state = Dojo(thm).__enter__()
    for step in range(max_steps):
        candidates = model.sample(state.pp, num_samples=32)   # 先给采样预算
        advanced = False
        for tac in candidates:
            result = dojo.run_tac(state, tac)
            if not isinstance(result, LeanError):
                state, advanced = result, True
                break                                        # 取第一个编译通过的
        if not advanced or is_closed(state):
            break
    record(thm, state)
    dojo.__exit__(None, None, None)
```

该循环的两个工程要点：一是先给采样预算（pass@32 起步），单发准确率通常很低；二是每个候选都要真正送进 Lean 编译，用模型自评代替内核判定的做法我们不推荐。

在模型选择上，当前可本地部署的开源证明模型包括 DeepSeek-Prover-V2（7B 可在单张 24 GB 显卡运行，671B 需多卡）、Goedel-Prover-V2（8B/32B，支持 self-correction 模式）、Kimina-Prover、LongCat-Flash-Prover（567B MoE）。提示模板上，DeepSeek 与 Goedel 系列都要求先给出 proof plan 再给出代码。

## 10.7 自动形式化

### 10.7.1 问题定义

自动形式化（autoformalization）指把自然语言（或 LaTeX）表述的数学命题翻译为形式语言中的命题，必要时连同证明一起翻译。它是统计学者最关心的环节：研究者手里的原始材料是论文与教材，而不是 Lean 命题。

形式化命题与自然语言命题之间不是逐句对应，而是一次重新表述。自然语言命题携带大量约定：变量的取值范围由上下文给出，量词被省略，"随机变量"默认指某个概率空间上的可测函数，"收敛"默认指某种特定的拓扑。形式化要求把所有约定写成显式符号，这一步无法由翻译规则完成，只能由理解数学的主体完成。

### 10.7.2 四类主要困难

**未言明的假设。** 教科书中的定理常把正则条件写在章节开头而不写进定理。形式化的过程中，这些条件要逐条补进陈述，补错或漏补都改变命题。我们遇到过的一种情形是：一条关于估计量相合性的定理，原文假设只写了"独立同分布"，形式化时才发现还需要可积性、可测性与参数空间的紧性，三者缺一不可。

**定义歧义。** 同一术语在文献中有多个等价（或仅在额外条件下等价）的定义。收敛模式、$O(\cdot)$ 与 $o(\cdot)$ 的取极限方向、次高斯范数、覆盖数与度量熵、条件期望的定义域，都属于此类。这类情形下形式化要选定一个版本，而这个选择具有实质后果。

**与库中已有定义的对齐。** 即便研究者心中有一个明确的定义，Mathlib 中被广泛使用的定义也可能与之不同（例如某个结构要求更强的拓扑假设）。采用自定义定义会导致后续无法复用库定理；采用库定义则可能需要调整陈述。这是形式化工作中反复出现的权衡。

**忠实性与可证性的张力。** 系统有动机把命题改弱以使其可证：去掉一个条件、缩小量词范围、把上确界换成某个固定值。改弱后的命题仍然合法、仍可被证明，但已不是原命题。这是自动形式化最难防范的失败模式。

### 10.7.3 翻译正确性的判定方法

| 方法               | 做法                            | 能发现的错误             | 局限                   |
| ---------------- | ----------------------------- | ------------------ | -------------------- |
| 编译检查             | 内核接受形式化命题                     | 语法错误、类型错误、引用不存在的常量 | 完全不能发现语义偏差           |
| 公理检查             | `#print axioms` 确认无 `sorryAx` | 未完成证明（`sorry` 占位）  | 不能发现命题偏差             |
| 往返翻译（round-trip） | 形式化命题再翻译回自然语言，与原命题比对          | 明显的语义漂移、量词丢失       | 依赖回译模型的能力，两次错误可能互相掩盖 |
| 双盲翻译             | 两条独立的形式化路径，检查二者是否逻辑等价         | 暴露歧义与主观选择          | 成本翻倍；二者可能犯同类错误       |
| 加强版证否（disprove）  | 尝试证明形式化命题的加强版；若轻易被证否说明命题可能被改弱 | 被改弱的命题             | 需要有效的反例搜索            |
| 实例化数值检查          | 把形式化命题代入具体分布、具体样本量，与数值结果比对    | 量化顺序错误、常数错误、方向错误   | 只对可计算实例有效            |
| 人工逐行核对           | 由熟悉该领域的人逐行读定理陈述               | 全部                 | 成本高，但唯一可靠            |

对统计学者，最后两项我们倾向于多加强调。统计命题通常可以实例化：一个关于尾部概率的界，可以代入具体分布与具体 $n$ 做数值检验；一个关于估计量收敛速度的陈述，可以用蒙特卡洛模拟检查其数值表现是否符合形式化后的断言。这是统计学相对纯数学的一个便利，用可执行的一致性检查部分替代语义判断。人工逐行核对仍然不可省略：内核只检查"这份证明证明了这份陈述"，它不知道这份陈述是不是想证的那个。

### 10.7.5 面向统计学者的建议流程

我们的顺序通常是这样，供参考，它未必最优：

第一，先只形式化陈述，不形式化证明。把一个技术引理的命题写成 Lean 的 `theorem` 语句，证明用 `sorry` 占位，确认类型检查通过。这一步的成本远低于完整形式化，却已经能暴露隐含假设。

第二，进行实例化数值检查与往返翻译，确认陈述忠实。

第三，再进入证明阶段，优先尝试库中已有定理的组合，其次才考虑模型生成。

第四，卡住的位置要专门记录。形式化过程中卡住的地方，通常是原论文中隐含假设未写出的地方，这一观察在已有的形式化实践中被反复验证，也与我们的几次经历吻合。

### 10.7.6 端到端流水线与静默失败的位置

把 10.5.2 的数字与 10.7.3 的判定方法放在一起看，整条流水线可以画成下面这样。我们特别把"改弱"这条支路画出来，因为它不产生任何报错：

```text
  自然语言命题 P
        │
        ▼
  ┌───────────────┐        支路（静默）：把 P 改写成更弱的 P'
  │ 形式化 F       │──────────────────────────────┐
  └───────┬───────┘                               │
          ▼                                       ▼
  ┌───────────────┐                       ┌───────────────┐
  │ 证明搜索       │                       │ 证明搜索（更容易）│
  └───────┬───────┘                       └───────┬───────┘
          ▼                                       ▼
  ┌───────────────┐                       ┌───────────────┐
  │ 内核检查       │                       │ 内核检查       │
  └───┬───────┬───┘                       └───────┬───────┘
      ▼       ▼                                   ▼
    通过    拒绝（显式失败，                     通过 → 系统报告"已证明"
    │       系统知道自己没证出来）                 │
    ▼                                             ▼
 记录"已证明 P"                          记录"已证明 P'"，而 P' ≠ P

```

这张图想说明的是：两条支路在机器看来完全一样，区别只在人这一侧。因此判定"是否真的证出来了"的手段必须在流水线之外，往返翻译、双盲翻译、实例化数值检查、人工逐行核对，四者都在图外。这也是为什么我们在 10.8.10 把"逐行读定理陈述"列为不可省略的一步。

### 10.7.7 转换流水线：自然语言到形式化的六步

把 10.7.1–10.7.5 的方法按执行顺序排成一条流水线，AI 在其中两个环节承担主要工作量，在其余环节承担辅助工作：

```text
 自然语言命题（论文 / 教材 / 笔记里的一句话）
       │
       ▼
 ┌─────────────────────────────────────────────────────┐
 │ [1] 预处理：抽出命题、补齐上下文、列出术语表           │
 │     参与：人工为主，LLM 辅助                成本：低   │
 └───────────────────────────┬─────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────┐
 │ [2] 陈述翻译：NL → Lean 命题（证明用 sorry 占位）     │
 │     参与：LLM 主力，低 temperature，多轮迭代  ★主力   │
 │     产出：能通过类型检查的 theorem 声明               │
 └───────────────────────────┬─────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────┐
 │ [3] 忠实性核对：量词顺序 / 隐含前件 / 定义选择         │
 │     手段：人工逐行 + 往返翻译 + 实例化数值检查 ★关键  │
 │     发现偏差 ──► 回到 [2] 改写，并记录分歧点          │
 └───────────────────────────┬─────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────┐
 │ [4] 证明搜索：库定理组合 → 自动化 tactic → 模型采样   │
 │     参与：LLM 主力，高采样预算（pass@8 起步）★主力    │
 └───────────────────────────┬─────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────┐
 │ [5] 内核检查：lake build + #print axioms             │
 │     拒绝 ──► 报错逐字拼回 [4] 迭代                    │
 │     通过 ──► 继续                                    │
 └───────────────────────────┬─────────────────────────┘
                             ▼
 ┌─────────────────────────────────────────────────────┐
 │ [6] 交付自检：无 sorry / 无自定义公理 / 逐行读陈述    │

 └─────────────────────────────────────────────────────┘
```

三点说明。其一，[2] 与 [4] 是 AI 的主力环节，但两者的失败性质不同：[4] 的失败是显式的（内核拒绝），[2] 的失败是静默的（翻译错了照样能编译），所以 [3] 必须夹在两者之间，而不能放在流水线末尾一次性补做。其二，[3] 的三个手段有先后顺序：实例化数值检查成本最低，先做它排除量词顺序与常数方向的低级偏差；往返翻译其次；人工逐行核对放最后、也只对存疑处精读，这是在成本与可靠性之间的一种取舍。其三，按笔者的记录，[2]+[3] 与 [4]+[5] 的耗时大致相当，"把话说对"与"把它证出来"各占一半上下；这与 10.9.1 中那条时间记录的结构一致，也与 10.5.2 中端到端准确率被形式化环节压住的结论互为印证。10.8.11 的提示词模板将按这条流水线上的任务类型逐一给出。

### 10.8.3 写第一条证明：从 `norm_num` 到自写定理

第一条证明的价值不在于命题本身，而在于把"写一个 `by` 块 → 看 InfoView → 改一行 → 再看"这个循环跑起来。下面按我们当时的顺序排列。

```lean
-- 第 0 步：确认工具链可用。这三行不需要任何 import。
#eval (1 : Nat) + 1              -- 输出 2
example : 1 + 1 = 2 := by norm_num
example : 1 + 1 = 2 := by rfl    -- Nat 加法在字面量上可计算，rfl 也能闭合
```

```lean
-- 第 1 步：自写一条定理。只用 core，不需要 import Mathlib。
theorem my_add_zero (n : Nat) : n + 0 = n := by
  induction n with
  | zero      => rfl           -- 基础情形：0 + 0 = 0，按定义计算
  | succ n ih => simp [ih]     -- 归纳情形：化简后交给归纳假设 ih

theorem my_add_assoc (a b c : Nat) : (a + b) + c = a + (b + c) := by
  induction a with
  | zero      => simp
  | succ a ih => simp [ih]

theorem my_add_comm (a b : Nat) : a + b = b + a := by
  induction a with
  | zero      => simp [my_add_zero]
  | succ a ih => simp [ih, my_add_assoc]
```

逐条说明这几个 tactic 在做什么：

- `induction n with | zero => ... | succ n ih => ...` 对 `n` 做结构化归纳，产生两个分支；第二个分支里 `ih` 是归纳假设，它的类型可以在 InfoView 里看到。把 `ih` 写进 `simp [ih]`，就是让简化器用这条等式做一次重写。
- `simp` 反复应用被标记为 `[simp]` 的重写规则直到不再变化；`simp [ih]` 是在这些规则之外临时追加 `ih`。想知道 `simp` 到底用了哪些规则，把它换成 `simp?`，InfoView 会给出一条可粘贴的 `simp only [...]` 建议。
- `rw [h]` 只按给定规则改写一次、只改匹配到的位置，不做后续的循环简化。需要精确控制改写位置时（例如只改等式左边）用 `rw`，需要"把明显的垃圾清掉"时用 `simp`。
- `rfl` 只处理定义相等：两边计算到同一个范式就通过。它不查任何定理，所以失败很快，适合用来判断"这个式子是否只是计算问题"。
- `exact t` 直接给出一个项。当 `simp` 之类的自动化把目标改得面目全非时，先 `guard_target = ...` 断言目标形状，再 `exact`，是定位问题的常用组合。

下面三个片段是刻意写错的版本，用来演示报错长什么样（编译不通过，仅作演示）：

```lean
-- (a) rw 找不到匹配的模式
theorem bad_rw (a b : Nat) : a + b = b + a := by
  rw [my_add_assoc]
  -- 报错样式：tactic 'rewrite' failed, did not find instance of the
  --          pattern in the target expression:  (?m.1 + ?m.2) + ?m.3

-- (b) 归纳情形里忘了用归纳假设
theorem bad_induction (a b : Nat) : a + b = b + a := by
  induction a with
  | zero => simp
  | succ a ih => rfl
  -- 报错样式：tactic 'rfl' failed, ... 并在证明块结束时追加
  --          unsolved goals
  --          ⊢ a + b = b + a

-- (c) 结论类型对不上：Nat 的等式不能当 Int 的等式用
theorem bad_type (a b : Nat) : (a + b : Int) = b + a := by
  exact my_add_comm a b
  -- 报错样式：type mismatch
  --          my_add_comm a b
  --        has type  a + b = b + a
  --        but is expected to have type  ↑(a + b) = ↑b + ↑a
```

读这类报错时，我们按一个固定的顺序做：先看最后一行（它通常说明期望类型与实际类型），再看 `⊢` 后面留下的目标，最后才回头看 tactic 的名字。这个顺序能避免被长篇上下文带偏。

### 10.8.4 读报错：五条最常见的 Lean 报错

下面五条是我们遇到次数最多的报错。原文样式随版本变化，结构保持一致。

| 报错 | 原文样式（节选） | 常见成因 | 排查步骤 |
|---|---|---|---|
| unsolved goals | `unsolved goals` / `⊢ a + b = b + a` | 证明块结束时仍有未关闭的目标；分支写漏、`simp` 没能化简到底 | 看 `⊢` 后的目标形状；用 `guard_target` 确认它是不是自己以为的那个；缺的那一步往往是某个前件没用上 |
| type mismatch | `type mismatch` / `h` / `has type a ≤ b` / `but is expected to have type a < b` | 变量类型不一致（ℕ 与 ℤ、ℝ 混用）；定理的某个隐式参数被推断成了别的类型 | 对相关常量 `#check`；用 `@` 前缀打印全部隐式参数（`#check @Integrable`）；必要时显式写类型标注 |
| unknown identifier | `unknown identifier 'Integrable'` | 未 `import` 对应模块；命名空间未打开；或该版本里名字已改 | 先试全限定名 `#check MeasureTheory.Integrable`；再 `open` 命名空间；仍失败则按 10.8.5 检索 |
| failed to synthesize | `failed to synthesize instance` / `MeasurableSpace (Nat → ℝ)` | 类型类实例缺失：函数类型、积类型上没有默认的可测空间或拓扑实例 | 补前件 `[MeasurableSpace α]`、`[MeasurableSingletonClass α]` 等；用 `#synth MeasurableSpace ℝ` 验证实例能否合成；检查是否漏了 `BorelSpace` |
| application type mismatch | `application type mismatch` / `IndepFun f g` / `argument g has type Ω → ℝ` / `but is expected to have type Ω → β` | 传给函数的实参类型与形参不符，常由宇宙层级或隐式参数推断错误引起 | `#check @IndepFun` 展开全部参数；逐个比对；把可疑的隐式参数显式写出 |

几条补充经验：

- `simp` 相关的问题，先换成 `simp?`，看它给出哪一组重写规则；规则里出现不认识的名字，就 `#check` 它。
- 报"heartbeats 超支"（形如 `deterministic timeout`）时，多半是 `simp` 或 `aesop` 搜索空间过大。一种做法是在该定理前加 `set_option maxHeartbeats 0 in`（取消限制），另一种是把自动化拆成两步。我们倾向于后者，前者会把编译时间变得不可控。
- 报"maximum recursion depth"或栈溢出，通常是自定义递归定义没有通过终止性检查，需要改成结构递归或加 `termination_by`。
- 报错里出现 `?m.123` 这样的元变量是正常的，它表示"此处待推断"。

### 10.8.5 检索定理的四种途径与对比

10.4.2 列出了可用的检索入口，这里补充它们在成本、前提与失败模式上的差别。四种途径指的是：`#check`/`#print`（已知名字）、tactic 反问（`exact?`/`apply?`/`rw?`）、网络检索引擎（Loogle / Moogle / LeanSearch）、本地全文检索（`rg`）。

| 途径 | 前置条件 | 单次成本 | 是否联网 | 能发现"命题被改弱"吗 | 典型失败 |
|---|---|---|---|---|---|
| `#check` / `#print` | 已知完全限定名 | 秒级 | 否 | 不能 | 名字不对则 unknown identifier |
| `exact?` / `apply?` / `rw?` | 工程能编译、目标已写出 | 秒到分钟级 | 否 | 不能 | 目标写错时它给出的是"另一个命题"的解 |
| Loogle / Moogle / LeanSearch | 能描述类型形状或自然语言 | 秒级 | 是 | 不能 | 语义检索命中率依赖表述；可能返回已弃用名字 |
| 本地 `rg` | 有 Mathlib 副本 | 秒级 | 否 | 不能 | 命中太多；只匹配名字不匹配语义 |

第四列全是"不能"，这一点值得单独说：检索工具只回答"库里有没有这个东西"，不回答"这是不是你要的那个东西"。我们曾经用 `exact?` 拿到一条建议，粘贴进去编译通过，直到写讲义时才发现那条定理的结论比自己想要的弱（它只要求存在某个常数，而原命题要求对任意常数成立）。

组合使用的顺序上，我们目前的选择是这样，代价是在没有本地副本时不适用：

```text
第 1 步  #check 猜测的名字          （零成本，命中就结束）
第 2 步  exact? / apply?            （让 tactic 自己搜，最省脑力）
第 3 步  本地 rg "词片段" Mathlib/  （有副本时最可靠，还能看到上下文注释）
第 4 步  LeanSearch / Loogle        （联网，用自然语言或类型模式）
第 5 步  带上 #check 输出与 lean-toolchain 版本号去 Zulip 提问
```

在 Lean 文件里动手的顺序示例（可直接粘进 `Basic.lean` 编译）：

```lean
import Mathlib

-- 已知名字：查签名
#check Nat.add_assoc
#print Nat.add_assoc

-- 未知名字、目标已知：让 tactic 找
example (a b c : ℕ) : a + (b + c) = (a + b) + c := by
  exact?     -- InfoView 给出建议，例如：exact (Nat.add_assoc a b c).symm
             -- 把这一行替换掉即可；若它建议的是 sorry，说明库里没有现成结论

-- 用 apply? / rw? 分别问"能不能用某条定理收尾"与"能不能重写这一步"
example (a b : ℝ) (h : a = b) : a + 1 = b + 1 := by
  rw?        -- 建议 rw [h]
  -- 或者：apply?   -- 建议 congrArg 之类的函数

-- 按类型模式找（#find 由 Mathlib 提供；若版本不支持，改用 Loogle 网页）
#find _ + 0 = _
```

本地检索与之配合使用：

```bash
# 确认本地副本位置后再搜；用 lake new 建的工程副本在 lake-packages/mathlib4
rg -n "^(theorem|lemma|def)" lake-packages/mathlib4/Mathlib/Probability | rg -i "indep" | head -20

# 命中后回到 Lean 里 #check 全名，再决定要不要用
```

### 10.8.6 让 Agent 看见编译状态：lean-lsp-mcp

`lean-lsp-mcp`（github.com/oOo0oOo/lean-lsp-mcp）通过语言服务器协议（LSP）在模型与 Lean 内核之间架桥，是 Numina-Lean-Agent 的核心组件。没有它，编码 agent 只能猜测编译结果。它提供三类能力：

- 语义感知：`lean_file_outline`（文件大纲）、`lean_goal`（精确查询当前目标）、`lean_diagnostic_messages`（权威验证结果）；
- 代码执行：`lean_run_code`（即时编译孤立片段）、`lean_multi_attempt`（在单个节点并行尝试多种策略）；
- 定理检索：`lean_local_search`、`lean_loogle`，专门用于抑制引用不存在的定理。

配置方式（VS Code 的 `mcp.json`）：

```json
{
  "servers": {
    "lean-lsp": {
      "type": "stdio",
      "command": "uvx",
      "args": ["lean-lsp-mcp"],
      "env": {
        "LEAN_PROJECT_PATH": "/path/to/your/lean/project",
        "LEAN_LOG_LEVEL": "NONE"
      }
    }
  }
}
```

该工具的 README 自标为 beta，且具备本地文件系统访问与建仓能力，我们倾向于用它的 Docker 隔离方案（只读挂载源码、可写 lake 缓存）。

如果只需要一个不依赖 MCP 客户端的最小调用，下面这段是我们自己用的骨架（协议握手与工具参数名以仓库当期 README 为准）：

```python
# 示意骨架：用 Python 通过 stdio 驱动 lean-lsp-mcp
import json
import os
import subprocess

env = dict(os.environ,
           LEAN_PROJECT_PATH="/path/to/your/lean/project",
           LEAN_LOG_LEVEL="NONE")
proc = subprocess.Popen(["uvx", "lean-lsp-mcp"],
                        stdin=subprocess.PIPE, stdout=subprocess.PIPE,
                        env=env, text=True, bufsize=1)


def rpc(method: str, params: dict, rid: int = 1) -> None:
    proc.stdin.write(json.dumps({"jsonrpc": "2.0", "id": rid,
                                 "method": method, "params": params}) + "\n")
    proc.stdin.flush()


rpc("initialize", {"protocolVersion": "2024-11-05", "capabilities": {}})
rpc("tools/call", {"name": "lean_run_code",
                   "arguments": {"code": "import Mathlib\n#check Nat.add_assoc"}})
# 之后从 proc.stdout 逐行读取 JSON-RPC 响应；实际使用时需要先读 initialize 的响应
```

对我们来说，这套接口真正改变的不是"能不能证出来"，而是"报错能不能被看见"。没有它时，agent 生成一段 Lean 代码后只能靠下一次编译反馈；有了它，每一步的目标与诊断都能实时取回，试错的粒度从"整个文件"降到"一条 tactic"。

### 10.8.8 常见坑与我们的处理

| 坑 | 表现 | 我们的处理 |
|---|---|---|
| 版本漂移 | 昨天能编译的代码今天报 unknown identifier；或 `lake build` 报 toolchain 不匹配 | 提交 `lake-manifest.json` 与 `lean-toolchain`；升级时先 `lake update` 再看 diff；实验记录里记下 mathlib 的 commit |
| `sorry` 遗留 | 编译通过，但 `#print axioms` 输出 `sorryAx` | 交付前跑 `rg -n "sorry\|admit"`；CI 里让它非零退出即失败 |
| `axiom` / `unsafe` 引入 | 编译通过，公理列表里出现自定义条目 | 交付前 `#print axioms <theorem>`，只接受 `propext`、`Classical.choice`、`Quot.sound` |
| `import Mathlib` 编译时间 | 改一行等几分钟 | 迭代期换成 `import Mathlib.<子模块>`；归档时再改回全量导入 |
| Windows 路径问题 | 反斜杠、中文用户名、长路径导致 lake 找不到文件 | 用 WSL2；或把工程放在短路径下（如 `C:\lean\`）；`LEAN_PROJECT_PATH` 用正斜杠 |
| 编码与终端 | Windows 下 lake 输出中文乱码 | 终端先 `chcp 65001`；或把输出重定向到文件再看 |
| 缓存失效 | 换 toolchain 后 olean 不兼容 | `lake clean`（或删 `.lake`）后重新 `lake exe cache get && lake build` |
| 自动化超时 | `deterministic timeout` / heartbeats 超支 | 把 `simp` 拆成显式步骤；必要时 `set_option maxHeartbeats 0 in` 但记录编译耗时 |


几条命令合起来可以做成交付前的固定检查：

```bash
# 1) 全量构建
lake build

# 2) 扫描占位符（有命中即非零退出）
rg -n "sorry|admit|axiom |unsafe|opaque " . --glob '*.lean' && echo "FOUND PLACEHOLDER"

# 3) 记录版本，便于半年后复现
cat lean-toolchain
git -C lake-packages/mathlib4 rev-parse HEAD   # 若依赖是以 git 方式拉取的

# 4) 抽查一条关键定理依赖的公理
#    在 Lean 文件末尾加：#print axioms my_key_theorem
lake env lean MyProofs/Basic.lean | tail -20
```

### 10.8.9 从 0 到能读懂 Mathlib 概率论定义的六周路线

下面是一条我们走过、也改过几轮的路线。每周给出任务与自检标准；自检标准的作用大于任务清单，因为"做完了"和"真的会了"在形式化学习里差距很大。每周按 6–8 小时估算，个体差异不小。

| 周次 | 任务 | 自检标准（不满足就重来一周） |
|---|---|---|
| 第 1 周 | 通关 NNG4 至 Advanced Multiplication；做 Glimpse of Lean 精简版；通读 Tactic Cheatsheet | 不看提示能写出 `my_add_assoc` 的归纳证明；能说清 `simp` 与 `rw` 的差别 |
| 第 2 周 | Mathematics in Lean 第 2–5 章（基础、集合、函数、实数）；卡住时用 LeanSearch 检索 | 能独立写出含 $\forall$、$\exists$、$\land$ 的命题；能用 `exact?` 独立解决三个练习 |
| 第 3 周 | 本地环境：`lake new` + `lake exe cache get` + `lake build` 跑通；克隆 Mathematics in Lean 仓库作练习目录 | 能 `#check` 出 `MeasureTheory.Measure` 的类型签名，并逐项解释每个类型类参数的含义 |
| 第 4 周 | 读 Mathlib 概率论官方说明；按 10.4.5 的清单读 `Mathlib/Probability` 与 `MeasureTheory` 的文件头 | 能读懂 `μ[f \| m]`、`IndepFun`、`condDistrib` 的签名；能用 `rg` 在五分钟内定位条件期望所在文件 |
| 第 5 周 | 只写陈述：把一条自己研究里的技术引理写成 `theorem ... := by sorry`，确认类型检查通过 | 陈述回译成自然语言后与原命题一致；`#print axioms` 的输出里只有 `sorryAx` |
| 第 6 周 | 完成一次完整形式化：优先用库定理组合，其次用模型生成；记录卡住的位置 | `lake build` 通过；`#print axioms` 无 `sorryAx`；逐行核对陈述与原命题 |

第 3 周往往是最容易放弃的一周：前两周在浏览器里做题是有即时反馈的，第 3 周全在和构建系统打交道。我们的做法是把它安排在有一段连续时间的时段，而不是零散的晚上。

第 5 周值得单独说明。只写陈述不写证明这一步，成本大约是完整形式化的十分之一，却能暴露原命题里被省略的前件，我们在自己的一次尝试中，就是在这个阶段发现原文的"在正则条件下"实际上包含了三个不同的可积性要求。

### 10.8.10 拿到"证明"之后必做的三件事

我们不太敢相信任何工具返回的 "proved" 状态，于是养成了三步自检的习惯：

```bash
# 1) 真编译一遍
lake env lean MyProofs/Basic.lean

# 2) 查依赖了哪些公理 ， 出现 sorryAx 说明证明不完整
#    在文件末尾加：
#print axioms my_lemma
#    期望输出：propext, Classical.choice, Quot.sound

# 3) 逐行读定理陈述
```

第三步在我们的实践中最容易被跳过，也最不该省。内核只检查"这份证明证明了这份陈述"，它不知道这份陈述是不是研究者想证的那个。一个统计量漏写可测性条件、一个极限少写一个"几乎处处"，代码照样编译通过，这也是当前数学界对若干形式化工作提出质疑的焦点所在。

两种已知的作弊模式需要人工专门检查：其一，**层层外包**，把核心难度推给一个用 `sorry` 占位的辅助引理，等价于"假设我们能解决这个，于是我们就解决了"；其二，**幻觉引理**，直接引用一个不存在的定理（形式化系统中这类引用会被内核拦下，但在自然语言层的伪形式化产物中仍会出现）。

我们自己在写这一章时犯过一次第一类错误的变体：把一个关键步骤交给一条自己写的 `lemma`，后来发现该 `lemma` 的前提里藏了一个与结论同等强度的假设。编译通过，自评通过，只有逐行读的时候才暴露出来。

### 10.8.11 面向四类任务的提示词模板、参数选择与校验

10.8.6–10.8.7 解决的是"让模型看见 Lean 的状态"，这一节解决"对模型说什么"。按 10.7.7 流水线上的任务类型，我们把日常用到的提示词整理成四个模板。模板本身逐字可复制，占位符用尖括号标出；每个模板后面附一句设计意图，说明为什么要这样写。

**上下文安排先行。** 无论哪个模板，喂给模型的内容都遵循同一份清单：目标命题的原文、所在文件的完整 `import` 头、`lean-toolchain` 的版本行、以及与任务直接相关的若干条 `#check` 输出。不要把整个文件乃至整个项目粘进去，按笔者的经验，无关代码越多，模型编造不存在的库常量名的频率越高（这只是经验观察，不是受控结论）。如果模型报出的库常量名不在我们提供的 `#check` 输出里，一律视为"待验证"而不是"可用"。

**模板一：陈述翻译**（流水线环节 [2]，对应 10.7 的自动形式化）

```text
请把以下自然语言命题翻译为 Lean 4 + Mathlib 的形式化陈述。
要求：
1. 写出所有量词与隐含条件（可测性、可积性、正性、非退化等），不要省略；
2. 只写陈述，不写证明，证明的位置用 sorry 占位；
3. 对每个你不确定的库常量名，单独列在末尾，并注明"未经 #check 验证"；
4. 若原命题存在歧义（量词顺序、收敛模式、定义版本），列出所有候选读法，
   不要替我选择；若你认为需要选择，把每个选择对命题强弱的影响说清楚。
使用的 Lean 版本与 Mathlib 版本如下（来自 lean-toolchain）：
<版本行>
相关库常量的现有签名如下（来自 #check 输出）：
<签名列表>
自然语言命题如下：
<命题原文>
```

设计意图：第 1 条把隐含条件显性化，直接对应 10.7.2 的第一类困难；第 2 条把"翻译"与"证明"两个失败面分开，让陈述可以先被单独核对（这正是 10.7.5 建议流程的第一步）；第 3 条把模型对自身不确定性的判断外显成一份可勾选清单，配合第 11 章 11.5.6 的批量 `#check` 做法一次性核对，能拦下大部分幻觉引用；第 4 条明确禁止模型替人做歧义选择，模型默认的倾向是把命题改弱以便后续可证（10.7.2 第四类困难），把选择权显式收回是抵御这一倾向的主要手段。

**模板二：tactic 补全**（流水线环节 [4]）

```text
以下是 Lean 4 + Mathlib 中一条进行到一半的证明。
当前证明状态（来自编辑器 Goals 面板，逐字粘贴）：
```

设计意图：要求"3 个候选并排序"而不是"1 个最优解"，是因为单发命中的概率低、而内核判定成本低，多点撒网配合逐个送内核的做法（10.6.2 的闭环）整体上更快；要求粘贴 Goals 面板的实际状态而不是描述"我在证什么"，是因为模型对目标形状的想象经常与真实状态差一个繁饰细节；第 1 条与第 4 条合起来是防止"改弱命题"的重复防线。

设计意图：第 1 条针对的失败是"重构时顺手把陈述改了"，这类改动在 diff 里很小，却改变命题；第 3 条的"公理依赖集合不变"比"不用 sorry"更强：重构前后各跑一次 `#print axioms`，输出应当完全一致，这是重构没有夹带私货的机器可查证据。

**参数选择。** 下表是笔者的经验建议而非定论：temperature 的实际效果随模型、解码实现与提示词而变，数字只用于建立起点。各参数的准确名称与取值范围以所用服务商的当期文档为准。

上表最值得强调的一行是 tactic 补全：它与其他三类任务的方向相反，要的是"多样且敢于尝试"的候选，而不是一个安全的答案。这也是 10.6.3 里"先给采样预算（pass@32 起步）"的同一逻辑在提示词层面的对应物。

对照方法上，一种可以自行执行的检验是：从 ProofNet 或 miniF2F 固定抽取 20 条任务（记录抽题规则以便复现），对每个温度档各跑 3 次，统计"内核通过率"与"幻觉常量名个数"（即建议的 `#check` 清单中不存在的名字数）两个指标，做配对比较。样本量只够看量级差异，不够下统计结论；若两种温度的差异落在抽题波动之内，就承认这个问题在自己的设置上没有定论。

**结果校验：一切以内核为准。** 无论哪类任务、哪个参数档，模型的输出在送进内核之前都只是"候选文本"。判定只有两个来源：`lake build`（或 `lake env lean 文件名`）通过，以及 `#print axioms` 的输出不含 `sorryAx` 与自定义公理。模型的自评、置信度、以及"我确认这段代码可以编译"之类的表述，都不算数，10.9.7 记录的那次静默失败，正是在用自评代替内核时漏掉的。

下面是一段笔者与模型的对话节选，演示"报错 → 追问 → 修复"的迭代形态。对话内容为笔者按当时的实际交互整理的示例，措辞经过压缩，报错文本为逐字粘贴的部分保留原样：


### 10.8.12 手把手走查：把 $|x+y| \le |x| + |y|$ 从零形式化

这一节把 10.7.7 流水线在一个最小的命题上完整走一遍。选它是为了避开测度论（纯代数命题，不牵扯可测性），同时保留绝对值这个"非线性"障碍，它恰好能演示自动化 tactic 的能力边界。除标注"编译失败"的讲解用代码块外，其余代码可保存为单个文件编译；凡笔者不能确认在当前 Mathlib 版本必然存在的名字，都在注释中注明"以 Mathlib 当前版本为准"。

**第一步：写陈述。**

```lean
import Mathlib

-- 陈述先行，证明用 sorry 占位。这一步能编译，但带 warning，
-- 且 #print axioms 会显示 sorryAx，这是开发期的正常状态。
theorem abs_add_le (x y : ℝ) : |x + y| ≤ |x| + |y| := by
  sorry
```

核对陈述是否等价于原命题：原命题读作"对任意实数 $x, y$，$|x+y| \le |x| + |y|$"。代码里 `theorem abs_add_le (x y : ℝ) : ...` 的绑定参数写法与 `theorem abs_add_le : ∀ x y : ℝ, ...` 在 Lean 中是同一个命题（绑定参数就是全称量词的语法糖），两种写法任选其一即可；需要留意的只有一点，`(x y : ℝ)` 是显式参数，`{x y : ℝ}` 是隐式参数，两者命题相同但使用方式不同，建议初学阶段一律用显式。本命题只含全称量词，没有量词顺序问题；统计命题常见的 $\forall\exists$ 顺序陷阱此处不出现，那类问题的系统讨论见 11.3.2。

**第二步：让 AI 起草。** 用 10.8.11 模板二，把 Goals 面板状态（`⊢ |x + y| ≤ |x| + |y|`）贴过去。模型返回的第一版草稿是：

```lean
-- AI 草稿一（编译失败，保留原样用于讲解）：
theorem abs_add_le (x y : ℝ) : |x + y| ≤ |x| + |y| := by
  have h : x + y ≤ |x| + |y| := by
    linarith [le_abs_self x, le_abs_self y]
  linarith
  -- 报错样式：linarith failed / unsolved goals
  --          ⊢ |x + y| ≤ |x| + |y|
```

**第三步：核对报错、判断问题所在。** 第一行 `have` 是成立的：`le_abs_self x : x ≤ |x|`（该名字以 Mathlib 当前版本为准），`linarith` 用 $x \le |x|$ 与 $y \le |y|$ 两条事实确实能闭合 $x + y \le |x| + |y|$。失败的是最后一行：上下文里没有任何一条把 $|x+y|$ 与 $x+y$ 联系起来的事实，`linarith` 只做线性算术，它把 $|x+y|$ 当成一个与 $x+y$ 毫无关系的原子变量，于是无解。诊断结论：缺的不是"更强的算术"，而是一条**关于绝对值的库引理**。

**第四步：补 tactic，两条路线。**

```lean
import Mathlib

-- 路线 A：手工两步。教学价值在于看见绝对值不等式拆成两条线性不等式。
-- abs_le 在 Mathlib 中的陈述形如：|a| ≤ b ↔ -b ≤ a ∧ a ≤ b
theorem abs_add_manual (x y : ℝ) : |x + y| ≤ |x| + |y| := by
  rw [abs_le]                        -- 目标变为两条不等式的合取
  constructor                        -- 拆出两个子目标
  · -- 子目标 1：-(|x| + |y|) ≤ x + y
    have h1 : -|x| ≤ x := neg_abs_le x   -- 名字以 Mathlib 当前版本为准
    have h2 : -|y| ≤ y := neg_abs_le y
    linarith
  · -- 子目标 2：x + y ≤ |x| + |y|
    have h1 : x ≤ |x| := le_abs_self x
    have h2 : y ≤ |y| := le_abs_self y
    linarith

-- 路线 B：库定理一步。这正是 exact? 能检索到的答案。
-- abs_add 的签名形如：abs_add (x y : α) : |x + y| ≤ |x| + |y|，
-- 对线性有序加法交换群一般成立，ℝ 有对应实例。
theorem abs_add_lib (x y : ℝ) : |x + y| ≤ |x| + |y| := by
  exact abs_add x y
```

**第五步：常见报错与修复。** 这一小段代码在实际操作中最容易撞上四类报错，成因与处理整理如下：

| 报错 | 触发写法 | 成因 | 处理 |
|---|---|---|---|
| `rw [abs_le]` 报 rewrite failed | 目标写成 `|x| + |y| ≥ |x + y|`（方向反了） | `abs_le` 的模式是 `|?a| ≤ ?b`，≥ 方向匹配不上 | 先确认目标方向；或用 `abs_le.mp` 从证明项一侧构造 |
| `constructor` 报 no constructor applicable | 在 `rw` 没生效或目标已闭合时误用 | 目标不是合取或存在 | 先看 Goals 面板的真实形状，再选拆分 tactic |
| `linarith` 单独使用失败 | 不写两个 `have` 直接 linarith | 上下文缺 $x \le |x|$ 这类原料 | 缺哪条补哪条；`linarith` 不会自己去找库引理 |
| unknown identifier `neg_abs_le` | 版本差异或拼写 | 名字随版本变动 | 按 10.8.5 的检索链：`#check` 全名 → Loogle → 本地 `rg` |

`neg_abs_le` 与 `le_abs_self` 这两个名字在笔者核对过的 Mathlib 版本中存在，但按 10.8.8 的经验，版本漂移后这类短名字是最先出问题的；若报 unknown identifier，用 Loogle 按结论形状（`-|?a| ≤ ?a`）检索是最快的替代路径。

**第六步：`#print axioms` 检查。**

```lean
-- 编译通过后，核对两条路线的公理依赖
#print axioms abs_add_manual
#print axioms abs_add_lib
-- 期望输出：两条均 does not depend on any axioms
-- 若输出含 sorryAx，说明某处还有占位符没清掉
-- 若输出含自定义公理名，说明引入了不可证的出发点，交付前必须清除
```

**第七步：反思。** 这次走查花了笔者约一小时，其中真正花在"证明"上的不足十分钟，其余在检索 `abs_le` 与 `neg_abs_le` 的名字、确认 `rw [abs_le]` 之后目标的真实形状。两条路线的对照有一点方法论意味：路线 B 一行就闭合了目标，但路线 A 的价值在于暴露了不等式的结构（绝对值不等式必然拆成上下两条），这个结构在处理 $|x+y| \le |x| + |y|$ 的加强版（例如带系数、带条件）时仍然是起点。库里有现成结论时当然优先用库，但读过一次手工拆解，之后遇到 `exact?` 失灵的情形才知道往哪个方向构造。

### 10.8.13 练习记录：第一次用 Lean 证明一个小定理

前面的叙述都是事后整理过的。这一节保留一份原始形态的记录：笔者第一次独立用 Lean 证明"一个小定理"的完整过程，目标是 $(1 : \mathbb{N}) + 1 = 2$ 与它的实数版本，外加当晚顺手试的一条实数不等式。文中标注"编译失败"的代码块只用于展示报错，不必也不应粘进同一文件；当晚真正留在编辑器里的，是文末的最终版本。记录的目的是给读者一个对"上手时的真实体验"的预期，第一个晚上，报错的条数远多于成功的条数，而且每条报错单看都令人沮丧，连起来看才是学习曲线。

**目标一：$(1 : \mathbb{N}) + 1 = 2$。**

```lean
-- 第一晚写的第一条：
example : 1 + 1 = 2 := by rfl
-- 通过。字面量按 Nat 解释，Nat 加法在内核里可计算，rfl 直接闭合。

-- 同一条的 tactic 版本（norm_num 不在 Lean 核心里，需要 import
-- Batteries/Std 或 Mathlib；若无 import，保留 rfl 版本即可）：
import Mathlib
example : 1 + 1 = 2 := by norm_num
```

然后是当晚第一个弯路。装好 Mathlib 之后，笔者想把同一句话"升级"成实数版本，仍然用 `rfl`：

```lean
-- 弯路一（编译失败）：
example : (1 : ℝ) + 1 = 2 := by rfl
-- 报错样式：rfl tactic failed / 两边不是定义相等的（表述随版本而异）
```

失败原因过了一阵才想通：`rfl` 只处理**定义相等**，而"定义相等"取决于类型是怎么构造的。$\mathbb{N}$ 的加法是内核可直接计算的结构递归；$\mathbb{R}$ 在 Mathlib 中是柯西序列的商，加法不可计算，内核无路可走。修复是把计算交给专门的 tactic：

```lean
-- 修复后：
example : (1 : ℝ) + 1 = 2 := by norm_num

-- 有理数是构造上可计算的，rfl 在部分版本上可行；若失败换 norm_num：
example : (1 : ℚ) + 1 = 2 := by norm_num
```

当晚的教训记为：`rfl` 失败不等于命题难，先问"这个类型的运算在内核里可不可计算"，再考虑换 tactic。

**目标一附带的弯路：tactic 与 term 混用。** 想当然地写下：

```lean
-- 弯路二（编译失败）：
example : (1 : ℕ) + 1 = 2 := by
  exact 2
  -- 报错样式：type mismatch，term 2 has type ℕ : Type
  --          but is expected to have type (1 + 1 = 2) : Prop
```

报错信息其实已经把话说尽了：`2` 是数据（`Type` 侧），目标是命题（`Prop` 侧），两者之间隔着 10.1.2 讲的那层对应关系，要给命题提供的是**证明项**（例如 `rfl` 本身），不是命题里出现的数值。这次失败反而把 10.1.2 的表格变成了肌肉记忆。

**目标二：一条实数不等式。** 顺手试 $2ab \le a^2 + b^2$，这里集中了当晚剩下的一半弯路：

```lean
-- 弯路三：想用 linarith，失败。
theorem two_ab_le_sq (a b : ℝ) : 2 * a * b ≤ a ^ 2 + b ^ 2 := by
  linarith
  -- 报错样式：linarith failed
```

`linarith` 只做线性算术，$a \cdot b$ 与 $a^2$ 这类二次项对它是原子，约束系统无解。这一失败的正面价值是：它划清了 `linarith` 与 `nlinarith` 的分工，比任何教程里的文字描述都记得牢。

```lean
-- 弯路四：括号问题（编译失败）。
theorem two_ab_le_sq (a b : ℝ) : 2 * a * b ≤ a ^ 2 + b ^ 2 := by
  nlinarith [sq_nonneg a - b]
  -- 报错样式：application type mismatch，argument b
  --          has type ℝ : Type but is expected to have type Prop : Type

-- 修复：给 sq_nonneg 补上括号。函数应用优先级高于减法，
-- sq_nonneg a - b 被解析成 (sq_nonneg a) - b，即"命题减实数"。
theorem two_ab_le_sq' (a b : ℝ) : 2 * a * b ≤ a ^ 2 + b ^ 2 := by
  nlinarith [sq_nonneg (a - b)]
```

弯路四的报错初看令人困惑（`b` 明明是 `ℝ`，怎么会"期望是 `Prop`"），把表达式按解析结果重新读一遍才明白：`sq_nonneg` 只吃到了 `a`。这类报错的处理经验是：看到 "has type X but is expected to have type Y"，先别怀疑命题，先把出错表达式按运算符优先级手工重新切分一遍。

**弯路五：Mathlib 库函数找不到。** 笔者最初以为 Mathlib 里应该有一条名字就叫 "one plus one" 的定理，用自然语言在文档站里搜，一无所获。后来按 10.4.2 的检索链改用 `exact?`：

```lean
-- exact? 的用法：目标写好，把 tactic 位置留给它
example : (1 : ℝ) + 1 = 2 := by exact?
-- InfoView 会给出候选建议；候选内容随版本不同，
-- 笔者当时拿到的是一条可直接闭合目标的建议（替换掉 exact? 即可）
```

这件事让 10.4.1 的那句提醒（Mathlib 的命名描述结论而非俗称）从文字变成了体验：库里不是没有 $1+1=2$，而是它以某个描述代数性质的名字存在着，按俗称检索注定找不到。

**当晚的最终版本与公理检查。**

```lean
-- 练习的最终版本（三条全部通过编译）
theorem one_plus_one_nat : (1 : ℕ) + 1 = 2 := by rfl

theorem one_plus_one_real : (1 : ℝ) + 1 = 2 := by norm_num

theorem two_ab_le (a b : ℝ) : 2 * a * b ≤ a ^ 2 + b ^ 2 := by
  nlinarith [sq_nonneg (a - b)]

#print axioms one_plus_one_nat    -- 期望：does not depend on any axioms
#print axioms one_plus_one_real   -- 同上
#print axioms two_ab_le           -- 同上
```

**当晚的小结**，按时间顺序记了五条。其一，报错是常态而非异常，第一晚的通过率大约是五分之一，且没有一条报错最终没被解决，内核的拒绝永远给出位置与类型信息，这比自然语言审稿意见的"此处不妥"友好得多。其二，每个失败的 tactic 都在教边界：`rfl` 教了可计算性，`linarith` 教了线性与非线性，`exact 2` 教了 `Prop` 与 `Type`。其三，检索要早做，晚做的话会在一个名字上空耗半小时。其四，类型标注宁多勿少，`(1 : ℝ)` 这类标注看似啰嗦，省掉之后排查歧义的时间远多于写它的时间。其五，把每条报错和最终解法记进笔记，第二周回看时这份笔记的价值超过了当时读过的任何教程章节。这份记录的方法部分后来沉淀成了 10.8.4 的读报错顺序与 10.8.11 的模板三。

## 10.9 失败模式与瓶颈

### 10.9.1 形式化代价

形式化仍需要数倍于撰写自然语言证明的工作量。陶哲轩对自己一篇 Maclaurin 型不等式论文的形式化记录是：约 100 小时，分散在一个月内完成，比用 LaTeX 写这篇论文慢约 20 倍。其公开的经验中有一条我们反复引用：难的不是数学上有趣的部分，而是那些"显然"的步骤，他曾为证明一个涉及自然数减法的显然等式耗去数小时，原因是 Lean 在 $\mathbb{N}$ 上定义的减法实为 $(a, b) \mapsto \max(a - b, 0)$。他给出的处理办法是尽早把式子改写成不使用自然数减法（例如移到 $\mathbb{Z}$ 或 $\mathbb{R}$ 上）的形式，我们在自己的尝试里照做后确实省了不少时间。

另一位学习者的判断是：形式化的复杂度中，约 80% 是固有的（数学严谨性本身就要求这些），20% 来自 Lean 与 Mathlib 的偶然设计。这个比例意味着很难指望工具再变简单多少，大部分代价来自数学本身。

我们自己记录过一次小样本的时间分配，量级与上述比例大致吻合：形式化一条约一页的教科书引理，前后花了大约 15 小时，其中约 3 小时花在检索定理名与读库定义上，约 2 小时花在环境与缓存上，其余都在处理前件与拆证明步骤。这条记录只有一次，不能当作规律，但它提示了一件可以提前安排的事：把"找名字"和"搭环境"的时间单独预留出来，会比把它们算进证明时间里更接近实际。

与统计学者熟悉的工作对照一下：形式化的成本结构更像"写一篇需要逐条核对假设的审稿意见"，而不像"再推导一遍"。推导的部分往往很快，核对的部分很慢。

### 10.9.2 库覆盖不足

Mathlib 的覆盖并非均衡。有系统在文档中标明了覆盖薄弱的领域：拓扑、概率、线性代数，恰好是统计学最依赖的三块。实践中表现为：一条在教科书中一句话引用的引理，在库中可能根本不存在，需要自行形式化；或者存在但采用了不完全匹配的假设版本，需要额外处理适配。

对统计学者而言，这一问题的缓解方式是利用已有项目（AI4SLT 的约 3 万行代码、ATLAS 中《High Dimensional Statistics》的 31,715 行）作为基础设施，而非从零构造。我们在自己选题时的做法是先花半天检索这两处，再决定这条引理值不值得形式化。

### 10.9.3 定义选择的歧义与"证明通过但命题写错"

已在 10.1.5 与 10.7.3 讨论。此处补充其后果的严重性：这类错误不会触发任何警告，不会产生任何日志，在只统计编译通过率的评测中会被完全吸收。它是形式化验证唯一无法自动防御的失败模式，也是我们倾向于由研究者亲自守住的边界。

### 10.9.4 统计与概率定理的特殊困难

第一，**测度论基础重**。一条集中不等式的形式化，需要可测空间、测度、Lebesgue 积分、可积性、$L^p$ 空间、几乎处处相等等一整套前置结构。这些结构在 Mathlib 中已有，但掌握它们的使用方式需要相当的学习量。

第二，**极限定理的证明长**。大数定律与中心极限定理的自然语言证明本身就有相当篇幅，形式化后还要把三角阵、截尾、特征函数或 Lindeberg 交换等步骤全部展开。已有的形式化经验表明，这类工作的量级远超竞赛题。

第三，**隐含条件的密度高**。AI4SLT 的报告指出，形式化过程暴露了标准统计学习理论教材中省略的可测性、可积性与拓扑条件。这些条件在自然语言文献中被默认为"显然成立"，而在形式系统中必须逐条给出并证明。

第四，**渐近陈述的多重量化**。$o_p(1)$、$O_p(1)$、一致收敛、对某族分布一致成立，都涉及多层量词与滤子层面的表述（如 `Tendsto u atTop (𝓝 l)`）。量词顺序一旦写错，命题就变了，而机器不会提示。我们在写这类陈述时倾向于先把量词逐字读一遍（"对任意 epsilon，存在 N，对任意 n 大于等于 N"），再检查它与原命题的读法是否一致。

### 10.9.5 更上层的风险：无人阅读的"证明"

形式化验证消除了证明内部的错误，但没有消除对结果的误读。已有的大规模实验数据值得正视：某系统扫描 700 个 Erdős 开放问题后，在约 200 个可判定的候选解中，68.5% 有根本性错误，31.5% 形式上成立，但只有 6.5% 真正回答了 Erdős 原本提出的问题。陶哲轩给出的口径是：AI 在 Erdős 问题上的成功率约 1–2%，且集中在容易的题目上；353 题中只解出 9 题。

另一条观察来自 Erdős 问题网站的维护者：越来越多 100–200 页的论文被发布出来，其作者声明"我让 AI 生成证明、检查证明并撰写论文"，但没有人类读过它。形式化验证与人类理解是两件事：机器可验证不等于人类可理解，更不等于结论回答了原问题。

### 10.9.6 其他工程性瓶颈

| 瓶颈 | 表现 | 现有缓解方式 |
|---|---|---|
| 数据稀缺 | 特定领域（概率、统计）的形式化样本远少于竞赛数学 | 用领域内库（Probability / MeasureTheory）做定向微调；用教材自动形式化扩充语料 |
| 搜索爆炸 | tactic 序列的分支因子大，深度证明的搜索空间呈指数增长 | 检索增强（ReProver）、证明规划（先给 proof plan 再给代码）、self-correction |
| 编译开销 | 每次候选都要调用 Lean 编译，是闭环中最慢的环节 | 批量并行尝试（`lean_multi_attempt`）、预编译缓存（`lake exe cache get`） |
| 类型错误与自动化失败 | `simp`/`nlinarith` 失败时的报错对初学者不友好 | 结构化 tactic 逐步拆解目标；`#check` 与 `guard_target` 定位 |
| 自动化可信度 | 强自动化 tactic 可能静默改变目标 | 关键步骤禁用自动化，手工核验；`#print axioms` |
| 环境可复现性 | Mathlib 与 toolchain 更新快，半年后无法重建当时的判定 | 钉住 `lean-toolchain` 与 `lake-manifest.json`；记录 mathlib commit |


## 本章小结

- 命题即类型（Curry–Howard 同构）把命题对应于类型、证明对应于程序、推理对应于函数应用，这是形式化验证的理论基础；tactic 只是构造证明项的交互手段。
- 证明助手的 TCB 只包含内核与显式引入的公理；tactic、简化器、检索器、语言模型都不在 TCB 内，它们的错误只会导致内核拒绝，不会导致错误定理被接受。
- "通过编译即零幻觉"的严格含义限于引用不幻觉、不跳步、不可篡改三条；内核不判断命题是否忠实于研究者意图，"证明通过但命题写错"是唯一无法自动防御的失败模式。
- 形式化证明保证"在给定定义与假设下结论成立"，与统计学中模型设定错误的处境同构；收敛模式、量词顺序、可测性与可积性条件是统计学命题最易出错的三处。
- Lean 4 凭借现代语法、强元编程与 Mathlib4（超 150 万行）成为 AI 与数学结合的主流载体；Coq/Rocq 强在程序验证，Isabelle/HOL 的 Isar 可读性最好，Metamath 验证器极简，HOL Light 的分析与测度论积累深厚。
- miniF2F 上形式化陈述已知时的 SOTA 为 88.9%–92.2%，而端到端准确率约 36%；落差说明形式化环节是主要瓶颈，且其失败是静默失败。
- LeanDojo 把数据抽取、程序化交互与检索增强基线标准化，使"训练自己的证明器"成为可复现的工程流程；复现 ReProver 约需 1 GPU 周。
- 自动形式化的正确性只能靠往返翻译、双盲翻译、实例化数值检查与人工逐行核对的组合来判断，其中人工核对不可替代；对统计命题，实例化数值检查是额外可用的手段。
- 形式化的代价约为自然语言证明的十倍量级，其中大部分来自数学固有的严谨性要求；概率与统计类定理因测度论基础重、渐近陈述量词复杂而成本更高。
- 上手路径上，我们自己的经验是：先玩游戏与做入门练习建立直觉，再装本地环境，先只写陈述再写证明；报错与检索是后续工作中耗时最多的两项，值得专门练。
- 把 AI 接入形式化工作时，四类任务（陈述翻译、tactic 补全、报错解释、证明重构）各有对应的提示词模板与参数档：翻译与诊断用低 temperature 保稳定，tactic 生成用高采样数保覆盖；一切输出在通过 `lake build` 与 `#print axioms` 检查之前都只是候选文本，模型自评不作为判定依据。
- 陈述忠实性的核对位于流水线中部而非末尾（翻译之后、证明之前），因为形式化环节的失败是静默失败；实例化数值检查、往返翻译、人工逐行核对三者按成本从低到高依次使用。
- 第一次上手体验的合理预期是：报错条数远多于成功条数，每个失败的 tactic 都在划定一条能力边界，且这些报错最终都有定位路径可循（10.8.13 的练习记录）。
