# 第9章 部署上线与持续运营


## 本章导读

前八章解决的是"得到一个能用的模型或工作流"。从这一章开始，问题变成"让它在真实环境里长期稳定地提供结果"。这个转变带来一组新的约束：请求是并发到达的，延迟有尾部分布，显卡显存有限，模型会更新，数据分布会漂移，成本按 token 累积。这些问题中没有一个是靠调提示词能解决的，它们的共同特点是**可度量、可变差、需要持续观察**，这是统计学熟悉的内容。

本章按"引擎—压缩—架构—监控—评估—迭代—成本—安全—案例"的顺序展开。9.1 比较 vLLM、TensorRT-LLM、SGLang、Ollama、llama.cpp、TGI、LM Studio 等推理引擎并给出选型决策树；9.2 讨论量化与压缩，重点不是如何量化，而是**如何评估量化后的模型在统计任务上是否仍然可用**；9.3 讲服务架构的核心机制（continuous batching、前缀缓存、KV 缓存管理、张量并行、网关与扩缩容）；9.4 给出监控指标清单，并指出这些指标本质上是过程质量监控，与统计过程控制（SPC）的控制图同源；9.5 是本章统计含量最高的一节，讨论上线后 A/B 测试的完整统计设计，随机化单元、样本量与功效、序贯检验与 alpha spending、多重比较校正、新奇效应；9.6 处理反馈闭环与灰度发布；9.7 讨论多模型路由与成本优化；9.8 讨论安全与权限；9.9 给出从权重到 API 端点的完整操作案例。

本章与第 8 章的分工是：第 8 章是研究者个人与课题组层面的工具链，本章是服务层面的工程与统计方法。9.5 的 A/B 测试与 8.13 的实验设计使用同一套统计工具（因子设计、功效分析、区组、多重比较校正），区别在于随机化单元从"配置组合"变成"用户请求"，且存在溢出效应与时间异质性这两个额外的干扰。9.4 的控制图思想与第 17 章的审计监控相接。本章的价格、吞吐与显存数字都随硬件与版本快速变化，凡给出具体数值处均标注为示例测算，实际部署应以实测为准。

## 9.1 推理引擎选型

### 9.1.1 推理的两个阶段与四个指标

自回归解码的一次请求分为两个阶段。**预填充**（prefill）阶段并行处理整个输入提示，计算所有位置的键与值并写入 KV 缓存，这一阶段是计算密集的；**解码**（decode）阶段逐个生成 token，每一步只算一个位置但需要读取全部历史 KV 缓存，这一阶段是带宽密集的。两阶段的瓶颈不同，因此优化手段也不同：prefill 靠算子融合与并行，decode 靠批处理与缓存管理。

评价一个推理服务的四个核心指标是：

| 指标 | 定义 | 受什么影响 | 典型关注方 |
|------|------|------------|------------|
| TTFT（首 token 延迟） | 从请求到达到收到第一个 token 的时间 | prefill 速度、排队时间、批处理策略 | 交互式使用者 |
| TPOT / ITL（每 token 间隔） | 相邻输出 token 之间的间隔 | decode 速度、批处理规模、KV 读取带宽 | 流式输出体验 |
| 吞吐 | 单位时间完成的请求数或输出 token 数 | 批处理规模、显存、调度策略 | 批量评估与离线任务 |
| 并发能力 | 在延迟约束下能同时服务多少请求 | 显存中 KV 缓存的可用容量 | 服务端容量规划 |

四者之间存在明确的取舍：增大批处理规模提升吞吐，但会拉长单个请求的排队与解码间隔；限制批大小保住尾延迟，则单位成本上升。一条有用的经验关系是把吞吐—延迟曲线画出来，在曲线的"拐点"处选择工作点，拐点之后吞吐增长趋缓而延迟急剧上升。

### 9.1.4 选型决策树

选型的第一步不是比较引擎，而是回答三个前置问题。

1. **数据能否离开本地。** 若处理未发表数据或受监管数据，只能在本地或私有云部署，候选收敛为 Ollama、llama.cpp、vLLM/TGI/SGLang 自建。
2. **负载形态是什么。** 单人交互（笔记本、无 GPU）选 Ollama 或 llama.cpp；批量离线评估（成千上万条 prompt）选 vLLM 或 SGLang；在线高并发服务选 vLLM、TensorRT-LLM 或 TGI。
3. **谁在维护。** 无人专职运维的课题组应选容器化开箱可用的方案（Ollama、TGI、vLLM 官方镜像）；有工程支持时再考虑 TensorRT-LLM 这类需要编译与调优的方案。

## 9.2 量化与压缩

### 9.2.1 数值格式与量化映射

模型权重与激活在推理时以某种数值格式存储。常见的格式包括 FP16（半精度浮点）、BF16（脑浮点，指数位更多、动态范围更大）、FP8（两种变体：E4M3 精度较高用于权重与激活，E5M2 动态范围较大用于梯度），以及整型的 INT8、INT4。FP8 格式的规范见 arXiv:2209.05433。

均匀量化的映射可以写为

$$\hat W = s \cdot \mathrm{clip}\!\left(\mathrm{round}\!\left(\frac{W}{s}\right),\ -2^{b-1},\ 2^{b-1}-1\right), \qquad s = \frac{2 z_p \sigma}{2^b - 1}$$

其中 $b$ 是位宽，$s$ 是缩放因子（步长），$z_p$ 是截断阈值（以权重标准差 $\sigma$ 为单位），截断区间为 $[-z_p\sigma, z_p\sigma]$。按权重矩阵、按通道、按分组采用不同的 $s$ 是量化精度的主要调节手段：分组越细，$s$ 越贴合局部尺度，误差越小，但元数据开销越大。

### 9.2.2 量化误差的分解

量化误差来自两个来源：**截断**（clip）与**舍入**（round）。设权重服从 $W \sim N(0, \sigma^2)$，在 $\pm z_p\sigma$ 处截断后作步长为 $s$ 的均匀量化，总均方误差可分解为

$$\mathrm{MSE}(z_p, b) = \underbrace{2\sigma^2\Big[Q(z_p)\,(1 + z_p^2) - z_p\,\phi(z_p)\Big]}_{\text{截断误差}} \;+\; \underbrace{\frac{s^2}{12}}_{\text{舍入误差}}$$

其中 $\phi(z) = \frac{1}{\sqrt{2\pi}}e^{-z^2/2}$ 是标准正态密度，$Q(z_p) = 1 - \Phi(z_p)$ 是上尾概率。截断项中的 $-2\sigma^2 z_p \phi(z_p) = -\frac{2 z_p}{\sqrt{2\pi}}e^{-z_p^2/2}\,\sigma^2$ 是截断区"重心偏移"带来的修正项；舍入项 $s^2/12$ 来自舍入误差在步长区间内近似均匀分布的方差。

把 $s = 2z_p\sigma/(2^b - 1)$ 代入，得到相对误差

$$\frac{\mathrm{MSE}}{\sigma^2} = 2\Big[Q(z_p)(1+z_p^2) - z_p\phi(z_p)\Big] + \frac{4 z_p^2}{12\,(2^b-1)^2}$$

两项随 $z_p$ 的变化方向相反：$z_p$ 增大则截断误差减小、但步长变大导致舍入误差增大。因此存在一个最优阈值 $z_p^\ast$，使两项之和最小，这正是各类量化算法中"校准"（calibration）环节在做的事：搜索最优的截断比例或等效的缩放因子。位宽 $b$ 越小，第二项越大，$z_p^\ast$ 越小，说明低比特量化必须更激进地截断，这也解释了为什么 INT4 比 INT8 对异常值更敏感。

误差如何传播到输出同样可以给出一阶刻画。对线性层 $y = W x$，若各权重的量化误差独立、方差为 $\sigma_q^2$，则

$$\mathrm{Var}(y_i - \hat y_i) = \|x\|^2\,\sigma_q^2$$

即输出扰动随输入范数与权重数量放大，并在多层堆叠后逐层累积。这一结论有两个实际含义：一是激活中存在极端离群通道时（Transformer 中常见），误差会被显著放大，这也是 SmoothQuant 一类方法要先处理激活离群的原因；二是长序列、深层模型对量化更敏感，评估时应覆盖长输入场景。

### 9.2.3 主要的后训练量化方法

| 方法 | 核心思想 | 位宽 | 是否需要校准集 | 代表实现 | 主要局限 |
|------|----------|------|----------------|----------|----------|
| 逐张量/逐通道 PTQ | 按统计量直接定缩放因子 | INT8 | 少量 | TensorRT、Optimum | 低比特下精度损失明显 |
| LLM.int8() | 把激活中的离群维度拆出来做 FP16 计算，其余走 INT8 | INT8 | 不需要 | bitsandbytes（arXiv:2208.07339） | 离群维度多时加速比下降 |
| GPTQ | 逐列量化，用二阶（Hessian）信息补偿已量化权重引入的误差 | INT4/INT3 | 需要 | AutoGPTQ（arXiv:2210.17323） | 校准集选择影响大，低比特下易崩 |
| AWQ | 激活感知：按激活幅度为权重通道分配等效缩放，保护显著权重 | INT4 | 需要 | AutoAWQ（arXiv:2306.00978） | 需要遍历若干缩放超参 |
| SmoothQuant | 把激活的离群难度迁移到权重上，使激活易量化 | INT8 | 需要 | 已被多引擎集成（arXiv:2211.10438） | 迁移强度 $\alpha$ 需调 |
| QLoRA / NF4 | 4 位正态浮点加双重量化，配合 LoRA 微调 | NF4 | 训练时 | bitsandbytes、Unsloth（arXiv:2305.14314） | 属微调方案，推理需反量化或专用内核 |
| GGUF k-quants（如 Q4_K_M） | 按块分组量化，且块内不同重要性部分用不同位宽 | 2–8 位混合 | 转换时 | llama.cpp | 格式与 llama.cpp 生态绑定 |

选择时的一个实用判据：**先试最高精度、再看是否够用**。INT8 与 FP8 在多数统计任务上的损失通常可以接受，INT4 需要逐任务验证，INT4 以下（3 位、2 位）应视为研究性方案，仅在显存极度受限且评估充分的场景下使用。

### 9.2.4 校准集的选择

凡是需要校准集的方法，校准集的性质直接决定缩放因子，因此校准集是一项统计设计问题而不是随手抓一批数据。

三条原则。一是**代表性**：校准数据应当与实际输入的 token 分布、长度分布、领域词汇一致；用通用网页语料去校准一个处理病历文本的模型，缩放因子会系统性偏离。二是**规模适中**：校准集通常只需数百到数千条样本即可估计出稳定的缩放因子，继续增大收益递减；更重要的是覆盖度，罕见但重要的输入模式（长表格、大量数字、公式）必须在校准集中出现。三是**分布漂移监控**：服务上线后输入分布会变化，缩放因子是在旧分布上估出的，应当定期重估。

一个常被忽略的检查是**换一批校准集重测**：若换集后评估指标波动明显，说明量化参数过拟合到特定校准集，量化方案的稳健性不足。

### 9.2.5 量化后模型在统计任务上的评估

量化方案的公开评测通常以 MMLU、常识问答等通用基准的分值下降幅度为指标。对统计研究者而言，这类指标**不足以支持决策**，原因有三：一是这些基准多为选择题，对数值精度极不敏感，模型只要排序正确即得满分；二是它们不覆盖长链数值推理，而量化误差正是在长链中累积；三是它们不检验输出的统计性质（校准性、区间覆盖率）。

建议按下表的五个维度评估，并采用**配对比较**设计：同一条输入、同一随机种子，分别跑基线（FP16 或 BF16）与量化模型，逐条配对。

| 维度 | 具体指标 | 计算方法 | 判定标准（示例） |
|------|----------|----------|------------------|
| 数值精度 | 相对误差的中位数与 95 分位 | $\lvert \hat y_q - y_b \rvert / \lvert y_b \rvert$ | 中位数 < 1e-3，95 分位 < 1e-2 |
| 区间覆盖率 | 置信区间覆盖率 | 重复 $n$ 次，统计真值落入报告区间的比例 | 与名义 95% 的偏差不超过 2 个百分点 |
| 检验性质 | I 类错误率与功效 | 在零效应数据上重复，统计"报告显著"的比例 | 与 $\alpha$ 的偏差在抽样误差内 |
| 结构化输出 | 格式合规率（JSON 可解析率、字段齐全率） | 机械校验 | 不低于基线的 99% |
| 长链稳定性 | 长序列上与基线的一致性率 | 序列越长，一致性越低，观察拐点 | 拐点不早于业务序列长度 |

覆盖率与 I 类错误率的评估需要重复实验，样本量必须在实验前算清。以覆盖率为例：欲检出覆盖率从 0.95 降到 0.93，取 $\alpha = 0.05$、功效 0.8，两比例比较所需样本量为

$$n = \frac{\big(z_{0.975}\sqrt{p_0(1-p_0)} + z_{0.8}\sqrt{p_1(1-p_1)}\big)^2}{(p_0-p_1)^2} \approx 1030$$

即需要约 1030 次独立重复。若只做 100 次重复，能检出的覆盖率下降约为 6 个百分点，远大于关心的最小差异，这正是"量化没有显著影响"这类结论常常不可信的原因：不是没有影响，而是样本量不足以检出。

二值指标（格式合规、是否显著）的配对比较应使用 McNemar 检验而非独立两样本检验。设 $b$ 为"基线成功、量化失败"的条数，$c$ 为"基线失败、量化成功"的条数，则

$$\chi^2 = \frac{(b - c)^2}{b + c}$$

在大样本下近似 $\chi^2_1$。McNemar 只利用不一致对，因此天然控制了输入难度这一混杂因素。

更进一步，若目标是**证明量化后不劣于基线**（而不是证明有差异），应使用等价性检验（TOST）：设定一个可接受的劣化边际 $\delta$，检验两个单侧假设 $H_{01}: \Delta \leq -\delta$ 与 $H_{02}: \Delta \geq \delta$，两个都拒绝时才可断定等价。这比"未发现显著差异"的结论强得多。

```python
# quant_eval.py ， 量化模型的配对评估骨架
import numpy as np
from scipy.stats import norm
from statsmodels.stats.contingency_tables import mcnemar

def coverage_test(x, alpha=0.05, power=0.80):
    """覆盖率与基线比例比较所需样本量"""
    p0, p1 = 0.95, x
    z_a, z_b = norm.ppf(1 - alpha/2), norm.ppf(power)
    return (z_a*np.sqrt(p0*(1-p0)) + z_b*np.sqrt(p1*(1-p1)))**2 / (p0 - p1)**2

def paired_binary_test(base_ok, quant_ok):
    """配对二值指标的 McNemar 检验"""
    b = int(np.sum((base_ok == 1) & (quant_ok == 0)))
    c = int(np.sum((base_ok == 0) & (quant_ok == 1)))
    res = mcnemar(np.array([[int(np.sum((base_ok==1)&(quant_ok==1))), b],
                            [c, int(np.sum((base_ok==0)&(quant_ok==0)))]]), exact=False)
    return {"discordant_b": b, "discordant_c": c, "pvalue": res.pvalue}

# 数值相对误差：报告分位数而非均值（分布重尾）
rel = np.abs(y_quant - y_base) / (np.abs(y_base) + 1e-12)
print("相对误差 中位数/P95：", np.median(rel), np.quantile(rel, 0.95))
```

评估协议的执行要点有四：固定随机种子与解码参数（温度设为 0 或固定种子以保证可复现）；每条输入独立跑基线而不复用缓存结果；报告分位数而非均值（相对误差分布重尾）；把失败案例按类型归档（算术错误、格式错误、指令遗忘），因为不同失败类型对应不同的补救手段。

**协议在合成任务上的最小模拟。** 上面代码骨架中依赖真实模型的部分无法在书里直接运行，但协议本身的逻辑可以用一个合成任务完整演练：把一个四层线性网络当作"模型前向计算"的载体，对权重做逐行对称 INT8 量化，然后在带噪特征上比较基线与量化模型的输出。这一模拟的统计解释是**测量误差模型**：量化后的输出等于真实输出加一个测量误差，协议要回答的是这个误差是否大到改变下游决策（分类标签、显著性判定、区间覆盖），而不是误差本身是否为零，零误差的量化并不存在。

```python
# quant_protocol_sim.py ， 量化评估协议的合成任务演练
import numpy as np
from scipy.stats import binomtest

rng = np.random.default_rng(2026)

# 合成"模型"：4 层线性网络（仅作量化误差传播的载体）
dims = [16, 64, 64, 32, 8]
Ws = [rng.normal(0, 1/np.sqrt(a), size=(a, b)) for a, b in zip(dims[:-1], dims[1:])]

def quantize_int8(W):
    """逐输出通道对称 INT8 量化，返回反量化权重"""
    s = np.abs(W).max(axis=1, keepdims=True) / 127.0
    s = np.where(s == 0, 1e-12, s)
    return np.clip(np.round(W / s), -127, 127) * s

def forward(x, weights):
    h = x
    for W in weights:
        h = np.tanh(h @ W)
    return h

Wq = [quantize_int8(W) for W in Ws]

# 合成分类任务：两个高斯类；真标签由 FP 基线在无噪特征上的输出定义
n_per = 3000
X = np.vstack([rng.normal(-0.5, 1.0, (n_per, 16)),
               rng.normal(+0.5, 1.0, (n_per, 16))])
y_label = (forward(X, Ws)[:, 0] > 0).astype(int)

# 带噪观测：比较两模型在噪声特征上的判别
Xn = X + rng.normal(0, 0.35, size=X.shape)
logit_b, logit_q = forward(Xn, Ws)[:, 0], forward(Xn, Wq)[:, 0]

# 协议第 1 项：数值一致性（相对误差分位数）
rel = np.abs(logit_q - logit_b) / np.maximum(np.abs(logit_b), 1e-6)
print(f"相对误差 中位数={np.median(rel):.5f}, P95={np.quantile(rel, 0.95):.5f}")
print(f"相关系数 = {np.corrcoef(logit_b, logit_q)[0, 1]:.5f}")

# 协议第 2 项：判别错误率（配对设计 + McNemar 不一致对）
pred_b, pred_q = (logit_b > 0).astype(int), (logit_q > 0).astype(int)
print(f"错误率: 基线={np.mean(pred_b != y_label):.4f}, 量化={np.mean(pred_q != y_label):.4f}")
b = int(((pred_b == y_label) & (pred_q != y_label)).sum())
c = int(((pred_b != y_label) & (pred_q == y_label)).sum())
print(f"不一致对 b={b}, c={c}, McNemar 精确 p={binomtest(b, b + c, 0.5).pvalue:.4f}")
```

输出（numpy 1.26.4、scipy 1.15.3）：

```text
相对误差 中位数=0.01506, P95=0.17644
相关系数 = 0.99988
错误率: 基线=0.1100, 量化=0.1103
不一致对 b=14, c=12, McNemar 精确 p=0.8450
```

三个读数各有含义。相对误差中位数约 1.5% 而 P95 达 18%，说明量化扰动集中在少数样本上，若只报告均值会得出"误差可忽略"的结论，这正是协议要求报告分位数的原因。错误率仅上升 0.3 个百分点，且不一致对 b=14 与 c=12 接近对称（p=0.845），在当前样本量下没有证据表明量化劣化有方向性；但按 9.2.5 的功效分析，6000 个样本只能检出约 3 个百分点以上的差异，"未检出"不等于"不存在"。判别结果尚且如此，对误差更敏感的区间覆盖率与 I 类错误率两项，模拟中无法直接构造，恰恰说明真实评估必须逐项落实而不能类推。

## 9.3 服务架构设计

### 9.3.1 请求生命周期

一次请求从到达到返回，依次经过以下环节：接入层鉴权与限速 → 网关路由与负载均衡 → 队列等待 → 调度器组批 → prefill → 逐步 decode → 流式回传 → 计量与日志。每一个环节都会贡献延迟，因此定位延迟问题时必须按环节分解，而不是只看端到端的平均值。

分解的含义可以用一个简单关系表达：端到端延迟 = 排队时间 + prefill 时间 + $n_{\text{out}} \times$ 单步 decode 时间 + 传输与序列化开销。首 token 延迟主要由前两项决定，总延迟主要由第三项决定。高负载下排队时间往往是尾延迟的主要来源，这一点常被误判为"模型变慢了"。

### 9.3.2 连续批处理

早期服务采用请求级批处理（request-level batching）：一批请求一起进、一起出，慢的请求拖住整批。连续批处理（continuous batching，也称 iteration-level scheduling）改为在**每次解码迭代**上重新组批：某个请求生成完毕就立刻离开批次并释放其 KV 缓存，新到达的请求立刻加入，无需等待。这一机制由 Orca（OSDI 2022）提出，现已成为 vLLM、TGI、TensorRT-LLM 等引擎的标配。

连续批处理的效果是吞吐显著提升而排队时间下降。它的代价是批次内请求的解码进度不一致，单步耗时由批次内最慢的请求决定（长上下文请求读取的 KV 更多），因此需要配合下一节的前缀缓存与下文的 KV 管理来控制长尾。

两种调度方式的差别可以用示意图表达（每个方块代表该次解码迭代内此请求在批中参与计算）：

```text
请求级批处理（request-level batching）：一批齐进齐出

  请求 A   █  █  █  █  █  █  █  █      A 最慢，决定了整批的
  请求 B   █  █  █  █  ·  ·  ·  ·      离开时刻；B、C 已完成
  请求 C   █  █  █  █  ·  ·  ·  ·      却仍占用调度与显存
                                     （· = 已完成但滞留批内）
                └──────── 一起出批 ────────┘

连续批处理（continuous batching）：逐迭代重组批

  迭代       1    2    3    4    5    6    7    8
  请求 A     █    █    █    █    █    █    █    █
  请求 B     █    █    █    █ ──完成，出批并释放 KV
  请求 C     █    █    █    █    █    █ ──完成，出批
  请求 D                    ↑ 新请求在下一次迭代即时入批
                             （显存腾出的同一迭代内被复用）
```

对统计研究者，一个有用的类比是把解码迭代看作固定的"检查周期"：请求级批处理相当于把整批观测的出口锁定在同一时点，个别长尾观测拖住全组；连续批处理则在每个周期重新分组，队长与队宽都不再由最慢的成员决定。这也解释了为什么连续批处理下监控延迟分位数更重要，逐迭代组批使请求之间的处理时点互相交织，延迟的方差来源比固定批次更多，靠均值看不出问题。

### 9.3.3 前缀缓存与 KV 复用

许多负载存在大量**重复前缀**：固定的系统提示、长文档问答中反复使用的同一份文档、多轮对话的历史部分。若每次请求都重新计算这些前缀的 KV，则重复付出 prefill 的算力。

前缀缓存（prefix caching）把已计算的 KV 块按内容索引保存，新请求到来时命中则直接复用，只计算新增部分。vLLM 提供自动前缀缓存，SGLang 的 RadixAttention 用基数树组织缓存，支持更灵活的共享与淘汰。命中率是这一机制的核心指标，应当在监控中单列（见 9.4）。

命中率的高低取决于负载结构，而非引擎本身。提升命中率的工程手段有三条：把稳定的长内容（系统提示、文档）放在提示的前部（前缀匹配是从左端开始的）；对同一文档的多轮提问尽量路由到同一实例；避免在提示前部插入每次都变的时间戳或请求 ID，这类字段会让所有前缀失配。

### 9.3.4 KV 缓存管理与显存预算

KV 缓存在长上下文下的占用量是容量规划的核心。以 32 层、8 个 KV 头、头维度 128、FP16 存储的典型 7–8B 模型为例，每 token 的 KV 缓存为

$$2 \times 32 \times 8 \times 128 \times 2\ \text{B} = 131{,}072\ \text{B} \approx 128\ \text{KiB/token}$$

一条 32k 上下文的请求约占 4 GiB。这意味着一张 40 GiB 显存的卡，扣除权重后剩下的空间只能容纳个位数的长上下文并发请求。分组查询注意力（GQA）与多头潜在注意力（MLA）等架构通过减少 KV 头数或压缩 KV 维度来降低这一开销，是模型侧的根本解法。

工程侧的解法是分页管理。PagedAttention（arXiv:2309.06180）把 KV 缓存切分为固定大小的块（block），用块表（block table）把逻辑上连续的序列映射到物理上不连续的块，从而消除碎片、支持按需分配与前缀共享。类比操作系统的虚拟内存可以帮助理解：块即页，块表即页表，显存即物理内存。它带来的直接收益是显存利用率接近理论上限，从而支撑更大的批处理规模。

容量规划的计算顺序是：显存总量 → 减去权重（参数量乘以每参数字节数）→ 减去激活与框架开销 → 剩余即为 KV 预算 → 按平均序列长度换算并发数。量化通过缩小权重占用间接扩大 KV 预算，这是低比特量化在服务端的主要价值之一。

### 9.3.5 并行策略

| 策略 | 切分对象 | 适用场景 | 通信开销 | 注意点 |
|------|----------|----------|----------|--------|
| 张量并行（TP） | 单个算子内的权重矩阵按列/行切分 | 单卡放不下模型；需要降低单请求延迟 | 高（每层多次 all-reduce），需 NVLink 级互联 | 并行度通常取 2、4、8，且需整除头数 |
| 流水线并行（PP） | 按层切分到不同设备 | 模型极大、跨机部署 | 中（仅在阶段边界传递） | 存在气泡，需微批填充 |
| 专家并行（EP） | MoE 模型的专家分布到不同设备 | MoE 架构 | 高（all-to-all 路由） | 负载不均衡是主要问题 |
| 数据并行（多副本） | 整个模型复制多份，请求分流 | 吞吐不足、延迟已达标 | 无 | 最简单，优先采用 |

实践中的优先级是：**先用多副本解决吞吐，再用张量并行解决单卡容量与延迟**。张量并行引入的通信开销在跨机（无 NVLink）时会大幅抵消收益，因此跨机扩展通常改用流水线并行或数据并行。

另两项近年被广泛采用的机制是分块预填充（chunked prefill，把长 prefill 切块与 decode 交错执行，避免长请求阻塞 decode）与 prefill-decode 分离部署（两类阶段算力特征不同，分别部署在不同设备上各自扩展）。二者针对的都是"prefill 与 decode 争抢同一批算力"这一结构性矛盾。

### 9.3.6 网关、负载均衡与扩缩容

服务化需要一层网关承担与模型无关的职责：鉴权、限速、配额、路由（按模型版本或任务类型）、重试与降级、审计日志与计量。LiteLLM 与 OpenRouter 是常用的代理层，前者自托管、后者为托管服务。

负载均衡策略对延迟影响很大。轮询（round-robin）不考虑实例的实际负载，在长请求聚集时会造成队头阻塞；**基于并发数或队列长度的调度**（把新请求交给当前在途请求最少的实例）更贴近实际负载，Kubernetes 生态中常用的 KPA（基于并发的自动扩缩）即采用这一思路。会话保持（把同一会话路由到同一实例）可以提升前缀缓存命中率，但会降低均衡性，二者需按负载特征权衡。

自动扩缩容的触发指标应当选择对使用者体验最直接的信号：在途请求数、排队时间分位数或 GPU 利用率。以 GPU 利用率为唯一指标是常见误区，利用率高可能只是批处理规模大，并不代表使用者在等待。

### 9.3.7 Serverless 与冷启动

Serverless 推理按请求计费、缩容到零，适合低频与波峰波谷明显的负载。主要问题是冷启动：需要拉取镜像、加载权重、初始化 CUDA 上下文与显存池，耗时从数十秒到数分钟不等。缓解手段包括预置常驻实例、把权重放在本地 NVMe 或内存盘、使用快照恢复（保存已初始化的进程状态）。

对统计研究者的批量评估场景，Serverless 通常不是最优解：任务集中、可预约、对延迟不敏感，直接按小时租用 GPU 跑完即释放，成本更低且可预测（见 9.9 与第 19 章的成本测算）。

## 9.4 监控与可观测性

### 9.4.1 指标清单

监控指标按系统、质量、成本三层组织。三层的关系是：系统层指标异常通常立刻可见，质量层指标劣化往往缓慢且隐蔽，成本层指标只在月末才被发现，而真正影响研究结论的是质量层。

| 层级 | 指标 | 定义与口径 | 告警建议 |
|------|------|------------|----------|
| 系统 | TTFT 的 P50/P95/P99 | 首 token 延迟的分位数 | P95 与 P99 分别设限，尾延迟比均值敏感 |
| 系统 | TPOT / 端到端延迟分位数 | 每 token 间隔与总延迟 | 按请求类型（长/短）分组统计 |
| 系统 | 吞吐 | 每秒完成请求数与输出 token 数 | 与容量上限比较 |
| 系统 | 错误率 | 5xx、超时、OOM 占比 | 立刻告警 |
| 系统 | GPU 利用率、显存占用、SM 占用率 | 设备层指标 | 显存接近上限时预警 |
| 系统 | KV 缓存命中率 | 前缀缓存命中请求占比 | 显著下降时排查提示构造 |
| 质量 | 幻觉率 | 抽样标注中事实错误的比例 | 用控制图监控漂移 |
| 质量 | 拒答率 | 模型拒绝回答或回答"不知道"的比例 | 突然上升常提示提示词或过滤规则变更 |
| 质量 | 格式合规率 | 结构化输出可解析比例 | 直接影响下游自动化流程 |
| 质量 | 任务完成率 | 按业务口径判定的成功比例 | 主指标 |
| 成本 | 每千 token 成本、每请求成本 | 费用除用量 | 按模型与端点分组 |
| 成本 | 日/周累计费用 | 绝对金额 | 预算阈值告警 |
| 成本 | 缓存节省额 | 命中缓存节省的 token 费用 | 衡量缓存策略有效性 |

延迟指标必须使用**分位数**而非平均值。延迟分布右偏（存在由排队、重试、长上下文造成的长尾），平均值会把少数极慢的请求掩盖掉；而对使用者而言，恰恰是这些请求决定了体验。工程上通常用直方图（而非平均后再算分位数）聚合，因为分位数不可加。

### 9.4.2 与统计过程控制的同源性

上述指标按时间排列，就是一条时间序列；判断它是否"发生了变化"，是统计学中已经解决得很成熟的问题，统计过程控制（Statistical Process Control, SPC）。控制图的思想是：区分**共同原因变异**（系统固有的随机波动）与**特殊原因变异**（可归因的异常），只对后者报警。

均值—极差控制图（X-bar/R 图）的标准做法是把观测按子组（subgroup）分组，例如每小时取 $n = 5$ 次请求的质量得分，计算子组均值 $\bar X$ 与极差 $R$，控制限为

$$\mathrm{UCL}_{\bar X} = \bar{\bar X} + A_2 \bar R, \qquad \mathrm{LCL}_{\bar X} = \bar{\bar X} - A_2 \bar R$$

其中 $\bar{\bar X}$ 是子组均值的均值，$\bar R$ 是平均极差，$A_2$ 是只依赖子组大小的常数（$n = 5$ 时 $A_2 = 0.577$，$R$ 图的系数为 $D_3 = 0$、$D_4 = 2.114$）。等价的写法是 $\bar{\bar X} \pm 3\hat\sigma/\sqrt{n}$，即用平均极差估计 $\hat\sigma = \bar R/d_2$。这与假设检验中的 $3\sigma$ 界限同源，但控制图的目的不是检验某个预设假设，而是**持续监视**，这一点决定了它的阈值应当来自过程本身的变异，而不是来自"我认为 acceptable 的水平"。

评价控制图性能的标准量是**平均运行链长**（Average Run Length, ARL）：受控期的 $\mathrm{ARL}_0$ 是两次误报之间的平均观测数（对应检验的特异度），过程漂移后的 $\mathrm{ARL}_1$ 是从漂移出现到报警的平均延迟（对应检验的功效）。控制图在统计上就是检验统计量的序贯应用：每个子组做一次 $3\sigma$ 检验，连续做下去，ARL 把逐次检验的 I 类错误与功效折算成了"平均多少个子组后报警"这一工程上可直接使用的量。下面的最小实现演示了控制限的估计与漂移检出：

```python
# xbar_demo.py ， X-bar 控制图最小实现：估计控制限并检出均值漂移
import numpy as np

rng = np.random.default_rng(2026)
mu, sigma, n = 0.85, 0.05, 5     # 每请求质量得分 ~ N(mu, sigma^2)，子组 n=5
A2, D3, D4 = 0.577, 0.0, 2.114   # n=5 的控制图系数

def subgroups(m, shift=0.0):
    """生成 m 个子组，子组均值上移 shift 个标准差"""
    return rng.normal(mu, sigma, (m, n)) + shift * sigma

# 第一阶段：受控期 25 个子组，估计控制限
x = subgroups(25)
xbar, R = x.mean(axis=1), x.max(axis=1) - x.min(axis=1)
CL, Rbar = xbar.mean(), R.mean()
UCL, LCL = CL + A2 * Rbar, CL - A2 * Rbar
print(f"CL={CL:.4f}, UCL={UCL:.4f}, LCL={LCL:.4f}, sigma_hat={Rbar/2.326:.4f}")

# 受控期验证：另取 100 个子组，统计误报
xbar_ic = subgroups(100).mean(axis=1)
print(f"受控期误报: {int(((xbar_ic > UCL) | (xbar_ic < LCL)).sum())}/100 子组")

# 第二阶段：注入持续漂移，观察首次报警子组
for delta in (0.5, 1.0, 2.0):
    xbar_oc = subgroups(30, shift=delta).mean(axis=1)
    hits = np.where((xbar_oc > UCL) | (xbar_oc < LCL))[0]
    print(f"漂移 {delta}sigma: 首次报警子组 = "
          f"{hits[0] + 1 if len(hits) else None}, 30 个子组报警 {len(hits)} 次")
```

实测输出（numpy 1.26.4，随机种子 2026）：

```text
CL=0.8531, UCL=0.9170, LCL=0.7892, sigma_hat=0.0476
受控期误报: 0/100 子组
漂移 0.5sigma: 首次报警子组 = 17, 30 个子组报警 1 次
漂移 1.0sigma: 首次报警子组 = 2, 30 个子组报警 8 次
漂移 2.0sigma: 首次报警子组 = 2, 30 个子组报警 27 次
```

几处读数与理论一致：估计出的控制限近似为 $\bar{\bar X} \pm 3\hat\sigma/\sqrt{5}$，宽度由过程自身变异决定；受控期 100 个子组零误报，符合单子组越界概率约 0.27% 的名义水平；漂移 0.5$\sigma$ 时首次报警延迟到第 17 个子组，而 1$\sigma$、2$\sigma$ 时几乎立即检出。这说明 X-bar 图对大漂移灵敏、对小漂移迟钝，小漂移下每个子组只有部分信息，需要 EWMA 这类累积机制补足。

对不同指标应选用不同图型：

| 指标类型 | 适用控制图 | 说明 |
|----------|------------|------|
| 连续型质量得分（每请求得分的子组均值） | X-bar/R 图、X-bar/S 图 | 子组内变异代表固有噪声 |
| 错误率、拒答率等比例 | p 图（固定子组量）或 u 图（变动子组量） | 二项/泊松变异，控制限随子组量变化 |
| 罕见事件计数（OOM 次数） | c 图、u 图 | 计数型 |
| 缓慢漂移（质量缓慢劣化） | EWMA 图、CUSUM 图 | 对小偏移更敏感 |

延迟这类右偏数据不宜直接套用正态假设的控制图。可行做法是取对数后监控（对数延迟通常近似对称），或监控分位数并配 bootstrap 确定控制限。另一个实用选择是监控中位数与 MAD（中位数绝对偏差），对离群点稳健。

对小漂移，指数加权移动平均（Exponentially Weighted Moving Average, EWMA）图比 Shewhart 图更有效：

$$z_t = \lambda x_t + (1 - \lambda) z_{t-1}, \qquad \text{控制限 } \pm 3\sigma\sqrt{\frac{\lambda}{2-\lambda}}$$

$\lambda$ 取 0.1 至 0.3 时对小幅、持续的漂移敏感；$\lambda$ 越大越接近普通控制图。判异规则方面，除"点出界"外，常用的 Western Electric 规则还包括连续 9 点位于中心线同侧、连续 6 点递增或递减，后者正是模型质量缓慢劣化的典型形态。

EWMA 对小漂移的优势可以用 ARL 直接量化。下面的模拟在标准正态过程上比较单值 Shewhart 图（$3\sigma$ 界限）与 $\lambda = 0.2$ 的 EWMA 图，ARL 用 Monte Carlo 估计（约需一到两分钟）：

```python
# ewma_arl.py ， Shewhart 与 EWMA 的 ARL 对比（Monte Carlo）
import numpy as np

rng = np.random.default_rng(2026)
LAM, K = 0.2, 3.0

def arl(chart, delta, max_t=20000, reps=20000):
    """delta=0 时返回 ARL0，否则返回漂移检出延迟"""
    stops = []
    for _ in range(reps):
        z, t_hit = 0.0, max_t
        for t in range(1, max_t + 1):
            x = rng.normal(delta, 1.0)
            if chart == "shewhart":
                hit = abs(x) > K
            else:
                z = LAM * x + (1 - LAM) * z
                lim = K * np.sqrt(LAM / (2 - LAM) * (1 - (1 - LAM) ** (2 * t)))
                hit = abs(z) > lim
            if hit:
                t_hit = t
                break
        stops.append(t_hit)
    s = np.array(stops, float)
    return s.mean(), np.quantile(s, [0.5, 0.95])

for delta in (0.0, 0.5, 1.0):
    a_sh, _ = arl("shewhart", delta)
    a_ew, _ = arl("ewma", delta)
    print(f"漂移 {delta:.1f}sigma: Shewhart ARL={a_sh:.1f}, EWMA(0.2) ARL={a_ew:.1f}")
```

输出：

```text
漂移 0.0sigma: Shewhart ARL=371.8, EWMA(0.2) ARL=545.1
漂移 0.5sigma: Shewhart ARL=154.4, EWMA(0.2) ARL=42.6
漂移 1.0sigma: Shewhart ARL=43.5, EWMA(0.2) ARL=9.8
```

读法与功效分析完全平行：受控期 Shewhart 图的 $\mathrm{ARL}_0$ 约 372，与理论值 $1/0.00267 \approx 374$ 吻合（EWMA 取时变控制限时 $\mathrm{ARL}_0$ 略大，二者误报率都压在同一量级）；而在 0.5$\sigma$ 的持续小漂移下，Shewhart 平均要 154 个观测才报警，EWMA 只要 43 个，功效的差异约三到四倍。对应的工程含义是：若每个观测是一小时的质量抽检，Shewhart 图对小漂移的平均报警延迟约为一周，EWMA 约两天。对幻觉率这类缓慢滑落的质量指标，这个差距直接决定了发现问题时已流失多少低质量输出。模拟中 EWMA 用的是随时间收敛的精确控制限，工程实现若用稳态极限 $\pm 3\sigma\sqrt{\lambda/(2-\lambda)}$，早期数步的误报率会略高于名义值，对结果影响不大但值得知道。

把控制图用于 LLM 服务时有一处重要差别需要注意：传统 SPC 假设观测独立同分布，而 LLM 服务的请求是异质的（不同意图、不同长度、不同难度）。因此应当**先分层再监控**：按意图类别或请求类型分层，各自建图；否则请求构成的日常波动会被误判为过程异常。

### 9.4.3 质量指标的抽样估计

幻觉率、任务完成率这类质量指标通常无法全量获取（需要人工判断）。可行做法是抽样：每日随机抽取 $n$ 条请求做人工标注，用样本比例估计总体比例。$n$ 的选取取决于期望精度，用 Wilson 区间，在 $\hat p = 0.05$、$n = 200$ 时，95% 置信区间约为 $[0.027, 0.090]$，即只能把错误率定位在几个百分点的量级。若要检出从 0.05 到 0.07 的变化，需要约 1000 条标注量，成本不低。

分层抽样可以降低方差：按请求类型（问答、摘要、计算）分层，各层独立抽样后加权汇总，方差低于简单随机抽样。这与 8.13 的区组思想一致。

用模型评判模型（LLM-as-judge）是降低成本的常见替代，但它是一把**有偏的尺子**：评判模型会偏好自家风格的输出、对长答案有偏好、对数值细节不敏感。正确做法不是直接采信，而是把它当作替代测量（surrogate measurement），用人工标注校正：抽取一小批双标样本（人工与 judge 同时评），估计二者的混淆矩阵，据此把 judge 的估计值校正到人工口径。这在统计上是一个经典的测量误差校正问题，忽略它会导致系统性的乐观结论。

### 9.4.4 日志、追踪与工具

三类可观测数据各有用途：**日志**记录离散事件（请求、错误、工具调用），**指标**是聚合后的时间序列，**追踪**（tracing）记录单次请求在多个组件间的完整调用链。LLM 应用的追踪比常规服务更重要，因为一次请求内部可能包含检索、多次模型调用、工具执行与后处理，只看到端到端延迟无法定位瓶颈。

LLMOps 工具（LangSmith、LangFuse、Helicone 等）提供提示版本管理、追踪、评估数据集与在线打分。选择时的关键考量是数据存放位置（是否需要自托管）与是否支持把追踪数据导出为标准格式（便于自行做统计分析）。

把前三小节串起来，一个与统计口径对齐的监控数据流可以画成：

```text
数据采集                指标聚合                 统计监控                  处置
──────────            ──────────              ──────────              ──────
[请求日志]   ─┐
[错误日志]   ─┤  按时间窗口聚合  [系统指标: TTFT P95, 吞吐, 错误率] ─┐
[网关计量]   ─┘  (分位数不可加,  [成本指标: 每 token 成本, 日累计]    ├─ 按请求类型分层
[抽样标注]   ──→ 用直方图)      [质量指标: 幻觉率, 拒答率, 合规率] ─┘        │
                                                                         ▼
                                                              [控制图]
                                                    X-bar/R   p/u 图   EWMA/CUSUM
                                                                         │
                                                          判异: 点出界 / 连续 9 点同侧
                                                               / 连续 6 点单调
                                                                         ▼
                                                              [告警] → 值班判定 → 处置
                                                                         │
                                                         "告警—判定—处置"记录回流,
                                                          用于评估告警规则自身
```

这张图里有两个容易做错的统计细节。一是聚合层：分位数不可加，跨实例、跨窗口的分位数必须从直方图或原始样本重算，先平均再取分位数会系统性低估尾部。二是分层与控制图的先后：分层发生在建图之前（否则请求构成的波动会污染控制限），而控制图的输出，而非原始指标，才是告警的输入，跳过控制图直接对原始时序设静态阈值，就退化回了 9.4.5 要批评的主观阈值告警。

### 9.4.5 告警设计的统计考量

告警过多会导致麻木，告警过少会漏掉真实劣化。几条与统计直接相关的原则：

- 阈值应来自过程变异（控制限），而不是主观设定的"合理值"。主观阈值在分布变化时要么天天响、要么永不响。
- 多指标并行监控等价于多重比较：同时看 20 个指标、每个用 3σ 界限，则至少一次误报的概率约为 $1 - 0.997^{20} \approx 6\%$。解决方法是对核心指标单独设严，对辅助指标用 Bonferroni 类校正或改用综合统计量。
- 告警应基于**持续性**而非单点：要求连续两个子组越界或连续若干点趋势异常，可显著降低误报。
- 每次告警都应记录处置结果，形成"告警—判定—处置"的历史，用于回头评估告警规则本身的准确率与召回率。

## 9.5 评估与A/B测试

### 9.5.1 上线前的三层评估

上线前的评估分三层，各自回答不同的问题。

| 层次 | 内容 | 回答的问题 | 局限 |
|------|------|------------|------|
| 离线基准 | 在固定测试集上跑指标；与上一版本配对比较 | 新版本在已知任务上是否更优 | 测试集与真实分布存在差距 |
| 红队测试 | 主动构造对抗输入、越权尝试、敏感场景 | 是否存在安全与滥用风险 | 覆盖不完全，依赖测试者的想象力 |
| 人工评估 | 抽样人工打分，含一致性检验 | 质量是否在人可接受范围 | 成本高，需控制标注者偏差 |

离线基准应当采用 9.2.5 的配对比较与 McNemar 检验，而不是分别跑两次再比较均值，配对设计控制了题目难度这一强混杂因素，效率显著更高。人工评估需要报告标注者间一致性（分类任务用 Cohen's kappa，连续评分用 ICC），一致性过低时结论不可用。

### 9.5.2 随机化单元与 SUTVA

A/B 测试的第一步是确定**随机化单元**（randomization unit）。常见选项及其适用条件如下。

| 随机化单元 | 优点 | 风险 | 适用 |
|------------|------|------|------|
| 请求（request） | 样本量最大，实验最快 | 同一使用者在不同请求间看到不同版本，体验不一致；存在溢出效应 | 无状态、无记忆的工具型功能 |
| 会话（session） | 单会话内体验一致 | 同一使用者的跨会话体验不一 | 多轮对话类功能 |
| 使用者（user） | 体验一致，符合长期效果评估 | 样本量最小；使用者活跃度差异大 | 需要学习、记忆、个性化的功能 |
| 聚类（团队、机构、设备） | 可控制溢出 | 有效样本量大幅下降 | 存在网络效应或共享上下文的场景 |

单元选择的核心约束是**稳定单元处理值假设**（Stable Unit Treatment Value Assumption, SUTVA）：一个单元的处理状态不受其他单元处理状态的影响，且处理是单一明确的。在多轮对话与共享知识库的场景中，SUTVA 极易被违反，例如实验组使用者产生的对话被写入共享知识库，影响了对照组使用者的检索结果。违反 SUTVA 时唯一可靠的办法是把**相互影响的单元聚为一类并整体随机化**（聚类随机化），代价是有效样本量下降。

聚类随机化的方差膨胀由设计效应刻画：

$$\mathrm{deff} = 1 + (\bar m - 1)\rho$$

其中 $\bar m$ 是平均簇大小，$\rho$ 是 intraclass correlation（组内相关系数）。有效样本量为 $n_{\text{eff}} = n / \mathrm{deff}$，所需样本量则乘以 $\mathrm{deff}$。若聚类内每次请求的相关性较高（$\rho = 0.1$）且平均每使用者 20 次请求，则 $\mathrm{deff} = 1 + 19 \times 0.1 = 2.9$，即样本量需求接近三倍。忽略聚类而按请求数计算样本量，是 A/B 测试中导致"显著但不可复现"的主要技术原因。

### 9.5.3 样本量与功效

实验开始前必须确定最小可检出效应（minimum detectable effect, MDE）与所需样本量。连续型指标（如响应质量评分）的两组比较：

$$n_{\text{每组}} = \frac{(z_{1-\alpha/2} + z_{1-\beta})^2 \cdot 2\sigma^2}{\Delta^2}$$

比例型指标（如任务完成率）的两组比较：

$$n_{\text{每组}} = \frac{(z_{1-\alpha/2} + z_{1-\beta})^2\big[p_1(1-p_1) + p_2(1-p_2)\big]}{(p_2 - p_1)^2}$$

代入 $\alpha = 0.05$、功效 $0.8$、$p_1 = 0.70$、$p_2 = 0.73$，得每组约 3550 次观测（按使用者随机化时，这是 3550 个使用者，而非 3550 次请求）。再乘以前述设计效应，才是实际需要的规模。

```python
# ab_sample_size.py
import numpy as np
from scipy.stats import norm

def n_prop(p1, p2, alpha=0.05, power=0.80, deff=1.0):
    z_a, z_b = norm.ppf(1 - alpha/2), norm.ppf(power)
    return int(np.ceil((z_a + z_b)**2 * (p1*(1-p1) + p2*(1-p2)) / (p2-p1)**2 * deff))

def mde_prop(p1, n, alpha=0.05, power=0.80):
    """给定样本量反解可检出的最小差异（数值求解）"""
    from scipy.optimize import brentq
    f = lambda d: n_prop(p1, p1 + d, alpha, power) - n
    return brentq(f, 1e-4, 0.5 - 1e-4)

print(n_prop(0.70, 0.73))            # 约 3550（按独立单元）
print(n_prop(0.70, 0.73, deff=2.9))  # 聚类随机化下约 10300
print(round(mde_prop(0.70, 3000), 4))  # 每组 3000 时的最小可检出差异
```
输出：
```text
3551
10296
0.0326
```


反解 MDE 往往比正算样本量更有用：在流量固定的情况下，先算出"这个实验能检出多大的效应"，再决定是否值得做。若 MDE 大于预期改进幅度，这个实验在统计上是无望的，应当改用方差缩减或换用更敏感的指标，而不是硬做然后寄希望于显著。

### 9.5.4 方差缩减：CUPED

CUPED（Controlled-experiment Using Pre-Experiment Data）利用实验前的历史数据降低指标方差。设 $Y$ 为实验期指标，$X$ 为同一单元在实验前的同口径指标，构造

$$\hat Y_i = Y_i - \theta (X_i - \bar X), \qquad \hat\theta = \frac{\widehat{\mathrm{Cov}}(X, Y)}{\widehat{\mathrm{Var}}(X)}$$

由于 $E[\bar X]$ 在处理组与对照组间无差异（$X$ 在随机化之前测得），校正不引入偏倚，而方差降为

$$\mathrm{Var}(\hat Y) = \mathrm{Var}(Y)\,(1 - \rho^2)$$

其中 $\rho$ 是 $X$ 与 $Y$ 的相关系数。若历史指标与实验期指标相关系数为 0.7，则方差降低约 51%，等效于样本量翻倍。所需样本量按 $(1-\rho^2)$ 缩放：

$$n_{\text{CUPED}} = n \times (1 - \rho^2)$$

这一方法的统计本质是**协变量调整**（ANCOVA）：把与结果强相关的基线协变量纳入模型，从而削减残差方差。它与随机化不冲突，随机化保证无偏，协变量调整提升精度。除 CUPED 外，还可以在回归中加入单元层面的协变量（设备类型、地区、历史活跃度），同样属于方差缩减。

```python
# cuped.py ， CUPED 方差缩减
import numpy as np

def cuped_adjust(y, x):
    """y: 实验期指标；x: 实验前同口径指标（同一单元，缺失可用均值填）"""
    x = np.asarray(x, float); y = np.asarray(y, float)
    theta = np.cov(x, y, ddof=1)[0, 1] / np.var(x, ddof=1)
    return y - theta * (x - x.mean()), theta

y_adj, theta = cuped_adjust(y_treatment, x_treatment)
print("theta =", theta, "方差缩减比例 =", 1 - np.var(y_adj, ddof=1) / np.var(y_treatment, ddof=1))
```

### 9.5.5 序贯检验与 alpha spending

固定期设计（fixed-horizon）要求实验开始前确定样本量，且中途不看结果。实践中几乎无人做到， dashboards 随时可见，团队总想早下结论。**反复窥视**（peeking）会严重破坏 I 类错误控制：在 5 个等间距时点用 $\alpha = 0.05$ 做固定期检验，实际 I 类错误率约为 0.14，接近名义水平的三倍。原因是每次窥视都是一次新的检验机会，多次检验的联合拒绝概率被累积。

这一数字可以用零效应场景的 Monte Carlo 模拟直接验证，同时对比固定期检验与 O'Brien-Fleming 序贯界限：

```python
# peeking_sim.py ， optional stopping 使第一类错误膨胀的模拟
# 零效应 A/B：固定期检验 vs 每积累 200 观测窥视一次 vs O'Brien-Fleming 界限
import numpy as np
from scipy.stats import norm

rng = np.random.default_rng(2026)
N, LOOKS, ALPHA, REPS = 1000, 5, 0.05, 20000

def sim(strategy):
    rejections = 0
    for _ in range(REPS):
        a = rng.normal(0, 1, N)     # 处理组（零效应）
        b = rng.normal(0, 1, N)     # 对照组
        rejected = False
        for k in range(1, LOOKS + 1):
            n = k * N // LOOKS
            z = (a[:n].mean() - b[:n].mean()) / np.sqrt(2.0 / n)
            if strategy == "fixed":
                if k == LOOKS:
                    rejected = abs(z) > 1.96
            elif strategy == "peek":
                if abs(z) > 1.96:
                    rejected = True
                    break
            elif strategy == "obf":
                c = norm.ppf(1 - ALPHA / 2) / np.sqrt(k / LOOKS)
                if abs(z) > c:
                    rejected = True
                    break
        rejections += rejected
    return rejections / REPS

for s in ("fixed", "peek", "obf"):
    print(f"{s:>6}: 零效应下拒绝比例 = {sim(s):.4f}")
```

实测输出（numpy 1.26.4、scipy 1.15.3，随机种子 2026）：

```text
 fixed: 零效应下拒绝比例 = 0.0493
  peek: 零效应下拒绝比例 = 0.1442
   obf: 零效应下拒绝比例 = 0.0607
```

三行数字分别对应三种决策纪律：固定期检验的实测 I 类错误率 0.049 与名义 0.05 吻合；逐次窥视把拒绝概率推到 0.144，且模拟只窥视了 5 次，dashboard 式的每日一看在一个月的实验里意味着 30 次窥视，膨胀会更严重。O'Brien-Fleming 界限把膨胀压回到 0.061 附近。此处有一点需要如实说明：模拟中把临界值 $z_{1-\alpha/2}/\sqrt{t}$ 在各时点独立使用，只是 OBF 支出函数的近似用法，严格的总 $\alpha$ 控制需要按检验统计量各时点的联合分布计算 Lan-DeMets 边界，因此 0.0607 略高于名义 0.05 属于预期之内，量级上仍足以说明序贯设计把"三倍膨胀"压回到了接近名义水平的区间。

无论采用哪种序贯方案，三条纪律不变：看点时点（或支出函数）必须在启动前写入文档；结果一旦越界并停止，后续的"再看几天确认"会再次破坏错误率控制；停止时刻会影响效应量的估计，早期停止时估计量偏大（winner's curse），报告效应量时应给出相应的置信区间并注明是序贯停止后的结果。

正确的做法是**序贯检验**（sequential testing），其设计要点是把总的 $\alpha$ 预算按信息量（information fraction，通常近似为已收集样本占比）分配。O'Brien-Fleming 支出函数为

$$\alpha^\ast(t) = 2\Big[1 - \Phi\big(z_{1-\alpha/2}/\sqrt{t}\big)\Big], \qquad \text{对应临界值 } c(t) = \frac{z_{1-\alpha/2}}{\sqrt{t}}$$

其中 $t$ 是信息分数。这一函数在早期极其严格（$t = 0.25$ 时临界值约 3.92，几乎不可能拒绝），在 $t = 1$ 时恰好消耗完 $\alpha$。它的性质与固定期设计非常接近，所需最大样本量通常只比固定期设计高几个百分点，因此是最常用的选择。Pocock 支出函数各次看点的临界值近似相同（早期比 OBF 宽松），代价是最大样本量膨胀更多。

Lan-DeMets 支出函数把上述思路推广到任意看点时点：先指定支出函数形式（OBF 或 Pocock 型），再按实际信息分数计算每一步的临界值，从而在"看点时点不确定"的现实条件下仍然保持总 $\alpha$ 可控。这一灵活性很重要：流量往往不均匀，预设的看点时点难以准确命中。

对于需要**连续监控**（而非有限次看点）的场景，可使用混合序贯概率比检验（mixture SPRT, mSPRT）或 always-valid p 值：其检验统计量在任何停止时刻都保持 I 类错误控制，因此可以每天看一次而不必预先规划。代价是这类方法在效应为零时可能长期不停止，需要配合实际的时间预算。

### 9.5.6 多重比较

一次 A/B 测试通常同时观测多个指标（完成率、满意度、延迟、成本），有时还有多个处理臂（新模型 A、新模型 B），若再按天或按用户分层查看，比较次数迅速膨胀。设 $m$ 次独立比较、每次 I 类错误 $\alpha$，则至少一次假阳性的概率为 $1 - (1-\alpha)^m$；$m = 20$、$\alpha = 0.05$ 时约为 64%。

标准应对有三层：

1. **预先指定主指标**（primary outcome），只有主指标的检验结果用于决策；其余为次要指标，用于解释与假设生成。
2. **对次要指标做校正**：FWER 控制用 Holm 逐步法（比 Bonferroni 稍强且同样简单），探索性场景用 Benjamini-Hochberg 控制错误发现率（FDR）。二者的选择取决于代价结构，漏掉真实效应代价高时选 FDR，误报代价高时选 FWER。
3. **多臂比较**先做 omnibus 检验（如卡方或 ANOVA），显著后再做两两比较并用 Tukey 或 Dunnett（对共同对照组）法校正。

分层分析（按地区、设备、新老使用者）是假阳性最常见的来源。规范做法是：分层分析必须在分析计划中预先声明，且报告时说明校正方式；事后发现的分层差异（subgroup discovery）应作为假设生成，用新数据验证，而不能直接写入结论。

### 9.5.7 新奇效应与时间异质性

新功能上线后，使用者的行为在短期内与稳定期不同：好奇驱动的试用量上升（novelty effect），或因习惯旧版本而短暂表现变差（primacy effect）。若只跑三到五天，测得的效应很可能是这些短期成分的混合物。

处理办法按成本递增排列：

| 方法 | 做法 | 适用 |
|------|------|------|
| 延长实验 | 至少覆盖一到两个完整周期（通常 7–14 天） | 通用，成本最低 |
| 分群观察 | 按使用者首次接触时间分组，观察效应随暴露时长的变化 | 判断是新奇效应还是持久效应 |
| 混合效应模型 | 在模型中纳入日期随机效应与使用者随机效应 | 同时处理时间相关与使用者的重复测量 |
| 新老使用者分层 | 分别估计新使用者与老使用者的效应 | 二者机制不同，合并会掩盖差异 |
| Switchback 设计 | 在同一单元上交替切换处理与对照，多次反转 | 单元数量少、无法长期固定分组的场景（如调度策略） |

Switchback 设计需要注意**携带效应**（carryover）：前一期的处理影响后一期的结果。缓解办法是在切换后设置"洗脱期"（washout period）丢弃前若干观测，或在模型中显式纳入前期处理的滞后项。

### 9.5.8 分流健康检查：样本比率失配

在分析实验结果之前，必须先检查分流是否正确。样本比率失配（Sample Ratio Mismatch, SRM）指各组的实际样本量显著偏离预设比例，通常意味着分流逻辑、日志埋点或过滤规则存在错误，而这类错误会让后续所有结论无效。

检验方法是对各组观测数做卡方拟合优度检验：设预设比例为 $\pi_k$，观测数为 $O_k$，总样本 $N$，则

$$\chi^2 = \sum_{k} \frac{(O_k - N\pi_k)^2}{N\pi_k} \sim \chi^2_{K-1}$$

实践中的告警阈值通常取 $p < 0.001$（而非 0.05），因为这一检验每天自动运行、误报代价高。SRM 一旦出现，正确的处置是**暂停实验、排查分流与埋点**，而不是继续分析结果。

```python
from scipy.stats import chisquare
obs = [50231, 49812]          # 两组的实际样本量
exp = [sum(obs) * 0.5] * 2    # 预设 50/50
print(chisquare(f_obs=obs, f_exp=exp))
```
输出：
```text
Power_divergenceResult(statistic=1.7548554121727657, pvalue=0.18526750191209126)
```


### 9.5.9 指标设计与护栏

指标分三类，各司其职：**主指标**用于决策，应当是唯一的、可解释的、与业务或研究目标直接对应的量；**护栏指标**（guardrail metrics）用于否决，即使主指标改善，只要护栏指标越界（延迟显著上升、错误率上升、成本超预算、拒答率异常），改动也不应上线；**诊断指标**用于解释主指标变化的原因，不参与决策。

代理指标（surrogate metric）的使用需要谨慎。当真实目标难以直接测度时，用代理指标替代是常见做法，但代理与真实目标的相关性必须被估计而不是假定。可行做法是抽取一批样本同时测度代理与真实目标，估计相关系数及其置信区间，并在实验结论中说明代理指标的局限。

### 9.5.10 上线评估检查清单

| 环节 | 检查项 | 通过标准 |
|------|--------|----------|
| 设计 | 随机化单元、主指标、MDE、样本量已写入分析计划 | 全部文档化，启动前冻结 |
| 设计 | 聚类结构已知，设计效应已计入样本量 | 有 ICC 估计或上界 |
| 设计 | 监控方案（固定期或序贯）已确定 | 看点时点或支出函数已声明 |
| 实施 | SRM 检验通过 | $p > 0.001$ |
| 实施 | 实验时长覆盖完整周期 | 不少于一个业务周期，通常 7–14 天 |
| 分析 | 主指标检验 + 置信区间 | 报告效应量与区间，不只报 p 值 |
| 分析 | 次要指标已做多重比较校正 | Holm 或 BH，方法已声明 |
| 分析 | 护栏指标未越界 | 全部在预设范围内 |
| 分析 | 分层分析为预先声明 | 事后分层仅作假设生成 |
| 归档 | 实验配置、代码版本、模型快照已记录 | 可回溯复现 |

## 9.6 持续迭代与反馈闭环

### 9.6.1 反馈信号的收集与偏差

反馈分显式与隐式两类。显式信号包括评分、点赞/点踩、纠错提交；隐式信号包括是否复制结果、是否继续追问、是否中途放弃、是否重跑任务。两类信号都有系统性偏差，直接当作质量指标会得出错误结论。

显式信号的偏差是**回复偏差**：不满的使用者更倾向于留下评价，满意者沉默，因此评分均值偏低；同时，愿意评价的使用者与沉默使用者在任务类型上分布不同。隐式信号的偏差是**归因模糊**：中途放弃可能是因为结果已足够好，也可能是因为结果糟糕。

可行的校正思路有三条：用随机抽样的主动调研补充自然反馈（随机机制保证代表性）；把反馈率本身作为监控指标（反馈率突然变化常意味着产品或模型有变）；对反馈做倾向性加权（按使用者与任务特征对反馈样本加权回总体分布），这本质上是调查抽样中的非应答调整。

### 9.6.2 失败案例分析

失败案例（bad case）分析是迭代的起点。标准流程是：按分层抽样从失败样本中抽取固定数量（如每周 50 条），由标注者归入预先定义的根因类别（指令误解、知识缺失、数值错误、格式错误、检索失败、工具调用错误），统计各类占比及其随时间的变化。

根因分类需要**互斥且完备**的类别体系，并报告标注者间一致性（Cohen's $\kappa$）。$\kappa < 0.6$ 时分类结果不可用，应重新定义类别或加强标注培训。分类结果的用途是指导优先级：某一类占比持续上升意味着存在系统性缺陷，而零星个例只需记录。

从统计角度看，每周 50 条的抽样只能检出占比变化在 10 个百分点量级的位移；若关心 3 个百分点的改善，需要约 1000 条的标注量。因此应把"根因分布"与"总体失败率"分开监控：前者用控制图看趋势，后者用比例估计看水平。

### 9.6.3 数据回流与增量微调

把真实使用数据回流进训练集是提升效果的有效手段，也是风险集中的环节。四类风险需要分别处理。

**去污（decontamination）。** 若评估集的数据混入训练集，评估结果将失去意义。回流数据必须与所有评估集做去重比对（精确匹配加近重复检测），并记录去污过程。

**灾难性遗忘。** 在新数据上继续训练会削弱原有能力。缓解手段包括混合一定比例的旧数据（replay）、限制学习率与训练步数、用参数正则约束偏离，以及在每次更新后跑一遍覆盖全部能力的回归评估集。

**分布失衡。** 回流数据的分布由使用者行为决定，热门任务占比远超长尾任务。若直接训练，模型会在长尾任务上退化。应对是按任务类别分层采样，控制各类别的配额。

**质量噪声。** 使用者数据中包含大量不良提示与错误示范。训练前应过滤与加权，而不是全盘接收。

微调之外，还有两条更轻的迭代路径，优先级通常更高：**提示词与 Skill 迭代**（改提示、增加少样本示例、调整输出契约，成本极低、见效快）与**检索库更新**（补充文档、修正分块，对知识型错误的针对性最强）。只有在这两条路径都触及天花板时，才考虑微调。

### 9.6.4 版本管理与回滚

需要版本化的不止是模型。一个线上系统的行为由四类要素共同决定，缺一不可追溯：

| 要素 | 版本标识 | 存储方式 |
|------|----------|----------|
| 模型权重与快照 | 模型版本号或权重哈希 | 模型注册表、对象存储 |
| 提示词与 Skill | 提示版本号（语义化版本或 Git 哈希） | 提示仓库，见第 7 章 |
| 检索库与索引 | 索引构建时间与语料清单哈希 | 索引元数据 |
| 服务代码与配置 | 镜像摘要与配置哈希 | 容器镜像、配置仓库 |

回滚能力依赖两件事：旧版本随时可重新部署（镜像与权重不被删除），以及配置与代码可以整体回退（用声明式配置而非手工改动）。回滚的触发条件应当预先定义（例如错误率超过某阈值、主指标下降超过某幅度并持续两个监控周期），而不是临场判断。

### 9.6.5 金丝雀与灰度发布

| 策略 | 做法 | 优点 | 代价 |
|------|------|------|------|
| 金丝雀（canary） | 先放 1–5% 流量到新版本，观察无异常后全量 | 限制爆炸半径 | 小流量下统计功效低，只能检出巨大差异 |
| 灰度（滚动放量） | 按 5% → 20% → 50% → 100% 逐步放大，每级观察一段时间 | 兼顾安全与证据积累 | 周期长，组间存在时间混淆 |
| 影子流量（shadow） | 新版本并行处理真实请求但不返回结果，只比对输出 | 不影响使用者，可离线比对 | 只测输出质量，不测真实使用者反应 |
| 蓝绿部署 | 两套环境整体切换 | 回滚最快 | 资源占用翻倍 |

小流量阶段的统计局限必须清楚：5% 流量下若每日 2000 个使用者，则每组每天 100 个，两天也只能检出十几个百分点量级的差异。因此金丝雀阶段的目标不是"证明新版本更好"，而是"排除明显的崩溃与严重退化"；效果验证应放在灰度中后期或直接做完整的 A/B 测试。影子流量是唯一不受此限制的方案，因为它离线比对全部请求。

### 9.6.6 模型退役与迁移

模型退役（例如某版本停止服务）时的迁移评估与上线评估同等重要。标准做法包括：双跑比对（新旧版本在相同输入上同时运行，用配对指标与 McNemar 检验）；设定等价性边际（用 9.2.5 的 TOST 思路，证明新版本不劣于旧版本超过 $\delta$）；保留旧版本一段时间以便回滚；向使用者公告变更并提供反馈渠道。迁移完成后，旧版本的提示词与评估集应归档而非删除，它们记录了这个版本的行为边界，是下一次迁移的对照材料。

## 9.7 多模型路由与成本优化

### 9.7.1 成本模型

自建服务的单位成本可以从硬件时租与吞吐推出：

$$C_{\text{自建}}(\text{每百万输出 token}) = \frac{\text{实例时租}}{\text{每小时输出 token 数}} \times 10^6$$

示例测算（参数需按实际报价与实测吞吐替换）：设某 GPU 实例时租约 1.5 美元，单实例在目标负载下输出约 3000 token/秒，即每小时 $1.08 \times 10^7$ token，则每百万输出 token 的成本约 $1.5 / 10.8 \approx 0.14$ 美元，另需计入输入处理、空闲时段与运维成本。空闲是关键变量：按小时计费的实例在低谷期仍然计费，因此自建服务的实际单位成本随利用率反比上升。

调用商用 API 的成本为

$$C_{\text{API}} = \frac{N_{\text{in}} \cdot p_{\text{in}} + N_{\text{out}} \cdot p_{\text{out}}}{10^6}$$

其中 $p_{\text{in}}$、$p_{\text{out}}$ 分别为每百万输入、输出 token 的价格。输入 token 常被低估：长系统提示、检索上下文与多轮历史会迅速累积，而前缀缓存与上下文压缩正是针对这一项。

总成本还应包含三项常被忽略的支出：**失败重试**（错误率 5% 意味着约 5% 的额外消耗）、**人工审核**（质量保障的人力成本）、**工程维护**。把三者计入后，"自建一定比 API 便宜"的结论经常不成立。

### 9.7.2 按任务复杂度路由

不同任务的难度差异极大：把一段文字分类为三类，与推导一个统计量的渐近分布，不需要同等规模的模型。路由（routing）的基本形式是级联：先用小模型处理，若置信度低于阈值则升级到大模型。

路由器的阈值选择可以用假设检验的语言表述：把"该请求需要大模型"视为阳性，则路由器的**漏检**（把难题交给小模型）造成质量损失，**误报**（把简单题交给大模型）造成成本浪费。绘制不同阈值下的 (误报率, 漏检率) 曲线，即为 ROC 曲线；最优阈值由两类错误的**相对代价**决定，而不是由准确率最大化决定。若一次漏检的代价（使用者得到错误答案）远高于一次误报的代价（多花一点算力），阈值应向"宁可升级"的一侧移动。

| 路由信号 | 说明 | 局限 |
|----------|------|------|
| 规则（请求长度、任务类型、来源） | 简单、可解释、零延迟 | 无法捕捉语义难度 |
| 小模型自评置信度 | 成本低，可在线计算 | 模型自评往往过度自信，需校准 |
| 独立路由器模型 | 可学习难度特征 | 需标注数据，自身也有成本 |
| 历史表现（按用户/任务类别） | 利用积累的观测 | 冷启动阶段无数据 |

一个实践要点是**校准**：小模型输出的自评置信度与实际正确率常常不匹配（过度自信是通病）。应先用留出集估计置信度与实际正确率的对应关系（可靠性曲线），必要时用保序回归或 Platt 缩放校准后再用于路由决策，这与统计中校准预测概率的标准做法一致。

### 9.7.3 语义缓存

缓存分两级：精确缓存（输入完全相同）与语义缓存（输入语义等价，用嵌入相似度判定）。语义缓存把命中请求的模型调用替换为缓存结果，成本节省近似为命中率乘以该部分请求的成本。

风险是**误命中**：两个语义相近但期望答案不同的请求被判定为等价。误命中的代价远高于命中带来的节省（使用者得到错误答案），因此阈值的设定应当使误命中率极低，并在上线后通过抽样审计持续监控：随机抽取 $n$ 条命中请求人工判定是否正确，$n = 300$ 且零错误时，Wilson 95% 区间上界约为 1.2%，即只能把误命中率控制在 1% 量级的证据水平。

缓存还需要失效策略：模型版本更新、提示词变更、检索库更新后，相关缓存必须失效。把模型版本与提示哈希写入缓存键是最简单的做法。

### 9.7.4 批处理与峰谷调度

对延迟不敏感的任务（批量评估、离线摘要、合成数据生成），应使用批处理接口或错峰调度。商用 API 的批处理通常提供价格折扣，代价是完成时间不确定；自建服务则可在低谷期提高批处理规模、高峰期降低，从而提升整体利用率。

排队策略上，长任务与短任务混合会互相干扰：长任务占用大量显存并拉长短任务的排队时间。可行的分流办法是按预估长度路由到不同队列或不同实例组，这与按复杂度路由是同一种思想在调度层的体现。

### 9.7.5 压缩、蒸馏与混合架构

| 手段 | 成本节省 | 质量风险 | 适用场景 |
|------|----------|----------|----------|
| 量化（INT8/FP8） | 显存与算力显著下降 | 低，需按 9.2.5 评估 | 通用 |
| 量化（INT4） | 进一步下降 | 中，任务依赖 | 显存受限、有评估能力 |
| 蒸馏到小模型 | 单位请求成本下降一个量级 | 中高，能力边界收窄 | 任务固定、分布稳定 |
| 路由（大小模型级联） | 通常节省 30–70% | 取决于路由器质量 | 任务难度分布分散 |
| 语义缓存 | 取决于命中率 | 误命中风险 | 重复查询多的负载 |
| 前缀缓存 | 降低 prefill 算力 | 无质量风险 | 长固定前缀 |
| 批处理 | 折扣或利用率提升 | 无 | 离线任务 |

"通常节省 30–70%"是文献与工程报告中常见的区间，实际数值高度依赖负载构成与路由阈值，应通过自身数据实测。

混合架构是多数团队的现实选择：常规流量走自建服务（成本可控、数据不出内网），峰值或超出能力范围的任务走商用 API（弹性、无需预留容量）。LiteLLM 与 OpenRouter 这类代理层让混合架构的实现变得简单，把多家后端收敛为统一的 OpenAI 兼容接口，切换只需改配置。代价是增加了一层依赖与一处故障点，因此对代理层本身的可用性监控同样必要。

## 9.8 安全与权限

### 9.8.1 密钥管理

API 密钥是系统的入口凭证。基本要求是：密钥不写入代码库（用环境变量或密钥管理服务注入，并在 CI 中加入密钥扫描）；按用途分发不同的密钥（开发、测试、生产分离），便于定位泄露源与单独吊销；定期轮换（记录上次轮换时间与负责人）；开通用量上限与异常告警，使泄露后的损失可控。

给外部使用者发放密钥时，应发放**作用域受限**的密钥（限定模型、限定额度、限定 IP 段），而不是共享主密钥。多租户场景下，每个租户独立配额与独立计量，既是安全要求也是成本核算的前提。

### 9.8.2 访问控制与数据隔离

访问控制模型按粒度递增为：角色访问控制（RBAC，按角色授权）、属性访问控制（ABAC，按使用者属性、资源标签、环境条件授权）。对涉及未发表数据或受监管数据的科研服务，最小权限原则与默认拒绝（deny by default）是基本要求。

数据隔离的三层是：存储隔离（不同租户的数据分开存放或加密密钥分离）、传输加密（TLS）、使用隔离（日志与追踪中脱敏，避免 PII 进入可观测系统）。第三层最容易被忽略，把完整请求内容写进日志，等于把敏感数据复制到了一个防护较弱的系统中。

### 9.8.3 速率限制与配额

速率限制用于防止滥用与保护系统稳定。常用算法是令牌桶（允许短时突发、限制长期平均速率）与漏桶（严格平滑输出速率）。限流维度应当是多层的：按密钥、按使用者、按接口、按全局，任何一层触顶即限制。

配额与限流的区别是时间尺度：限流管每秒，配额管每日或每月。配额的意义在于成本可控，没有配额的系统，一次循环调用就可能耗尽月度预算。

### 9.8.4 内容过滤与输出审查

护栏分输入侧与输出侧。输入侧过滤越权请求、注入尝试与违规内容；输出侧审查生成内容是否合规、是否泄露系统提示或内部数据。

从统计角度看，过滤器是一个**二元分类器**，其性能由误杀率（合法请求被拦）与漏放率（违规内容通过）共同刻画，二者此消彼长，工作点的选择取决于两类错误的相对代价。过滤器的实际性能必须在自身流量上估计，而不是采信厂商给出的通用指标，不同领域的文本分布差异极大。估计方法是抽样标注，并用 Wilson 区间给出错误率的上界（尤其当观测到的错误数为零时，必须给出区间上界而不是报告"零错误"）。

| 环节 | 控制手段 | 常见失效 |
|------|----------|----------|
| 输入 | 注入检测、PII 识别与脱敏、长度与格式校验 | 绕过检测的同义改写 |
| 工具调用 | 最小权限、参数白名单、危险命令拦截 | 智能体被诱导执行越权操作 |
| 输出 | 合规审查、敏感信息检测、事实一致性检查 | 审查过严导致拒答率上升 |
| 日志 | 脱敏、分级访问、保留期管理 | 原始请求被完整落盘 |

### 9.8.5 提示注入与工具权限

提示注入（prompt injection）指通过输入内容操纵模型行为，使其忽略原有指令或执行 unintended 操作。在智能体场景中危害被放大：模型具备文件与命令执行能力时，一次成功的注入可能导致数据外泄或系统破坏。

防御是分层的，没有单一手段足够：把不可信内容（网页、上传文档、邮件）与指令明确区分并标记；工具权限最小化（只读工具不给写权限，写工具限定目录，网络访问限定域名）；敏感操作（删除、发送、支付）必须经人工确认，不交给模型自主决策；对工具调用的输入做参数校验，防止路径穿越与命令拼接。

### 9.8.6 审计日志与合规

审计日志记录"谁在什么时候、用什么身份、对什么数据、做了什么操作"。它是事后追溯与合规证明的唯一依据。设计要求包括：不可篡改（写入只追加存储或带签名的日志系统）、包含足够的上下文（请求标识、模型版本、提示哈希、工具调用与参数）、保留期符合规定、访问审计日志本身也需要授权。

合规要求因领域与法域而异，涉及个人数据的服务通常需要考虑：数据最小化（只收集必要数据）、保留期限（到期删除）、可删除权（能定位并删除特定个人的全部数据）、跨境传输限制（数据存放位置）。这些要求会反过来约束架构选择，例如跨境限制直接排除了部分境外托管方案，这也是 9.1 决策树把"数据能否离开本地"作为第一问的原因。

### 9.8.7 与统计工作的交叉点

审计日志对统计研究者还有一层额外价值：它是**回顾性研究的数据源**。日志中记录的每次调用构成一条观测，可用于分析使用模式、失败模式与质量漂移。使用时的两个技术要点是日志数据具有抽样偏差（只记录系统内的行为，不记录使用者放弃的部分）与结构依赖性（同一使用者的多次调用相关，需聚类稳健方差）。这与 9.5.2 的聚类随机化问题是同一个结构。

## 9.9 部署实践案例

### 9.9.1 方案一：Ollama 本地部署 7B 模型

适用于笔记本或小型服务器上的单用户场景，数据不出本地。

```bash
# 安装（Linux/macOS）
curl -fsSL https://ollama.com/install.sh | sh

# 拉取并运行模型
ollama pull qwen2.5:7b-instruct
ollama run qwen2.5:7b-instruct

# 以后台服务方式运行，暴露 OpenAI 兼容接口
ollama serve &

# 调用（默认端口 11434）
curl http://localhost:11434/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model":"qwen2.5:7b-instruct",
       "messages":[{"role":"user","content":"解释中心极限定理"}],
       "temperature":0}'
```

自定义参数（上下文长度、温度、系统提示）用 Modelfile 固化：

```dockerfile
# Modelfile
FROM qwen2.5:7b-instruct
PARAMETER temperature 0
PARAMETER num_ctx 8192
SYSTEM """
你是统计分析助手。只依据用户给出的数据作答，不编造数值。
"""
```

```bash
ollama create stat-assistant -f Modelfile
ollama run stat-assistant
```

注意两点：默认上下文长度通常小于模型支持的最大值，处理长文档需显式设置 `num_ctx`；多并发场景下 Ollama 的吞吐有限，组内共享应改用 9.9.2 的方案。

### 9.9.2 方案二：vLLM 生产级服务

适用于批量评估或组内共享服务。

```bash
# 方式一：pip 安装后直接启动 OpenAI 兼容服务
pip install vllm
python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --served-model-name qwen25-7b \
  --tensor-parallel-size 1 \
  --gpu-memory-utilization 0.90 \
  --max-model-len 8192 \
  --enable-prefix-caching \
  --max-num-seqs 256 \
  --port 8000

# 方式二：官方容器（推荐，避免环境依赖问题）
docker run --gpus all --shm-size 8g -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen2.5-7B-Instruct \
  --enable-prefix-caching --max-model-len 8192
```

关键参数的含义与调优方向：

| 参数 | 作用 | 调优方向 |
|------|------|----------|
| `--gpu-memory-utilization` | 显存中可分配给 vLLM 的比例 | 显存不足时上调；与机器上其他进程共存时下调 |
| `--max-model-len` | 单请求最大长度 | 设得过大会限制并发数（KV 预算被长序列占用） |
| `--max-num-seqs` | 最大并发序列数 | 吞吐不足时上调，尾延迟恶化时下调 |
| `--enable-prefix-caching` | 前缀缓存 | 有固定系统提示或长文档复用时开启 |
| `--tensor-parallel-size` | 张量并行度 | 单卡放不下模型时设置，需整除注意力头数 |
| `--quantization` | 量化后端（如 awq、gptq、fp8） | 需与权重格式匹配 |

压测用官方脚本，固定请求速率观察延迟分位数：

```bash
python benchmarks/benchmark_serving.py \
  --backend vllm --model qwen25-7b --base-url http://localhost:8000 \
  --dataset-name sharegpt --num-prompts 500 --request-rate 10 \
  --save-result --result-dir ./bench
```

压测结论应当记录完整配置（模型、版本、参数、硬件、并发、数据集），否则无法与后续结果比较。建议把压测脚本与配置纳入版本控制，把它当作 9.6.4 中"服务代码与配置"的一部分。

### 9.9.3 方案三：CPU 与 Apple Silicon 上的 GGUF 量化

无 GPU 环境下的可行路径。

```bash
# 1. 转换与量化（FP16 -> Q4_K_M）
python convert_hf_to_gguf.py ./Qwen2.5-7B-Instruct --outfile model-f16.gguf
./llama-quantize model-f16.gguf model-Q4_K_M.gguf Q4_K_M

# 2. 启动服务（OpenAI 兼容端点）
./llama-server -m model-Q4_K_M.gguf \
  -c 4096 -ngl 99 --host 127.0.0.1 --port 8080
```

`-ngl` 指定卸载到 GPU 的层数，Apple Silicon 上设较大值可利用 Metal；纯 CPU 运行时层数设为 0。Q4_K_M 是常用的折中档位（按块分组、块内分层量化），比同等位宽的均匀量化误差更小。量化后应跑一遍 9.2.5 的评估协议，而不是假定"4 位够用"。

### 9.9.4 方案四：云 GPU 部署

按小时租用 GPU 适合批量评估与短期高峰。通用流程如下：

```bash
# 1. 租用实例（以常见的云 GPU 平台为例：选择 CUDA 驱动完备的基础镜像）
ssh root@<实例IP>

# 2. 安装运行时
pip install -U vllm

# 3. 启动服务并放到后台
nohup python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct --port 8000 \
  --enable-prefix-caching > vllm.log 2>&1 &

# 4. 本地端口转发后从笔记本访问
ssh -L 8000:127.0.0.1:8000 root@<实例IP>
```

云部署的三条实践要点：一是**数据与权重分开存放**，实例释放后数据盘保留、系统盘重置，避免把成果留在会被销毁的位置；二是**用完后立即释放实例**，按小时计费的空转是最常见的浪费；三是**固定镜像与驱动版本**并写入脚本，否则重建实例时环境不一致会破坏可复现性。

### 9.9.5 方案五：LiteLLM 统一网关

当后端有多个（本地 vLLM、云端 API、不同厂商）时，用代理层统一接口。

```bash
pip install litellm

# config.yaml
# model_list:
#   - model_name: local-qwen
#     litellm_params: {model: openai/qwen25-7b, api_base: http://localhost:8000/v1, api_key: EMPTY}
#   - model_name: cloud-strong
#     litellm_params: {model: claude-sonnet-4-5, api_key: os.environ/ANTHROPIC_API_KEY}

litellm --config config.yaml --port 4000
```

之后所有调用都指向 `http://localhost:4000`，切换后端只改配置文件。代理层同时提供统一的计量与限速，便于 9.7 的成本核算与 9.8 的权限管理。

### 9.9.6 从权重到 API 端点的完整流程

| 步骤 | 内容 | 产出 | 验证方式 |
|------|------|------|----------|
| 1 | 确定约束（数据能否出本地、延迟要求、预算） | 部署方案 | 9.1 决策树 |
| 2 | 获取模型权重，记录版本标识与许可 | 权重目录 + 版本清单 | 校验哈希与许可条款 |
| 3 | 选择精度（FP16/BF16/量化）并做量化 | 量化模型 | 9.2.5 评估协议 |
| 4 | 选定引擎与并行策略，规划显存 | 启动参数 | 单请求冒烟测试 |
| 5 | 压测，记录吞吐—延迟曲线 | 压测报告 | 选定工作点 |
| 6 | 配置网关：鉴权、限速、配额、路由 | 网关配置 | 越权与限流测试 |
| 7 | 接入监控：系统、质量、成本三层指标 | 仪表盘与控制图 | 空跑验证告警 |
| 8 | 灰度发布或 A/B 测试 | 实验报告 | 9.5 检查清单 |
| 9 | 归档配置、镜像摘要、评估结果 | 归档记录 | 可回溯复现 |

### 9.9.7 三种方案的适用场景对比

| 方案 | 部署耗时 | 吞吐 | 数据位置 | 成本形态 | 适用 |
|------|----------|------|----------|----------|------|
| Ollama 本地 | 分钟级 | 低 | 本机 | 仅电费与硬件 | 个人使用、教学、敏感数据 |
| vLLM 自建 | 小时级 | 高 | 自有服务器/云 | 硬件或时租 | 组内共享、批量评估 |
| 云 GPU 租用 | 十分钟级 | 高 | 云端 | 按小时 | 短期高峰、无自有硬件 |
| 商用 API | 零 | 取决于厂商 | 厂商侧 | 按 token | 快速验证、弹性负载 |

一条实用的组合路径：先在商用 API 上验证流程是否成立（零部署成本，快速迭代提示与工作流）；流程稳定后用 Ollama 或 vLLM 在本地复现，评估开源模型是否够用（这一步同时解决数据合规问题）；只有在确认长期、稳定、量大的需求后，才投入自建服务的运维成本。

## 本章小结

1. 推理服务的四个核心指标是首 token 延迟、每 token 间隔、吞吐与并发能力，它们受 prefill/decode 两阶段不同瓶颈的制约，存在明确的吞吐—延迟取舍；选型应先回答数据能否离开本地、负载形态与运维能力三个前置问题，再比较引擎。
2. 量化误差可分解为截断项 $2\sigma^2[Q(z_p)(1+z_p^2) - z_p\phi(z_p)]$ 与舍入项 $s^2/12$，二者随截断阈值反向变化，校准的本质是求最优阈值；误差经线性层按 $\|x\|^2\sigma_q^2$ 放大并逐层累积。
3. 量化方案的评估不能依赖 MMLU 一类通用基准：它们对数值精度与输出统计性质不敏感。应改用配对比较设计，覆盖数值精度、置信区间覆盖率、I 类错误率、格式合规率与长链稳定性五个维度，并按功效分析确定重复次数（检出覆盖率从 0.95 降至 0.93 约需 1030 次独立重复）。
4. 服务架构的关键机制是连续批处理（迭代级调度）、前缀缓存、分页式 KV 管理与并行策略；容量规划的顺序是显存减去权重与框架开销后换算并发数，典型 7–8B 模型每 token 的 KV 缓存约 128 KiB，32k 上下文单请求约 4 GiB。
5. 监控指标分系统、质量、成本三层，其本质是过程质量监控，与统计过程控制的控制图同源：连续型指标用 X-bar/R 图，比例型用 p 图或 u 图，缓慢漂移用 EWMA 或 CUSUM；请求异质性要求先分层再建图。
6. A/B 测试的统计要点是：随机化单元须与干预一致并检验 SUTVA，聚类随机化需按设计效应 $1+(\bar m-1)\rho$ 放大样本量，可用 CUPED 按 $(1-\rho^2)$ 缩减方差，反复窥视会破坏 I 类错误控制（5 次窥视约为 0.14），须用 O'Brien-Fleming 或 Lan-DeMets 支出函数做序贯检验，多指标与分层分析须做多重比较校正。
7. 成本优化的四条主要路径是按复杂度路由、语义缓存、批处理与量化蒸馏，其中路由阈值的选择由漏检与误报的相对代价决定（ROC 视角），语义缓存需以抽样审计控制误命中率并给出 Wilson 区间上界。
8. 安全控制的重点是密钥按用途分离与轮换、工具权限最小化、输入输出的双层护栏、不可篡改的审计日志；护栏本身是二元分类器，其误杀率与漏放率须在自身流量上估计。
