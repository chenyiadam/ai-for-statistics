# 第17章 可复现、审计与验证基础设施


## 本章导读

统计学家对"可复现"的要求由来已久：一份结果要能被第三方在同样的输入下重新得到。但传统统计论文的可复现单元是"数据加代码"，而 AI 研究的可复现单元要宽得多——多出模型权重、提示词、解码参数、外部 API 调用与 GPU 上的非确定性归约。这五类东西的共同特点是：它们变化时不会留下 Git 记录，却足以让一个结论从显著变为不显著。

本章的中心判断是：**可复现性的终点不是"能跑通"，而是"结论的不确定性能被独立评估"**。能跑通只是说存在一条路径产生该数字；能评估不确定性则要求第三方知道这个数字对不同环境、不同随机种子、不同实现方式的敏感程度。这与统计学处理随机性的方式一脉相承：一个估计量值得报告，不是因为它在某次抽样下取值漂亮，而是因为它的抽样分布可以被刻画。

把这些需要锁定的对象组织起来，可以得到一个自下而上的五层结构。下层是上层的前提：环境失效时，代码与数据即使完好，重跑的数字也对不上；模型快照失效时，调用日志就成了无法对账的流水。每一层的失效后果不同，检查手段也不同。

```text
可复现性的五层结构（下层失效会向上传播，使上层证据失去意义）

  层 5  调用日志    外部 API 的请求与原始响应、模型快照标识、解码参数
  层 4  模型快照    权重哈希、registry 版本号、推理配置
  层 3  数据        内容哈希或 DVC 指针、数据卡
  层 2  环境        锁文件、镜像摘要、驱动与 BLAS 实现、环境指纹
  层 1  代码        Git commit、tag、提示词模板哈希
        ────────────────────────────────────────────────
各层失效的后果
  层 1 失效  结果对不上任何一段代码，"这个数字哪来的"无法回答
  层 2 失效  换机器重跑数字对不上，且差异大小不明（见 17.2.1）
  层 3 失效  结论无法对照数据核验；数据被原地覆盖后永久丢失
  层 4 失效  服务方更新权重后行为改变，旧结果失去解释依据
  层 5 失效  无法回答"当时模型到底返回了什么"，API 证据链断裂
```

图 17-1 的一个推论是：审计应当自下而上进行。第三方复核时先锁定层 1 与层 2（代码与环境），再核对层 3 的数据哈希，然后才谈得上评估层 4、层 5 的模型与调用证据；顺序颠倒时，环境问题会伪装成数据或模型问题，浪费双方的时间。本章 17.1 至 17.3 依次处理层 1 至层 3 与层 2 的交叉部分，17.5 至 17.6 处理层 4、层 5 的留证。

本章按基础设施的八个组件展开。17.1 到 17.3 处理"输入侧"的锁定：代码与数据大文件的分离、环境作为一类可量化的方差来源、实验追踪对研究者自由度的记录。17.4 到 17.6 处理"输出侧"的留证：可执行文档、验证日志（含失败记录）、数据卡与模型卡。17.7 给出可执行的复现检查清单与独立复现者制度，17.8 处理云平台上的环境快照与镜像导出。全章的命令均可直接复制，不依赖特定集群。

阅读本章需要的前提是基本的命令行操作与线性模型（随机效应、方差分量）的概念。与前序章节的关系上，17.2 承接第 8 章 8.14 节的环境锁，17.3 承接第 16 章的评估方法论（把一次实验视为一次抽样），17.5 承接第 10 至 12 章的形式化验证产出。

## 17.1 版本控制

### 17.1.1 版本控制的对象清单

科研项目的版本控制对象远多于"源代码"一项。下表列出需要被锁定并留痕的七类对象、各自的锁定标识与推荐存放位置。

| 对象 | 锁定标识 | 存放位置 | 常见失效形式 |
|---|---|---|---|
| 分析代码与管道脚本 | Git commit 哈希 / tag | Git 仓库 | 交互式执行的代码未落盘 |
| 提示词与提示词模板 | 内容哈希 + 版本号 | 仓库内 `prompts/`，或 Skill 目录 | 提示词只存在于对话框历史 |
| Skill 与 Agent 配置 | SKILL.md + `version` 字段 | 仓库内 `skills/`（详见第 7 章） | 平台内建的草稿 Skill 未导出 |
| 原始与中间数据 | sha256 / DVC 指针 | 对象存储 + 指针文件进 Git | 数据被原地覆盖，历史版本丢失 |
| 模型权重与快照 | 权重哈希 + registry 版本号 | 模型仓库或对象存储 | 只记录"Qwen3-8B"，未记录具体快照 |
| 环境与依赖 | 锁文件 / 镜像摘要 | 仓库内 `environment.yml`、锁文件、Dockerfile | 只记录"Python 3.11" |
| 运行结果与日志 | manifest 文件（含全部输入哈希） | `runs/<timestamp>/` | 结果文件与产生它的输入无法对应 |

判定标准很简单：**任何影响最终数字的东西，都必须有一个可引用的标识符**。无法引用就无法核对，无法核对就无法复现。

### 17.1.2 工作流与提交规范

分支策略的取舍取决于协作规模。单人项目用主干开发（trunk-based）即可：直接在 `main` 上小步提交，用 tag 标记投稿、返修等关键节点。多人协作时用短生命周期的特性分支（feature branch），合并前做一次快进合并或 squash，避免长期存在的分支积累冲突。GitFlow 那一套 `develop`/`release`/`hotfix` 的多分支结构对学术论文项目通常是过度设计，其收益（并行维护多个发布版本）在论文场景下不出现。

提交规范建议采用 Conventional Commits 的简化形式：`type(scope): subject`，其中 `type` 取 `feat`、`fix`、`data`、`exp`、`docs`、`refactor` 等。价值不在格式本身，而在于使提交历史可被机器解析——事后要回答"数据版本在什么时候被换过"时，一条 `git log --oneline --grep='^data'` 就能给出答案。

提交粒度上有一条与实验设计直接对应的原则：**一次提交只改变一个可被归因的因素**。这条原则与第 8 章 8.13 节"配置与数据的混淆"是同一件事：若在更换超参数的同时更换了数据集，测得的效应无法归因，而混合提交会让这种混淆在事后不可拆解。

```bash
# 仓库初始化与基础配置
git init -b main
git config core.autocrlf input            # 跨平台协作：统一换行符
git config user.name  "Your Name"
git config user.email "you@example.com"

# 提交规范示例
git commit -m "exp(seed): 固定全局种子为 20260101，重跑主实验"
git commit -m "data(v2): 更新调查问卷第二轮数据（sha256 见 manifest）"
git commit -m "fix(ci): 修正 BLAS 线程数导致的非确定性"

# 投稿与返修节点打 tag（附注 tag 带签名与日期）
git tag -a v1.0-submission -m "首次投稿版本"
git tag -a v1.1-revision  -m "一审返修版本"

# 事后检索：找出所有改动数据的提交
git log --oneline --grep='^data'
# 找出某个数字被引入的提交
git log -S "0.873" --oneline -- results/*.json
```

### 17.1.3 代码与大文件的分离：Git LFS 与 DVC

Git 对二进制文件的处理方式是存储每个版本的完整副本，一旦把几百 MB 的数据集提交进仓库，仓库体积会随每次修改线性增长，克隆时间变得不可接受，且历史难以清理（需要 `git filter-repo` 重写历史）。两种标准解法是 Git LFS 与 DVC。

Git LFS（Large File Storage）用指针文件替换仓库中的大文件，实际内容存在 LFS 存储区。它的心智模型最接近 Git 本身，适合数量不多、单个文件在数百 MB 以内、且不太频繁变动的资产（如一张大图、一份权重文件）。

DVC（Data Version Control）把数据与代码彻底解耦：Git 只存一个记录内容哈希的 `.dvc` 指针文件，数据本体放在本地缓存或对象存储（S3、OSS、MinIO 等）。DVC 额外提供管道定义（`dvc.yaml`）与阶段缓存，可以把"原始数据→清洗→特征→模型→评估"声明为有向无环图，只重算输入发生变化的分支。

| 维度 | Git LFS | DVC | 直接提交进 Git |
|---|---|---|---|
| 仓库体积增长 | 缓慢（仅指针） | 极缓慢（仅指针） | 随版本线性增长 |
| 数据存储位置 | LFS 存储区（平台托管） | 本地缓存或自建对象存储 | 仓库内 |
| 管道与依赖声明 | 无 | 有（`dvc.yaml`） | 无 |
| 跨平台与自托管 | 依赖平台 LFS 配额 | 可完全自建 | 无依赖 |
| 适用规模 | 少量大文件 | 数据集与多阶段管道 | 小于数 MB 的文本 |

```bash
# ---- Git LFS ----
git lfs install
git lfs track "*.parquet" "*.pt" "*.safetensors"
git add .gitattributes                      # track 规则必须进仓库
git add model/weights.safetensors && git commit -m "feat: 加入权重快照 v1"
git lfs ls-files                            # 确认哪些文件走了 LFS

# ---- DVC ----
dvc init
dvc remote add -d myremote s3://bucket/proj-data     # 或 oss://、gs://、本地路径
dvc add data/raw/survey_2026.csv                     # 生成 .dvc 指针与 .gitignore
git add data/raw/survey_2026.csv.dvc data/raw/.gitignore
git commit -m "data(v1): 原始问卷数据"
dvc push                                             # 内容推到远端

# 在另一台机器上按哈希取回
git pull && dvc pull
dvc status                                           # 检查工作区与指针是否一致

# 声明管道：只有 raw 变化时才重跑下游
dvc stage add -n clean -d src/clean.py -d data/raw/survey_2026.csv \
              -o data/clean/survey.parquet python src/clean.py
dvc repro                                            # 增量重算
```

### 17.1.4 提示词、Skill 与外部调用的版本管理

提示词是 AI 工作流中变动最频繁、也最容易被遗漏的一类输入。把提示词写在对话框里等于没有版本管理：它既不进仓库，也不出现在日志中，几个月后无法回答"这个结果是用哪句提示词生成的"。可行做法是把提示词作为模板文件放进仓库（Jinja 或简单的 `{占位符}` 形式），由脚本渲染后调用模型，并把渲染后的完整文本与响应一并写入运行日志。

Skill（第 7 章）同理：SKILL.md 与其 `scripts/`、`references/` 应整体入库，frontmatter 中的 `version` 字段用于标识迭代。平台内建的草稿 Skill 必须导出到仓库，否则合作者无法获得同一份技能包。

外部 API 调用的记录包含三项：调用时刻、模型快照标识与解码参数、原始响应正文。第三项常被忽略，但它是唯一能在服务方后台更新权重后回答"当时到底返回了什么"的证据。

```python
# prompts/ 与渲染：提示词入库的最小实现
from pathlib import Path
import hashlib, json, datetime

def render(template_path: str, **kwargs) -> str:
    text = Path(template_path).read_text(encoding="utf-8")
    for k, v in kwargs.items():
        text = text.replace("{{" + k + "}}", str(v))
    return text

prompt = render("prompts/stat_test_select.j2", data_desc=desc, alpha=0.05)
rec = {
    "template": "prompts/stat_test_select.j2",
    "template_sha256": hashlib.sha256(Path("prompts/stat_test_select.j2")
                                      .read_bytes()).hexdigest(),
    "rendered_sha256": hashlib.sha256(prompt.encode()).hexdigest(),
    "rendered_text": prompt,
    "model_snapshot": "claude-sonnet-4-5@2026-01-01",
    "temperature": 0.0,
    "timestamp": datetime.datetime.now(datetime.timezone.utc).isoformat(),
}
json.dump(rec, open("runs/2026-01-01T10-00Z/prompt.json", "w"),
          ensure_ascii=False, indent=2)
```

### 17.1.5 常见错误与修正

| 错误 | 直接后果 | 修正方式 |
|---|---|---|
| 把数据集或权重直接提交进 Git | 仓库膨胀，克隆耗时，历史难以清理 | 改用 DVC 或 LFS；已提交时用 `git filter-repo` 重写历史 |
| 提交密钥、令牌、口令 | 凭据泄露，需全量轮换 | 密钥进密钥管理器；仓库加 `.gitignore` 与提交前扫描 |
| 交互执行代码但不落盘 | 结果无法追溯到任何 commit | 交互式探索后立即固化为脚本并重跑 |
| 依赖 `latest` 标签或主干分支 | 上游更新导致行为变化 | 锁定 tag、commit 或镜像摘要 |
| 数据原地覆盖 | 旧版本永久丢失 | 数据只读化，产出写到新目录 |
| 忽略 `.gitattributes` | 跨平台换行符与 LFS 规则不一致 | 显式声明换行符与 LFS track 规则 |
| 分支长期不合流 | 合并冲突集中在投稿前 | 短分支、小步合并，配合 CI |

## 17.2 环境管理

### 17.2.1 环境不确定性是一类可量化的方差来源

同一份 commit、同一份数据，在不同机器上跑出的数字可能不同。差异的来源包括：BLAS/LAPACK 实现与多线程归约顺序不同、编译器优化等级不同、浮点运算不满足结合律因而累加顺序改变结果、GPU kernel 的原子归约非确定、CUDA 与 cuDNN 版本差异、以及库本身的算法更新。这些差异在单次运行中通常落在末位有效数字上，但在长链条的迭代计算（优化、采样、递归）中会被放大。

本章提出的核心判断是：**环境不确定性本身是可量化的一类方差来源，应当用重复运行来估计它，而不是假定它为零**。具体做法是把"环境"当作随机效应纳入一个单因素随机效应模型。

设同一份代码在 $M$ 套环境（不同镜像、不同机器或不同驱动版本）上运行，每套环境重复 $R$ 次，得到指标 $Y_{mr}$。模型写作

$$Y_{mr}=\mu+b_m+\varepsilon_{mr},\qquad b_m\stackrel{\mathrm{iid}}{\sim}\mathcal N(0,\sigma_b^2),\quad \varepsilon_{mr}\stackrel{\mathrm{iid}}{\sim}\mathcal N(0,\sigma_e^2),$$

其中 $b_m$ 是环境效应，$\varepsilon_{mr}$ 是同一环境内的运行波动（含种子差异）。令 $\overline{Y}_{m\cdot}$ 为第 $m$ 套环境的均值，$\overline{Y}_{\cdot\cdot}$ 为总均值，则方差分量的矩估计为

$$\hat\sigma_e^2=\mathrm{MS}_W=\frac{1}{M(R-1)}\sum_{m}\sum_{r}(Y_{mr}-\overline{Y}_{m\cdot})^2,\qquad
\hat\sigma_b^2=\frac{\mathrm{MS}_B-\mathrm{MS}_W}{R},\quad \mathrm{MS}_B=\frac{R}{M-1}\sum_m(\overline{Y}_{m\cdot}-\overline{Y}_{\cdot\cdot})^2 .$$

组内相关系数 $\mathrm{ICC}=\hat\sigma_b^2/(\hat\sigma_b^2+\hat\sigma_e^2)$ 度量"换一套环境"相对于"同环境内重跑"的相对重要性。

这套估计给出一个可操作的判据：若 $\hat\sigma_b$ 与所报告的效应量处于同一量级或更大，那么该结论的不确定性的主要成分不是抽样误差，而是环境漂移；此时论文必须声明结论在环境维度上的稳健性，例如报告跨 $M$ 套环境的中位数与极差，或把环境作为随机效应纳入主分析。

第二个判据来自实验设计：若环境差异与处理条件相关——例如方法 A 跑在旧镜像上、基线 B 跑在新镜像上——则环境效应与处理效应混淆，这与混杂因子的标准处理相同。对策是**把环境作为区组（block）**：让所有待比较的方法在同一套环境内各跑一遍，环境间的差异通过区组效应被吸收。这条规则与配对设计的道理相同，第 16 章讨论模型比较时给出的配对协议在此完全适用。

在固定总运行次数 $N=MR$ 的预算下，增大 $M$ 比增大 $R$ 更有利于估计 $\sigma_b$：方差分量估计的精度取决于组数而非组内重复数。实践上 $M\ge 3$、$R\ge 2$ 是一个能给出粗略量级判断的最低配置。

```r
# R：用 lme4 估计环境方差分量（M 套环境 × R 次重复）
# df 列：env（环境标识）、y（指标）
library(lme4)
fit <- lmer(y ~ 1 + (1 | env), data = df)
vc <- as.data.frame(VarCorr(fit))
sigma_b <- sqrt(vc$sdcor[vc$grp == "env"])   # 环境效应标准差
sigma_e <- sqrt(vc$sdcor[vc$grp == "Residual"])
c(env_sd = sigma_b, run_sd = sigma_e, icc = sigma_b^2 / (sigma_b^2 + sigma_e^2))
```

```python
# Python：等价的矩估计（不依赖混合模型库）
import numpy as np
def variance_components(Y):           # Y shape = (M, R)
    M, R = Y.shape
    mbar = Y.mean(axis=1)
    gbar = Y.mean()
    MS_W = ((Y - mbar[:, None]) ** 2).sum() / (M * (R - 1))
    MS_B = R * ((mbar - gbar) ** 2).sum() / (M - 1)
    s2e = MS_W
    s2b = max((MS_B - MS_W) / R, 0.0)   # 截断，避免负值
    return {"sigma_b": np.sqrt(s2b), "sigma_e": np.sqrt(s2e),
            "icc": s2b / (s2b + s2e) if (s2b + s2e) > 0 else 0.0}
```

上述模型可以用数值实验直接演示。不同 BLAS 线程数的主要影响是改变并行归约的分组与合并顺序；浮点加法不满足结合律，顺序不同则舍入误差不同。下面的演示用"分块求和的块数 $K$"作为线程数的代理、用"数据载入顺序的随机排列"作为运行间差异的代理，构造出 $M\times R$ 的指标矩阵后交给方差分量模型。演示在 Python 3.10 与 numpy 1.26.4 下实测，输出为实测结果。

第一段演示良态情形：多元回归系数估计。设计矩阵含一列近似共线变量，条件数约 $9.5\times 10^7$，足以把 $10^{-16}$ 量级的求和顺序差异放大到可见。

```python
# 环境漂移演示一：良态线性估计下的数值漂移
import numpy as np

rng = np.random.default_rng(0)
n, p = 200, 4
x1 = rng.standard_normal(n)
x2 = rng.standard_normal(n)
x3 = x1 + x2 + 0.0003 * rng.standard_normal(n)   # 近似共线，抬高条件数
x4 = rng.standard_normal(n)
X0 = np.column_stack([x1, x2, x3, x4])
y = X0 @ np.array([1.0, 1.0, -1.0, 0.5]) + 0.5 * rng.standard_normal(n)

A = X0.T @ X0
print(f"cond(XtX) = {np.linalg.cond(A):.3e}")
se3 = np.sqrt(np.linalg.inv(A)[2, 2] * 0.25)     # beta_3 抽样标准误（近似）
print(f"beta_3 的抽样标准误(近似) = {se3:.3e}")

def xtx_blocked(X, K):
    # 模拟 K 路并行归约：块内 XtX，块和顺序累加
    T = np.zeros((X.shape[1], X.shape[1]))
    for c in np.array_split(X, K):
        T += c.T @ c
    return T

def xty_blocked(X, yv, K):
    t = np.zeros(X.shape[1])
    for cX, cy in zip(np.array_split(X, K), np.array_split(yv, K)):
        t += cX.T @ cy
    return t

ref_beta = np.linalg.solve(X0.T @ X0, X0.T @ y)
Ks = [1, 2, 4, 8, 16, 32]              # 环境：分块数（线程数的代理）
M, R = len(Ks), 5
Y = np.empty((M, R))
for i, K in enumerate(Ks):
    for r in range(R):                 # 运行：数据载入顺序（种子）
        perm = np.random.default_rng(1000 + 10 * i + r).permutation(n)
        Xp, yp = X0[perm], y[perm]
        b = np.linalg.solve(xtx_blocked(Xp, K), xty_blocked(Xp, yp, K))
        Y[i, r] = b[2] - ref_beta[2]

print("beta_3 偏差 (x1e-6):")
print(np.round(Y * 1e6, 3))

mbar = Y.mean(axis=1)
MS_W = ((Y - mbar[:, None]) ** 2).sum() / (M * (R - 1))
MS_B = R * ((mbar - Y.mean()) ** 2).sum() / (M - 1)
s2e = MS_W; s2b = max((MS_B - MS_W) / R, 0.0)
icc = s2b / (s2b + s2e) if s2b + s2e > 0 else 0.0
print(f"sigma_b={np.sqrt(s2b):.3e}  sigma_e={np.sqrt(s2e):.3e}  ICC={icc:.3f}")
```

```text
beta_3 偏差 (x1e-6):
[[-0.15  -0.302  0.051 -0.151 -0.101]

```

读法有二。其一，就统计推断而言，$10^{-7}$ 量级的环境漂移相对 $10^{2}$ 量级的抽样标准误完全可以忽略——对良态的线性估计量，环境方差分量通常不构成威胁，这与求和顺序误差被条件数放大的理论界限一致。其二，就复现而言，这些偏差虽小却真实存在：同一 commit、同一数据在"不同线程数"下给出的系数从第七位小数起不同，若复现检查采用文件哈希逐比特比对（17.7 的 L1 级），重跑必然失败。这一矛盾的出路是把哈希比对用于不会变化的输入（数据、代码、manifest），而对数值产物改用带容差的比较，容差取多少应参考实测的 $\hat\sigma_b$ 而非任意指定。

第二段演示相反的极端：当报告量本身来自大数相消的计算时，求和顺序带来的差异可以吞没抽样噪声。以下用方差的一遍公式 $\frac{1}{n}\sum x_i^2-\bar{x}^2$ 在 float32 下计算一个均值远大于标准差（$\bar{x}=1000$，$\sigma=1$）的样本，此时 $\sum x_i^2/n$ 与 $\bar x^2$ 都在 $10^6$ 量级而其差约为 1，每一位舍入误差都被相对放大。

```python
# 环境漂移演示二：大数相消的计算中，数值噪声压过抽样噪声
import numpy as np

rng = np.random.default_rng(0)
n = 200_000
x = 1000.0 + rng.standard_normal(n)

def var_twopass_f64(a):                # 参照实现：float64 两遍公式
    m = a.mean()
    return float(((a - m) ** 2).mean())

def var_naive_f32(a, K):
    # 一遍公式 sum(x^2)/n - mean^2，float32 累加，K 路分块
    a32 = a.astype(np.float32)
    s1 = np.float32(0.0); s2 = np.float32(0.0)
    for c in np.array_split(a32, K):
        s1 += np.float32(c.sum(dtype=np.float32))
        s2 += np.float32((c * c).sum(dtype=np.float32))
    m = float(s1) / len(a)
    return float(s2) / len(a) - m * m

ref = var_twopass_f64(x)
print(f"参照实现 (float64 两遍): {ref:.6f}")

bs = np.array([var_twopass_f64(x[np.random.default_rng(r).integers(0, n, n)])
               for r in range(20)])
print(f"抽样噪声参照: bootstrap SE = {bs.std(ddof=1):.4f}")

Ks = [1, 2, 4, 8, 16, 32]
M, R = len(Ks), 5
Y = np.empty((M, R))
for i, K in enumerate(Ks):             # 环境：分块数
    for r in range(R):                 # 运行：数据载入顺序
        perm = np.random.default_rng(1000 + 10 * i + r).permutation(x)
        Y[i, r] = var_naive_f32(perm, K) - ref

print("naive float32 一遍公式的偏差:")
print(np.round(Y, 4))

mbar = Y.mean(axis=1)
MS_W = ((Y - mbar[:, None]) ** 2).sum() / (M * (R - 1))
MS_B = R * ((mbar - Y.mean()) ** 2).sum() / (M - 1)
s2e = MS_W; s2b = max((MS_B - MS_W) / R, 0.0)
icc = s2b / (s2b + s2e) if s2b + s2e > 0 else 0.0
print(f"sigma_b={np.sqrt(s2b):.4f}  sigma_e={np.sqrt(s2e):.4f}  ICC={icc:.3f}")
```

实测输出：

```text
参照实现 (float64 两遍): 1.002401
抽样噪声参照: bootstrap SE = 0.0027
naive float32 一遍公式的偏差:
[[ 0.0498  0.0459  0.0498 -0.0322 -0.036 ]
 [-0.1141  0.1278 -0.0322 -0.1141  0.2059]
 [ 0.0459 -0.0322 -0.0322 -0.1141 -0.1141]
 [-0.0322  0.1278  0.0459 -0.0322 -0.1141]
 [ 0.0459  0.2098  0.2059 -0.0322 -0.0322]
 [ 0.2098  0.2878 -0.1102  0.3698  0.0536]]
sigma_b=0.0504  sigma_e=0.1209  ICC=0.148
```

偏差矩阵的量级在 $10^{-2}$ 到 $10^{-1}$ 之间，而同一统计量在稳定实现下的 bootstrap 标准误只有 0.0027：数值噪声是抽样噪声的二十倍以上。此时若论文报告"方差为 1.00，bootstrap 标准误 0.003"，那个 0.003 根本不是不确定性的主要来源。演示刻意选用了 float32 与一遍公式来放大效应；主流数值库对这类计算已有稳定实现（成对求和、两遍公式或 Welford 递推），float64 下的同类差异要小若干个数量级。但风险场景真实存在：自实现的在线或分块更新、派生量中的大数相消（如 $1-\mathrm{RSS}/\mathrm{TSS}$ 形式的拟合优度、协方差的两种展开式）、以及 GPU 与嵌入检索管线中常见的 float32 计算。两个演示合起来给出一条操作建议：环境方差分量应当被测量而不是被假定，$\hat\sigma_b$ 与效应量或抽样标准误的比值决定了环境锁定需要做到 17.2.2 至 17.2.4 中的哪一层。


### 17.2.2 工具层级与选择

环境管理手段按隔离层级从低到高排列：语言级虚拟环境、系统级包管理、容器、以及可复现构建系统。层级越高，锁定的范围越完整，代价是构建时间与体积。

| 层级 | 代表工具 | 锁定物 | 跨平台 | 主要短板 |
|---|---|---|---|---|
| 语言级（Python） | `uv`、`pip-tools`、`poetry` | 包版本与哈希 | 部分（需按平台求解） | 不锁定系统库与编译器 |
| 语言级（R） | `renv` | 包版本、R 版本、源 | 是（源码安装） | 二进制包依赖平台仓库 |
| 系统级 | `conda` / `mamba` + `conda-lock` | 跨语言包与部分系统库 | 是（多平台锁文件） | 锁文件体积大，解析慢 |
| 容器 | Docker / Podman | 整个用户态文件系统 | 是（同一架构内） | 依赖基础镜像，体积大 |
| 容器（HPC） | Apptainer（原 Singularity） | 单一 SIF 文件 | 是 | 需要管理员安装运行时 |
| 可复现构建 | Nix / Guix | 完整依赖图与哈希 | 是 | 学习成本高，生态较小 |

选择建议：统计项目的默认组合是 `renv`（R 侧）或 `uv` / `conda-lock`（Python 侧）加持续集成；容器用于需要长期归档或跨平台交付的场景；Apptainer 用于校内集群（多数 HPC 不提供 root 权限，无法运行 Docker 守护进程）。

### 17.2.3 锁文件的正确性

锁文件的常见错误不是"没有锁"，而是"锁错了粒度"。三个具体问题：

第一，`conda env export` 默认输出 build string（如 `numpy=1.26.4=py311h...`），这些 build 号与平台绑定，把 Linux 上导出的环境拿到 macOS 上还原会直接失败。正确做法是加 `--no-builds`，只保留包名与版本号，再由 `conda-lock` 为每个目标平台分别求解。

第二，`pip freeze` 只记录顶层 pip 安装的包，且不包含哈希，无法防御 PyPI 上的同名包被替换。用 `pip-compile --generate-hashes` 从 `requirements.in` 生成带哈希的完整闭包，安装时用 `pip install --require-hashes`。

第三，R 的 `renv.lock` 记录包版本与来源，但若依赖系统库（如 GDAL、GEOS、Java），锁文件不覆盖这些系统依赖，换机器后仍会失败。此类项目应配容器或在文档中写明系统依赖的安装命令。

```bash
# ---- conda / conda-lock ----
conda env export --no-builds -n repro > environment.yml      # 可移植的环境声明
conda-lock lock -f environment.yml -p linux-64 -p osx-arm64    # 为每个平台求解
conda create -n repro --file conda-linux-64.lock
conda list --explicit -n repro > spec-file.txt                 # 精确到包 URL 的清单
conda create -n repro2 --file spec-file.txt                    # 同平台内可精确重建

# ---- uv（Astral，Rust 实现）----
uv venv --python 3.11
uv pip compile requirements.in -o requirements.txt --generate-hashes
uv sync                                                        # 按锁文件同步环境
uv export --format requirements-txt > frozen.txt               # 导出完全锁定版本

# ---- pip-tools ----
pip-compile --generate-hashes --output-file=requirements.txt requirements.in
pip install --require-hashes -r requirements.txt

# ---- renv（R 控制台内）----
# renv::init()      建立项目级库
# renv::snapshot()  生成 renv.lock
# renv::restore()   在另一台机器上重建
# renv::status()    检查锁文件与库是否一致
```

锁文件还有一个常见的隐性失效方式：写完之后再没人在干净机器上验证过它能装通。一种成本很低的做法是把"从锁文件重建环境"放进持续集成（continuous integration，CI），在 GitHub Actions 等服务（延伸资源）提供的干净虚拟机上定期执行一次安装与最小冒烟测试（导入关键库、跑一个几秒的端到端脚本），失败即通知。CI 环境与本机不同这一事实本身就是检验：它恰好模拟了"合作者或复现者拿到仓库后"面临的处境。审稿或返修阶段收到"代码跑不起来"的反馈之前，这一步大概率已经把问题暴露了。

### 17.2.4 容器不等于可复现

容器常被视为可复现的终极方案，但一个 Dockerfile 本身并不足以锁定环境。四类漂移仍然存在：

**基础镜像漂移。** `FROM python:3.11` 指向的标签会被上游重新构建，三个月后拉到的镜像与当初不同。锁定方式是按摘要引用：`FROM python:3.11@sha256:<digest>`。摘要可从 `docker images --digests` 或 registry 查询获得。

**构建期依赖漂移。** Dockerfile 中的 `apt-get update && apt-get install` 每次构建都从发行版源取最新版本，源内容随时间变化。缓解方式是固定发行版快照源，或在构建后把镜像整体归档（见下）。

**层缓存与非确定性构建。** 构建缓存使得本地构建与他人构建可能走不同路径；`docker build --pull` 强制拉取最新基础镜像反而加剧漂移。CI 中应使用 `--no-cache` 或明确的缓存策略，并记录构建时间。

**运行时依赖。** 容器不包含 GPU 驱动与内核，宿主机驱动版本差异仍会改变数值结果。这部分只能靠环境指纹记录（17.2.6）。

因此容器的正确用法是：**先用摘要固定基础镜像，构建完成后立即归档镜像本体**，而不是把 Dockerfile 当作可复现凭证。对需要长期保存的项目，推荐导出为单一文件（`docker save` 或 Apptainer 的 SIF），连同校验和一起存入归档库。

```bash
# 固定基础镜像摘要
docker pull python:3.11
docker images --digests python:3.11        # 取 Digest: sha256:...
# Dockerfile 首行写作：FROM python:3.11@sha256:<上面得到的摘要>

# 构建：把 git commit 写入镜像标签与标签元数据
docker build --no-cache \
  --label "org.opencontainers.image.revision=$(git rev-parse HEAD)" \
  -t statproj:$(git rev-parse --short HEAD) .

# 归档：镜像本体存为单一文件
docker save statproj:$(git rev-parse --short HEAD) | gzip > statproj_image.tar.gz
sha256sum statproj_image.tar.gz > statproj_image.tar.gz.sha256

# 运行前核对镜像 ID（本地未推送时 RepoDigests 为空，用 Id）
docker inspect --format '{{.Id}}' statproj:$(git rev-parse --short HEAD)

# HPC 场景：容器转 SIF
apptainer build statproj.sif docker-daemon://statproj:$(git rev-parse --short HEAD)
apptainer exec --nv statproj.sif Rscript analysis.R     # --nv 挂载 GPU
```

### 17.2.5 数值确定性的开关

即便锁定了全部库版本，GPU 与多线程仍可能引入运行间差异。可显式打开的确定性开关包括：

| 层面 | 开关 | 作用 |
|---|---|---|
| Python 哈希 | `PYTHONHASHSEED=0` | 固定 `set`/`dict` 迭代顺序 |
| PyTorch | `torch.use_deterministic_algorithms(True)` | 强制使用确定性实现，不支持的算子直接报错 |
| PyTorch（cuDNN） | `torch.backends.cudnn.deterministic = True` | 选择确定性卷积算法 |
| cuBLAS | `CUBLAS_WORKSPACE_CONFIG=:4096:8` | 确定性矩阵乘所需的工作区配置 |
| TensorFlow | `TF_DETERMINISTIC_OPS=1` | 确定性算子 |
| BLAS 线程 | `OMP_NUM_THREADS=1`、`OPENBLAS_NUM_THREADS=1` | 消除多线程归约顺序的随机性 |

需要注意代价：单线程 BLAS 会显著拖慢大矩阵运算，确定性卷积算法也会牺牲吞吐。因此确定性开关适合用于**最终结果的确认性运行**，而探索阶段的多次重复运行用于估计运行间波动。两者都需要，作用不同。

### 17.2.6 环境指纹的采集

环境指纹是"当时到底在什么上面跑"的一份快照，应与结果文件一起归档。至少包含：操作系统与内核版本、CPU 型号、GPU 型号与驱动版本、CUDA/cuDNN 版本、解释器版本、关键包版本、环境变量中的确定性开关、git commit、以及采集时间。

```bash
# 一键采集环境指纹（Linux）
{
  echo "== timestamp =="; date -u +%Y-%m-%dT%H:%M:%SZ
  echo "== host ==";      uname -a; cat /etc/os-release | head -3
  echo "== cpu ==";       lscpu | grep -E "Model name|Socket|Core|Thread"
  echo "== gpu ==";       nvidia-smi --query-gpu=name,driver_version,memory.total \
                            --format=csv 2>/dev/null || echo "no nvidia-smi"
  echo "== cuda ==";      nvcc --version 2>/dev/null | tail -2 || echo "no nvcc"
  echo "== python ==";    python -VV; which python
  echo "== pip ==";       pip freeze --all 2>/dev/null || uv pip freeze
  echo "== conda ==";     conda list --explicit 2>/dev/null | head -50
  echo "== R ==";         R --version | head -1; Rscript -e 'sessionInfo()' 2>/dev/null
  echo "== git ==";       git rev-parse HEAD; git status --porcelain | head
  echo "== env vars ==";  env | grep -E "PYTHONHASHSEED|OMP_|MKL_|CUBLAS_|TF_DETERMIN|CUDA_VISIBLE"
} > runs/$(date -u +%Y%m%dT%H%M%SZ)/env_fingerprint.txt
```

## 17.3 实验追踪

### 17.3.1 追踪什么

实验追踪系统（experiment tracking）记录每一次运行（run）的输入、过程与产出。追踪字段的取舍标准是：**缺失后能否回答"这个数字是怎么来的"**。下表给出建议的最小字段集。

| 类别 | 字段 | 获取方式 | 缺失后果 |
|---|---|---|---|
| 身份 | run_id、启动时间、执行者 | 追踪系统自动分配 | 无法定位具体运行 |
| 代码 | git commit、是否有未提交改动 | `git rev-parse HEAD`、`git status --porcelain` | 结果与代码对应不上 |
| 环境 | 锁文件哈希、镜像 ID、GPU 型号 | 17.2.6 的指纹脚本 | 无法判断环境漂移 |
| 数据 | 输入数据 sha256、数据版本 | DVC 指针或哈希清单 | 无法确认用了哪份数据 |
| 参数 | 超参数、配置文件的完整内容 | 配置文件序列化 | 无法复现设置 |
| 随机性 | 全局种子、各随机源种子 | 配置文件 | 结果不可重得 |
| 模型 | 权重快照标识、解码参数 | registry 版本号或哈希 | 模型更新后无法对齐 |
| 指标 | 评估指标及其不确定性 | 评估脚本 | 只能比较点估计 |
| 资源 | 墙钟时间、峰值显存、能耗 | 计时与采样（17.3.4） | 无法评估成本与可行性 |
| 产物 | 输出文件路径与哈希、图表、日志 | 追踪系统的 artifact 存储 | 结果丢失或无法核对 |

只记录"超参数与最终指标"是常见的不足配置：它保留了比较所需的数字，却丢掉了判断可信度所需的上下文。

| 自建 CSV/SQLite | 本地 | 无依赖 | 任意 | 自行实现 | 单人小项目 | 无 UI，检索与对比需自己写 |

选择依据有三条：数据能否离开本地（涉密项目只能选自托管方案，见第 18 章）、是否需要多人共享与权限管理、以及是否需要把运行调度也纳入（ClearML 一类工具带有远程执行代理，MLflow 不带）。对单个研究者，`MLflow + 本地 artifact 目录`或`Aim`已足够；与云上训练结合的团队项目适合自带调度能力的工具。

### 17.3.3 与预注册和实验记录簿的对接

实验追踪在统计学中有一个现成的对应物：**预注册（pre-registration）加实验记录簿（lab notebook）**。二者的分工是：预注册冻结分析计划，记录簿记录执行过程与偏离。追踪系统正是记录簿的机器化版本，而且它记录得比人工笔记更完整——每一次运行都被自动打上时间戳与环境指纹，无法事后补写。

这套机制直接对应统计学对**研究者自由度（researcher degrees of freedom）**的关切。同一份数据上可行的分析路径构成一个分叉花园（garden of forking paths），若只报告最终走通的那一条，名义显著性水平与真实的第一类错误率之间的关系便断裂。追踪系统的价值不在于阻止探索，而在于让探索过程可审计：事后能回答"在得到这个显著结果之前，一共试过多少种设定"。

对应的做法有三条：一是在探索阶段就用追踪系统记录每一次运行，不要等结果确定后才补录；二是把探索性运行与确认性运行用 tag 区分，论文中报告的是后者，前者作为附录；三是在预注册文件（或内部分析计划）中写明主要终点与样本量判据，并把该文件纳入版本控制，其 commit 哈希与最终结果一起归档。

### 17.3.4 能耗与资源追踪

能耗既是成本问题也是环境问题（第 18 章 18.8 节）。追踪方式分三层：GPU 功率采样精度最高但需要权限且只在本地可用；软件估算工具（如 CodeCarbon）通过功耗模型与区域电网碳强度换算，跨平台但依赖假设；最粗的一层是记录 GPU 型号与 GPU 小时数，让读者自行换算。

### 17.3.5 最小实现

## 17.4 报告与文档

### 17.4.1 可执行文档

可执行文档（executable document）指的是正文、代码与结果在同一份源文件中，渲染时代码被执行、结果被插入正文。三类主流工具是 Quarto、R Markdown 与 Jupyter Book。

Quarto 是新一代的开源出版系统，支持 R、Python、Julia 与 Observable JS 的混排，输出 HTML、PDF、Word、reveal.js 幻灯片等多种格式，参数化渲染与项目级缓存是它的原生能力。R Markdown 是它的前身，生态成熟、模板丰富，但跨语言支持与项目管理弱于 Quarto。Jupyter Book 基于 Sphinx 与 MyST Markdown，适合把一批 notebook 组织成书或课程站点，对已有 Python 项目的接入成本最低。

| 工具 | 语言支持 | 输出格式 | 缓存机制 | 适合场景 |
|---|---|---|---|---|
| Quarto | R/Python/Julia/Observable | HTML、PDF、Word、幻灯片、书 | `freeze` 按内容哈希缓存执行结果 | 论文、技术报告、课程 |
| R Markdown | R（可经 reticulate 调 Python） | HTML、PDF、Word、幻灯片 | `cache=TRUE` 按块缓存 | 既有 R 项目 |
| Jupyter Book | Python（MyST 亦可含 R） | HTML、PDF | 需配合 jupyter-cache | 教程、书籍、文档站 |
| nbconvert / papermill | Python | HTML、PDF、notebook | papermill 参数化执行 | 批量参数化报告 |

### 17.4.2 动态报告与静态报告的取舍

动态报告（每次渲染都重算）保证图表与数据一致，代价是渲染时间随计算量增长，且依赖完整环境——环境一旦失效，报告就渲染不出来。静态报告（结果已固化）渲染快、可长期阅读，代价是结果可能过期，读者无法确认正文中的数字是否对应当前代码。

折中方案是**按内容哈希缓存执行结果**：Quarto 的 `freeze: auto` 只在该代码块的代码或其依赖发生变化时重算，否则复用上次的执行结果。这样在正常迭代中保持静态报告的响应速度，而在代码真正变化时自动触发重算，一致性由哈希而非人工判断来保证。

```yaml
# _quarto.yml（项目级配置）
project:
  type: default
  render:
    - report.qmd
    - appendix.qmd
execute:
  freeze: auto          # 代码未变则复用缓存结果
  cache: true
format:
  html:
    toc: true
    embed-resources: true     # 产出单文件 HTML，便于归档
  pdf:
    keep-tex: true
```

```bash
# Quarto：渲染与参数化
quarto render report.qmd                        # 渲染单文件
quarto render --to pdf                          # 指定格式
quarto render report.qmd -P alpha:0.01 -P seed:7  # 传入参数（params 需在 YAML 头声明）
quarto preview report.qmd                       # 预览，改动即重渲染

# 参数化批量报告（同一模板跑多个子群体）
for g in male female; do
  quarto render report.qmd -P group:$g --output "report_${g}.html"
done
```

### 17.4.3 Notebook 的版本管理

Notebook 的 JSON 结构包含输出与执行计数，直接进 Git 会产生大量噪声与合并冲突。标准做法是三件配套：用 Jupytext 把 notebook 配对为纯文本脚本（`.py` 或 `.qmd`），只把脚本文档进仓库；用 nbstripout 在提交前清除输出；用 papermill 做参数化批量执行，每次执行生成带参数标记的副本。

```bash
pip install jupytext nbstripout papermill

# 建立 py:percent 配对，此后只编辑 .py，.ipynb 自动同步
jupytext --set-formats ipynb,py:percent analysis.ipynb
jupytext --sync analysis.ipynb            # 双向同步

# 提交前自动清除输出
nbstripout --install --attributes .gitattributes

# 参数化批量执行：同一份模板跑不同年份
papermill analysis.ipynb out/analysis_2024.ipynb -p year 2024 -p alpha 0.05
papermill analysis.ipynb out/analysis_2025.ipynb -p year 2025 -p alpha 0.05

# 渲染为静态报告（含输出，用于归档）
quarto render out/analysis_2024.ipynb --to html
```

### 17.4.4 与统计写作的对接

统计论文的"表 1"（基线特征表）与回归结果表是手工誊抄错误的高发区：从输出窗口把数字敲进 Word，一位小数的差别不会被任何人发现。可执行文档把这一步变成渲染时自动插入，从机制上消除了誊抄环节。

配套要求有两条：一是结果数字与输出文件之间存在可追溯映射（表格中的数字由哪个对象的哪个字段生成）；二是正文中出现的每个数字都能在产物清单中找到出处。第 17.7 节的复现检查清单第 21 条即针对此项。

## 17.5 验证日志

### 17.5.1 三类证据

验证日志（verification log）是"这个结论被检查过、怎么检查的、由谁检查的"的留证。它包含三类性质不同的证据。

| 证据类型 | 产出物 | 特点 | 局限 |
|---|---|---|---|
| 机器可检验证据 | Lean 编译输出、单元测试结果、类型检查、静态分析 | 可重复执行，判定无歧义 | 只覆盖被形式化的部分 |
| 数值证据 | 蒙特卡洛校验、bootstrap 结果、模拟覆盖 | 可量化，但不构成证明 | 只在被检验的点上成立 |
| 人工复核证据 | 复核人、日期、复核范围、发现的问题、结论 | 能发现命题陈述层面的错误 | 不可重复，依赖复核人水平 |

三类证据不可互相替代。Lean 编译通过说明证明在给定形式化下无误，但不能说明形式化本身对应了原本想证的自然语言命题——后者恰恰依赖人工复核。第 11 章 11.6 节强调"逐行读定理陈述"，正是指这一类由人承担的、不可自动化的检查。

### 17.5.2 为什么必须保存失败记录

只保存成功的验证记录，会系统性地扭曲证据基础。这与统计学中的**选择性报告（selective reporting）**与**抽屉问题（file drawer problem）**是同一结构：若十次尝试中只有一次通过且只报告这一次，那么"通过"这一事实的证据价值远低于表面。

具体后果有三：

其一，无法评估证明搜索或调参的真实成本。Lean 场景中，一个定理是三轮 tactic 就通过还是三百次采样才通过，对可信度的含义不同——后者可能意味着命题在所选形式化下并不自然，或者形式化本身有偏差。记录失败的 tactic 序列与尝试次数，是评估这一点的唯一依据。

其二，无法做多重比较的校正。若研究员在不同设定下跑了若干次、挑最好的一次报告，那么名义上的不确定性是无效的。保存全部运行记录后，才能用第 16 章的多重比较方法给出校正后的判断。

其三，无法审计"是否发生过结论方向的改变"。一次分析从"无效应"变成"显著"的过程若不被记录，读者看到的只是最终版本。

因此验证日志的保存原则是：**失败记录与成功记录同等重要，且都应包含完整的输入哈希与命令**。日志的删除应当被视为数据销毁，需要理由与记录。

### 17.5.3 形式化验证的日志内容

针对第 10 至 12 章的形式化验证工作，日志除通用字段外还应包含：

| 字段 | 取值方式 | 判据 |
|---|---|---|
| Lean 工具链版本 | `lean-toolchain` 文件内容、`lake env lean --version` | 与归档声明一致 |
| Mathlib 版本 | `lake-manifest.json` 中的 commit | 与归档声明一致 |
| 编译结果 | `lake build` 的退出码与完整 stdout/stderr | 退出码为 0 |
| 未完成证明检查 | `grep -rn "sorry"` 计数，期望为 0 | 计数为 0 |
| 依赖公理检查 | `#print axioms <theorem>` 的输出 | 不出现 `sorryAx` |
| 编译耗时与心跳数 | `lake build` 计时、`set_option maxHeartbeats` | 记录以供对照 |
| 复核人 | 人工，见 17.5.1 | 至少一名非作者 |

其中 `sorry`（占位证明）与 `sorryAx`（`sorry` 引入的公理）的检查是形式化验证日志的关键一项：一个含 `sorry` 的文件可以编译通过，但其中的定理并未被真正证明，只是被声明。`#print axioms` 列出的公理中若出现 `sorryAx`，即说明该定理依赖了未完成的证明。

```bash
# 形式化验证的一次完整留证
cd proofs/myproject
git rev-parse HEAD                       > ../runs/$(date +%s)/commit.txt
cat lean-toolchain                       > ../runs/$(date +%s)/toolchain.txt
lake env lean --version                  >> ../runs/$(date +%s)/toolchain.txt

lake exe cache get                       # 拉预编译缓存，省去本地编译 Mathlib
time lake build 2>&1 | tee ../runs/$(date +%s)/build.log

grep -rn "sorry" . | wc -l               # 期望 0
```

```lean
-- 在文件末尾追加：打印定理依赖的公理，检查是否出现 sorryAx
import Mathlib

theorem my_hoeffding_bound (X : ℕ → ℝ) (n : ℕ) : True := by
  trivial

#print axioms my_hoeffding_bound
-- 期望输出：'my_hoeffding_bound' depends on axioms: [propext, Classical.choice, Quot.sound]
-- 若出现 sorryAx，说明证明中有未完成的占位
```

### 17.5.4 日志的最小结构

验证日志的生命周期可以概括为"三类证据进入同一目录、目录内一切以哈希绑定、目录被三类用途消费"。失败尝试与成功运行走同一条通道，这是 17.5.2 的原则在结构上的落实。

```text
       产生                    存储                        使用
 ┌──────────────┐   ┌─────────────────────┐   ┌────────────────────────┐
 │ 机器可检验证据 │   │ runs/<时间戳>/       │   │ 独立复现者按 manifest   │
 │ 编译、测试     │──▶│  manifest.json      │──▶│ 对照执行（L1/L2 检查）  │
 ├──────────────┤   │  verification/      │   ├────────────────────────┤
 │ 数值证据       │   │  stdout/ stderr    │   │ 多重比较校正：成功之前  │
 │ 蒙特卡洛、bootstrap│ │  metrics.json     │   │ 的失败次数计入试验次数 │
 ├──────────────┤   │  failed/attempt_*   │   ├────────────────────────┤
 │ 人工复核证据   │   │  review.md          │   │ 争议时的第三方审计      │
 │ 复核人、结论   │   └─────────────────────┘   └────────────────────────┘
 └──────────────┘        目录内全部输入与产物以哈希互相绑定
```

```text
runs/
└── 20260101T103022Z/
    ├── manifest.json          # 输入哈希、种子、代码 commit、模型快照
    ├── env_fingerprint.txt    # 环境指纹（17.2.6）
    ├── command.sh             # 实际执行的命令原文
    ├── exit_code.txt          # 退出码
    ├── stdout.log             # 标准输出
    ├── stderr.log             # 标准错误
    ├── metrics.json           # 指标与不确定性
    ├── artifacts.json         # 产物路径与哈希
    ├── verification/          # 机器可检验证据
    │   ├── build.log
    │   └── axioms.txt
    ├── review.md              # 人工复核记录
    └── failed/                # 失败尝试（同等保留）
        ├── attempt_001/
        └── attempt_002/
```

```bash
# 一次运行的日志包装器：run.sh
#!/usr/bin/env bash
set -euo pipefail
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
DIR="runs/${STAMP}"; mkdir -p "${DIR}/verification" "${DIR}/failed"
echo "$*" > "${DIR}/command.sh"
bash 17.2_env_fingerprint.sh > "${DIR}/env_fingerprint.txt" || true
{ time "$@" ; } > "${DIR}/stdout.log" 2> "${DIR}/stderr.log" || echo $? > "${DIR}/exit_code.txt"
echo "exit=$?" >> "${DIR}/exit_code.txt"
echo "run recorded at ${DIR}"
```

人工复核记录 `review.md` 的最小字段为：复核人、复核日期、复核范围（哪些文件、哪些定理或哪些表）、复核方式（通读、对照原文、独立重算）、发现的问题清单、结论（通过 / 有条件通过 / 不通过）、以及复核人对结论的置信度。最后一项看似主观，但它提供了读者所需的关键信息：形式化验证的产出并非"正确"与"错误"二值，而是带有证据强度的判断。

### 17.5.5 验证日志的最小文件格式与读取器

17.5.4 的目录结构适合单次运行的完整留证；跨运行汇总时，还需要一个能把每次检查追加进去的轻量格式。一种被验证够用的做法是 JSON Lines（JSONL）：每行一条独立的 JSON 记录，追加写（append-only）不需重写文件，`grep` 与任何语言的标准库都能直接读取。记录的最小字段为：时间戳 `ts`、关联的运行标识 `run_id`、检查类型 `check`（机器可检验或人工复核）、状态 `status`（pass 或 fail）、人可读的 `detail`，以及被检查对象的输入哈希 `inputs`。状态只设 pass 与 fail 两级，避免"基本通过"一类无法审计的中间态；有条件通过放进 `detail` 描述。

下面的脚本演示写入与读取的完整往返，日志中故意保留了三条失败记录（路径硬编码、种子未固定、环境漂移超容差），脚本在 Python 3.10 下实测：

```python
# 验证日志的最小文件格式（JSONL，含失败记录）与读取器
import json, pathlib

BASE = pathlib.Path("runs_demo")
log = BASE / "verification_log.jsonl"

# ---- 1. 写入：每次验证一条记录，失败与成功同等保留 ----
records = [
    {"ts": "2026-09-20T09:12:00Z", "run_id": "20260920T091200Z", "check": "numeric",
     "status": "fail", "detail": "绝对路径 C:\\Users\\a\\data 硬编码于 fit.py 第 41 行",
     "inputs": {"fit.py": "3f2a..."}},
    {"ts": "2026-09-21T10:02:00Z", "run_id": "20260921T100200Z", "check": "numeric",
     "status": "fail", "detail": "种子未固定，两次运行 AUC 差 0.021",
     "inputs": {"fit.py": "8b1c..."}},
    {"ts": "2026-09-22T15:40:00Z", "run_id": "20260922T154000Z", "check": "numeric",
     "status": "fail", "detail": "环境漂移：容器外重跑偏差 3e-4，超出容差 1e-5",
     "inputs": {"fit.py": "8b1c..."}},
    {"ts": "2026-09-23T11:05:00Z", "run_id": "20260923T110500Z", "check": "numeric",
     "status": "pass", "detail": "在镜像 sha256:9a1f 下重跑，与归档结果差 2e-9",
     "inputs": {"fit.py": "8b1c...", "input.csv": "c4d9..."}},
    {"ts": "2026-09-24T14:30:00Z", "run_id": "20260924T143000Z", "check": "human_review",
     "status": "pass", "detail": "复核人 L.W.，对照 codebook 逐字段核对",
     "inputs": {"review.md": "e05b..."}},
]
BASE.mkdir(parents=True, exist_ok=True)
with open(log, "w", encoding="utf-8") as f:
    for rec in records:
        f.write(json.dumps(rec, ensure_ascii=False) + "\n")

# ---- 2. 读取器：汇总通过率、首次通过前的失败次数、失败明细 ----
def summarize(log_path):
    recs = [json.loads(l) for l in
            pathlib.Path(log_path).read_text(encoding="utf-8").splitlines() if l.strip()]
    n_pass = sum(r["status"] == "pass" for r in recs)
    first_pass = next((i for i, r in enumerate(recs) if r["status"] == "pass"), None)
    fails = [r for r in recs if r["status"] == "fail"]
    print(f"记录总数 {len(recs)}，通过 {n_pass}，失败 {len(fails)}")
    if first_pass is not None:
        print(f"首次通过前有 {first_pass} 次失败尝试（多重比较校正时须计入）")
    for r in fails:
        print(f"  [FAIL] {r['ts']} {r['check']}: {r['detail']}")
    # 检查项覆盖：机器可检验证据之外是否有人工复核
    kinds = {r["check"] for r in recs}
    if "human_review" not in kinds:
        print("提示: 仅有机器可检验证据，缺少人工复核记录（17.5.1）")

summarize(log)
```

实测输出：

```text

首次通过前有 3 次失败尝试（多重比较校正时须计入）
  [FAIL] 2026-09-20T09:12:00Z numeric: 绝对路径 C:\Users\a\data 硬编码于 fit.py 第 41 行
  [FAIL] 2026-09-21T10:02:00Z numeric: 种子未固定，两次运行 AUC 差 0.021
  [FAIL] 2026-09-22T15:40:00Z numeric: 环境漂移：容器外重跑偏差 3e-4，超出容差 1e-5
```

读取器输出中"首次通过前有 3 次失败尝试"一行值得单独说明。假如这条日志被用来声称"本方法的复现检查通过"，只报告最后一条 pass 就是教科书式的选择性报告：通过这一次发生在三次失败之后，其证据强度与一次即过完全不同。17.5.2 的三条后果在此都能落到具体字段——试验次数由记录条数给出，结论方向的改变由按时间排序的状态序列给出，检查成本由时间戳间隔给出。这个格式刻意保持简陋，为的是它足够低门槛，低到探索阶段的每一次检查都值得记；格式一旦重到"稍后再补"，选择性报告就从缺省行为开始了。

## 17.6 数据卡与模型卡

### 17.6.1 三类文档的定位

| 文档 | 提出者 | 描述对象 | 主要用途 | 篇幅 |
|---|---|---|---|---|
| Datasheets for Datasets | Gebru 等（2021） | 数据集 | 记录动机、组成、收集、预处理、分发、维护 | 较长，问卷式 |
| Data Cards | Google 提出的实践 | 数据集 | 结构化、机器可读的摘要 | 中等，字段固定 |
| Model Cards | Mitchell 等（2019） | 训练好的模型 | 记录预期用途、训练数据、评估结果、限制 | 中等 |

三者的共同点是都要求回答一组固定问题，而不是自由描述。这一设计的目的与调查问卷的设计目的一致：**用固定字段强制披露容易被省略的信息**（数据来源、失败模式、不适用场景），并对不同对象之间提供可比的结构。

### 17.6.2 数据卡字段清单

数据卡（Data Card）的标准字段包括：数据集名称与版本、维护者与联系方式、许可、创建动机与资助来源、数据组成（实例数、字段含义、单位）、收集过程（抽样设计、时间窗口、采集设备或平台、知情同意情况）、预处理与标注流程（标注者数量、一致性度量、清洗规则）、推荐使用场景与明确不推荐场景、分发方式与获取条件、维护计划与更新频率。

对统计研究而言，标准字段之外还应补充五项：**抽样设计与目标总体**（样本对哪个总体有代表性，是否概率抽样）、**缺失机制**（缺失是完全随机 MCAR、随机 MAR 还是非随机 MNAR，以及判断依据）、**权重与设计变量**（分层、聚类、整群抽样的标识变量与权重）、**测量误差**（变量是实测、自报还是派生，已知的测量误差量级）、**可识别性前提**（若用于因果分析，需要哪些假定才使目标量可识别，见第 16 章）。

### 17.6.3 模型卡字段清单

模型卡（Model Card）的标准字段包括：模型名称与版本、开发者与联系方式、模型类型与架构、训练数据与数据卡引用、训练过程（目标函数、超参数、算力）、预期用途、超出范围的用途、评估数据与方法、量化结果（分群体报告）、限制与已知失败模式、伦理考虑与缓解措施。

统计学者使用模型卡时应特别关注**分群体评估是否附带不确定性**。只报告整体准确率会掩盖子群体上的性能差异，而子群体样本量小、点估计噪声大，因此分群体指标必须同时给出样本量与置信区间，否则"某群体表现差"这一判断本身可能只是抽样波动。

### 17.6.4 数据卡与模型卡的归档

两类卡片应随数据、模型一起版本化，并在论文中以链接形式引用。归档时的三条检查：卡片中的哈希是否与数据/权重的实际哈希一致；卡片中的脚本路径是否存在于仓库的对应 commit；卡片声明的"不适用"场景是否与论文实际用法冲突。第三项最容易被忽略，也是最容易被审稿人指出的一项。

## 17.7 复现检查

### 17.7.1 复现的分级

"可复现"不是一个二值属性。按证据强度从弱到强分为四级。

| 级别 | 名称 | 要求 | 证据 |
|---|---|---|---|
| L1 | 重跑（rerun） | 在同一环境中按给定命令重跑，得到一致结果 | 重跑日志与哈希比对 |
| L2 | 重建（rebuild） | 从锁文件或镜像在新机器上重建环境后重跑，结果在容差内一致 | 新环境指纹 + 结果对比表 |
| L3 | 独立实现（reimplement） | 由第三方按论文描述独立写代码，结论方向一致 | 独立仓库 + 对比报告 |
| L4 | 稳健性复现（robustness） | 在新数据或改动设定下，主要结论仍成立 | 稳健性分析表 |

一篇论文声称"可复现"时应指明是哪一级。多数论文只能达到 L1 或 L2，这已比不提供环境信息的状态好得多；L3 与 L4 属于额外的可信度证据，通常出现在复现研究或争议性结论的核查中。

### 17.7.2 复现检查清单（30 条）

下列清单按"环境—数据—代码—随机性—结果—结论"六组组织，每组五条。检查方式为逐条打勾并记录证据位置。

**环境**
1. 提供锁文件或容器镜像，且镜像以摘要（`sha256`）固定而非 `latest` 标签。
2. 记录操作系统、内核、CPU 型号、GPU 型号与驱动版本、CUDA/cuDNN 版本。
3. 记录随机数生成器与确定性开关（`PYTHONHASHSEED`、`use_deterministic_algorithms`、`CUBLAS_WORKSPACE_CONFIG` 等）。
4. 明确解释器版本与关键数值库（BLAS/LAPACK）的实现与线程配置。
5. 在新机器上从零构建一次，记录构建耗时与失败点。

**数据**
6. 原始数据与中间数据均给出内容哈希（`sha256`）或 DVC 指针。
7. 数据的获取方式、日期、许可、版本可追溯；外部数据给出下载脚本与快照。
8. 数据字典齐全：变量含义、单位、取值域、编码规则、缺失值编码。
9. 训练/验证/测试（或调优/评估）的划分依据与划分脚本公开，无交叉污染。
10. 存在不可公开数据时，给出脱敏流程、访问申请路径与审核方。

**代码**
11. 代码仓库给出精确 commit 哈希或 tag，并在论文中引用。
12. 所有脚本可非交互执行，无依赖手工点击或临时改动的参数。
13. 无硬编码的绝对路径、用户名、密钥与临时目录。
14. 入口单一化：一个命令或一条 Makefile 目标完成端到端运行。
15. 依赖安装命令完整，安装后不需要联网下载额外资源，或下载源可指定。

**随机性**
16. 全局种子固定，且种子写在配置文件而非散落在代码中。
17. 覆盖全部随机来源：初始化、数据洗牌、dropout、采样、解码参数、客户端抽样。
18. 并行与 GPU 归约的非确定性被显式处理（确定性开关或多次运行取分布）。
19. 报告多次运行的分布（均值、标准差、最小值、最大值），而非单次结果。
20. 使用外部 API 时固定模型快照版本与解码参数，并保存原始响应。

**结果**
21. 论文中的数字由脚本生成，可追溯到输出文件，无手工誊抄。
22. 关键指标附带不确定性（置信区间、标准误、跨运行极差）。
23. 中间产物可被重建，且重建结果与归档一致（哈希比对）。
24. 计算耗时、峰值显存/内存、能耗被记录。
25. 每次运行有对应的 manifest 文件，把输入与输出一一绑定。

**结论**
26. 论文主张与代码产出之间存在显式映射（哪个表/图支撑哪个论断）。
27. 稳健性检验（不同种子、不同子集、不同设定）的结果被报告。
28. 与基线的比较使用配对设计或重复测量，而非独立样本比较。
29. 失败与阴性结果被记录并可查，未隐藏未成功的尝试。
30. 给出复现联系人、复现窗口期与环境失效时的应对方案。

### 17.7.3 独立复现者制度

独立复现者（independent reproducer）是指未参与原始分析、按文档独立执行一次复现的人。制度要点如下。

人选上，复现者应不是原分析的直接参与者，但属于同一课题组或相邻领域，以避免因完全陌生而卡在基础操作上。复现者不得提前看到"应该得到什么结果"，只拿到代码、数据与文档；若复现过程中需要向原作者提问，所有问答应被记录在案，作为文档的缺陷证据。

产出物是一份复现报告，包含：使用的机器与环境、按文档执行的实际命令与偏离之处、每一条检查项的通过情况、得到的关键数字与原文数字的对比表、失败项的诊断、以及总体结论（达到哪一级）。复现报告应与论文一同归档或作为补充材料发表。

激励问题上需要正视：复现工作不产生新的科学发现，因此在以新颖性为评价标准的体系中不被计入。可行的补救方式是把复现报告作为可引用的成果（有 DOI 的补充材料或数据论文），并在项目组内把复现轮换排入常规工作量。部分出版机构设有结果复现环节或复现编辑角色，具体形式与适用范围以各机构的当期政策为准。

内部复现的最小可行安排是：投稿前由组内一名未在该项目上投入的成员执行一次 L1/L2 复现，耗时通常可控，却能发现绝大多数环境问题与文档缺失。

### 17.7.4 自动校验脚本

清单中可自动化的条目（6、11、21、23、25）可以用脚本批量校验，避免人工逐项核对。

```python
# tools/check_repro.py：复现检查的自动部分
import hashlib, json, pathlib, subprocess, sys

def sha256(p):
    h = hashlib.sha256()
    with open(p, "rb") as f:
        for b in iter(lambda: f.read(1 << 20), b""):
            h.update(b)
    return h.hexdigest()

def check(manifest_path="runs/manifest.json", code_files=("src",)):
    m = json.load(open(manifest_path))
    problems = []

    # 6/23：数据哈希与产物哈希是否仍然匹配
    for role in ("inputs", "artifacts"):
        for path, want in m.get(role, {}).items():
            if not pathlib.Path(path).exists():
                problems.append(f"[缺失] {role}: {path}")
            elif sha256(path) != want:
                problems.append(f"[哈希不一致] {role}: {path}")

    # 11：代码 commit 是否与 manifest 记录一致
    head = subprocess.check_output(["git", "rev-parse", "HEAD"]).decode().strip()
    if head != m.get("git_commit"):
        problems.append(f"[commit 不一致] 记录={m.get('git_commit')} 当前={head}")

    # 13：是否存在硬编码的绝对路径或疑似密钥
    for d in code_files:
        for f in pathlib.Path(d).rglob("*.py"):
            t = f.read_text(encoding="utf-8", errors="ignore")
            if "/home/" in t or "C:\\\\Users" in t:
                problems.append(f"[硬编码路径] {f}")
            if "sk-" in t.lower():
                problems.append(f"[疑似密钥] {f}")

    print("PASS: 无问题" if not problems else "\n".join(problems))
    return 0 if not problems else 1

sys.exit(check())
```

### 17.7.5 结果校验和链与 manifest 的最小演示

17.7.4 的脚本回答"现在的文件与记录是否一致"，还需要另一个动作回答"记录本身是否可信"：对每次运行的输入与产物计算 SHA-256，写进 manifest，使结果与产生它的输入被哈希不可抵赖地绑定。这个机制在统计实践中的对应物是数据集的校验和发布；在链式记账的语境里，若让每个 run 的 manifest 记录上一个 run 的 manifest 哈希，就得到一条校验和链（checksum chain），任何一次中途改动都会使后续所有环节对不上。第 18 章 18.9.3 节的审计日志哈希链是同一原理在权限审计上的应用，此处不重复展开。

下面的脚本演示最小闭环：构造一次运行的输入与产物、写 manifest、逐文件校验、篡改一个数字后再校验。在 Python 3.10 下实测：

```python
# 结果校验和链：对一次运行的产物做 SHA-256、写 manifest、校验并演示篡改检出
import hashlib, json, pathlib

BASE = pathlib.Path("runs_demo")

def sha256_file(p):
    h = hashlib.sha256()
    with open(p, "rb") as f:
        for b in iter(lambda: f.read(1 << 20), b""):
            h.update(b)
    return h.hexdigest()

# ---- 1. 构造一次运行的输入与产物 ----
run = BASE / "runs" / "20260925T081500Z"; run.mkdir(parents=True)
(run / "input.csv").write_text("x,y\n1,2\n3,4\n5,7\n", encoding="utf-8")
metrics = {"estimate": 0.8731, "se": 0.0122, "n": 12480}
(run / "metrics.json").write_text(json.dumps(metrics), encoding="utf-8")

# ---- 2. 写 manifest：把全部输入与产物哈希绑定 ----
manifest = {
    "run_id": run.name,
    "created_utc": "2026-09-25T08:15:00Z",
    "git_commit": None,
    "command": "python fit.py --data input.csv",
    "inputs":    {"input.csv":    sha256_file(run / "input.csv")},
    "artifacts": {"metrics.json": sha256_file(run / "metrics.json")},
}
mp = run / "manifest.json"
mp.write_text(json.dumps(manifest, indent=2, ensure_ascii=False), encoding="utf-8")

# ---- 3. 校验函数：逐文件重算哈希并与 manifest 比对 ----
def verify(run_dir):
    m = json.loads((pathlib.Path(run_dir) / "manifest.json").read_text(encoding="utf-8"))
    ok = True
    for role in ("inputs", "artifacts"):
        for name, want in m[role].items():
            p = pathlib.Path(run_dir) / name
            if not p.exists():
                print(f"FAIL  {role}/{name}: 文件缺失"); ok = False
            else:
                got = sha256_file(p)
                print(f"{'PASS' if got == want else 'FAIL'}  {role}/{name}")
                ok &= (got == want)
    return ok

print("== 首次校验 ==")
assert verify(run)

# ---- 4. 篡改演示：改一个数字后校验失败 ----
metrics["estimate"] = 0.8732
(run / "metrics.json").write_text(json.dumps(metrics), encoding="utf-8")
print("== 篡改后校验 ==")
assert not verify(run)

# ---- 5. 运行间链：下一 run 的 manifest 记录上一 run 的 manifest 哈希 ----
prev_sha = sha256_file(mp)
print(f"链头: manifest.json sha256 = {prev_sha[:16]}...（写入下一个 run 的 manifest.parent 字段）")
```

实测输出：

```text
== 首次校验 ==
PASS  inputs/input.csv
PASS  artifacts/metrics.json
== 篡改后校验 ==
PASS  inputs/input.csv
FAIL  artifacts/metrics.json
链头: manifest.json sha256 = aae3405b81786ee7...（写入下一个 run 的 manifest.parent 字段）
```

演示里被检出的改动只有 0.0001——恰是手工誊抄或"顺手修一下数字"最可能造成的差异量级，哈希比对对它一视同仁。两点补充。其一，此处的哈希绑定只适用于不随环境变化的字节流（数据、代码、manifest、日志）；对 17.2.1 演示一那种从第七位小数起随线程数漂移的数值产物，重跑的哈希必然不同，属于 17.7.1 的 L2 级容差比较而非 L1 级哈希比对，两级检查的对象应事先分清。其二，manifest 的哈希字段防的是无意的漂移与事后篡改，但它不能防止"生成 manifest 时就写错"——所以 17.7.3 的独立复现者要在另一台机器上从头重算这些哈希，两条机制互为补充。

## 17.8 云平台操作复现

### 17.8.1 平台类型与取舍

云 GPU 平台按控制粒度分为三类：交互式 notebook（Colab、Kaggle Notebooks 等）、按实例租用的 GPU 主机（AutoDL、阿里云 PAI-DSW / ECS GPU 实例、以及国际云厂商的 GPU 实例）、以及校级或国家级 HPC 集群（Slurm 加模块系统或 Apptainer）。

| 类型 | 环境固化方式 | 数据持久化 | 主要风险 |
|---|---|---|---|
| 交互式 notebook | 安装脚本 + 依赖清单 | 依赖网盘挂载，会话结束即失 | 会话临时，会话间环境不一致 |
| 按实例租用的 GPU 主机 | 自定义镜像、实例转镜像、conda-pack | 数据盘可保留，实例可释放 | 未做镜像即释放，环境不可恢复 |
| HPC 集群 | 模块 + Apptainer SIF | 项目目录长期保留 | 无 root 权限，软件安装受限 |

选择依据是三件事：数据能否上传（涉密数据原则上不得上传公有云，见第 18 章）、任务时长（交互式 notebook 有会话时长上限）、以及是否需要可归档的环境（需要则必须有镜像导出能力）。

### 17.8.2 环境快照与镜像导出

环境固化的手段按"可逆性"从弱到强排列：记录安装命令、导出依赖清单、打包整个环境目录、导出整个实例的镜像。前两种在新机器上需要重新联网解析依赖，后两种可以直接恢复。

```bash
# 层级一：依赖清单（可移植，需重新解析）
conda env export --no-builds -n repro > environment.yml
conda list --explicit -n repro > spec-file.txt      # 同平台内可精确重建
pip freeze --all > requirements.txt
uv export --format requirements-txt > frozen.txt

# 层级二：打包整个环境目录（离线可恢复，同平台）
pip install conda-pack
conda pack -n repro -o repro-env.tar.gz
# 在目标机器上：
mkdir -p /opt/repro && tar -xzf repro-env.tar.gz -C /opt/repro
source /opt/repro/bin/activate

# 层级三：容器镜像（跨平台，需先构建）
docker commit <container_id> statproj:2026.09
docker save statproj:2026.09 | gzip > statproj_2026.09.tar.gz
sha256sum statproj_2026.09.tar.gz > statproj_2026.09.tar.gz.sha256

# 层级四：实例转镜像（各平台的入口与命名不同，以平台当期文档为准）
# 通用原则：先清理临时文件与密钥，再停止任务，最后执行"保存镜像/创建镜像"
```

关键操作次序是：**先清理，后保存**。密钥、令牌、SSH 私钥、含个人信息的日志一旦被打进镜像，会随镜像被分发。保存前应删除 `~/.bash_history`、`~/.ssh` 下的私钥、环境变量文件中的明文密钥，以及临时目录中的中间数据。

### 17.8.3 一次完整的云端复现流程

```bash
# ---- 0. 本地准备：确认代码干净且可追溯 ----
git rev-parse HEAD > runs/commit.txt && git status --porcelain

# ---- 1. SSH 配置（~/.ssh/config）----
# Host autodl
#   HostName <平台提供的连接地址>
#   Port <平台提供的端口>
#   User root
#   IdentityFile ~/.ssh/id_ed25519

# ---- 2. 上传代码（排除 .git 与原始数据，数据另走对象存储）----
rsync -av --exclude '.git' --exclude 'data/raw' --exclude '.venv' \
      ./ autodl:/root/proj/

# ---- 3. 远端恢复环境 ----
ssh autodl 'source ~/miniconda3/etc/profile.d/conda.sh && \
            conda env create -f /root/proj/environment.yml && \
            conda activate repro && pip install -r /root/proj/requirements.txt'

# ---- 4. 后台运行（tmux 便于断线后重连查看）----
ssh autodl 'tmux new-session -d -s run "cd /root/proj && \
            source ~/miniconda3/etc/profile.d/conda.sh && conda activate repro && \
            python run.py > run.log 2>&1"'
ssh autodl 'tmux attach -t run'          # 查看进度（Ctrl-b d 脱离）

# ---- 5. 监控资源 ----
ssh autodl 'nvidia-smi --query-gpu=utilization.gpu,memory.used,power.draw \
            --format=csv -l 5'

# ---- 6. 结果回传与校验 ----
rsync -av autodl:/root/proj/results/ ./results/
ssh autodl 'cd /root/proj && sha256sum results/* > results.sha256'
rsync -av autodl:/root/proj/results.sha256 ./ && sha256sum -c results.sha256

# ---- 7. 释放：确认镜像已保存、结果已回传后再释放实例 ----
```

```bash
# 对象存储中转（rclone，远端名称以本地配置为准）
rclone copy ./data/raw remote:bucket/proj/raw --progress
rclone copy remote:bucket/proj/results ./results --progress
```

Colab 一类交互式 notebook 的额外注意事项有三条：会话结束时虚拟机会被回收，因此所有产物必须在会话内写回网盘或对象存储；每次会话的环境需要重新安装依赖，故应把安装步骤写成一个可重复执行的单元并记录 `pip freeze` 的输出；免费档的 GPU 型号与可用性不固定，跨会话的性能比较会混入硬件差异，这类比较应视为带有额外噪声来源，必要时按 17.2.1 的方法把"硬件"也作为一个随机效应纳入。

### 17.8.4 成本与释放

云端复现的成本由三部分构成：GPU 实例费、存储费、以及出网流量费。控制手段包括：使用抢占式或竞价实例（可能被回收，需配合断点续跑）、把原始数据放在对象存储而非实例数据盘、结果压缩后再回传。

释放环节的常见失误是"先释放后发现镜像没保存"或"释放后数据盘一起被删"。检查次序应为：结果已回传且校验通过 → 环境已固化为镜像或锁文件 → 数据盘内容已备份 → 释放实例。多数平台对停止状态的实例仍收取存储费，长期不用的实例应释放而非停机。

## 本章小结

1. 可复现的单元在 AI 研究中扩展为七类对象：代码、提示词与 Skill、数据、模型权重、环境、配置与运行日志；每一类都需要一个可引用的标识符。
2. 环境不确定性是可量化的一类方差来源，可用单因素随机效应模型 $Y_{mr}=\mu+b_m+\varepsilon_{mr}$ 估计 $\sigma_b$ 与 $\sigma_e$，并以 ICC 度量换环境的相对影响；环境差异若与处理条件相关则构成混杂，应以区组设计消除。
3. 容器不等于可复现：基础镜像漂移、构建期依赖漂移、层缓存与运行时驱动差异四类漂移仍在，锁定手段是按 `sha256` 摘要引用基础镜像并归档镜像本体，而非仅保存 Dockerfile。
4. 锁文件的常见错误是粒度错误而非缺失：`conda env export` 需加 `--no-builds`，`pip-compile` 需 `--generate-hashes`，`renv.lock` 不覆盖系统库。
5. 实验追踪是预注册与实验记录簿的机器化版本，其治理对象是研究者自由度；探索性运行与确认性应用应以 tag 区分并全部记录。
6. 验证日志必须保存失败记录，否则证据基础因选择性报告而扭曲；形式化验证日志的关键检查项是 `sorry` 计数与 `#print axioms` 输出中是否出现 `sorryAx`。
7. 数据卡除标准字段外应补充抽样设计、缺失机制、权重与设计变量、测量误差、可识别性前提五项统计字段；模型卡的分群体指标必须同时给出样本量与置信区间。
8. 复现分为重跑、重建、独立实现、稳健性复现四级，论文应声明所达到的级别；独立复现者制度的产出物是可归档的复现报告。
9. 云平台复现的操作次序是"先清理、后保存"，密钥与含个人信息的文件不得进入镜像；释放实例前须确认结果已回传并校验。
10. 环境漂移的实测显示：良态线性估计下数值漂移（约 $10^{-7}$）远小于抽样误差但足以破坏比特级复现，哈希比对应只用于不随环境变化的字节流，数值产物用带容差的比较；大数相消的计算中数值噪声可超过抽样噪声二十倍以上，环境方差分量应当实测而非假定。manifest 校验和与 JSONL 验证日志（含失败记录）是无需外部依赖、当日可落地的最小留证手段。
