# 第14章 人机协作、众包与大规模形式化工程


## 本章导读

前四章讨论的都以"一个研究者面对一个问题"为基本单位。有一类数学与统计工作不满足这个前提：命题已经被人类证明，但把证明翻译成机器可检查的形式需要数千个引理、数十万行代码、数十人月的劳动。这类工作的瓶颈不在智力，而在组织。

本章要解决的是：这种规模的工作，人与 AI 的分界线应该划在哪里，任务应当按什么粒度切开，切开之后如何保证拼起来的东西仍然正确，以及谁该被记为作者。

线索按四个层次展开。14.1 节给出协作模式的层次划分与责任边界，这是全章的概念框架。14.2 至 14.6 节是案例：等式理论项目（ETP）是迄今规模最大的众包形式化项目，也是"普通人可参与"这一特性的来源；PFR 猜想形式化展示了蓝图化与 DAG 拆解如何把一个研究级证明切成可并行认领的子任务；Prove2Me 与 Fuse 是两种为规模化协作而设计的平台形态；14.6 节记述陶哲轩从 2023 年起持续至今的个人实践，以及他在 2026 年对 AI 数学能力的公开评估。14.7 与 14.8 节落到操作：如何组织一个多人 + AI 的形式化项目，贡献质量的统计描述（贡献分布的形状、审核的抽样结构、独立形式化的一致性），协作场景中的 AI 提示词模板与校验清单，以及普通研究者从认领一个 issue 到提交一个 PR 的完整流程走查，最后是大规模形式化工程的实践清单。14.9 节讨论局限与争议，包括"形式化是否等于理解""自动化是否会稀释洞察""贡献归属"，以及 2026 年发生的两次公开表态。

两点预先说明。第一，本章多处涉及 2026 年的事件（ICM 演讲、菲尔兹奖得主公开声明、各类平台发布）。凡属公开报道而尚无同行评议论文或可编译代码支撑的，文中均以"据公开报道"标明，只作陈述不作引申。第二，第 12 章已讨论过的具体系统（AlphaProof、DeepSeek-Prover-V2、费马大定理形式化等）在本章只在与"组织方式"相关的部分出现，技术细节不重复。

## 14.1 人机协作模式

### 14.1.1 三种协作层次

人机协作不是一个单一概念。按"谁提出方向"与"谁承担验证"两个维度，可以划分出三种层次，三者的责任结构完全不同。

| 层次 | 方向由谁定 | 执行由谁做 | 验证由谁做 | 适用任务 | 典型失效 |
|---|---|---|---|---|---|
| 人主导、AI 辅助 | 人 | 人以 AI 为工具 | 人（可辅以编译器） | 探索性推导、文献调研、代码编写、绘图 | 人把 AI 的输出当作已验证结论 |
| AI 主导、人审核 | 人给出问题与规范 | AI | 人或机器逐条复核 | 大规模枚举、批量转写、候选证明生成 | 审核带宽不足，审核退化为抽查 |
| 对等迭代 | 交替 | 交替 | 机器（编译器/评估器）为主，人做语义复核 | 形式化工程、程序搜索、猜想—反例循环 | 双方都以为对方检查过了 |

第一种层次是日常科研的形态，AI 在其中是加速器而非代理人。第二种层次在批量任务上效率最高，但它的成本结构容易被误判：审核一个错误的证明通常比自己写一个正确的证明更慢，因此当 AI 的错误率超过某个阈值时，"AI 生成 + 人审核"会慢于"人自己写"。这个阈值随任务而定，应当在项目开始时估计而不是事后发现。第三种层次是本章的重点，它的成立前提是**机器验证**，因为只有机器验证才能把"谁检查过了"这个问题从流程中移除。

### 14.1.2 任务分解与"人在回路"的位置

规模化协作的可行性取决于一件事：任务能否被切成彼此弱耦合的块。形式化工程之所以适合协作，正是因为它天然有这种结构——一个大证明的依赖图是一个有向无环图（DAG），每个节点是一个引理，节点之间的边是依赖关系。只要声明（statement）被固定，一个节点的工作就不依赖于其他节点**如何**被证明，只依赖于它们**已经**被证明。这个性质使并行成为可能，也是 14.4 节"陈述与证明分离"这一设计的依据。

人在回路（human-in-the-loop）的位置决定质量。可以放的位置有四个：

1. **问题定义与选题**：不可外包。选题决定了整个项目的价值，AI 可以提供候选方向但不能判断价值。
2. **陈述的形式化**：不可外包，但可以辅助。形式化陈述与原命题的语义等价性由人签字确认——机器不管语义，一个统计量漏掉可测性条件照样编译通过。这是第 11.9 节已经强调过的"忠实性复核"。
3. **证明的填充**：可以交给 AI，由编译器逐条检查。这是协作中唯一可以完全放手的环节。
4. **结果的解释与写作**：不可外包。形式化通过不等于人类理解了结构，从通过的代码到可传播的数学之间仍然需要人的工作。

四者中第 2 项与第 4 项是最容易被压缩的，也是最不该被压缩的。

### 14.1.3 责任边界

| 环节 | 人类 | AI | 机器验证 |
|---|---|---|---|
| 选题与问题定义 | 主责 | 提供候选方向 | 不参与 |
| 蓝图与 DAG 拆解 | 主责 | 提出候选拆分 | 检查依赖是否闭合 |
| 陈述的形式化与语义复核 | 主责，不可外包 | 生成候选陈述 | 类型检查（不检查语义等价） |
| 引理检索与复用 | 审核 | 检索与排序 | 不参与 |
| tactic 生成与证明填充 | 不参与 | 主责 | 逐步校验 |
| 失败重试与死路归档 | 设定终止条件 | 主责 | 提供报错 |
| 结果解释与理论整合 | 主责，不可外包 | 辅助 | 不参与 |
| 贡献记录与署名 | 主责 | 不参与 | 提供可审计的提交记录 |

表中"死路归档"一行常被忽略。多智能体或多志愿者协作时，被放弃的尝试如果不记录，后来者会重复走进同一条死路。Prove2Me 把失败路径显式归档作为平台机制之一（见 14.4 节），这一设计值得任何协作项目借鉴。

## 14.2 等式理论项目

### 14.2.1 问题与规模

等式理论项目（Equational Theories Project，ETP）由陶哲轩于 2024 年 9 月 25 日在个人博客上发起。研究对象是**原群**（magma）：一个集合 $M$ 配一个二元运算 $\diamond:M\times M\to M$。等式定律（law）是用 $\diamond$ 与若干形式变元写成的恒等式，例如交换律 $x\diamond y\simeq y\diamond x$，或 Tarski 公理 $x\simeq y\diamond(z\diamond(x\diamond(y\diamond z)))$。

项目的任务是：对所有能用不超过四次运算写出的等式定律（共 **4694** 条），判定两两之间的蕴含关系是否成立。需要判定的蕴含总数为 $4694\times(4694-1)=22{,}028{,}942$ 条。对每一条，要么证明它成立，要么给出一个反例（一个使前提成立而结论不成立的原群）。

这个规模使问题既不能靠手工完成（两千多万次判定），也不能靠纯形式化完成（为每条蕴含都写 Lean 证明，编译成本不可承受）。项目的实际做法是分层推进，见 14.2.3 节。

### 14.2.2 为什么适合普通人参与

ETP 的关键设计在于它对参与者的技能要求极低。判定一条蕴含不成立，只需给出一个有限原群的乘法表；判定它成立，通常是写一个几行的 Lean 证明或用自动定理证明器搜索。参与者**不需要理解整个证明的整体结构**，甚至不需要是代数学者——这一点在 PFR 项目中已被陶哲轩观察到，在 ETP 中被放大为设计原则。

参与门槛低带来三个后果。第一，贡献者群体的技能构成高度异质，项目管理必须容忍"有人只懂 Lean、有人只懂自动定理证明器、有人只懂 Python 枚举"；第二，任务必须自足（self-contained），即一个任务所需的全部信息都在任务卡里，不需要参与者去读整个项目；第三，验证必须完全自动，因为无法指望人类审核者对异质贡献做一致判断。这与 14.1.3 节的责任边界表是一致的：把人的判断压缩到陈述层，把执行与验证交给机器。

### 14.2.3 自动化、LLM 与人类专家的三层分工

| 层次 | 承担的工作 | 工具 | 产出 | 谁复核 |
|---|---|---|---|---|
| 自动化层 | 有限原群的批量枚举与反例搜索；蕴含的传递闭包推导 | Python 脚本、有限原群搜索、Vampire / Prover9 / Mace / Duper / Z3 / MagmaEgg 等 ATP | 大量蕴含的真假判定 | 由 Lean 对代表性子集复核 |
| LLM 层 | 把判定转写为 Lean 代码；补全 tactic；给出候选证明思路 | GitHub Copilot 等代码补全与生成 | Lean 代码片段 | Lean 内核逐行检查 |
| 人类层 | 提出策略、处理 ATP 失败的硬案例、维护蓝图与仪表盘、发现结构性规律 | 数学直觉与工程判断 | 定理、工具、新概念 | 同行在 Zulip 上讨论 |

三通道如何汇入同一条校验流水线，可以用一幅示意图概括。它的要点是：三个通道并行推进、互不等待，但所有产出汇入同一个 Lean 内核校验，校验结果决定进入主线还是回传重试。

```text

                              │
              按依赖关系拆分为自足的任务卡（issue / 蓝图节点）
                              │
      ┌───────────────────────┼───────────────────────┐
      ▼                       ▼                       ▼
┌──────────────┐   ┌──────────────────┐   ┌──────────────────┐
│ 自动化通道    │   │ LLM 通道          │   │ 人类专家通道      │
```

图中"回传重试"这条边是整个设计的枢纽：失败不是终点，而是一份带报错信息的任务卡。自动化层与 LLM 层可以无限次消费它而不消耗人力，只有当两条机器通道都反复失败时，任务才真正落到人类层——这正是硬案例的下沉机制。

自动化层之所以能在两天内推进到 99% 以上，靠的是有限原群的批量枚举：对一条蕴含 $A\Rightarrow B$，只要找到一个使 $A$ 成立而 $B$ 不成立的原群，蕴含即被证伪，且验证成本只是对一张乘法表做有限次求值。其核心逻辑可以用几十行 Python 表达：

```python
import itertools

def variables(term):
    """term: 变元名（字符串），或 ('op', t1, t2) 表示一个二元运算节点。"""
    if isinstance(term, str):
        return {term}
    return variables(term[1]) | variables(term[2])

def evaluate(term, env, table):
    if isinstance(term, str):
        return env[term]
    return table[evaluate(term[1], env, table)][evaluate(term[2], env, table)]

def satisfies(law, n, table):
    """law: (lhs, rhs)；检查该定律在 n 阶原群上是否对所有赋值恒成立。"""
    names = sorted(variables(law[0]) | variables(law[1]))
    for vals in itertools.product(range(n), repeat=len(names)):
        env = dict(zip(names, vals))
        if evaluate(law[0], env, table) != evaluate(law[1], env, table):
            return False, env
    return True, None

def find_counterexample(law_a, law_b, n):
    """搜索满足 law_a 但不满足 law_b 的 n 阶原群；找到即证伪 law_a ⇒ law_b。"""
    for flat in itertools.product(range(n), repeat=n * n):
        table = [list(flat[i * n:(i + 1) * n]) for i in range(n)]
        ok_a, _ = satisfies(law_a, n, table)
        if not ok_a:
            continue
        ok_b, witness = satisfies(law_b, n, table)
        if not ok_b:
            return table, witness        # 反例：A 成立，B 在 witness 赋值下失败
    return None, None
```

这段代码只在很小的 $n$ 上可行——搜索空间是 $n^{n^2}$，$n=3$ 时约两万张表，$n=4$ 时已达 $10^9$ 量级。实际项目中使用同构化简、SAT 求解器与专用工具（Mace、MagmaEgg 等）来扩展可搜索的规模，但判定逻辑本身与上面完全一致：证伪一条蕴含只需一个对象，而证明它需要覆盖全部情形。第 12 章讨论过的证伪—证明不对称性，在这里是项目能在 48 小时内推进到 99% 的直接原因。

三层的分工是动态的：自动化层先扫掉绝大多数容易的蕴含，剩下的硬案例下沉到人类层；人类层解决一个硬案例通常会产生一个可被自动化层复用的引理。项目论文（arXiv:2512.07087）明确记述了这一推进方式，并指出出于编译效率的考虑，并非每一条蕴含都在 Lean 中被直接证明——项目只对较小的一组蕴含给出 Lean 证明，其余通过传递性（若 A 蕴含 B 且 B 蕴含 C，则 A 蕴含 C）与对偶对称性推导得出。这是一个重要的工程取舍：**用传递闭包换取编译成本**，代价是蕴含图上的每条边不再都有独立的机器证明。

### 14.2.5 工具链

ETP 用到的工具组合本身就是一份大规模形式化工程的清单：

- **Lean 4 与 Mathlib**：验证层，所有最终结论的判定依据。
- **leanblueprint**（Patrick Massot）：项目管理层，生成依赖图与网页/ PDF，供参与者查看哪些节点已完成、哪些待认领。
- **Lean Zulip 专设频道**：协调层，讨论、认领任务、报告进度。
- **GitHub 与 CI**：版本控制与自动构建，每次提交自动编译。
- **自动定理证明器**：Vampire、Prover9、Mace、Duper、Z3、MagmaEgg 等，批量处理。
- **自研界面**：ETP dashboard、Equation Explorer、Graphiti、Finite Magma Explorer，用于可视化蕴含图与原群搜索。

其中 dashboard 的作用值得单独指出：在一个有 50 人参与的项目里，"现在还剩什么没做"这个问题如果没有机器答案，协调成本会随人数超线性增长。仪表盘把进度查询从"问主持人"变成"查网页"，这是去中心化的前提。

## 14.3 PFR 猜想形式化

### 14.3.1 背景

PFR 猜想（Polynomial Freiman–Ruzsa 猜想，又称 Marton 猜想）是加性组合学的核心猜想之一，涉及阿贝尔群中集合的加法结构与其熵之间的关系。2023 年 11 月，Gowers、Green、Manners 与陶哲轩发表了该猜想在 $\mathbb{F}_2$ 上的自然语言证明。

论文完成后，陶哲轩在 Lean 社区发起形式化项目：把这篇新证明在 Lean 4 中形式化。项目从发起到完成用了约三周，2023 年 12 月 5 日宣布完成。这个速度在当时是异常的——同类工作通常需要数月至数年。

### 14.3.2 蓝图化与 DAG 拆解

项目的核心工程手段是把整篇论文拆成一张依赖图。每张节点是一个引理，边是依赖关系，节点有三种状态（已证明 / 进行中 / 未完成），由 leanblueprint 自动生成网页与依赖图。这张依赖图的形态大致如下（节点与分支为示意，非真实编号）：

```text
 目标定理：PFR（常数 C=12 版本）
     │
     ├── L1 逼近引理 ──── 依赖：Mathlib 已有结果（绿色：直接引用）
     ├── L2 熵不等式 ──── 依赖：L1
     │        ├── L2a 局部估计 ── 状态：已证明（绿）
     │        └── L2b 浓缩步骤 ── 状态：进行中（已认领）
     ├── L3 递归分解 ──── 依赖：L2
     │        └── L3a 归纳步 ──── 状态：未完成（待认领）
     └── 主定理组装 ───── 依赖：L2、L3
              │
              ▼
   leanblueprint 生成网页：节点按状态着色，依赖关系可点击，
   每个节点链接到对应的 Lean 陈述文件与 Zulip 讨论帖
```

认领者的视角下，这张图回答了三个问题：我该做什么（未完成节点）、我现在能不能做（上游是否全绿）、我做完之后谁受益（下游节点解锁）。把依赖图进一步压缩，就是下面这张原始资料中的流程图：

```text
[人类数学家自然语言论文]
        │
        ▼
┌───────────────────────────────────────────┐
│ 1. 蓝图化 (Blueprinting)                  │ ──► 利用 leanprover-community/blueprint
│    将复杂证明拆解为有向无环图 (DAG) 的 Lemma │
└─────────────────────┬─────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ 2. AI 辅助代码翻译 (LLM + Autoformalizer) │ ──► 使用 LLM (Copilot/GPT-4) 将简单 Lemma
│    将自然语言数学断言转译为 Lean 4 形式化代码 │     自动翻译为 Lean 4 的 Tactic 代码
└─────────────────────┬─────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ 3. Lean 4 形式化编译器 (Kernel)           │ ──► 绝对严格的类型检查机制；
│    自动校验每一个证明步骤的逻辑无瑕性     │     通过即意味着推理链无误
└───────────────────────────────────────────┘
```

蓝图化的价值不止于"看得见进度"。它把一个连续的工作（读完论文、理解全貌、再动手）切成离散的、可独立认领的单元，使贡献者可以在不理解全局证明的情况下完成一个局部子任务。陶哲轩在项目结束后的总结中明确记录了这一点：许多贡献者只做局部子任务，未必理解整体证明，甚至不在这个结果所属的数学领域（加性组合学）内。

需要说明的是图中第 3 步的"100% 正确"这一表述应当加限定：编译通过意味着**从所给定的公理与形式化陈述出发**的推理链无误，不意味着形式化陈述与原论文命题语义等价。语义等价性由人签字。

### 14.3.3 分工与经验

项目结束当天，陶哲轩在 Zulip 上做了一段总结，其中的量化信息对任何想组织类似项目的人都有参考价值：

- 他本人只贡献了约 **5%** 的代码行数；大部分时间花在数学侧（组织蓝图）与协调侧（协调贡献者）。他的判断是：这说明数学家可以领导 Lean 形式化项目，而不需要精通 Lean 编程（但至少需要能把引理陈述写出来的水平）。
- Yaël Dillies 在 48 小时内搭起了项目骨架；参与者的完整名单包括 Rémy Degenne、Sebastien Gouezel、Bhavik Mehta、Heather Macbeth、Kalle Kytölä、Paul Lezeau、Scott Morrison、Mauricio Collares、Patrick Massot、Arend Mellendijk、llllvvuu、Jonas Bayer、Floris van Doorn、Ben Eltschig、Mantas Baksys、Kyle Miller、Aaron Anderson、Rob Lewis 等。
- 最耗时的不是数学上最有趣的部分，而是技术上"显然"的步骤——最后是独立随机变量的性质那一类。
- 形式化只发现原论文中极少数笔误；问题比较多的是蓝图本身：某些标准假设（如可测性）有时被省略，依赖树有时画错。
- 编译整个项目约需半小时，不是瓶颈；瓶颈在人的可用性。

另一条经验与 AI 无关但极有说服力。项目形式化的是常数 $C=12$ 的版本。后来有人在 arXiv 上发布短文，指出对源论文做 5 处修改可把 12 降到 11。团队原本预期又要三周，实际做法是：把 Lean 中最终陈述里的 12 改成 11，观察哪些代码行变红，逐个按新方法修复；修复 5 行后又出现 10 行变红，继续处理。**一天之内**完成了整个证明向 $C=11$ 的更新。这个例子说明形式化产物具有高度模块化的性质：可以做出极局部的讨论与修改，而不必理解全体。陶哲轩把这种"只看 3 行就能诊断 1000 行代码里的问题"的能力称为 Lean 的独特之处。

### 14.3.4 对统计学者的启示

PFR 是纯数学问题，但组织方式可以直接迁移到统计理论的形式化（第 12.8 节的 AI4SLT 是一例）。迁移时需要注意统计证明的特殊难点：可测性、可积性、正则性条件在自然语言证明中常被省略，形式化会把它们全部暴露出来；随机变量的独立性、条件期望的形式化负担远高于代数结构。因此统计定理的蓝图化通常需要比 PFR 更细的粒度，且蓝图中必须显式列出正则性条件。第 11.4 节与第 12.8 节已给出具体案例。

## 14.4 Prove2Me 平台

### 14.4.1 定位与起源

Prove2Me 是哥伦比亚大学 DAPLab 的 Tianyi Peng、Shuze Chen 与 Henry Yuen、Kunal Marwaha 开发的开放式数学形式化协作平台。它的直接动因是一次失败：在费马大定理（FLT）的形式化任务上，早期几十个智能体直接协作时，每个智能体不知道别人已证明什么、自己该做什么，协作很快失效。据项目方记述，这些失败尝试最终只贡献了最终成果中约 7% 的非样板代码。

平台的核心抽象是 **mission**（任务）：一个结构化、边界清晰的证明义务。大型定理被组织成一棵定理陈述树／DAG，节点之间由 Lean 证明连接；人类与 AI 智能体都可以认领节点并行推进。

### 14.4.2 四个机制

| 机制 | 解决的问题 | 具体做法 |
|---|---|---|
| 定理 DAG | 智能体不知道别人已做了什么、自己该做什么 | 每条定理是一个节点，依赖关系是边；新智能体加入时先查 DAG，判断哪些已证、在证、待证 |
| 陈述与证明分离 | 修改证明会影响依赖它的其他工作；全量重编成本高 | 陈述一经提交即固定，与证明存放在不同文件，独立维护连接；编译时只重编变更文件 |
| 自然语言描述 | 智能体无法检索已有结果，容易重复劳动 | 每条定理附可搜索的自然语言描述，支持语义检索与复用 |
| 失败归档 | 死路被丢弃后反复重走 | 被放弃的尝试不删除，留给后续轮次使用 |

第四个机制值得强调。多数协作系统只记录成功路径，而大规模搜索中失败路径占比极高；保留失败记录使后来的智能体可以排除已知死路，其价值与成功记录相当。

### 14.4.3 规模数据

据项目方与 Anthropic 公布，FLT 形式化工程的公开数据为：

| 指标 | 数值 |
|---|---|
| 墙钟时间 | 11 天（数十个智能体并行，非单智能体连续运行） |
| 中间定理数 | 约 29,500 条 |
| Lean 4 代码规模 | 约 1,300 万行，为 Mathlib 的 5 倍以上 |
| 输出 token | 约 60 亿 |
| 最终构建 | 96 个并行任务，约 5 小时 32 分，全部通过 Lean 编译器检查 |
| 质量核验 | 与 Mathlib 自带的 FLT 陈述比对；另用 Rust 编写的独立内核 nanoda 复验 |

项目方同时划清了边界：它证明的是 Wiles 的人类证明可以被自动翻译为机器可逐步验证的 Lean 形式，证明路线沿用 Darmon–Diamond–Taylor 对 Wiles 证明的简化重述，使用 Lean 的三条标准公理、无额外假设；它**没有**发现新的数学定理。帝国理工学院的 Kevin Buzzard 在审阅后认为，这一成果为现代数学文献的自动形式化打开了大门，对同行评议与验证 AI 生成的数学结果都有意义。

平台还做了一次规模小得多的实验：研究者用三个个人版 Claude Max 账号，通过 Prove2Me 协作，用三天完成了维诺格拉多夫三素数定理（Vinogradov's three-prime theorem）的形式化。这个数字的意义在于：类似工作未必长期局限于大型实验室，只要任务拆解与协作机制足够成熟，普通研究团队也可能参与。

### 14.4.4 使用方式与边界

Prove2Me 目前以开放平台形式运行，网址为 beta.prove2.me，据项目方公布已有 186 个 mission 开放，覆盖数论、代数拓扑、组合学、图论、算术几何、优化与偏微分方程等方向。人类贡献者与智能体均可参与。

使用时需要注意三点。第一，平台提供的是**协调层**，不是证明能力本身；模型能力决定单个节点走多远，平台决定几十个智能体能否围绕同一目标持续协作。第二，DAG 上的节点声明仍然由人把关；与第 11.9 节一样，语义等价性机器不管。第三，平台产出的是可编译的代码，不自动产出可读的阐述——这一落差在 14.9 节会详细讨论。

## 14.5 Fuse 平台

### 14.5.1 公开资料的状况

需要如实说明：截至本章写作时，关于名为 Fuse 的形式化平台，可核验的公开技术资料（论文、仓库、API 文档）十分有限。它出现在若干形式化学习资源列表中，与 Aristotle、Leanstral、Archon 等系统并列，被描述为一种人机交互的形式化平台；但本章未能找到可据以描述其机制、接口与性能的一手材料。因此本节不对 Fuse 的具体功能做断言，只记述它在资源列表中的定位，并转而给出同类中**可核验**的实践，供读者参照。

若读者需要使用该平台，建议以官方发布的一手材料为准，并优先核实三件事：平台的验证层是什么（是否真的调用 Lean 内核）、陈述与证明是否分离、失败路径是否保留。这三点决定了它在 14.4.2 节那张机制表上的位置。

### 14.5.2 可核验的同类实践：Math Inc. 与 Gauss

在同一类"人类设计策略 + AI 生成 Lean 代码 + 内核验证"的模式上，Math Inc. 的 Gauss 自动形式化智能体有公开仓库与项目主页可查，可以作为该模式的具体样本。

| 项目 | 目标 | 规模 | 用时 | 仓库 |
|---|---|---|---|---|
| 强素数定理（strong PNT） | Tao 与 Kontorovich 于 2024 年 1 月提出的挑战 | 约 25,000 行 Lean，1,100 余条定理与定义 | 三周 | github.com/math-inc/strongpnt |
| 有限域 Kakeya 集下界（Dvir 2008） | 建立 Kakeya 集大小的下界 | 约 300 行 Lean | —— | github.com/math-inc/KakeyaFiniteFields |

两个项目的共同工作流是：人类提供 LaTeX 蓝图（blueprint）与关键引理的策略性指导，Gauss 生成大部分陈述与证明代码，Lean 内核逐条检查，人类复核关键引理。仓库结构也高度一致：Lean 源码目录、`blueprint/` 目录（LaTeX 蓝图与依赖图）、`home_page/`（Jekyll 站点）、`.github/workflows/`（CI）、`lakefile.toml` 与 `lean-toolchain`（版本锁定）。这一结构本身就是 14.8 节工程清单的现成模板。

据《科学美国人》报道，Math Inc. 用 Gauss 形式化 Viazovska 的球堆积证明（8 维与 24 维）后，数学界的反应相当冷淡，部分原因在于项目并未按许多专家期待的方式展开——这一过程性细节对评估"AI 形式化成果如何被共同体接受"有参考价值，属于 14.9 节讨论的范畴。

### 14.5.3 该模式的通用工作流

把上述实践抽象出来，这类平台的通用工作流是：

1. 人类写出 LaTeX 蓝图，把目标定理拆成引理 DAG；
2. 人类标注关键引理的策略（使用哪些已知结果、走哪条路线）；
3. AI 智能体按节点生成 Lean 陈述与证明；
4. Lean 内核编译，报错原文回传给智能体修改；
5. 人类复核关键节点与最终陈述的语义等价性；
6. CI 固化，依赖图更新，新节点解锁。

六步中第 1、2、5 步由人承担，第 3、4 步可全自动，第 6 步由工具承担。这是 14.1.3 节责任边界表的一次实例化。

## 14.6 陶哲轩 AI 数学实践

### 14.6.1 起点

陶哲轩于 2023 年 10 月 9 日在社交媒体宣布开始学习 Lean 4（"必要时使用 AI 协助"）。他选择的练手项目是自己一篇关于 Maclaurin 型不等式的论文：先按传统方式写完约 10 页证明，再转译为 Lean 代码，原估计一周完成，实际用了一个月。

这次练手有两个副产品。其一，形式化过程中发现原论文第 6 页的论证在 $n=3,k=2$ 时存在一个不易察觉的问题，他在论文新版本中添加了脚注说明。其二，他记录了 GitHub Copilot 在补全 tactic 时的表现，以及 Lean 的重写（rewrite）策略相对于 LaTeX 手工编辑的优势：在 LaTeX 中修改一个跨越多行的长表达式只能靠剪切粘贴，错别字会沿文档传播；在 Lean 中重写是自动且被验证的。

### 14.6.2 Blueprint 工作流

从 PFR 项目开始，陶哲轩的工作流固化为一套可复制的模式：

1. 用 LaTeX 写蓝图（blueprint），把目标定理拆成引理 DAG，每个节点写明陈述、依赖与证明思路的关键字；
2. 用 leanblueprint 生成网页，节点按状态着色（已完成为绿）；
3. 在 Zulip 开专设频道，用"待认领任务"帖协调；贡献者在帖子下认领节点；
4. 贡献者（人或 AI 辅助）提交 Lean 代码，CI 自动编译；只有通过的提交才合并进主线；
5. 主持人的工作是维护蓝图、处理卡点、验收语义等价性。

他在 PFR 项目总结中特别提到"待认领任务"帖的作用，并希望未来能与蓝图系统做更紧的集成——例如把任务认领与释放做成可被工具管理的"令牌"。这正是后来 Prove2Me 一类平台要解决的问题。

### 14.6.3 工具使用与具体案例

陶哲轩公开演示过的用法有三类：用 GitHub Copilot 加速 Lean 形式化；用 GPT-4 / Claude 探索证明思路、生成候选反例；用 LLM 做跨领域文献检索与数值实验。判断与筛选始终由人完成。

一个被公开记录的完整案例是 Erdős 问题 613 的反例构造。据公开报道，他用 ChatGPT 辅助形式化一个反例（44 条边、15 个顶点的图），最终 Lean 代码 1125 行，耗时近一周。他对该代码的评价是结构混乱、充满 AI 生成的冗长绕行与中途更改思路的痕迹——但因为 Lean 最终验证通过，每一句推理在逻辑上都是成立的。他的判断是：相对于自己从零写这 1125 行，AI 至少节省了一半以上的时间精力；同时，AI 会陷入狭窄思路反复产出同样的错误代码，需要人引导跳出。

### 14.6.4 对 AI 能力的公开评估

陶哲轩多次公开给出对 AI 数学能力的量化估计，其中被引用最多的是**开放问题成功率约 1–2%** 这一数字。需要准确理解它的含义：这不是"AI 能解决 1–2% 的数学问题"，而是在把 AI 工具系统性地应用到一批开放问题上时，单个问题的成功率约为 1–2%，且成功集中在那些此前无人认真尝试过、缺乏文献关注的问题上。已发表的进展数字（例如 Erdős 问题中由 AI 参与解决的数十个）与单个问题 1–2% 的成功率并不矛盾：前者是从上千个问题中筛出来的，后者是系统性应用时的命中率。

另一个广为流传的表述是"跳高运动员与攀岩者"（亦被译作"跳跃机器人与攀岩者"）的比喻。其语境如下：陶哲轩在 Dwarkesh Podcast 的一次长访谈（据公开报道为 2026 年 3 月）中，把数学研究比作在黑暗的山脉中攀爬——有矮墙、中墙、高墙和悬崖峭壁，研究者点蜡烛、画地图，慢慢摸清哪些可以攀爬、哪些墙上有可先抵达的局部路径。AI 工具像能跳两米高、比任何人类跳得都高的弹跳机器：把它们放到山脉里，它们能找到并翻越所有最矮的墙，成果令人兴奋；但它们不会在半空中停住、抓住岩壁上的把手、把同伴拉上来再继续攀爬。核心区别在于**能否从失败中累积局部进展**：人类会做标记、识别部分进展、调整策略，AI 要么一次成功要么彻底失败，且没有评估局部进展的办法。

同一访谈中他还给出了若干判断：AI 擅长广度，人类专家擅长深度，二者互补；当前做数学与科学的方式以深度为中心，因为那是人类的专长，需要重新设计以利用广度；辅助任务上他个人感到快了数倍，论文中代码与图形变多，但最困难的核心问题仍靠纸笔；把假说生成的成本压到近零之后，瓶颈移到了验证与评估。

### 14.6.5 2026 年的公开表态

据公开报道，陶哲轩在 2026 年 7 月于美国费城举行的国际数学家大会（ICM）上作了题为《人工智能时代的数学》（Mathematics in the Age of AI）的公众演讲。演讲内容可归纳为以下几点：

- 他把当前局面与 1900—1930 年的数学基础危机类比，认为 AI 迫使数学共同体重新检视自身的目标与实践，并把这称为数学价值观与实践的基础危机。
- 他提出一个工作假设：假定关于 AI 能力的一个相当强的版本为真，然后分析在此假设下数学的目标与价值应当如何重排。
- 他引古德哈特定律（Goodhart's law）说明：过去"解决问题"这一目标可以代表理解、理论建设、培养下一代等一揽子目标，因为这些目标在人的实践中同步推进；一旦用机器单独优化"解决问题"这一指标，目标之间会彼此分离。
- 他把一条数学结果的成熟过程描述为五个阶段：**生成**（generation）→ **验证**（verification）→ **阐释**（exposition）→ **发表与共同体接受** → **进入标准理论与教材**（canonization）。AI 可以大幅提高前端的生产效率，却无法自动扩建后端；每一阶段的通过率差异会造成"阻抗失配"，他把由此产生的积压称为**证明的消化不良**（proof indigestion），并判断数学将从证明稀缺的时代进入**证明过剩**的时代。
- 他提出的三条建议是：让 AI 使用的披露常态化；重新校准评价体系（降低"率先解决"的权重、提高"消化与整合"的权重）；以及一条经验法则——作者若不能对自己的结果作出清晰的、专家水准的讲解，就不应发表。他还公开说明自己的演讲幻灯片使用了 AI 做文字补全与图表生成。

同一报道提到，他在演讲中引用了 2026 年 5 月的 First Proof 基准作为受控条件下的证据：该基准用 10 道新的研究级数学问题测试了四个 AI 系统，据称其中 7 道达到可发表质量，单题算力成本在 10 至 1000 美元之间；他同时指出，关于 AI 数学能力的大部分证据并非在受控的科学条件下收集，存在严重偏差。他还引用了 2026 年 6 月的《莱顿人工智能与数学宣言》（Leiden Declaration on AI and Mathematics）作为共同体的一种回应。上述内容均据公开报道转述，具体数字以官方发布的论文或演讲材料为准。

## 14.7 众包工作流

### 14.7.1 任务拆分粒度

拆分粒度是众包项目最关键的设计决策。过粗则无人认领，过细则协调开销超过收益。经验规则：

| 粒度 | 特征 | 适用对象 | 风险 |
|---|---|---|---|
| 一个引理（10–50 行 Lean） | 自足、可独立验证、依赖清晰 | 大多数志愿者与智能体 | 数量过多时依赖图难以维护 |
| 一个证明步骤（1–10 行） | 极小、几乎无认知负担 | 自动定理证明器、LLM 批量处理 | 无法判断整体方向是否正确 |
| 一个章节／子定理（100–500 行） | 需要理解局部结构 | 有经验的贡献者 | 认领冲突，长时间无反馈 |
| 非证明任务（文献核对、反例枚举、可视化、工具开发） | 不需要证明能力 | 跨学科志愿者 | 容易被视为边缘贡献，需明确记入贡献列表 |

ETP 的经验是：**优先把非证明任务也做成正式任务**。该项目能在两天内推进到 99%，靠的是 Python 脚本的有限原群枚举，而不是形式化。把"写脚本枚举反例"与"写 Lean 证明"放在同一张任务板上，才能动员技能异质的群体。

### 14.7.2 CI 与权限

自动化验证是众包的前提，因为它把"是否接受这份贡献"的判断从人转移到机器。最小配置应包含：

- 每次 PR 触发 Lean 编译（增量编译，配合缓存）；
- 编译失败则禁止合并；
- 检查 `sorry` 与 `admit` 的残留（它们会让证明"通过"但内容为空）；
- 检查新增定理依赖的公理（`#print axioms`），出现 `sorryAx` 即为不完整；
- 检查未使用的导入与命名规范（可选）。

```yaml
# .github/workflows/lean-ci.yml —— 最小可用配置，具体版本以项目实际情况为准
name: Lean CI
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: leanprover/lean-action@v1        # 安装 elan 与 lean-toolchain 指定的版本
      - name: 拉取预编译缓存（省去数小时编译）
        run: lake exe cache get || true        # 缓存不可用时继续，不阻断构建
      - name: 编译
        run: lake build
      - name: 检查残留的 sorry / admit
        run: |
          if grep -rn --include="*.lean" -E "\b(sorry|admit)\b" . ; then
            echo "发现未完成的证明占位符"; exit 1
          fi
```

权限管理上有一条来自 PFR 项目的教训：陶哲轩在总结中提到自己多次用管理员权限直接推送更新而绕过 CI 并弄坏了构建。教训是**主持人的权限不应当大于贡献者**，或者至少应当走同一条 CI。这一点在 AI 智能体参与时更重要：智能体通常持有写权限，若绕过 CI 提交，错误会以机器速度扩散。

### 14.7.3 贡献归属

贡献记录应当在项目启动时就定好规则，而不是在写论文时决定。可参考 ETP 的做法：项目论文列出 30 位作者，并说明参与总人数约 50 人——即区分"达到作者标准的贡献者"与"参与者"。

需要预先约定的事项包括：什么算作者级贡献（通常是一条实质性的数学或形式化贡献，而非格式修改）；非证明类贡献（脚本、工具、可视化、协调）如何记录；AI 智能体的产出如何标注（由认领该节点的贡献者负责，还是单列）；以及贡献记录由什么来支撑（GitHub 提交记录是最客观的依据，应在项目说明中明确要求每个任务对应一个可追溯的 PR）。

Johan Commelin 在 PFR 项目总结帖中提出了一个尚未解决的问题：形式化工作者（formalizer）将如何被数学共同体承认，这类活动在学术就业市场上如何被估价。这个问题至今没有共识，但它决定了众包项目能否持续吸引人才，14.9 节会再回到这一点。

### 14.7.4 组织流程清单

1. 建立仓库，锁定 `lean-toolchain` 与 `lake-manifest.json`，README 写明如何编译。
2. 写蓝图（LaTeX），生成依赖图网页，作为唯一的任务来源。
3. 在 Zulip 或 Discussions 开协调频道，置顶"如何认领任务"的说明。
4. 建立任务看板，每个任务卡包含：节点编号、陈述原文、依赖节点、已知相关引理、难度标注、认领人。
5. 配置 CI（见上），并规定所有提交必须经 PR。
6. 规定贡献记录方式（PR 关联任务编号）。
7. 定期发布进度摘要（自动从 dashboard 生成），降低"还剩什么"的查询成本。
8. 项目启动时即约定署名规则与 AI 使用披露方式。

### 14.7.5 贡献质量的统计视角

把众包形式化项目当作一个数据生成过程来看，有几个统计结构值得单独描述。它们不涉及新的工具，但决定了这个工作流的可靠性边界。

**贡献分布的形状**。开源协作项目的贡献分布普遍呈重尾（heavy-tailed）：少数核心贡献者承担了大多数提交，长尾部分由只参与一两次的贡献者构成。这一形状在软件工程文献中被反复观察到，具体参数随项目差异很大，笔者不给具体数字。在本章已有可核查的例子中：PFR 项目里陶哲轩本人只贡献约 5% 的代码行数（14.3.3 节），说明即使是名义上的主持人，其产出也远不占主导；ETP 项目论文（arXiv:2512.07087）记录的 30 位作者与约 50 位参与者之间也存在明确的密度差——达到作者门槛的是少数。对组织者的含义有两条：其一，审核带宽应按核心贡献者的产出速率配置，而不是按人均产出配置；其二，长尾贡献者的每一份 PR 平均需要更多审核投入，因为他们对项目规范不熟悉，这一成本在估算项目吞吐量时常被低估。

AI 智能体的加入会改变这条分布曲线的形态，但不会取消重尾本身。智能体可以以机器速度充当长尾——大量小节点的提交由它完成——而头部仍然是少数人类核心贡献者与维护者。变化发生在约束一侧：当提交速率不再受人手限制时，14.7.2 节那种"编译失败禁止合并"的自动门槛成为唯一可扩展的过滤器，人力审核从"逐份把关"退到"处理自动门槛筛不掉的东西"，即语义层与规范层的争议。这也是 14.1.1 节第二种协作层次的失效模式（审核退化为抽查）在大规模场景下的重现，组织者应预先设计复核的分层规则，而不是默认每份 PR 都有人细读。

**审核作为两阶段抽样**。14.7.2 节的 CI 机制在统计语言里可以拆成两个阶段。第一阶段对**逻辑有效性**做普查：Lean 内核对每一份证明逐行检查，无抽样误差——这一阶段不存在漏检，代价是只能检查"从给定陈述出发推理是否成立"。第二阶段对**语义等价性**做人力审查：陈述是否忠实于原始命题（第 11.9 节的忠实性复核），这一阶段无法普查，因为机器不掌握"原命题是什么"，只能由人抽样复核。抽样审查的统计风险在于：复核概率与节点的显著度相关，而显著度又与错误率相关——越容易被质疑的陈述越可能被复核，越平庸的陈述越可能被默认放行，这意味着漏检并非均匀分布。一种低成本的缓解是把"哪些陈述经过了人工语义复核"记录在案，使已复核子集成为一个可追溯的抽样框，后来者据此判断每个结论的验证层级。

按"哪一阶段负责检出"给常见错误分类，两个阶段分工的边界会更直观：

| 错误类型 | 例子 | 由哪一阶段检出 |
|---|---|---|
| 证明推理错误 | tactic 序列不成立 | 内核普查，必然检出 |
| 证明不完整 | `sorry` 残留 | 内核与 CI（axiom 检查） |
| 陈述转写失真 | 漏掉独立性条件、量词次序颠倒 | 人工语义复核，抽样，可能漏检 |
| 定义版本不一致 | 与项目基底定义同名但不同义 | 人工语义复核与 review 讨论 |
| 规范偏差 | 命名、文档字符串、PR 描述不合规 | CI lint 与维护者 review |

表中前两行是可以完全交给机器的部分，后三行是人力审核的全部辖区。审核资源的分配问题，本质上是估计后三类错误的发生率并决定复核强度——这与调查抽样中"先估变异再定样本量"是同构的。

**标注者一致性**。经典标注任务用标注者一致性（inter-rater agreement，如 kappa 系数）评估编码规则的模糊程度。形式化协作有一个经典标注不具备的性质：若两位贡献者独立形式化同一自然语言命题，两个 Lean 陈述是否等价，本身可以（部分地）交给机器判定——在相同的定义基底下，可以尝试证明两个陈述互相蕴含，或检查它们是否定义相等。不一致即暴露自然语言陈述的歧义，其作用等同于问卷设计中"同一问题两种措辞得到不同答案分布"的信号。这是形式化协作相对一般众包的一个可检验性优势。需要如实说明：笔者没有找到关于"同一命题独立形式化一致率"的系统性公开数据，上述内容是机制分析而非经验测量；把它变成可报告的数字，本身是一个待做的实证工作。

一致性的机器判定还有一个层级差别值得写清。两个独立的形式化陈述 $S_1$ 与 $S_2$ 之间，可能存在三种关系：定义相等（definitional equality，机器瞬间判定）；可证等价（存在 $S_1\Rightarrow S_2$ 与 $S_2\Rightarrow S_1$ 的 Lean 证明，通常也能自动找到）；以及实质不等价（各自忠实于原命题的不同解读）。前两层机器可以代劳，第三层需要人读两个陈述的差别并裁决哪一种解读符合原意。实践中多数分歧落在第三层，而且往往追溯到上游某个定义的选择（例如"收敛"取的是依分布还是几乎必然）——分歧点本身就是原命题歧义所在的位置。

### 14.7.6 协作场景中的 AI 使用方式：提示词模板与校验

单人使用 AI（第 11 章的流程）与协作场景使用 AI 的区别在于：AI 的输出不再只是个人草稿，而是要进入多人共享的代码库，接受项目规范乃至陌生 review 者的检视。因此校验标准比"内核通过"多出一层——除了编译通过，还要符合项目的命名规范、文档字符串规范与 PR 描述规范。本节给出三个逐字可复制的模板与一张检查清单，模板面向通用形式化项目（以 Mathlib 与 ETP 类仓库的习惯为参照），使用前应替换占位内容并核对目标项目的具体规范。

**模板一：把 issue 中的数学陈述转写为 Lean 4 陈述。** 协作中最常见的 AI 用法。关键设计是只要求转写陈述、不要求写证明，并把所有非平凡决定显式列出，留给人类确认。

```text
你是一名熟悉 Lean 4 与 Mathlib 的形式化助手。下面是一条来自形式化项目 issue 的数学陈述，以及项目中已有的相关定义。

任务陈述（自然语言）：
<粘贴 issue 中的数学陈述原文>

项目中相关的定义与记号：
<粘贴相关的 Lean 定义代码，或注明其所在文件与命名空间>

请完成：
1. 把该陈述转写为一个 Lean 4 定理陈述（只写 statement，证明用 sorry 占位），不要尝试写证明；
2. 逐项列出你在转写中做出的每个非平凡决定（隐含的正则性条件、量词顺序、定义版本的选择等）；
3. 指出自然语言陈述中含糊或有歧义、需要人确认的地方；
4. 定理命名遵循项目规范（若有命名空间或前缀约定，按约定执行）。
转写的忠实性由人最终确认，你不为此负责，但必须把每个可争议之处标出来。
```

**模板二：让 AI 解释他人证明的每一步。** 认领一个节点之前，往往需要读懂上游已合并的证明。这是 LLM 在协作中的高价值用法，因为解释是低风险输出（错了会被读者发现），却能省去逐行查 tactic 文档的时间。

```text
下面是一段 Lean 4 证明代码。请逐步解释它，面向熟悉统计学但不熟悉 Lean 的读者。

<粘贴证明代码>

要求：
1. 按 tactic 逐行解释：每一行对证明目标（goal）做了什么改变；
2. 区分哪几行是实质性数学步骤，哪几行只是处理类型、记号或退化情形；
3. 用一段话概括整个证明的数学思路，并指出它对应自然语言证明中的哪一步（若能对应）；
4. 对你不确定的行明确标注"不确定"，不要猜测补足。
```

**模板三：让 AI 为自己的形式化草稿找反例与边界。** 提交前的自查。注意这里的对象是**陈述**而不是证明——证明的正确性由内核保证，陈述的毛病（漏条件、退化情形空洞成立）内核不管。

```text
下面是我刚完成的一个 Lean 定理陈述。请扮演审稿人，专门攻击陈述本身，不要评价证明。

<粘贴定理陈述（statement）>

请完成：
1. 检查该陈述在退化情形下的行为：空集、单点、零方差、样本量为 0 或 1、参数取边界值等，指出哪些情形下结论平庸或反直觉；
2. 尝试找出使该陈述空洞成立（vacuously true）的条件组合；
3. 指出陈述是否缺少常见正则性条件（可测性、可积性、有限性、非退化性）；
4. 各给出一个把陈述改得更弱与更强的最小修改方案。
只针对陈述，不评价证明。
```

**参数与校验**。三个模板都属于代码转写与分析任务，实践中通常取较低的 temperature（如 0 到 0.3 的量级；具体取值范围与默认值随厂商与界面版本变化，以所用工具当期文档为准），并优先把相关定义直接粘贴进上下文，而不是指望模型记得项目内部记号。转写类任务最大的风险不是语法错误（编译器会抓），而是**模型发明不存在的引理名**或选择了与项目不一致的定义版本，两种错误的输出都可能编译通过。

模型与上下文的选择上有三条经验。其一，上下文要给足项目侧信息：相关定义、所在命名空间、目标 Lean 版本，缺了这些，模型会用 Mathlib 的通用记号填补空白，而项目内部记号未必一致。其二，上下文给过头同样有害：把整个文件粘贴进去，模型会顺带"复用"文件里无关的引理与记号约定，转写结果在局部看着合理、放到项目里对不上。其三，陈述转写这类低量高险的输出（一个项目里陈述的数量远少于证明，但每个陈述的错误影响一片），值得用第二个模型独立转写一遍再人工比对，两个转写的分歧点与 14.7.5 节讲的标注者一致性是同一个信号。

协作场景的提交前检查清单如下：

| 检查项 | 手段 | 性质 |
|---|---|---|
| 编译通过，无错误 | `lake build` | 机器 |
| 证明完整，无 `sorry` / `admit` 残留 | grep 检查与 CI（见 14.7.2 节） | 机器 |
| 依赖的公理干净，无 `sorryAx` | `#print axioms 定理名` | 机器 |
| 命名符合项目规范（命名空间、前缀、无 `aux`/`temp` 类名字） | 对照项目 CONTRIBUTING | 人 |
| 公开声明附文档字符串（`/- -/`），写明自然语言陈述与来源 | 人工核对 | 人 |
| 无未使用的导入与调试残留（`#check`、`trace` 等） | lint（若项目配置）与人工核对 | 机器 + 人 |
| 陈述与 issue 原文语义一致 | 对照 issue 逐句核对 | 人，不可外包 |
| PR 描述引用 issue 编号与对应的蓝图节点 | 人工撰写 | 人 |

一个说明"内核通过不等于转写正确"的最小例子：设 issue 中的原命题是"样本均值依概率收敛于总体均值"。若转写后的 Lean 陈述漏掉了样本独立同分布的条件，只保留"样本量趋于无穷则均值收敛"，这条陈述照样通过编译——因为它作为一条定理是真的，只是不是原命题。内核检查的是转写产物的内部一致性，忠实性这个维度对它不存在。这类错误在单人流程里靠自觉防范，在协作流程里则由清单中的最后两行（对照 issue 逐句核对、PR 描述写明转写决定）制度化地防范。

### 14.7.7 从认领一个 issue 到提交一个 PR：完整流程走查

本节把"普通人参与"落到一条可照做的路径上。以 ETP 这类基于 GitHub 与 Lean 的项目为背景（Mathlib 本体及多数形式化项目流程相同，细节以各项目 CONTRIBUTING 为准），从看到任务到合并的完整走查如下。

**第一步：找任务。** 任务来源是项目的 dashboard 或蓝图网页（14.2.5、14.6.2 节），落到 issue 跟踪器上通常是带"good first issue"一类标签的条目。选择时先看三样东西：节点上游是否全绿（依赖是否已解决）、难度标注、是否已被认领。

**第二步：认领。** 在 Zulip 对应帖子或 issue 下留言说明接手，避免与他人重复劳动；若项目有任务令牌机制则按机制操作。认领后再开工，这是协作礼节也是效率。

**第三步：搭建本地环境。** fork 上游仓库到自己的账号，克隆自己的副本并关联上游，安装仓库指定的工具链，拉取 Mathlib 预编译缓存，首次全量构建：

```bash
# fork 之后，克隆自己的副本并关联上游仓库
git clone https://github.com/<用户名>/equational_theories.git
cd equational_theories
git remote add upstream https://github.com/teorth/equational_theories.git

# 安装仓库指定的 Lean 工具链，拉取 Mathlib 预编译缓存
elan toolchain install "$(cat lean-toolchain)"
lake exe cache get

# 首次全量构建（此后为增量编译）
lake build
```

这一步最常见的错误是跳过 `lake exe cache get` 直接 `lake build`，导致从源码编译 Mathlib，耗时以小时计（第 14.8.1 节）。

**第四步：切分支并写证明。** 从上游最新主线切出工作分支，在对应文件中找到占位陈述（`by sorry`），填充证明。过程中可使用 14.7.6 节的模板让 AI 协助，但陈述语义必须自己对照 issue 原文核对。完成后自检：

```bash
# 从上游主线切出工作分支
git fetch upstream
git checkout -b <简短分支名> upstream/main

# 证明完成后自检：无 sorry 残留，编译通过，检查公理依赖
grep -rn --include="*.lean" "\bsorry\b" .
lake build
# 另在编辑器中执行：#print axioms <你的定理名>
```

**第五步：提交并开 PR。** 提交信息按项目规范（CONTRIBUTING 中一般会规定格式），推送到自己的 fork，向上游开 PR。PR 描述的通行结构是：做了什么（对应哪个 issue 或蓝图节点）、怎么验证的（编译通过、`#print axioms` 输出）、有什么需要 review 者特别注意的地方（如转写中做出的非平凡决定）。描述写得清楚，review 轮次通常会明显减少。

**第六步：CI 与 review 循环。** PR 提交后 CI 自动编译（14.7.2 节），红了就按报错修复再推；CI 绿了之后由维护者 review。常见意见集中在命名、文档字符串与更简洁的证明写法，按建议修改后再推即可；若主线在 review 期间前进了，需要先合并上游再推。PR 合并后，蓝图网页上对应节点变绿，下游任务解锁。

首次提交者收到的 review 意见，多数落在下表左列的几类。预先自查一遍可以省去一到两轮往返：

| 意见类型 | 典型表述 | 对应预防措施 |
|---|---|---|
| 命名 | "请按项目命名空间规范重命名" | 提交前对照 CONTRIBUTING 与相邻文件的习惯 |
| 文档字符串 | "请补充自然语言陈述与来源" | 使用 14.7.6 节清单中的 docstring 条目 |
| 证明写法 | "这几行可以合并成一个 tactic" | 请求 AI 给出更短写法，但以可读为先 |
| 陈述范围 | "这个假设是不是可以更弱一些" | 属数学层讨论，如实回复自己的理由即可 |
| 位置与拆分 | "这段内容应放到另一个文件" | 提交前看清楚文件的职责划分 |

还有一类情形值得预先知道：认领后长期没有进展。协作项目的通行惯例是，发现自己做不动时在原认领帖下说明情况并释放任务，这比无声搁置对项目的伤害小得多——14.4.2 节的失败归档机制在人的层面同样适用，被放弃的尝试写下来，后来者就能避开同一条路。

整个循环中，数学部分可能只占工时的小头；环境搭建与规范遵循占的比重，对首次参与者而言往往超过一半。

### 14.7.8 第一人称记录：我提交的第一个 PR 的经历

以下一段为第一人称的练习性记录：笔者依据 Mathlib 与 equational_theories 项目的公开贡献文档、蓝图页面与社区讨论，把一位初学者的首次提交过程整理成叙事。文中不引用具体 PR 编号，涉及的报错与 review 意见是按公开文档与社区帖子归纳的常见情形；它的用途是让读者对流程有预期，而不是一份确证的日志。

"我选的是一条带入门标签的 issue：为主线上一条已经由反例判定的蕴含关系，把对应的 Lean 陈述核对并补齐文档字符串。工作本身不超过十行，但走完整个流程花了以周计的日历时间，其中几乎全部消耗在两处：环境与规范。

环境的教训发生在第一次 `lake build`。我没有先执行 `lake exe cache get`，于是 lake 开始从源码编译 Mathlib，风扇响了很久，进度条以分钟为单位爬行。我在社区帖子里找到答案：预编译缓存能把这一步从数小时压缩到几分钟。删掉构建产物、拉缓存、重新构建，一次通过。

写证明时我让 AI 起草了 tactic 序列。它给出的版本结构上是对的，但引用了一个不存在的引理名，编译器报 unknown identifier。我最初的反应是换个写法绕过去，后来意识到正确的做法是先在 Mathlib 文档里确认这个名字是否存在、语义是否是我要的。这次之后我形成了一个习惯：AI 给出的每个名字，编译通过之前先查一次文档——编译通过只说明名字存在，不说明它是我要的那个定理。

提交后 CI 红了，原因是 lint 报了一个未使用的导入。这是我第一次知道项目的 CI 检查的不只是编译。review 意见有两条：一是定理命名要按项目的命名空间规范调整，二是文档字符串要写清自然语言陈述与对应的蓝图节点编号。两条都改了，又按维护者的建议把三行 tactic 换成一个更短的组合写法，rebase 到最新主线后合并。

回头看，这次经历里 AI 承担的是起草与解释，真正构成门槛的是两件别的事：读懂项目自己的一套规范，以及接受'机器检查之外还有人的检查'。后者正是本章开头那张责任边界表想说的。"

这段记录同样有它的边界需要交代。它是按公开流程整理的练习性叙事，不对应任何具体的 PR 编号，也不应被当作对某个具体项目贡献规则的引用；每个项目的 CONTRIBUTING、PR 模板与 review 习惯各有细节，动手前应以目标仓库当期的说明为准。它想保留的只有一件事：众包形式化的可信性不来自参与者的善意，而来自一条任何人（包括首次参与者）都必须走过的、每一步都可核查的流水线。初次走这条流水线时觉得繁琐的每一道关卡，正是外部读者信任其中任何一个结论的理由。


## 14.8 大规模形式化工程的操作

### 14.8.1 依赖锁与缓存

形式化工程最常见的非数学故障是环境漂移。三条必须做：

- **锁定工具链版本**：仓库根目录放 `lean-toolchain`，写明确切的 Lean 版本号（如 `leanprover/lean4:v4.14.0`），由 elan 自动选用。
- **锁定依赖版本**：`lake-manifest.json` 记录 Mathlib 等依赖的确切 commit，提交进版本库；`lake update` 只在有意为之的时候执行。
- **使用预编译缓存**：`lake exe cache get` 拉取 Mathlib 的预编译产物，可省去数小时的首次编译。

```bash
# 首次搭建（命令以官方文档当前版本为准）
elan toolchain install "$(cat lean-toolchain)"   # 安装仓库指定的 Lean 版本
lake exe cache get                                # 拉取预编译的 Mathlib 缓存
lake build                                        # 增量编译本项目

# 生成蓝图网页与依赖图（需 uv 与 LaTeX 环境）
uvx leanblueprint pdf                             # 生成 PDF 版蓝图
uvx leanblueprint web && uvx leanblueprint serve  # 生成并本地预览依赖图网页

# 日常自检
grep -rn --include="*.lean" -E "\b(sorry|admit)\b" . | wc -l    # 剩余未完成节点数
lake build --verbose 2>&1 | tail -n 50                          # 查看编译耗时分布
```

### 14.8.2 CI 时间预算

编译时间决定协作节奏。若一次全量编译需要数小时，贡献者会在等待中流失；若只需数十分钟，则"改一行、提交、看结果"的循环可以维持。

控制编译时间的手段按效果排序：

1. **缓存**：`.olean` 产物缓存是最大头，必须配置。
2. **增量编译**：只重编变更文件及其下游；这要求文件切分合理——把频繁改动的部分与稳定部分放在不同文件。
3. **陈述与证明分离**：证明改动不触发依赖它的文件重编，这是 Prove2Me 明确采用的机制。
4. **并行**：`lake build` 本身并行；CI 上可再按子目录分片。
5. **分层构建**：把基础层与上层拆成两个 lake 包，基础层稳定后不重编。

预算上的经验值是：把 PR 级 CI 控制在 15 分钟以内，把每日全量构建控制在 2 小时以内。超过则应拆分仓库或引入分层。

### 14.8.3 定理 DAG 与模块化

依赖图既是管理工具也是数学对象。维护时的几条规则：

- **节点粒度与文件粒度对齐**：一个引理对应一个文件（或一个文件中的一节），使"哪个文件需要重编"与"哪个引理变了"一致。
- **避免长链**：依赖链越长，一处改动的下游影响越大。Mathlib 的概念依赖链深度可达数十层（据公开资料，最深可达 84 层），这类深度在大型库中难以避免，但项目内部应尽量做宽而浅的结构。
- **接口先行**：先把所有陈述写好（`by sorry` 占位），让依赖图成形，再填证明。这样并行可以立刻开始，且能早期发现循环依赖与缺失前件。
- **拒绝循环依赖**：DAG 的性质必须保持，任何环都说明拆分有误。

```lean
-- 接口先行的写法：先固定陈述，证明留作 sorry，由人或 AI 认领填充
import Mathlib

/-- 引理 3.2：在正则性条件 R1、R2 下，估计量的一致收敛速率。
    依赖：Lemma_2_5, Lemma_2_8。形式化陈述与自然语言命题的等价性由人复核。 -/
theorem lemma_3_2 (n : ℕ) (hR1 : Measurable f) (hR2 : Integrable f μ) :
    ‖θ̂ n - θ₀‖ ≤ C / Real.sqrt n := by
  sorry

-- 填充完成后，检查该定理依赖了哪些公理；出现 sorryAx 即为不完整
#print axioms lemma_3_2
```

### 14.8.4 重构与命名规范

大规模项目的代码质量直接决定后来者能否参与。规范应当尽早写入 CONTRIBUTING：

- **命名**：定理名体现内容与编号（如 `PFR.lemma_3_2`），命名空间按章节划分；避免 `aux`、`temp`、`foo` 一类名字。
- **注释**：每个非平凡的定理上方写明自然语言陈述、来源（论文编号或章节）、依赖关系。这是后来者与 LLM 检索的主要依据。
- **重构纪律**：重命名或移动定理会打断他人的在途工作，应当在协调频道公告并约定时间窗口，或要求重构 PR 自带批量替换脚本。
- **死代码清理**：被放弃的尝试（尤其是 AI 生成的冗长分支）应当归档到单独目录而非留在主线上，既保留可追溯性，又不污染阅读路径。

## 14.9 局限与争议

### 14.9.1 形式化是否等于理解

这是最根本的争议，也是本章反复出现的限定句的由来。一个通过 Lean 检查的证明，保证的是"从给定的形式化陈述与公理出发，推理链无误"。它不保证三件事：形式化陈述与原命题语义等价；证明所依赖的公理是研究者想要的那个；以及有人理解了这个证明为什么成立。

前两件可以通过人的复核解决（第 11.9 节的"忠实性复核"不可外包）。第三件没有技术手段。陶哲轩在 ICM 演讲中把"阐释"与"进入标准理论"列为独立于"验证"的两个阶段，正是对这一点的承认：机器验证解决的是正确性，不是可理解性。

对统计学者而言，这一区分有一个熟悉的对应：一个数值模拟可以证明某个估计量在特定设定下表现良好，但不解释它为什么好；渐近理论提供解释。两者缺一不可，形式化证明与人类阐述的关系与之类似。

### 14.9.2 大规模自动化是否会稀释数学洞察

反对意见的核心是：**数学问题的价值往往不在答案，而在求解过程中产生的工具与结构**。据公开报道，多位数学家在 2026 年的讨论中表达了这一立场——费马大定理历经三百五十余年才被攻克，期间人们寻找破局方向时发展出的工具被认为比结果本身更有价值；若 AI 直接给出答案而跳过过程，共同体获得的可能只是一个孤立的真命题。

支持意见的反驳是：AI 生成候选证明与候选结论的能力，把压力从生成端移到了评估端；评估"这个结果是否真正推进了理解"仍需要数学家判断，因此数学家的角色不是被替代，而是被重新定位。北京大学董彬教授在公开讨论中指出，AI 可以大量生成候选结果，但评估这些结果是否推进了数学理解、在知识体系中处于什么位置，仍由数学家判断，压力正在向评估与消化环节转移。

双方在一个事实上没有分歧：验证与消化的带宽不会随生成能力同步扩张。这是一个可观察的现象，而不是立场问题——据公开报道，某些方向上 AI 辅助产出的规模已经超过审稿与同行评议的承载能力。

### 14.9.3 贡献归属与署名

三个具体问题尚未有共识。

**形式化工作如何被计价**。Commelin 在 PFR 项目结束时提出的问题至今没有答案：形式化工作者的贡献如何被数学共同体承认，如何体现在职业评价中。这一问题的实际影响是：如果形式化工作不计入学术资本，那么大型项目的劳动力供给将持续依赖志愿者的热情或 AI 的替代。

**AI 的产出如何标注**。当一份 Lean 代码的 90% 由智能体生成（第 12 章记录的若干工程达到这一比例），其余 10% 由人提供蓝图、策略与关键引理时，贡献如何归属？目前通行的做法是：由认领该节点的人类贡献者承担署名，AI 作为工具披露；陶哲轩提出的建议是让 AI 使用的披露常态化。

**众包项目的作者名单**。ETP 的做法是 30 位作者对应约 50 位参与者，即设定了明确门槛。这一做法是否应成为惯例、门槛如何设定，仍有争论。

### 14.9.4 2026 年的两次公开表态

据公开报道，2026 年发生了两次由顶尖数学家主导的公开表态，均针对 AI 企业进入数学研究的方式。

**ICM 演讲**（2026 年 7 月，费城）：陶哲轩作《人工智能时代的数学》公众演讲，提出"证明过剩"与"证明的消化不良"的判断，并给出三条建议（AI 使用披露常态化、重新校准评价体系、作者须能清晰讲解自己的结果才能发表）。内容见 14.6.5 节。

**菲尔兹奖得主联合声明**（据公开报道为 2026 年 9 月 11 日）：陶哲轩、邓煜等 25 位菲尔兹奖得主联名发布公开声明，批评 AI 企业把攻克数学难题作为大模型性能基准与营销手段的做法，认为这对数学科学本身与数学共同体造成了损害。据公开报道，声明的触发点之一是 OpenAI 于 2026 年 9 月 8 日宣布用 1 万个智能体、88 小时完成 Navier–Stokes 千禧年难题的证明。报道同时提到，声明的写作背景还包括科研经费环境的变化（2027 财年美国预算提案中科研经费大幅缩减，部分学者转向寻求企业资助），因此该声明也带有为研究经费游说的维度。声明本身并非反对 AI 辅助数学研究——据报道，声明中同时写道"AI 有望增强和加速真正的数学研究与理解"。

对这两次表态，本章只作陈述，不作评价。需要提示读者的是：上述内容均来自公开报道，具体措辞、数字与参与名单应以官方发布的原文为准；且这些表态针对的是"AI 企业发布成果的方式"，而非"形式化方法本身"。

### 14.9.5 人类盲区与选择偏差

最后一类局限不属于技术，而属于认知。

**选择偏差**。关于 AI 数学能力的证据大多来自成功案例的报道，失败案例几乎不被记录。陶哲轩在 ICM 演讲中明确指出了这一点：多数证据并非在受控的科学条件下收集，存在严重偏差，他因此引用 First Proof 这类受控基准作为更可靠的证据来源。对统计学者而言这是熟悉的配方：把便利样本当作随机样本，会系统性地高估效应。

**人类盲区**。AI 在"此前无人认真尝试"的问题上成功率最高，这类问题之所以无人尝试，往往是因为人类研究者有共同的先验——认为它们不重要或不可能。这一观察有两种解读：AI 不受人类先验束缚，因而能拾起被忽略的低垂果实；或者 AI 只是在捡人类正确地判断为不重要的东西。两种解读的分野在于这些结果是否带来了后续的结构性发展，而这需要时间才能判断。

**验证不对称**。这与第 12 章的结论一致：反例一旦被验证即刻终结问题，证明必须覆盖全部情形。大规模自动化在证伪类任务上取得的无争议成果明显多于证明类任务，这一不对称性在可预见的将来仍会存在。

## 本章小结

- 人机协作按"谁定方向、谁承担验证"可划分为人主导/AI 辅助、AI 主导/人审核、对等迭代三个层次；第三层次成立的前提是机器验证，因为只有机器验证才能把"谁检查过了"从流程中移除。
- 规模化协作的可行性来自定理依赖图的 DAG 结构：声明一旦固定，一个节点的工作只依赖于上游节点"已被证明"，不依赖它们"如何被证明"。
- 等式理论项目（2024-09-25 发起）判定 4694 条等式定律之间全部 22,028,942 条蕴含关系，2025 年 4 月 14 日完成；启动后 48 小时内靠有限原群枚举解决绝大部分，第 57 天主体验证基本收官（剩余约百余条），项目论文列 30 位作者、约 50 人参与。
- 该项目的可参与性来自任务自足与验证自动：参与者不需要理解全局证明，也不需要是代数学者；自动化层、LLM 层与人类专家层按难度动态分工。
- PFR 形式化项目用三周完成（2023-12-05），核心工程手段是蓝图化与 DAG 拆解；陶哲轩本人只贡献约 5% 代码行数，多数时间在组织蓝图与协调；形式化后把常数从 $C=12$ 更新到 $C=11$ 只用了一天。
- Prove2Me 的四个机制是定理 DAG、陈述与证明分离、自然语言描述、失败归档；FLT 工程 11 天、约 29,500 条中间定理、约 1,300 万行 Lean，最终构建 96 个并行任务约 5 小时 32 分通过检查。
- 关于名为 Fuse 的平台，可核验的一手技术资料有限，本章未对其功能做断言；同类可核验的实践是 Math Inc. 的 Gauss（强素数定理约 25,000 行、三周；有限域 Kakeya 约 300 行），其工作流为人类蓝图 + AI 生成 + 内核验证。
- 陶哲轩对 AI 的公开评估包括：开放问题系统性应用的成功率约 1–2%，成功集中在缺乏文献关注的问题上；"跳跃机器能跳两米但不会攀岩"的比喻指向 AI 无法从失败中累积局部进展；瓶颈已从想法生成转移到验证与评估。
- 大规模形式化工程的四条实践要点是：锁定工具链与依赖并使用预编译缓存；把 PR 级 CI 控制在 15 分钟量级；接口先行、保持依赖图宽而浅；规范命名与注释并归档失败路径。
- 贡献质量的统计结构：贡献分布普遍呈重尾（PFR 项目中主持人本人仅贡献约 5% 代码行数，ETP 的 30 位作者对应约 50 位参与者）；审核在统计上是两阶段结构——内核对逻辑有效性做普查，人对语义等价性做有偏的抽样复核；独立形式化之间的陈述一致性可部分交由机器判定，这使形式化协作比一般众包多一层可检验性，但一致率的系统数据尚缺。
- 协作场景中的 AI 使用要点：转写陈述、解释他人证明、攻击陈述边界是三类高频低险用法，均以"只转写、只解释、只攻击，不做断言"为模板设计原则；校验除内核通过外，还包括命名规范、文档字符串、无残留占位与公理依赖干净等项目级规范。
- 普通研究者的参与路径是固定流程：认领 issue、fork 与缓存构建、填充证明、自检（grep 残留、`#print axioms`）、开 PR、CI 与 review 循环；对首次参与者，环境与规范占用的工时往往超过数学本身。
- 争议集中在四点：形式化不等于理解（验证解决正确性，不解决可理解性）；大规模自动化可能跳过产生工具与结构的过程；形式化工作与 AI 产出的贡献归属尚无共识；以及关于 AI 数学能力的证据存在严重的选择偏差。
